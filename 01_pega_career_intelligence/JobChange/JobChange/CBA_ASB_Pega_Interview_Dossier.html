Technical questions to rehearse (with answer outlines)

1. Walk me through your Kafka integration end to end.

Kafka topic → Kafka dataset (instance, topic, JSON) → real-time Data Flow (partitions match topic partitions) → transform/validate → Connect-SQL merge or case update → failure path: Queue Processor with retries and backoff → dead-letter queue → Service-REST replay API → dashboard plus pager alerts. Cover idempotency (business key or offset check before merge), ordering (per-key partition), and backpressure (thread count, batch size). Close with measurable outcomes.

2. Queue Processor vs Job Scheduler vs Agent: when do you use each?

Queue Processor: event-driven, per-item, retries and dead-letter, scalable across nodes (asynchronous work like a notification after case update). Job Scheduler: time-based batch (nightly reconciliation). Legacy agents: avoid in new work. Mention node classification and how you monitor queues in Admin Studio and PDC.

3. Explain rule resolution, and design an enterprise class structure for ASB lending.

Rule resolution: class and ruleset hierarchy, availability, circumstance, date/time, access group/ruleset list, then the best match, and cache. Class layers for ASB: ASB- (organisation) → ASB-FW-Lending- (reusable framework) → ASB-Lending-Work-HomeLoan (implementation), with data classes shared at the organisation layer and integration classes in ASB-Int-. Explain why: reuse across products, specialisation, ruleset governance.

4. Data Page scopes and refresh strategies; how do you avoid stale data?

Thread, requestor and node scope; editable vs read-only; parameterised/keyed pages; refresh on reload, timeout or a "do not reload when" condition; async loading. Example: node-level reference data with a timeout, requestor-level customer profile, thread-level case-specific lookups.

5. Data Transform vs Activity vs Declare Expression.

Prefer declarative (forward chaining) and data transforms for mapping; activities only for what's left over (for example complex Connect-SQL or obj-methods), with guardrail justification. Mention performance traps with chained declare expressions.

6. Design SLAs and routing for a hardship or collections case.

Goal, deadline and passed-deadline intervals; escalation actions (reassign to supervisor, notify); work queues by market or skill; Get Next Work with urgency; SLA calendars per market (NZ public holidays!). Talk about your real collections experience.

7. An external API times out in production. What do you do?

Triage: PDC alerts → Tracer/logs → check the connector (timeout, retry, circuit) → quick fix (route to a manual work queue, stop the retry storm) → root cause → permanent fix (async queue processor with retry and backoff, idempotent call, fallback status on the case, alert) → post-incident review. Use your replay-API story.

8. Securing a Pega app in a bank.

Access groups, roles, privileges; Access When / ABAC for data-level rules (for example a staff member sees only their branch's customers); auth via SSO (SAML/OIDC) and OAuth 2.0 for APIs; mTLS for service-to-service; no secrets in rules (use authentication profiles and keystores); audit trail; field-level encryption or masking for PII. Mention production rule-set locking.

9. Performance tuning: where do you start?

PAL counters (DB time, rules executed, clipboard size), alerts in PDC, expose columns used in report filters, add indexes, avoid loading large pages, use paging in reports, tune Data Flow threads and partitions. Use your 200,000-in-15-minutes example: what you measured and what you changed.

10. Release and branching on a squad.

Branch rulesets per story → merge with conflict review → Deployment Manager pipeline (Dev → QA → Staging → Prod) with guardrail and test gates → rollback. Add PegaUnit for decision and data-transform logic and scenario tests for key journeys. "Automation-first testing" is a CBA foundation, so show you value it.

11. Constellation in 60 seconds (even without production use).

Centre-out: business logic in case types and data; the UI is generated from views via the DX API v2, rendered by a React-based client; fewer custom sections, more out-of-the-box patterns; extend with DX components. Why banks move: upgradeability, consistent UX, Pega Cloud fit. Then your ramp plan: build one case type with views and a REST data page in a personal Infinity '25 environment and complete the Constellation mission on Pega Academy.

12. Pega Customer Service and KYC basics.

CS: interaction case → service requests (intents) → Interaction Portal, composite customer view, knowledge, next-best-action. KYC/CLM: onboarding case, KYC types and rules engine, due-diligence levels, periodic review, screening integrations. Say honestly that you'd map your service and collections case experience onto them.

13. How do you use AI in your engineering work?

CBA emphasises "AI-powered engineering at scale". Use your AI-assisted mapping utility (four weeks to ten minutes with human review) and AI-assisted bottleneck analysis. Stress validation, review and no customer data in prompts. Knowing Pega GenAI (GenAI Connect, Coach, Knowledge Buddy) is a plus.

14. Possible SQL or pseudo-code on screen-share.

Practise: join cases to customers with aggregates; find duplicates with GROUP BY/HAVING; window function for the latest record per account; a MERGE/upsert; and pseudo-code for a REST endpoint with validation and idempotency. (Your learnings\SQL 30-day lab covers this.)

Design scenarios to practise out loud (15 minutes each)

  1. Home-loan hardship request for ASB: case stages (Intake → Assess → Decide → Fulfil → Monitor), customer documents, affordability decision via a decision table/strategy, core-banking update via an async event, SLA per regulation, maker-checker approval, audit trail.
  2. KYC periodic review: batch trigger (Job Scheduler) creates review cases, screening via REST with retries, high-risk routing to a specialist queue, an outcome event to downstream systems, and evidence retained.
  3. Payment exception from Kafka: topic → data flow → case per exception (deduplicated by payment ID) → auto-resolve rules → manual queue → replay/fix → status event back to payments.

For each: state the assumptions, draw the boundary (what's Pega vs other systems), name the failure modes, and finish with how you'd test and observe it. That structure matches the Engineering Manager job description almost word for word.
