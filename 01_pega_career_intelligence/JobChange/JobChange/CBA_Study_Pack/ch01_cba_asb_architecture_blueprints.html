1.1 What we built, and why every boundary exists

Lending Care handles the moments when a home-loan customer is in trouble: a hardship application, an arrears follow-up, a payment arrangement, a promise to pay, and the regulatory clocks around them. It is built on Pega by a squad in Bengaluru for a lending tribe in Auckland, and it lives on a bank-wide event backbone. Every boundary below is stated with the failure that appears when it is removed, because a boundary that is not justified by a failure is just ceremony.

The integration boundary. Pega never calls the core directly and never binds to its payloads. Reads go through the API gateway, writes go through an integration framework with an outbox, and business events come in and go out through the event platform. Without that boundary, every case type contains core-specific calls. A change to the core's contract, which is certain during an SAP core migration, then becomes a change to every flow, and a slow core becomes an outage of every case that touches it. With it, the timeouts, the idempotency key, the single retry owner and the error classification live in one framework, and the core's failure is contained in one place.

The event boundary. Facts about loans (an instalment missed, an arrangement booked, a balance changed) arrive as events, and Pega's own decisions leave as events. Without it, Pega would poll the core for "anything new" or receive point-to-point calls from every system that cares. Polling is late and expensive; point-to-point means the collections system, the decisioning engine and the customer app each need a bespoke integration to learn that a hardship was approved. With it, the case engine publishes one event stream, hardship-status (received, under assessment, approved, declined, withdrawn), and every interested system subscribes. A new consumer next year needs no change in Pega. The cost of the boundary is that events can be duplicated, delayed and reordered, and the design must say what happens in each case (1.7).

The canonical model and its translation point. Between the vendor payload or event schema and the case sits a canonical model, and translation happens in the integration layer. Without it, a renamed field in the core's new SAP-based API breaks forty rules that happened to read it, and the migration doubles every flow. With it, a schema change touches one mapping and its unit test, unknown codes become an explicit Unknown with an alert instead of a silent default, and the case stores keys, deltas and decisions, never a copy of the loan.

The layered ruleset stack. Rules are organised in organisation, framework, implementation and application layers whose dependencies run one way. Without it, the first case type is built in one ruleset, the third copies rules because nothing is shared, and a change to the arrears letter header edits thirty rules. With it, shared frameworks sit low, true differences sit high, reference data changes without a code release, and a hotfix is not a full release.

The case-type split. Hardship, arrears, KYC periodic review, payment exception and service request are separate case types sharing frameworks, linked by keys. Without the split, one case carries every process's stages and clocks. A KYC escalation then cannot pause a hardship cleanly, and access cannot be restricted for financial-crime work. With it, each has its own clock, authority and access, and the types interact through events, tickets and child cases.

The asynchronous boundaries. Writes that matter commit an intent locally and complete through a queue processor; long operations complete by callback or event with a sweeper; notices go through a queue. Without them, a connector call sits inside a transaction holding locks for the length of a network wait, so a slow core becomes a platform stall, and a lost response leaves the case unable to know whether to act again. With them, the decision and its intent commit in milliseconds and the effect completes on someone else's clock, with an honest status in between.

The decisioning boundary. The case engine decides process (is the application complete, is it within authority, which option is lawful). A separate decisioning application decides conversations (which message, offer or nudge to show). Without the split, offer logic leaks into the hardship case, and the bank can end up showing a credit-card upgrade to a customer in hardship. With it, the hardship status is an event the decisioning engine consumes to suppress sales offers and switch to support messages, which is the "care" outcome.

The reference-data boundary. Rules own policy; data owns numbers. Hardship options, authority bands, NZ public holidays and letter templates are effective-dated reference data changed through a maker-checker case. Without it, a threshold change needs a developer release and cannot be effective-dated, so reprocessing an old application uses today's rule.

The audit boundary. Every decision records the rule version, its inputs, the approver and the event IDs that informed it. Evidence reconstructed afterwards is evidence that can be challenged, and in hardship the customer can take the decision to a dispute-resolution scheme.

The ownership boundary. The squad owns the Pega application end to end; a platform team owns the Kafka clusters, the schema registry and the gateway; the core team owns the core; the CoE owns Pega standards. Without it, every incident starts with "whose is this?" With it, an alert has one owner and one runbook, at 02:00 in either country.

Working assumptions (stated so they can be corrected)

  1. The core is the system of record for every loan fact; Pega stores keys, the snapshot an approver relied on, and evidence. It never becomes a second loan master.
  2. Pega Infinity on Pega Cloud, Constellation for all new staff UI; the exact release is to confirm, and release-sensitive behaviour is labelled where it matters.
  3. Kafka clusters, topic creation, ACLs and schema compatibility are owned by the platform team; the squad owns its producers, consumers and their behaviour.
  4. The core offers REST APIs for reads and arrangement writes, accepts an idempotency key on writes, and publishes loan-state events after it commits.
  5. Hardship policy (options, authority bands, evidence rules) is owned by the Lending tribe and Risk, delivered as reference data under change control.
  6. NZ working days and public holidays govern the statutory clocks; Bengaluru calendars govern only the squad's support rota.

1.5 The layered application, and the "everything in one layer" trap

The trap

A new squad under deadline builds the first case type in one ruleset because it is fastest. By the third case type, the arrears letter, the NZ holiday calendar and the gateway connector have been copied twice, each copy slightly different. When the core migrates, three connectors change instead of one. When a holiday is added, two calendars are updated and one is missed, and a statutory deadline is computed wrongly for one case type only. The trap is invisible for six months and expensive for years.

Rules that keep the layers honest

  • Dependencies run downward only. A framework ruleset never references a lending class, enforced by a pipeline check on rule references.
  • A copy of a framework rule into a higher layer needs a design-review comment explaining the difference; a report lists every override.
  • Connectors live only in TOTFWInt; a case flow calls an integration activity or data page, never a connector directly.
  • Constellation views live with the case type that owns them; shared views (customer summary, loan summary) live at the organisation layer and are reused, not copied.
  • Reference data is changed by a maker-checker case, effective-dated, and never by a developer release.

Why each field exists. eventId makes duplicates harmless. key keeps every event for one loan on one partition, so they arrive in the order they were produced. sequence lets a consumer refuse a stale event even when ordering is broken by a replay or a producer bug. occurredAt is the business time a clock may depend on, distinct from when the platform saw it. correlationId lets an engineer in Bengaluru trace an Auckland complaint from the app, through Pega, to the core and back in one search.

The translation boundary

The core's API and its events use their own field names. Mapping happens in TOTFWInt: one data transform per message and version, each with a unit test containing a real (masked) sample. A new schema version adds a new transform; it does not edit the old one, so replaying an old event still maps correctly. Unknown enumeration values map to Unknown and raise an alert, because a silent default in hardship is a wrong letter to a customer.

How Pega consumes

A Kafka data set points at the external cluster and topic, with the schema registry configured for Avro deserialisation. A real-time data flow reads it continuously and, for each event, runs a strategy or activity that (1) checks the dedupe table for eventId, (2) compares sequence with the stored snapshot for the key, (3) maps the payload through the canonical transform, and (4) writes the snapshot and the dedupe row in one commit. Only after that does it raise downstream work (open an arrears case, confirm an outbox row). The external Kafka is separate from the stream service Pega uses internally for its own queue processors; mixing the two up is a common interview slip.

release-sensitive How data-flow partitions map to node threads, and how offsets are committed relative to your processing, depend on the Pega release and configuration. The design does not depend on them: whatever is redelivered is made harmless by the dedupe and sequence guard.

Ordering

Kafka orders events within a partition, and the key decides the partition. Keying every lending topic by LoanID means "instalment missed" and "arrangement booked" for the same loan arrive in the order the core produced them. Ordering is not guaranteed across loans, and does not need to be. The sequence guard covers the cases where ordering still breaks (a replay, a producer that retried out of order): an event whose sequence is not newer than the stored snapshot is recorded and ignored, never applied.

Duplicates

Delivery is at least once. A consumer can process an event, crash before its offset is committed, and see the same event again; a producer can retry and publish twice. The dedupe row on eventId, written in the same commit as the effect, makes the second delivery a no-op. CBA has said publicly that message duplication was one of its hardest Kafka lessons, so saying this unprompted shows you understand their world.

Poison events and the dead-letter topic

An event that fails mapping (a new enum, a missing field, a schema the consumer cannot read) must not stop the partition behind it. The consumer writes it to the topic's DLQ with the error class, the original offset and the correlation ID, raises an alert to the owning engineer, and moves on. A loan whose event is in the DLQ is flagged on its snapshot as "state uncertain", so a specialist working its case sees a banner rather than a stale balance.

Replay

Replay is built, not assumed. The squad's replay tool reads selected DLQ events (or a time window from the source topic, through a dedicated replay consumer), re-runs them through the same consumer logic, and records the outcome. Because consumers are idempotent and sequence-guarded, a replay is safe to run twice. A platform-level offset reset is reserved for disasters and coordinated with the platform team. This is your Mercedes-Benz replay API, generalised: say so.

Producing safely: the outbox

When Pega decides a hardship, the case update and an outbox row for hardship-status commit in one transaction. A queue processor publishes the outbox row and marks it sent. If publishing fails, the row stays and is retried; the decision is never "made but not announced". Duplicated publishes are possible and acceptable because consumers dedupe on eventId, which is generated once when the outbox row is written. release-sensitive Whether a queue item enqueued from a flow commits atomically with the case write depends on how it is enqueued (immediate or deferred). Verify on the target release; if in doubt, write the outbox row as a data instance in the same commit and let a scheduler or queue processor sweep it.

1.8 One request end to end: Aroha's hardship, HA-20417

The test of an architecture is whether its boundaries hold under one real request. Aroha Ngata (PTY-30981) has a home loan HL-55210-01 with Tōtara: balance NZ$412,300.55, weekly instalment NZ$742.00. She was made redundant on 30 October 2026 and has missed two instalments. Mere Tane is the lending care specialist in Auckland, Liam Walker is her team leader and the checker, and Ananya Rao is the Bengaluru squad engineer on the India-hours rota. For every hop the walkthrough states the trigger, what runs, what data enters, what is committed, whether it is synchronous, what people see, and what happens when the hop fails. Times are New Zealand Daylight Time (UTC+13) with India Standard Time (UTC+5:30) in brackets, because the squad lives 7.5 hours behind the customer. Thresholds marked assumed Tōtara policy are the example's own; the statutory clocks are cited in 1.R.

Hop 0: the arrears event that came first

Trigger. At 06:00 (22:30 Sunday IST) the core's overnight cycle publishes loan-state.changed for HL-55210-01: sequence 10442, partition 7 of tot.lending.loan-state.v3, arrearsDays: 16. What runs. The real-time data flow dedupes on eventId, confirms 10442 is newer than the stored 10439, maps the payload, and commits the snapshot plus the dedupe row. A rule on the snapshot opens arrears case AR-88120 because arrears crossed 14 days assumed Tōtara policy. If it fails. If the arrears case creation fails after the snapshot commits, the case is created from a sweeper that finds snapshots with arrears and no open case, so the event is never the only chance. If the same event is redelivered at 06:03, the dedupe row makes it a no-op, and no second arrears case is opened. That is the whole reason the dedupe and the effect share one commit.

Hop 1: Aroha applies in the app

Trigger. At 09:12 (01:42 IST) Aroha completes the hardship form in the mobile app: reason "loss of employment", request "postpone payments for three months", consent to share her redundancy letter. The Act requires the application to be in writing and to state the reasonable cause; a completed in-app form with her authenticated identity is the written application in the example's policy. What runs. The app's backend-for-frontend calls Pega's Service-REST POST /hardship through the gateway with a client-generated request ID as the idempotency key. Pega validates against the canonical model and creates HA-20417 in class TOT-Lend-Work-Hardship, linked to LoanID, PartyID and the open arrears case AR-88120. What is committed, in one transaction. The case row (exposed columns for status, loan ID, received date and the three statutory due dates), the first history entry, the evidence reference for the uploaded consent, and an outbox row for hardship-status = RECEIVED. Sync or async. Synchronous, because Aroha is waiting; under 800 ms p95 assumed Tōtara policy. What Aroha sees. "We've received your request" with reference HA-20417. If it fails. A validation failure returns a field-level message and commits nothing. If the response is lost and the app retries, the request ID returns the same case instead of creating HA-20418. A duplicate application is a hop-1 problem, solved at hop 1.

Hop 2: the case reads what it does not own

Trigger. The Intake stage needs the loan's state and repayment schedule. What runs. D_LoanState[LoanID] reads the persisted snapshot (sequence 10442, as-of 06:00); D_RepaymentSchedule[LoanID] calls the core through the gateway (SYNC-READ). An eligibility decision checks the contract type is a consumer credit contract, the application is not a repeat within four months on the same grounds, and the default-length rule from the regulator's guidance cited. What is committed. Only the eligibility outcome and the snapshot the decision relied on: balance, instalment, arrears days and the snapshot's sequence and as-of time. The loan itself is never copied. If it fails. If the schedule read times out, the interactive path does not retry; Intake shows the snapshot with its as-of stamp and a banner, and a queue processor completes the read. The case never proceeds on a value it cannot date. If the snapshot is flagged "state uncertain" because an event is in the DLQ (1.7), the eligibility step waits for a human.

Hop 3: the statutory clocks start, and the bank stops chasing

Trigger. Intake completes. What runs. The NZ calendar framework computes the three deadlines from the received date, Monday 16 November, on working days: acknowledgement by Monday 23 November (5 working days), any information request by Monday 30 November (10), decision by Monday 14 December (20). Working days follow the Act's definition, implemented from reference data. confirm the definition with Legal The correspondence framework queues the acknowledgement letter at once, because policy is to acknowledge the same day even though law allows five. The queue processor publishes the outbox row: hardship-status = RECEIVED for key HL-55210-01. What changes elsewhere, without Pega calling anyone. The collections system consumes the event and pauses the dunning strategy for the loan, so nobody phones Aroha about arrears while she is in hardship assessment. The decisioning application consumes it and suppresses sales offers, switching her next-best-action to support content. The arrears case AR-88120 is moved to "Covered by hardship" by a ticket from HA-20417. If it fails. If publishing fails, the outbox row remains and is retried; an alert fires if any outbox row is older than 5 minutes assumed Tōtara policy, because a delayed RECEIVED means a possible collections call to a customer in hardship. That is a customer-harm alert and pages whichever country is on duty: at 09:14 NZDT that is the Auckland rota, not Ananya.

Hop 4: assessment, an information request, and evidence

Trigger. At 10:30 Mere takes the assignment via Get Next Work. What runs. The Constellation assessment view shows the snapshot, the clocks and the customer's stated reason. Mere asks the policy assistant (Pega GenAI Knowledge Buddy over Tōtara's hardship policy) whether a three-month postponement needs a redundancy letter; it answers with a citation to the policy page, and Mere decides. The assistant never decides and its answer is logged with its citation. On Tuesday 17 November Mere sends an information request (inside the 10-working-day limit) for the redundancy letter and a statement of expected income. On Thursday 19 November Aroha uploads both in the app; the DOC pattern stores them in document management, and the case keeps references and hashes. An affordability decision table, keyed by option and income band from reference data, recommends the three-month postponement with the term extended to keep the instalment unchanged afterwards. What is committed. The request, the uploads' references, the decision outcome with the decision-table version, and Mere's proposal. If it fails. If the upload service is down, the app queues the upload and the case shows "awaiting evidence"; the information-request clock is already satisfied by the request, not by the response.

Hop 5: maker, checker, and the arrangement write that times out

Trigger. At 13:50 on Friday 20 November Mere submits; at 14:04 Liam approves. Four layers stop a maker approving her own work: routing excludes her, an Access Deny on ApproveHardship when maker equals operator, a server-side validation on the approve action, and a daily detective report that must return zero. Liam's approval records his operator ID, the snapshot he saw and the authority-table version. What runs next. The integration framework, pattern SYNC+Q: in one commit the case moves to Pending-Core, writes history, and writes an outbox row for POST /loans/HL-55210-01/arrangements with idempotency key HA-20417-ARR-1. A queue processor makes the call at 14:05:02 (06:35 IST).

The failure. At 14:05:10 the read timeout elapses. A timeout on a write that may have succeeded is not transient; it is an unknown outcome. The core may have booked the arrangement and lost the response, or never received the request. The processor therefore does not re-post. It marks the outbox row Unknown, leaves the case in Pending-Core, and calls the status lookup by key. At 14:05:16 the answer is IN_PROGRESS; it schedules another lookup with backoff. What it must never do is send a new request with a new key, because the key identifies the intent, not the attempt: a new key is a second arrangement on the same loan. Mere sees Pending-Core, "confirming with the core", with the attempt count. Other failures have their own handling. A business rejection (an existing arrangement, a legal hold) becomes a fix assignment with the reason. A 409 duplicate returns the stored response. A sustained outage opens a breaker and routes to a dual-control manual fallback, so the statutory decision date is never at risk because of a system.

Hop 6: the confirmation arrives as an event

Trigger. At 14:06:10 the core commits the arrangement and publishes arrangement.booked on tot.lending.arrangement.v2, key HL-55210-01, with correlationId: HA-20417 and the arrangement reference ARR-771304. What runs. The consumer dedupes, checks sequence, persists, and finds the outbox row in Unknown for that correlation. The next status lookup returns BOOKED with the same reference; either signal alone is enough, and here they agree. The outbox row moves to Confirmed, the case stores ARR-771304 and moves to Notify. At 14:09 a duplicate of the same event arrives (the producer retried); the dedupe row ignores it. A loan-state.changed event (sequence 10451) then shows the next instalment date as 22 February 2027, and the snapshot updates. Sync or async. Asynchronous; nobody waits. If it fails. If neither the event nor the lookup resolves within 30 minutes assumed Tōtara policy, a sweeper raises an alert to the on-call engineer with the key, correlation ID and last lookup result, and a runbook step. The case shows the honest status throughout.

Hop 7: decision, notice, and the bank's other systems

Trigger. Notify stage. What runs. In one commit: status Approved, the decision letter queued through the correspondence framework (variation details, the new instalment date, how to contact the bank, and the dispute-resolution scheme), and an outbox row for hardship-status = APPROVED with the arrangement end date. The decision is made on the fourth working day of a 20-working-day window. What changes elsewhere. Collections keeps the strategy paused until the arrangement ends; decisioning keeps the support journey; the app shows "Approved, payments postponed until 22 February 2027". If it fails. A letter-gateway failure cannot undo the approval, because the letter is queued, not sent inline; a bounced email falls back to post per contact preference.

Hop 8: the audit trail and the trace

Everything above shares one correlation ID. A complaint on Monday, "did the bank call me after I applied?", is answered by one search in the observability platform: the app request at 09:12, the outbox publish of RECEIVED at 09:12:03, collections' consumer lag of 2 seconds and its pause at 09:12:05, and no outbound calls afterwards. The case itself holds the decision evidence: inputs, rule versions, approver, event IDs 10442 and 10451, arrangement ARR-771304 and key HA-20417-ARR-1. The arrears case AR-88120 closes as "resolved by arrangement" when the next instalment is paid. Why this matters for the squad. The trace is what lets Ananya, at 10:00 IST on Monday, answer an Auckland question asked at 17:30 NZDT the same day, without waking anyone.

1.11 Scale, failure, deployment and recovery

Scale: what happens at ten times the volume

Hardship volume is spiky, not steady. After a regional flood, applications can jump tenfold in a week (CBA has described using its decisioning engine to give same-day support to customers hit by natural disasters, which is exactly this kind of surge). The design scales in three places. Interactive creation is stateless and scales with nodes. The event consumer scales with topic partitions: more partitions or more data-flow threads, coordinated with the platform team, because a consumer group cannot usefully run more consumers than partitions. Correspondence and specialist work are throttled by people, so the clocks become the constraint. The calendar framework's dashboard shows how many cases will breach which deadline at current throughput, so the tribe can move staff before a breach, not after.

Recovery

Recovery objectives are owned by the bank, not the squad. The example assumes RPO 15 minutes and RTO 4 hours for Lending Care assumed Tōtara policy. The architecture's contribution is that recovery is replayable. Decisions are in the database with their outbox rows; events can be re-consumed within the topic's retention; consumers are idempotent. After a restore, the squad replays events from the restore point and re-sends unsent outbox rows, and nothing is applied twice.

Deployment: the paved road

Every change follows one pipeline: branch, peer review, merge, then automated gates (guardrail score threshold, PegaUnit for decisions and transforms, scenario tests for the hardship and arrears journeys, contract tests for integrations, consumer tests for duplicate, out-of-order and poison events), then promotion through environments with Deployment Manager, and production change approval. Schema changes are deployed before the producer starts using them: consumer first, producer second. A useful India advantage: NZ's quietest hours (overnight) fall in Bengaluru's afternoon and evening, so low-risk releases can run with the squad fully awake and the customer asleep.

1.13 Migration and rollout

Principles

  • Thin slice first: hardship via the app, end to end, before arrears or brokers.
  • Run new and old in parallel for the first cohort; compare outcomes daily.
  • Survive the core migration: the canonical model and versioned transforms mean a new core API or event schema is a new mapping, not a new flow. Run both schema versions during the transition, consumer first.

1.15 Using this in the interview

The five-minute whiteboard

  1. Draw the two doors. Gateway for request–response, event platform for facts. "Pega has exactly two ways out."
  2. Draw one case and its clocks. Hardship: received date, then 5, 10 and 20 working days. "The clocks are law, so they're computed and stored, not remembered."
  3. Draw the outbox. Decision and intent in one commit, then a queue processor. "A slow core can't stall the platform, and a decision is never made but not announced."
  4. Draw the timeout. "Unknown outcome: look up by the same key, never re-post with a new key."
  5. Draw the event fan-out. One hardship-status event: collections pauses, decisioning suppresses offers, app updates. "Care by construction."
  6. Name the guards. Dedupe on event ID in the same commit, sequence guard per key, DLQ, built replay.

Twelve prompts an interviewer might use, and where the answer is

1. "How do you stop processing the same Kafka message twice?" Dedupe row on event ID written in the same commit as the effect; sequence guard per key (1.7).
2. "A write to the core times out. What now?" Unknown outcome; status lookup by the same idempotency key; never a new key; breaker and manual fallback (hop 5).
3. "How do you keep events for one customer in order?" Key by loan or party ID so they share a partition; sequence guard for replays (1.7).
4. "What do you do with a message you can't parse?" DLQ with error class and offset, alert, flag the state as uncertain, fix the transform, replay (1.7).
5. "How does Pega tell other systems it made a decision?" Outbox in the same commit, queue processor publishes, at-least-once delivery, consumers dedupe (1.7, hop 7).
6. "Where would you put the mapping from the core's payload?" In the integration layer, one versioned transform per schema with a unit test; never in the flow (1.6).
7. "How would you structure rulesets and classes?" Organisation, frameworks, implementation, reference data, application; dependencies downward; connectors only in the integration framework (1.5).
8. "How do you scale a consumer?" Partitions bound parallelism; plan partitions with the platform team; scale data-flow threads; watch lag (1.11).
9. "How would you design hardship with SLAs?" Statutory clocks from the received date on working days, stored on the case, breach forecast, same-day acknowledgement (hop 3).
10. "How do you prevent a maker approving their own case?" Routing, Access Deny, server-side validation, detective report (hop 5).
11. "How would you work with a team in New Zealand?" Overlap ceremonies, one-page decisions, runbooks, outcome ownership, correlation-ID tracing (1.12).
12. "Where would GenAI fit?" Policy assistant with citations for specialists; a human decides; answers logged; never in the decision path (hop 4, risk 8).

1.Z Where we are now

What the application can do

Accept a hardship application from the app or the contact centre, start the statutory clocks, stop collections contact and sales offers within seconds through one event, assess with evidence and a policy assistant, approve under dual control, book the arrangement in the core through an idempotent write that survives a timeout, confirm it by event, notify the customer, and prove all of it from one correlation ID.

The mechanisms behind it

Two doors to the outside; a canonical model with versioned transforms; layered rulesets; separate case types; an outbox for every write and every published event; idempotent, sequence-guarded consumers with a DLQ and built replay; reference data under maker-checker; a decision log; and a working model where every alert has an owner in one of two countries.

What it still cannot do

Broker lodgement, cross-product hardship (a credit card and a home loan in one application), and automated income verification. Each is a variation the frameworks are designed to accept, which is the test of whether the boundaries were drawn in the right places.
