2. Pega Platform Core Source Material

2.1 What Pega Is

Pega is a model-driven, rules-based low-code platform used to build workflow, case management, decisioning, customer service and automation applications. In normal Java/Spring development, logic is spread across controllers, services, repositories, database scripts, workflow engines and UI code. In Pega, much of this is represented as rules: case types, flows, assignments, data transforms, data pages, decision tables, SLAs, connectors, service rules, correspondence and security rules.

The platform resolves which rule to run at runtime based on class hierarchy, ruleset version, circumstancing, access group and application stack. That is why Pega development is less about writing large blocks of code and more about choosing the correct rule type, class, ruleset and reuse pattern.

User / Event / API / File / Email → Pega receives request → Case type or service rule starts processing → Flow routes work through stages and assignments → Data Pages fetch reference/external data → Decision rules choose business path → Connectors update downstream systems → Queue Processors handle async work → SLAs, audit, correspondence and reports track the outcome

2.2 Pega Infinity / PRPC

PRPC historically means PegaRULES Process Commander. Pega Infinity is the modern platform branding. When a JD says PRPC 8.x / Infinity 24.x, they expect you to understand classic Dev Studio rule configuration and modern App Studio / Constellation direction.

AreaWhat to knowInterview angle
Dev StudioDetailed rule authoring, class structure, integrations, debugging.You have production hands-on here.
App StudioLow-code case lifecycle, views, channels, data objects.Useful for Constellation and business collaboration.
Admin StudioNodes, listeners, queue processors, system health.Important for production support.
Prediction StudioAI predictions, text analytics, adaptive models.Know conceptually for FCB AI roadmap.

2.3 Rule Resolution

Rule resolution is how Pega decides which rule instance to execute. It checks class hierarchy, ruleset list, version, availability, circumstance, date/time qualifiers and access context. This matters because bugs often happen when the wrong version or class-specific rule is picked.

Rule selected = Best match by class + ruleset + version + circumstance + availability + access context

Production troubleshooting example

If a data transform behaves differently in one market, check whether there is a market-specific circumstanced version, branch rule override or ruleset version mismatch.

2.4 Rulesets, Branches and Deployment

Rulesets package rules. Versions control release changes. Branches support parallel development. In enterprise delivery, you normally develop in branches, merge, package, promote through Dev/QA/UAT/Prod and use guardrail/tests as gates.

P2-level answer: I do not treat a rule change as isolated. I check class impact, ruleset version, dependent rules, integration contracts, regression scope, deployment sequence and rollback plan.

A case is a unit of work created to achieve a business outcome. In FCB Deposits, examples are Account Maintenance, Account Closure, Legal Process Order, Payment Exception and Reconciliation Exception. A case type defines the lifecycle; a case instance is the actual work item.

3.2 BPM

BPM is the orchestration of people, systems, rules and time. In Pega, BPM is implemented with case lifecycle, flows, assignment routing, decisioning, SLAs, integrations and audit. For a bank, BPM is not just convenience; it enforces regulatory discipline and operational consistency.

Deposit Account Maintenance Case 1. Intake request from email/portal/branch 2. Load customer/account data from core banking 3. Validate request and required documents 4. Route to maker/checker if risk condition is met 5. Call ESB/API to update core banking 6. Generate customer correspondence 7. Close case with audit trail

3.3 SLA Deep Dive

SLAs define urgency and escalation over time. Pega SLAs usually have goal, deadline and passed-deadline behavior. In banking workflows, some SLAs are soft operational targets, while others are hard legal or compliance deadlines.

SLA PartMeaningExample

  • Expose SLA status in manager dashboards.
  • Audit escalation events for compliance workflows.

4. Decisioning, Data Model, Data Pages and Declarative Rules

4.1 Decision Rules

Decisioning is about separating business logic from procedural code. In Pega, decision rules make changing policy easier and safer. In deposits, rules change by product, customer segment, state, risk category, channel or legal order type.

Rule TypeUseDeposits Example
Decision TableMatrix-style condition to resultState + order type + account type → exemption rule
Decision TreeNested branchingIf customer risk high, then enhanced approval path
When RuleBoolean reusable conditionIsHighRiskMaintenance
Map ValueTwo-dimensional mappingProduct + channel → fee code
CircumstancingRule variant by property/dateTexas garnishment logic vs California garnishment logic

4.2 Data Transforms

Data Transforms initialize or map data on clipboard pages. They are declarative and preferred over activities for simple mapping because they are easier to read and guardrail-compliant.

Use Data Transform for: - Initialize case fields - Map API response to case properties - Copy user input to data object - Set defaults - Normalize values before save Avoid using it for: - Complex loops requiring heavy logic - External calls - Long procedural processing

4.3 Declarative Rules

Declarative rules react to property changes or maintain derived values. They reduce manual recalculation.

Declarative RuleMeaningExample
Declare ExpressionAuto-calculate propertyTotalDue = Principal + Interest + Fees
Declare ConstraintValidation ruleClosure amount cannot be negative
Declare OnChangeTrigger logic when value changesIf account status changes to frozen, notify queue
Declare TriggerDatabase-trigger-like logicCreate audit record after insert/update

4.4 Data Pages

A Data Page is a reusable data source abstraction. It can source data from report definitions, connectors, lookup data, activities or data transforms. It can be read-only or editable, parameterized or non-parameterized, and scoped to node/requestor/thread.

ScopeUseExample
NodeShared reference dataD_StateLegalRules
RequestorUser session dataD_UserProfile
ThreadCurrent case contextD_AccountDetails[AccountID]

Performance considerations

  • Use refresh strategy to avoid stale data.
  • Parameterize correctly; wrong parameters cause cache misses.
  • Avoid loading huge lists unless needed.
  • Use node scope for stable reference data only.
  • For external APIs, handle timeout/failure gracefully.

4.5 Data Model and Class Structure

Class structure is the backbone of maintainability. Separate work classes, data classes and integration classes.

FCB-Deposits-Work FCB-Deposits-Work-AccountMaintenance FCB-Deposits-Work-LegalProcessOrder FCB-Deposits-Work-PaymentException FCB-Deposits-Data-Customer FCB-Deposits-Data-Account FCB-Deposits-Data-LegalOrder FCB-Deposits-Int-Fiserv FCB-Deposits-Int-Flexcube FCB-Deposits-Int-OFAC
P2 answer: I design class structure around reuse and separation of concerns. Work classes model business cases, data classes model reusable business objects, and integration classes isolate external request/response schemas.

5. Constellation UI, Traditional UI and DX API

5.1 Traditional UI

Traditional Pega UI uses sections, harnesses, flow actions, layouts, controls and skins. It is highly flexible and common in older Pega applications. Many Pega developers have deep experience here through Customer Service, CPM and older PRPC applications.

5.2 Constellation UI

Constellation is Pega's modern, view-based UI architecture. It uses a prescribed design system and React-based runtime. Instead of heavily customizing sections, developers configure views and use standardized components. This improves upgradeability and consistency.

Traditional UIConstellation UI
Section/harness-basedView-based
More custom layout freedomMore standardized UX
Custom JS/control commonPrefer OOTB components
Can become maintenance-heavyBetter upgrade path

5.3 DX API

DX API exposes Pega case and assignment data plus UI metadata to external front ends. Traditional APIs usually return only business data; DX API can return data, layout, actions and view metadata. This lets React/Angular/custom UI render Pega-driven workflows while Pega remains the case engine.

External UI / Constellation runtime → Calls DX API → Receives case data + view metadata + available actions → User submits assignment → DX API sends action to Pega → Pega advances case lifecycle
Interview answer: I have stronger hands-on in traditional UI/Customer Service patterns, but I understand Constellation as Pega's recommended modern architecture. For a greenfield FCB app I would prefer Constellation unless there is a strong custom UI requirement, because it keeps the app closer to guardrails and future platform direction.

6. Integration Sourcebook: REST, SOAP, JMS, ESB, Connect-SQL, Microservices

6.1 Integration Design Principles

In enterprise banking, Pega is usually not the system of record. Core banking, payments, KYC, AML, GL and document systems own data. Pega orchestrates work, captures audit, routes assignments and calls external systems through integration layers.

Pega Case Data → Data Transform maps request → Connector / Service / Listener → External System or ESB → Response mapping → Case status update → Error handling and audit

6.2 REST in Pega

REST uses HTTP methods and usually JSON. Pega uses Connect-REST to call external APIs and Service-REST to expose Pega APIs.

RuleDirectionExample
Connect-RESTPega → externalCall TIBCO ESB to update account address
Service-RESTExternal → PegaExternal system creates PaymentException case

Production-grade REST checklist

  • Timeout configured.
  • Authentication handled securely: OAuth/basic/mTLS depending on enterprise standard.
  • Request/response mapped through data transforms.
  • HTTP 4xx vs 5xx handled differently.
  • Correlation ID logged.
  • Retry only for retryable errors.
  • Sensitive data masked in logs.

6.3 SOAP

SOAP is XML-based and uses WSDL/XSD contracts. It is common in older enterprise systems. In Pega, Connect-SOAP consumes WSDL and maps XML request/response to clipboard structures.

Know: SOAP envelope, body, header, WSDL, XSD, namespaces, SOAP fault. For FCB, SOAP may appear through legacy banking or compliance services.

6.4 JMS

JMS is a Java messaging API for queues and topics. TIBCO EMS is a common enterprise messaging implementation. JMS supports asynchronous communication, decoupling Pega from downstream availability.

ConceptMeaning
QueuePoint-to-point; one consumer processes each message
TopicPublish-subscribe; multiple subscribers can receive message
Durable subscriberReceives messages even after temporary disconnection
Dead-letter queueFailed messages after retries

6.5 ESB / TIBCO Middleware

An ESB mediates between systems. It handles routing, transformation, protocol conversion, validation and sometimes orchestration. In FCB Deposits, Pega likely calls TIBCO endpoints; TIBCO talks to Fiserv, Flexcube or legacy systems.

Pega Connect-REST request → TIBCO ESB → Validate and transform payload → Route to Fiserv/Flexcube/Compliance system → Transform response to canonical format → Return to Pega

Why ESB matters

  • Pega does not need direct knowledge of every core banking protocol.
  • ESB provides canonical data model.
  • Downstream system changes can be hidden behind ESB contract.
  • Centralizes security, logging and routing.

6.6 Connect-SQL

Connect-SQL runs SQL against external databases. You used it for metadata-driven MERGE operations. In interviews, position it carefully: APIs are preferred for service boundaries, but Connect-SQL is valid for controlled database integration, reporting or bulk operations when approved.

Banking caution: Never use direct DB updates casually against systems of record. Mention approvals, transaction control, audit, parameterization and performance testing.

6.7 Microservices

Microservices are small independently deployable services around business capabilities. Pega consumes microservices for specific functions: customer lookup, account update, OFAC screening, document storage, notification delivery.

Kafka is an event streaming platform. It is used when systems need real-time or near-real-time event exchange at scale. A producer writes events to a topic. Topics have partitions. Consumers read events and commit offsets.

7.3 Queue Processors

Queue Processors run background tasks asynchronously. They are critical for performance when user-facing processing should not wait for heavy work. They also support retries and scalable processing.

Use caseWhy Queue Processor helps
Bulk case creationDo not block user/API thread
External system updateRetry transient downstream failures
Kafka event processingProcess records at scale
Notification sendingSend correspondence asynchronously

Your throughput story

I tuned Queue Processor and Job Scheduler-based processing to handle 200,000 records in 5 minutes. The key was moving heavy work out of synchronous flow, processing in controlled batches, reducing repeated lookups, standardizing mappings and adding operational monitoring for failures.

7.4 Job Schedulers

Job Schedulers run at configured times or intervals. They are used for nightly batches, reconciliation, reporting, cleanup and polling external queues.

Nightly Reconciliation Job Scheduler → Fetch file/extract data → Create batch control case → Queue individual records → Compare records → Create exception cases → Generate report

7.5 Data Flows and Datasets

Datasets define the source/destination. Data Flows define processing. Together they allow streaming or batch pipelines in Pega.

ComponentRole

8. File Listener, SFTP, Parse Rules, Email Listener and Email Channel

8.1 File Listener

A File Listener monitors a directory/repository/SFTP location for files. When a matching file appears, Pega moves it into processing, invokes a Service File rule, parses the content and processes each record.

External SFTP folder → File Listener scans for matching file pattern → Moves file into work folder → Service File rule is invoked → Parse rule reads file content → Service activity maps clipboard and creates/updates data → File moved to completed/error folder → Report/log generated

Configuration concepts

ItemMeaning

Polling intervalHow often listener checks for files
Service packageSecurity and access context for service
Service FileRule invoked for file processing
Parse ruleDelimited/fixed/XML parser
Error folderWhere failed files go

8.2 SFTP

SFTP is secure file transfer over SSH. Banks still use SFTP for ACH/NACHA files, statements, settlement files, regulatory reports, reconciliation extracts and legacy interfaces. SFTP is less real-time than APIs/Kafka but reliable and common for batch banking operations.

Operational controls

  • File naming convention and timestamp.
  • Manifest or control totals.
  • Archive processed files.
  • Retry failed transfers.
  • Audit arrival/processed count/error count.
  • Credential/key rotation.

9.2 Knowledge Buddy

Knowledge Buddy is Pega's enterprise knowledge assistant. It uses Retrieval Augmented Generation (RAG): approved enterprise content is ingested, chunked, embedded and retrieved to ground LLM responses.

SOPs / PDFs / Policy docs / Knowledge articles → Ingest into Knowledge Buddy → Chunk content → Generate embeddings → Store in vector database → User asks question → Retrieve relevant chunks → LLM generates answer based on source content → Return answer with references and security filtering

Why it matters in deposits

Deposit operations involve many procedures: account closure, deceased customer handling, legal orders, KYC exceptions, state-specific garnishments, ACH disputes. Agents cannot memorize everything. Knowledge Buddy can answer operational questions based on approved SOPs.

Question: How would Knowledge Buddy help a legal process order team?
Answer: It can ingest legal SOPs and state-specific policy documents. When an agent asks how to process a Texas garnishment, it retrieves the relevant procedure and returns grounded steps with references, reducing manual searching and inconsistent handling.

9.3 Agentic AI

Agentic AI goes beyond Q&A. It interprets intent, plans next steps and can call tools/actions under guardrails. In Pega, the likely use is not unrestricted autonomous agents but controlled AI-powered workflow assistance.

14.2 Deep File Listener + SFTP Implementation Playbook

File Listener is one of the most important banking integration patterns. It is used when data arrives in files rather than APIs/events. In deposits, this can be NACHA ACH return files, reconciliation files, legal order batches, GL extracts, statement files or legacy core banking files.

A. End-to-end architecture

External system / bank partner / core banking → Places file on SFTP location → Pega File Listener polls the location → Listener locks/moves file into processing directory → Service File rule receives file stream → Parse rule reads rows/segments → Service activity or data transform validates each record → Valid records create/update Pega cases/data → Invalid records go to error table / exception case → File archived to completed/error folder → Processing summary generated and support alerted if needed

B. Rules and data instances you need

ArtifactPurposeExample name
FTP Server / Repository data instanceDefines SFTP host, port, credentials/key, folder pathFCBDepositsSFTP
Service PackageSecurity/access context for service executionDepositsFileServices
Service File ruleEntry point for file processingProcessACHReturnFile
File ListenerPolls location and invokes Service FileACHReturnFileListener
Parse Delimited / Structured / XMLMaps file content to clipboardParseNACHARecord
Data TransformMaps parsed row to data/case modelMapACHReturnToPaymentException
Activity / Queue ProcessorValidates and processes records asynchronouslyQueueACHReturnRecord
Report Definition / DashboardOperational visibilityACHFileProcessingSummary

C. Implementation sequence

  1. Understand file contract: file format, delimiter/fixed width/XML, encoding, header/trailer, control totals, mandatory fields, max size, frequency and SLA.
  2. Create data model: staging class for file header, record class for each row, error class for failed records and final business case class.
  3. Configure SFTP access: host, port 22, folder, authentication mode, credentials/SSH key and network allowlist if needed.
  4. Create Service Package: define access group and authentication. For internal listeners this often uses an application service access group with limited permissions.
  5. Create Service File: set service method, request parsing, parse rule and service activity.
  6. Create Parse Rule: map each column/segment to properties. For fixed-width files define start and length. For delimited files define delimiter, quote handling and record mapping.
  7. Create File Listener: configure source location, file pattern, polling interval, service package, service file, processing folder, completed folder and error behavior.
  8. Add validation: required fields, duplicate file detection, duplicate record detection, amount/date format validation, account existence and control total validation.
  9. Queue heavy work: do not process 200K rows synchronously inside the listener thread. Stage records and queue them using Queue Processor.
  10. Add reconciliation summary: total records, success count, failed count, duplicate count, processing duration and file status.
  11. Add replay strategy: reprocess failed records after data correction; do not blindly reprocess whole file if partial processing already happened.
  12. Add monitoring: alert if expected file missing, file fails, error count exceeds threshold, queue backlog grows or processing exceeds SLA.

D. File format examples

Delimited ACH return sample: RecordType|TraceNumber|AccountNumber|Amount|ReturnCode|EffectiveDate ACH_RETURN|1234567890|987654321|250.00|R01|2026-10-10 Fixed-width example: Positions 1-10 TraceNumber Positions 11-22 AccountNumber Positions 23-32 Amount Positions 33-35 ReturnCode Positions 36-43 EffectiveDate

E. Staging table design

TablePurposeKey columns
deposit_file_batchOne row per filebatch_id, file_name, checksum, received_ts, status, total_count, success_count, error_count
deposit_file_recordOne row per parsed recordrecord_id, batch_id, line_no, account_no, amount, status, error_code
deposit_file_errorError detailserror_id, record_id, error_type, error_message, raw_payload

F. Duplicate prevention

Banking file processing must be idempotent. Idempotency means processing the same file/record twice should not create duplicate financial actions.

  • Calculate file checksum or use file name + date + control number.
  • Store batch ID and reject duplicate file unless explicitly reprocessed.
  • Use business key for records: trace number + account + amount + effective date.
  • Use unique constraint in staging table if possible.
  • For case creation, check if case already exists for record key before creating new case.

G. Error handling pattern

ErrorAction
Invalid file nameMove to error folder, alert support
Malformed rowSave row error, continue if allowed
Control total mismatchMark file failed; do not post records until reviewed
Account not foundCreate exception record/case
Downstream API timeoutRetry through Queue Processor; dead-letter after max retry
Interview answer: For high-volume banking files, I would not put all logic directly inside the File Listener. I would use the listener to securely ingest and stage data, validate file-level controls, then process records asynchronously through Queue Processors with idempotency, replay and monitoring.

B. SQL basics you should know

-- Select records SELECT account_no, status, updated_ts FROM deposit_account WHERE status = 'FROZEN'; -- Join batch and record tables SELECT b.file_name, r.line_no, r.status, r.error_message FROM deposit_file_batch b JOIN deposit_file_record r ON r.batch_id = b.batch_id WHERE b.status = 'FAILED'; -- Aggregate processing counts SELECT batch_id, status, COUNT(*) AS record_count FROM deposit_file_record GROUP BY batch_id, status;

C. MERGE / upsert concept

MERGE updates existing rows and inserts missing rows. PostgreSQL often uses INSERT ... ON CONFLICT DO UPDATE. SQL Server supports MERGE. Your resume mentions Connect-SQL MERGE, so be ready to explain the idea rather than syntax only.

-- PostgreSQL-style upsert example INSERT INTO deposit_account_snapshot(account_no, balance, status, updated_ts) VALUES (:accountNo, :balance, :status, CURRENT_TIMESTAMP) ON CONFLICT (account_no) DO UPDATE SET balance = EXCLUDED.balance, status = EXCLUDED.status, updated_ts = CURRENT_TIMESTAMP;

D. Indexing basics

Index type/useWhen useful
Single-column indexFrequent filter by one column, e.g., case_status
Composite indexFrequent filter by multiple columns, e.g., batch_id + status
Unique indexPrevent duplicates, e.g., file checksum or record business key
Partial indexIndex only subset, e.g., failed records

E. Pega DB performance basics

  • Do not load huge lists into clipboard if pagination/filtering can be done in DB.
  • Use indexed columns in report filters.
  • Avoid unbounded report definitions in production portals.
  • Commit in controlled batches for large processing.
  • Be careful with Obj-Browse over huge tables.
  • Use Queue Processors to break large work into smaller units.
  • Do not expose sensitive columns in logs or reports.

F. Transaction and locking interview answer

A database transaction should keep related changes atomic. In Pega, I avoid long-running transactions that hold locks while calling external systems. For heavy work, I queue records and commit in smaller units. For duplicate prevention I use business keys and idempotency checks so replay does not create duplicate financial actions.

C. Retry strategy

FailureRetry?Reason
Temporary ESB timeoutYesTransient downstream issue
Invalid JSON schemaNoBad producer payload; send to dead-letter
Account not foundMaybeCould be timing issue; limited retry then exception
Duplicate eventNoMark ignored/idempotent success
Database deadlockYesRetry with backoff

D. Queue Processor tuning concepts

  • Batch size: Too small means overhead; too large can increase memory/lock time.
  • Parallelism: More threads can improve throughput but may create lock contention.
  • Commit frequency: Commit after manageable units, not after enormous transactions.
  • Payload size: Store large payload externally or compress/archive if needed.
  • Back-pressure: If downstream is slow, queue grows; monitor queue depth and throttle if needed.
  • Idempotency: Essential for replay and duplicate event protection.

14.9 Production Support Runbook You Can Explain

Production support maturity is a major lead signal. Use this runbook when asked how you handle incidents.

  1. Confirm impact: which market, users, case type, integration, topic, file or queue is affected?
  2. Preserve evidence: case ID, correlation ID, timestamp, operator, node, request payload reference, error ID.
  3. Check dashboards: PDC, queue status, listener status, Kafka dashboard, Splunk/logs.
  4. Classify failure: data issue, rule issue, integration issue, infra issue, downstream issue, access issue.
  5. Contain: pause listener/queue if duplicate financial impact risk exists.
  6. Recover: replay failed records, restart listener, rerun job, correct data, deploy hotfix if needed.
  7. Validate: confirm successful processing and no duplicate side effects.
  8. Communicate: update ServiceNow/stakeholders with impact, ETA, workaround.
  9. Prevent recurrence: add validation, alert, retry, dashboard metric or test coverage.
Lead-style answer: I separate recovery from root-cause prevention. First I restore service safely, then I identify why controls failed and add monitoring or validation so the issue does not repeat.

Q: Explain File Listener.
A: A File Listener monitors a configured location for matching files. When a file arrives, it invokes a Service File rule, which uses Parse rules to read records and a service activity/data transform to map values. Q: Explain Email Listener vs Email Channel.
A: Email Listener is the lower-level mechanism that monitors an inbox and routes messages to Service Email. Email Channel is the higher-level channel configuration that can include routing, case creation, NLP topic/entity/sentiment detection and automated responses.
