1.0 The application and the request we will follow

About the worked example. Every chapter in this pack follows one application: Deposit Servicing, built for a fictional US bank called Riverbend. The customers, accounts, balances, case IDs, staff, policies, thresholds, SLAs and architecture are invented for teaching. They are not First Citizens' architecture, data or policy, and nothing here should be read as describing any real bank's internal processes. Where a figure is a legal requirement rather than an invented policy, it is cited to the regulation. Class names keep the FCB-Dep- prefix purely so the rule-resolution examples stay consistent across chapters.

Riverbend's Deposit Operations team services checking and savings accounts. Four people appear throughout. Dana Whitfield is a retail customer (CUS-4417). Marcus Reed (mreed) is a Deposit Operations analyst who works the DepOps-Maintenance queue; he can submit changes but cannot approve them. Priya Raman (praman) is the supervisor who approves sensitive changes and cannot approve a case she prepared herself. Sam Okonjo (sokonjo) builds the application, and Lena Fischer (lfischer) is the L2/L3 engineer who keeps it running. Two further customers appear only when the main journey cannot carry a process: Victor Osei for a legal order and Harlow Freight Co. for an ACH return.

The request that drives this chapter is small. On Monday 2 March 2026 Dana changes her mailing address in the web channel, and the application creates case AM-10417. Nothing about it is exotic, which is the point: the next fourteen sections explain what the platform must already know before that one case can behave correctly for Dana's state and product, and why the same application, with the same case type, must behave differently for someone else.

1.1 Why the request is not code

The obvious way to build the address change is to write it. A controller receives Dana's form, a service validates the new address, a repository updates the customer record, a workflow object tracks whether Marcus or Priya has looked at it, and a template produces the confirmation letter. That is a few weeks of work in Java and Spring, and it works for one bank in one state.

It stops working when Riverbend's reality moves, and in a bank reality moves constantly. A regulator changes what must be verified before a mailing address is changed. A second state needs a different confirmation notice. Compliance decides that an address changed within 30 days of a card reissue now needs a supervisor. Each of those is a change to logic that the original developers wrote into code, so each is a development ticket, a build, a regression pass and a deployment of a service that otherwise did not need to change.

Pega's answer is to treat the parts that change most as data. The process the request follows, the decisions about who must review it, the mapping of fields between the customer record and the case, the screens and the letter are each stored as a rule: a small, named, versioned record in the Pega database. The engine that runs the application does not contain Riverbend's logic at all. For each thing it needs to do, it asks which rule applies to the situation in front of it (that question is rule resolution, the subject of 1.6), generates executable Java for that rule the first time it is needed (assembly), caches the result, and runs it. Changing how Riverbend treats address changes in North Carolina becomes a matter of creating a variant of one rule, not rebuilding a service.

The comparison with Spring is worth holding in the same place, because it is what most interview questions ask for.

DimensionHand-written Java/SpringPega

That last row is the honest trade-off. The platform removes the build-and-redeploy cycle from business change, and in exchange it makes it easy to create thousands of rules that interact in ways nobody planned. Most of the rest of this chapter, and a good part of the pack, is about the discipline that keeps that from happening. The failure mode to recognise early is treating Pega as Java with a graphical editor: putting all logic into Java steps or activities loses rule resolution, circumstancing, reporting and auditability at once, and the guardrails (1.12) will say so.

1.3 What a rule is

For Dana's request Sam needs a way to say "an address change goes through Capture, Verify, Approve, Update core and Notify", a way to say "a change inside 30 days of a card reissue is sensitive", a way to fetch Dana's customer record from the core, and a letter to confirm the change. Each of those is a different kind of rule, and all rules share one anatomy.

A rule is a database record, an instance of a class that inherits from Rule-. It has a name (its purpose), an Applies-To class, a ruleset and version, an availability, and content that depends on the rule type. The rule type is simply which form you fill in: Flow, Data Transform, Decision Table, Section and so on. Rule instances live in the pr4_rule_* tables, one per family. Cases and customers are different: a case such as AM-10417 is a work instance stored in a work table, not a rule, which is why changing a rule does not change cases already in flight.

Rule-Obj-Flow FCB-Dep-Work-AccountMaintenance ProcessAddressChange [ruleset FCBDeposits:01-02-03] ^ rule type ^ Applies-To class ^ Purpose/Name ^ RuleSet:Major-Minor-Patch Instance key (pzInsKey): RULE-OBJ-FLOW FCB-DEP-WORK-ACCOUNTMAINTENANCE PROCESSADDRESSCHANGE #20260210T101500.123 GMT Resolution key: (rule type, class, name) -> many candidates; resolution picks ONE

The last line of that key is the one to keep. When the engine needs ProcessAddressChange for Dana's case, there may be several instances with that name and rule type: different versions, different rulesets, different classes, circumstanced variants. The resolution key does not identify one rule, it identifies a set of candidates, and choosing among them is the job of Section 1.6.

Dev Studio groups rule types into categories, and the grouping is a useful map of what a Deposit Servicing application is made of.

Every rule also carries the same handful of administrative fields: the Applies-To class that places it in the hierarchy, the ruleset and version that place it in a layer, an availability (Section 1.6 explains the five values and why they matter), optional circumstance or date qualifiers, an optional privilege required to run it, the developer who has it checked out, and a history of who saved it and why. They look administrative, and they are the inputs rule resolution uses.

1.4 Classes: where a case lives and where its rules come from

Sam now has a name for the case: FCB-Dep-Work-AccountMaintenance. The class matters for three reasons at once, and it helps to separate them. It determines which rules apply to AM-10417 (a rule defined on a parent class is usable by every descendant unless a more specific rule overrides it). It determines where the case is stored. And it determines which properties the case holds.

A Pega class is therefore not an object-oriented class with methods. It is a namespace and an inheritance node. The reason the platform works this way is variation: before inheritance-driven rule engines, each variation of a process meant a copy of the whole process. With a class tree Sam writes ValidateSigner once at FCB-Dep-Work and overrides it only for FCB-Dep-Work-AccountClosure, where signers behave differently.

Riverbend's application needs four kinds of class, and the way they differ is easiest to see from what happens to an instance of each.

KindExampleStored whereWhat it is for
Work class (concrete)FCB-Dep-Work-AccountMaintenanceThe work table of its class group, as a BLOB plus exposed columnsCase types: AM-10417 is an instance
Data classFCB-Dep-Data-Customer, FCB-Dep-Data-AccountIts own table, or noneReference and master data, embedded page structures
Integration classFCB-Dep-Int-CoreAccountNot storedThe shape of a request or response to the core; the mapping target for connectors
Abstract framework classFCB-, FCB-Dep-Never instantiatedHosts shared rules and properties for the classes beneath it

Abstract and concrete are worth one more sentence. An abstract class cannot be instantiated or saved and exists only to host shared rules, which is why FCB-Dep- never holds a case. A concrete class can have instances, and a concrete data class also needs a keys definition and a table mapping so that Pega knows how to open one.

The fields on a class rule that matter in practice are few. The class name is prefix-based and the hyphen separates levels, which is what pattern inheritance reads. An optional directed parent names an explicit inheritance parent. For work classes the class group maps the class to a table and an ID format. The keys define the primary key and become the lookup for Obj-Open.

@baseclass (universal rules: Pega-supplied) | Embed- / Data- / Work- / Rule- / History- / Index- ... (Pega base classes) | FCB- (organisation root: shared properties, correspondence, error handling) |-- FCB-Dep- (Deposits framework, abstract) | |-- FCB-Dep-Work (class group: case table + ID prefix) | | |-- FCB-Dep-Work-AccountMaintenance (AM-10417) | | |-- FCB-Dep-Work-AccountClosure (AC-10882) | | |-- FCB-Dep-Work-LegalOrder (LO-20331) | |-- FCB-Dep-Data-Customer (data class, DB table) | |-- FCB-Dep-Data-Account | |-- FCB-Dep-Int-CoreAccount (integration class, no table) |-- FCB-Common-Data-Address (reusable embedded data class)

The same hierarchy usually maps onto an application layering: an enterprise-common layer, a Deposits framework layer and an implementation layer, each with its own rulesets, so that a business unit's overrides live in the top layer without touching the framework (Section 1.7). The mistakes to avoid are the mirror images of what the tree is for: putting everything in one class so specialisation becomes impossible, creating a new case class for every minor product variation instead of using one class with circumstancing or decision rules, using work classes for reference data and bloating the work table, and putting an integration payload straight into the case rather than into an integration class that is mapped.

1.5 Pattern inheritance and directed inheritance

When the engine needs InitCase for Dana's case, it begins in FCB-Dep-Work-AccountMaintenance and, if the rule is not there, has to go up. How it goes up is inheritance, and there are two kinds.

Pattern inheritance comes from the name. The engine strips trailing segments at each hyphen: FCB-Dep-Work-AccountMaintenance, then FCB-Dep-Work-, then FCB-Dep-, then FCB-. You get it by naming classes sensibly. Directed inheritance is an explicit parent set on the class rule, used when a class needs to inherit from somewhere outside its own name path, such as a Pega framework class or a shared cover class.

The order of consultation is interleaved, and that is where the common wrong answer comes from. The engine searches the class itself, then its pattern chain; then it moves to the directed parent and runs a fresh pattern search from that class; it repeats until @baseclass. A rule not found at @baseclass is an error. It is not "all the pattern parents, then all the directed ones".

A separate idea is often mixed up with this one, and the distinction pays off in diagnosis. The class group is a persistence concept: it decides which table a case instance is written to and its ID prefix, and work classes in a group share one table. Directed inheritance is a rule-resolution concept. They are independent, so a class can belong to a class group and also have an unrelated directed parent. There is one documented interaction: belonging to a class group forces the "Find by name first (Pattern)?" checkbox on automatically. And one documented edge case: if the directed parent is the longest prefix of the class name ending in a hyphen, selecting or clearing that checkbox makes no difference to resolution.

Here is the inheritance search on a concrete rule. Sam has written a data transform named InitCase that sets default values on a new case. For an address-change case the engine looks for it like this.

Class searchedInitCase exists?Effect for AM-10417
FCB-Dep-Work-AccountMaintenanceNocontinue up
FCB-Dep-Work-Yes (sets a default SLA flag)Chosen unless a candidate with a better rank is found
FCB-Dep-Yes (generic)shadowed
Work-Pega-supplied defaultshadowed

If FCB-Dep-Work-AccountClosure later defines its own InitCase, it wins for closure cases only, and address changes keep using FCB-Dep-Work-. To extend rather than replace, the closure-level rule applies the superclass version first (data transforms have an explicit option to do so) and then adds its own settings. The note about class group and the "Find by name first" option is documented in the Class form's General tab; the interleaved search is described in Pega Academy's inheritance topic (references at the end of the chapter).

Directed inheritance has a legitimate use and a standing temptation. The use: a data class that must reuse another class tree, such as an integration class directed to a common data class to inherit property definitions, or a framework class that wants Pega's cover-class behaviour while sitting in Riverbend's naming. The temptation is long chains of directed parents for convenience. They make resolution hard to reason about at three in the morning, so keep them to the minimum necessary and write them down.

1.6 Rule resolution: which rule runs for Dana

Everything so far has been about where rules can sit. The question this section answers is what the engine does when several of them could apply. The answer is a small algorithm in five phases, and the most useful way to learn it is to run it on a single real lookup.

One rule, three candidates

Marcus opens AM-10417, and the review screen needs to know how much scrutiny the change deserves. That is a decision table named ReviewRequirement, Applies-To class FCB-Dep-Work-AccountMaintenance. Sam has authored it three times over the project's life, and all three exist in the database:

#Where it isQualifierWhat it says
1FCBDeposits:01-02-04, on FCB-Dep-Work-AccountMaintenance.State = "NC"North Carolina variant: adds a second identity check for sensitive changes
2FCBDeposits:01-03-02, on FCB-Dep-Work-AccountMaintenancenoneThe base rule, patched last week to read the new 30-day card-reissue flag
3FCBDeposits:01-01-00, on FCB-Dep-Work-noneThe original generic version on the parent class

Dana's case has .State = "NC". Which row runs? Intuition says the newest, row 2, because it has the latest patch. The platform says row 1, and the rest of this section is the explanation.

Gather, filter, rank

First the engine gathers: starting in the Applies-To class it walks up the inheritance structure (Section 1.5) and collects every instance of that rule type and name it finds on the way. Here that is all three rows. Then it filters out candidates that cannot apply at all. A candidate is dropped if its ruleset is not on the operator's ruleset list, if its version is higher than the version the list allows (a list entry FCBDeposits:01-02 permits 01-02-xx but not 01-03-xx), or if its availability is Not Available.

That second condition matters immediately. Marcus is logged into the production application, whose ruleset list allows FCBDeposits:01-03, so row 2 survives. If his access group were still pinned to 01-02, row 2 would be filtered out before ranking, and he would see the older behaviour for a different reason than the one coming next.

The survivors are then ranked, and the order of the sort keys is the thing to remember. First, class: the candidate closest to the Applies-To class ranks highest. Second, ruleset: the order of the operator's ruleset list. Third, circumstance (property or template). Fourth, circumstance date. Fifth, date and time range. Sixth, version, highest first within a ruleset. Rows 1 and 2 sit on the same class, so class does not separate them. They are in the same ruleset, so ruleset does not either. The third key does: row 1 is circumstanced on a property, row 2 is not. Row 1 therefore ranks above row 2, and version, the key that favours row 2, is not consulted until the sixth.

Pega states the reason directly: version is ranked last so that "circumstanced Rules are not automatically overridden if the base Rule is updated in a more recent Ruleset version." That sentence is the whole design. If the newest version always won, fixing the base rule would silently destroy every circumstanced variant, so the platform makes the opposite choice and leaves the maintenance burden with the developer.

Two clean-up steps follow ranking. If any candidate is marked Withdrawn, every candidate in a lower version of the same ruleset with the same Applies-To class, purpose and qualifiers is removed. And the highest-ranked candidate that has no qualifiers becomes the default candidate, the one that always matches; everything ranked below it is discarded, because it could never be reached. In this example row 2 is the default, and row 3 is discarded.

Cache, then qualify at runtime

What gets cached is not a winner. The engine stores the remaining ranked list (row 1, then row 2) in the rules cache, invalidated by a rule save, a check-in or a cache refresh on the node. At runtime the engine walks that list for this case, user and moment, and takes the first candidate whose qualifiers are satisfied. Dana's .State is "NC", so row 1 qualifies and runs. For a Texas customer, row 1's qualifier fails, the walk falls to the default, and row 2 runs. If the selected candidate were Blocked, the run would halt and log an error rather than fall through; if it is not yet assembled, the winner is assembled to Java now.

This is also why the cache holds a list. One cached result serves a North Carolina case and a Texas case and gives each its own rule. If it held a single resolved winner, circumstancing could not work at all, and the common wrong answer in interviews, "the resolved rule is cached", describes a system that would not be able to do what Pega does.

The consequence for Sam is practical and is the most expensive rule-resolution mistake in production. He patched the base rule and verified the fix in a state with no variant. North Carolina keeps running the old logic, silently, because its variant outranks the patch. The fix is to patch the base rule and every circumstanced variant, or to withdraw the variants deliberately, and the cheapest possible check before any base-rule fix is to look at the rule form's circumstance list.

Seeing it in Tracer

When Marcus reports that a Texas colleague sees different behaviour from his, Sam does not reason from memory. He runs as the affected operator (so the ruleset list is the right one), starts Tracer with data transforms, activities and rule resolution events enabled, and reads the rule instance key printed for ReviewRequirement: it names the class, the ruleset and version, and any circumstance tag that won. He opens the rule from that Tracer line rather than from the Records Explorer, which would open it as himself. The usual root causes, in the order they turn up: a higher ruleset layer in that market's application stack overriding the rule; a circumstanced variant on a property; a date-effective variant that went live; an operator whose ruleset list is pinned to an older version; a branch ruleset left in a personal list; and, rarely, a stale cache on one node.

Check your understanding.

Priya, logged in as a North Carolina supervisor, still sees the pre-patch behaviour after Sam checks in ReviewRequirement at FCBDeposits:01-03-02, but a Texas colleague sees the fix. Name the cause, the evidence you would look for, and two fixes.

Answer. The North Carolina case resolves to the older circumstanced variant at 01-02-04, because circumstance (the third sort key) outranks version (the sixth). Tracer shows the winning instance key with its circumstance tag. One fix is to patch the variant as well; the other is to withdraw it deliberately so the default serves everyone. The assumption this depends on is that both rules sit on the same class and ruleset; if the variant sat on a more specific class, or in a lower ruleset than a base on the same class, the ranking order would change the answer, which is what the next three worked examples show.

Three variations Sam has to understand

A more specific class beats a higher-priority ruleset. Riverbend keeps an overrides ruleset above the deposits ruleset, expecting it to win everything. Two candidates exist for CalculateFee: one on the more specific FCB-Dep-Work-AccountClosure in FCBDeposits:01-01-01 (lower priority), and one on the less specific FCB-Dep-Work in FCBOverrides:01-01-01 (higher priority). The closure-class candidate wins, because class is sort key one and ruleset only sort key two. The teams that expect an overrides ruleset to beat everything are then unable to explain why a class-level rule still wins; if the override must win, it belongs on the same class or a more specific one, not merely in a higher ruleset. One exception is documented: for a rule type whose class does not have "Use class-based inheritance to arrive at the correct Rule to execute" selected, class is not a ranking criterion at all and ruleset order decides.

An older circumstanced rule beats a newer base rule. This is the situation already seen on Dana's case, repeated with a legal-order rule so the numbers are explicit. CalculateHoldPeriod on FCB-Dep-Work-LegalOrder, in one ruleset: a circumstanced variant for .State = "CA" at FCBDeposits:01-02-04, and a base rule just patched at FCBDeposits:01-03-02. For a California case the older variant wins; the base rule becomes the default and serves every other state.

Not Available, Withdrawn and Blocked are three different things. They are easy to blur and the consequences differ sharply. One section rule, CreateRequest, one class, one ruleset, four versions present: 02-01-15, 02-01-10, 02-01-05, 02-01-01. In each case only the availability of 02-01-10 changes. If it is Available, 02-01-15 (the highest version) runs. If it is Not Available, only 02-01-10 is removed, and 02-01-15 still runs (and if 02-01-15 did not exist, 02-01-05, the next highest). If it is Withdrawn, 02-01-10 and everything at or below it in that ruleset (02-01-05 and 02-01-01) disappear, and 02-01-15 still runs because it is higher; if 02-01-15 did not exist the engine would look to the parent class or the next ruleset. If it is Blocked, nothing is removed because a blocked rule still ranks; 02-01-15 runs, but if 02-01-15 did not exist, 02-01-10 would be selected, the run would halt, an error would be logged and the section would not render, and 02-01-05 would never be reached. The mnemonic: Not Available skips one, Withdrawn deletes downwards, Blocked detonates, and Final locks the ruleset, not the rule.

The class-versus-ruleset question has a settled answer, and it is not genuinely ambiguous: class is the first sort key and ruleset the second, so a more specific class outranks a higher-priority ruleset, and ruleset order only breaks ties within the same class (the single exception being a class without class-based inheritance selected). Four things not to say.
  • "Withdrawn is basically Not Available." Not Available removes one candidate; Withdrawn removes a whole band of lower versions in that ruleset.
  • "Blocked makes resolution fall through to the next rule." It does not: it fails.
  • "Final stops anyone overriding the rule anywhere." A higher version in the same ruleset supersedes it.
  • "The resolved rule is cached." The ranked candidate list is cached.

Performance follows from the cache. The ranked list is cached, so a long ruleset list or many circumstanced variants do not matter at steady state, but they slow the first hit after a deployment and widen the troubleshooting surface; keeping the ruleset list lean is worthwhile for both reasons. And because resolution is a security-relevant mechanism too, remember that Access Deny and Final or Blocked availability protect rules, while hiding something in the UI protects nothing.

1.7 Rulesets, versions and the application stack

The patch to ReviewRequirement raised a question the walkthrough passed over: where does a new version of a rule live, and how does Sam ship it without disturbing everything else? The answer is the ruleset.

A ruleset is a named container of rules (for example FCBDeposits). Each ruleset has versions of the form MM-mm-pp, major-minor-patch, such as 01-02-03, and every rule is stored in one specific version. The ruleset list is the ordered list of ruleset and version-prefix entries that resolution uses (Phase 2 in 1.6 is a statement about this list). An application rule defines a stack of built-on applications and contributes its own rulesets to the list.

Versions exist so that change ships as a layer. Version 01-02-04 can contain only the rules that changed in a patch, resolution takes the highest version at or below the allowed prefix, and rolling back means moving the application or access group to the previous version. The three positions have conventional meanings: the major number marks a new release train that may be incompatible and is rare; the minor number marks a release with new features; the patch number marks a bug fix or hotfix overlay for production. Over time the stack of versions grows, and Pega can skim a ruleset, creating a new higher version that contains only the highest copy of each rule. Skimming is a release-management task, not a daily one.

Two kinds of locking get confused here, and the next section has a third. Ruleset-version locking is the one that matters for shipping: when 01-02-03 is released, Sam locks it with a password so no rule in it can change, creates 01-02-04 (or 01-03-01) as the new open version, and updates the application rule to include it. Production rulesets must be locked, and a hotfix is a new patch version, never an edit to a locked one. This has nothing to do with case locking, which Section 1.11 covers.

The application stack is how Riverbend layers its design. An operator's access group names an application, and the application is built on others.

Access Group: FCBDep:Operators -> Application: FCBDepOps:01-02 (the one the operator logs into) built on -> FCBDeposits:01-02 (deposits framework) built on -> FCBEnterprise:01-04 (enterprise common: addresses, audit, correspondence) built on -> PegaRULES:08-xx (Pega-supplied: Pega-ProcessEngine, Pega-UIEngine, ...) Effective RuleSet LIST built top-down: Personal/branch rulesets (if any) FCBDepOps_Rules:01-02-xx <- highest priority overrides FCBDeposits:01-02-xx FCBEnterprise:01-04-xx Pega-ProcessEngine, Pega-RULES, Pega-UIEngine, Pega-IntegrationEngine ... <- lowest

Marcus's ruleset list is that stack, flattened. Each layer has an owner and a cadence: enterprise-common holds the shared address and party classes and audit utilities and changes slowly; the deposits framework holds case types, flows, SLAs and decision tables for all deposit products; the implementation layer holds state- or product-specific overrides and reference data; and integration rules (connectors, mappings, service packages) sit in their own ruleset so the integration lead can release them independently. The layering matters because Chapter 13 will ask where a new rule belongs, and "everything in the implementation layer" is the answer that makes a greenfield application unmaintainable.

Rulesets have a handful of fields worth knowing: prerequisites (other rulesets and versions that must be present, checked when the list is built), the version lock, whether check-out is required before editing, the update password, and validation mode. The failures to avoid follow from them: working in the highest unlocked production version, one giant ruleset version with thousands of rules that cannot be hot-fixed cleanly, skipping prerequisites so a build that works on a laptop breaks in QA, and saving a rule as a copy into another ruleset without checking class and guardrails.

1.8 Branches and merge

Sam is not alone. While he patches ReviewRequirement, a second developer is changing the address-change flow, and both work against FCBDeposits. If they edited the same ruleset version they would lock each other out or overwrite each other, and half-finished work would leak into the shared environment.

A branch ruleset is a temporary ruleset that shadows a base ruleset for one developer or team. It is added to the top of that developer's ruleset list, so branch rules win in resolution, while everything not changed in the branch resolves from the shared trunk. Sam's changes save into the branch; the other developer's changes save into theirs; neither sees the other's.

The life of a branch has a clear shape. It is created against the base rulesets it will shadow. Development saves into it. Branch quality shows guardrail warnings and test coverage for the branch's rules, and PegaUnit runs against them. When the branch is ready, the merge wizard detects any rule that changed in the base ruleset since the branch was cut and asks Sam to pick or combine; the branch's rules are then merged into a target ruleset version and the branch is normally deleted; and the target version is locked at release.

TRUNK FCBDeposits:01-02-00 ----------------------------------------> release BRANCH FCBDeposits_AddrChg (branch ruleset of FCBDeposits) dev A edits ReviewRequirement, ProcessAddressChange flow dev B edits other branch (isolated) MERGE Branch Merge wizard: validate -> resolve conflicts -> target FCBDeposits:01-02-00 -> delete branch CI pipeline: build product archive -> unit tests -> deploy to QA

A pipeline tool such as Deployment Manager can merge branches on a trigger and run PegaUnit and guardrail checks as gates before promotion, which is the arrangement Section 1.13 builds on. The usual ways to get hurt are long-lived branches (conflicts accumulate), the same rule edited in two branches (a conflict at merge), editing trunk rules directly "just this once", and leaving branch rulesets in the lists of production access groups, where they quietly change what resolution returns.

1.9 The clipboard: the request's working memory

When Marcus opens AM-10417, rule resolution has chosen which rules to run. Those rules now need somewhere to read and write the case's data, and that somewhere is the clipboard: each requestor's in-memory workspace, a tree of pages, where each page is an instance of a class holding properties. Rules read and write pages; a save flushes a page to the database. The clipboard is not durable, so an unsaved change to the case is lost when the session times out.

Reading the clipboard is a basic skill, and the shape of the tree for Dana's closure case, which is richer than the address change, shows the vocabulary.

CLIPBOARD (requestor R123, thread STANDARD) |-- pyWorkPage class FCB-Dep-Work-AccountClosure | |-- pyID = "AC-10882" pyStatusWork = "Pending-Approval" | |-- AccountSummary (page) Balance, ProductCode, Status | |-- Signers (page list) [1] Name=D. Whitfield Role=Primary | |-- Holds (page group) ("HOLD-1") Amount, ReasonCode |-- pyWorkCover (if child case) |-- D_CustomerProfile_pa123 (data page, thread/requestor scope) |-- pxRequestor (operator, access group) |-- pxThread (thread-level system data) `-- Param.* (parameters for the rule currently executing)

A page directly on the clipboard is a top-level page, such as the case itself or a data page. A page-valued property inside another page is an embedded page. A page list is ordered and indexed from one (.Signers(1).Name); a page group is keyed by name (.Holds("HOLD-1").Amount); value lists and value groups do the same for simple values. When a report or list data page returns rows, they land in a page list named pxResults. Parameters for the rule currently running arrive on the parameter page (Param.AccountNumber). Two roles matter when reading rule logic: the primary page is the context a rule runs against, and a leading dot refers to it (.Name); the step page is the page an activity step operates on, set explicitly for each step.

The notation turns up often enough to be worth fixing in memory: .Name is a property of the primary page; pyWorkPage.Name is an explicit page reference; .Signers(2).Name and .Holds("HOLD-1").Amount address list and group elements; .pxResults(1) is the first result row; .Signers(<APPEND>) creates a new element, with <LAST>, <CURRENT> (the current loop element) and <PREPEND> as the other special indexes.

Saving is where the clipboard meets the database. When a case is saved and committed, Pega serialises the whole page tree into the pzPVStream BLOB column and copies the exposed properties into columns of their own; Chapter 03 explains the reporting and performance consequences, and Chapter 11 explains why SQL can only see the exposed ones. The point to carry forward is that changing a page on the clipboard is not the same as changing what is stored.

Four habits keep the clipboard from becoming a problem. Do not load very large page lists onto thread pages, because memory per requestor multiplies by concurrent users, and use paged reports or queue processors instead. Remember that a requestor-scope data page holding personal data is visible to that whole session. Remember that reading a property that does not exist yields an empty value rather than an error unless strict settings are on, so check for null explicitly. And remember that unsaved pages vanish.

The clipboard belongs to someone, and the question of who is the question of the requestor: a session-like context with one clipboard, one ruleset list, one access group and one operator identity. Marcus's browser session is one. The queue processor that will later update the core is another, and it behaves quite differently.

It helps to have the whole path of one interactive request in view, because every later chapter hangs something on it. A browser request reaches the Pega servlet. Authentication identifies the operator. A requestor is created or attached, and the access group yields the application and the ruleset list. The request is mapped to a harness or portal. For each rule the engine needs, rule resolution runs (cached after the first time) and rule assembly generates Java if this rule and context have not run before. The engine executes, loading data pages (with their scope and refresh rules) and running transforms and activities. Declarative rules fire as the properties they depend on change. The clipboard is modified, and locks are taken on cases opened for update. A save and commit serialises the page tree into the BLOB and exposed columns, writes a history row and maintains index tables. The response is produced, and PAL statistics and alerts record how it went.

Background work has its own, shorter lifecycle. Work is queued, a queue processor's batch requestor picks an entry (subject to partitioning and concurrency), loads its parameters and runs an activity. Success removes the item; failure retries under a retry policy and eventually moves the item to a failed state that someone must review. Admin Studio shows the delayed and failed items and the status of the requestors. Chapter 06 takes that lifecycle apart.

1.11 Locking and audit: two operators, one case

On Monday afternoon Marcus has AM-10417 open to complete his review. Priya, looking at the queue, opens the same case to see why it has not moved. The platform must stop one of them silently overwriting the other.

The default for work classes is pessimistic locking. When a user opens the case for update, the system takes a lock, a row in the lock table, and holds it until the user commits, releases or the lock times out; the second person sees the case read-only, or told it is locked by Marcus. The cost is that locks can get stuck, and parent and child cases updating one another can contend. The alternative, optimistic locking, holds no lock; at save time Pega compares the case's save timestamp with what was read, and if it has changed the save fails and the user must reload. That gives higher concurrency at the price that a user can lose edits, which suits APIs and processors better than people. The choice is made on the class group or work class rule, along with the lock timeout.

Which strategy fits depends on who is touching the case, and Riverbend's cases show three different answers. A manual maker-and-checker review of a closure wants pessimistic locking, because there is one auditable person acting. A background job applying return-file results to cases should keep transactions short and use optimistic locking or retry-on-lock, because a job must not wait on a human who left a case open overnight. A parent case with many child cases updating it is where lock contention becomes an incident, so minimise parent updates and propagate child status carefully. Digital self-service through the DX API is stateless HTTP with no long-lived lock holder, so optimistic checking with an entity tag is the natural fit. The patterns to avoid: a queue processor opening a case a user keeps open all day, a utility updating one parent from five hundred children at once, ignoring the lock timeout, and deleting rows from the lock table without understanding why they were there.

One distinction deserves stating plainly, because it is confused constantly. A Pega case lock is a logical lock in the lock table held for the requestor; a database row lock is held by a transaction. They have different lifetimes, different timeouts and different failure modes. Chapter 11 returns to the second kind.

The second half of the section is audit, and for a bank it carries as much weight. Regulators expect evidence of who changed a customer's address, when, and on whose approval. Pega gives several layers of it. History rows record who did what and when: case creation, flow action submissions, status changes, reassignments, attachments and SLA events, and they appear on the Case History tab. Field-level auditing captures old and new values of selected properties, so it is configured only for the ones that need it, such as account status, signer name and address. System stamps (pxCreateDateTime, pxCreateOperator, pxUpdateDateTime, pxUpdateOperator, pxSaveDateTime) are on every persistent instance. Rule history records developers' changes to rules. History tables grow without bound, so retention is a decision to make with Compliance rather than a clean-up to do later.

1.12 Guardrails: keeping the rules maintainable

Six months in, Riverbend has hundreds of rules, and Sam has noticed something the first section warned about: the platform lets anyone build anything, quickly, including things nobody will be able to maintain. Guardrails are Pega's response. They are best-practice rules enforced as warnings on rule forms and rolled up into a compliance score from 0 to 100 and a weighted warning count per application.

They show up in three places: as an indicator with a severity on each rule form's header, on the application's Guardrails landing page (compliance score, weighted score, warnings by rule type, the severe and unjustified lists), and as thresholds that a branch or pipeline can enforce as a gate. Severity matters: a severe warning is strongly discouraged and carries the highest weight in the weighted score, a moderate one should be reviewed, an informational one is awareness only. A warning can be justified in the rule with text, and justified warnings are tracked and reviewed rather than ignored. A common target is a compliance score of 90 or more, with 95 or more for strong teams.

The warnings group naturally into themes, and the grouping is more useful than a memorised count (Pega's own organisation varies by release and by who is describing it).

Raising a score is mostly a matter of method, and the method is the same whichever application you are in. Measure first: open the landing page, sort by rule type, list the severe warnings. Then fix by pattern, not by rule, because one bad pattern (an activity that runs Obj-Open in a loop, say) can account for hundreds of warnings and is fixed once in a reusable data transform or data page. Replace activities with declarative rules where the behaviour is simply mapping, conditions or fetching data. Remove dead rules, since unreferenced rules and old versions attract warnings. Deal with integration warnings by adding timeouts, error handling and authentication profiles to every connector and service. Fix UI warnings by moving inline styles into skin classes and flattening nesting. Justify only what cannot be fixed, with a technical reason and a ticket. Gate the result, with a minimum score and a zero-new-severe policy in the pipeline so it cannot regress, and review it weekly because the score decays without attention.

The thing not to do is to raise the score by justifying everything. It reads as gaming, and it is: the point is to fix the root pattern and justify only legitimate exceptions.

1.13 Testing and packaging

Sam's patch to ReviewRequirement is ready, and everything in this chapter has just made the next question urgent: how does Riverbend know the patch did what it should for every state, and how does it get from his development environment to production without being retyped by hand?

PegaUnit: making the rules testable

A PegaUnit test case is itself a rule. It records an input (clipboard setup and parameters) and assertions about the output, and it can target activities, data transforms, decision tables and trees, when rules, data pages, flows, case types, report definitions and strategies. Run it from the rule form, in a suite, or from a pipeline. The useful elements are the assertion (property comparison, list count, a when result, messages, run duration), the suite (a regression set run together), setup and clean-up of test data, simulation of data pages and connectors so a test does not call the real core, and an application-level coverage report that measures which rules tests exercised (rule coverage, not line coverage).

PegaUnit for decision table ReviewRequirement Test 1: .State = "NC", ReissueWithin30Days = true -> Assert .ReviewLevel = "Supervisor" Test 2: .State = "TX", ReissueWithin30Days = true -> Assert .ReviewLevel = "Supervisor" Test 3: .State = "NC", ReissueWithin30Days = false -> Assert .ReviewLevel = "Standard" Test 4: missing State -> Assert otherwise row => "Standard" Pipeline: Build -> Deploy to QA -> run PegaUnit suite -> check coverage -> check guardrail threshold -> approve -> Prod

The tests that the address-change application needs follow the failure modes the chapter has described, not a generic list. Rule logic in isolation (decision tables, data transforms, when rules) is tested with mocked data sources and connectors, with one scenario test for each case-type path and each rejection path. After any base-rule fix, the same input is run once per circumstanced variant, because Section 1.6 showed how a variant silently survives. Validation failures and business rejections are tested separately: a malformed input must fail validation with a field message, and a valid request that policy refuses must route to an assignment with a reason, with neither swallowed. Access is tested by running as each role in a lower environment, attempting the forbidden action, and repeating at a higher system level, which anticipates Chapter 10's point that a control that passes in QA must be re-tested at the production level. Scenario tests (UI-driven, from App Studio) cover the main case paths, and API tests from external tools and load tests sit outside Pega.

Check your understanding.

A fix to CalculateHoldPeriod passes all PegaUnit tests in the base rule's suite. Why might California still be wrong in production, and what test would have caught it?

Answer. The suite tested the base rule, which is only the default candidate; the California variant is a different rule that outranks it, so the suite never ran it. A test that sets .State = "CA" and asserts the patched result would have run the variant. This assumes the variant exists on the same class and ruleset as the base; the general discipline is to run each fix once per circumstanced variant and to list the variants on the rule form before shipping.

Packaging and deployment

What travels between environments is a product rule (a RAP): a rule that defines what to export, which includes applications, rulesets with versions, and data instances such as operators, access groups, work queues and decision data, with optional pre- and post-import processing. The export produces an archive that is imported into the next environment, either by hand through Dev Studio or Admin Studio, or by a pipeline tool that orchestrates branch merge, build, test, deploy, promotion and rollback. A hotfix is a small package or a patched ruleset applied to production with approval.

DEV --branch merge--> DEV integration -> pipeline 1 Create product archive (rulesets + data instances) 2 Import to QA, run PegaUnit + scenario tests + guardrail gate 3 Import to UAT, business sign-off 4 Import to PROD (lock ruleset versions; approval task) 5 Post-deploy smoke test; rollback plan = previous application version / reverse package

The ways this goes wrong are specific. Exporting by hand from Dev Studio into production skips every gate. Forgetting data instances (operator IDs, work queues, decision data) means the rules arrive without what they need. Deploying unlocked rulesets leaves them editable. Having no rollback plan means a bad release is fixed by improvisation. And mixing rules and data into one unmanageable product rule makes any of these harder to see.

1.14 Interview Q&A

Short answers, in the first person, to the questions this chapter prepares. Chapter 14 holds the full practice set.

Q1. How would you explain what Pega is to someone who only knows Java/Spring?

"Pega is a rules-driven platform where the process, decisions, data mapping and UI are stored as versioned rules in a database instead of compiled code. At runtime the engine selects the right rule for the context through rule resolution, generates and caches Java for it, and executes it. The main difference from Spring is that variation is handled by specialisation (class inheritance, ruleset layering and circumstancing) rather than by if/else or strategy beans. The trade-off is that without governance a rule platform sprawls, which is why guardrails and layering matter."

Q2. Explain rule resolution.

"The engine gathers every candidate with that name from the Applies-To class up the inheritance structure, filters out anything whose ruleset is not on my list, whose version is above what the list allows, or that is Not Available. It ranks what is left by class, then ruleset, then circumstance, then circumstance date, then date range, then version. Version is last, which is why a newer base rule does not override an older circumstanced one. Withdrawn rules take out the lower versions in their own ruleset, the highest unqualified candidate becomes the default, and the ranked list is cached. At runtime the engine takes the highest-ranked candidate whose circumstances match this case, falling back to the default. If that candidate is Blocked, the run fails rather than falling through."

Q3. Does a higher-priority ruleset beat a more specific class?

"No. Class is the first sort key and ruleset the second, so a more specific class outranks a higher ruleset, and ruleset order only breaks ties within the same class. The exception is a class without class-based inheritance selected, where class is not a ranking criterion and ruleset order decides. If an override has to win, it belongs on the same class or a more specific one."

Q4. Pattern versus directed inheritance?

"Pattern inheritance comes from the class name: the engine strips trailing segments at each hyphen. Directed inheritance is an explicit parent set on the class rule, for inheriting from outside the name path. The search interleaves them: the class, its pattern chain, then the directed parent with a fresh pattern search, repeating to the base class. A class group is a separate, persistence-only idea: it decides the table and ID prefix, though belonging to one forces 'Find by name first' on."

Q5. A rule behaves differently for one user. What do you do first?

"Run as that operator so the ruleset list is the right one, trace with rule resolution events on, and read the rule's instance key to see the class, ruleset version and circumstance that won. Then I check, in order, a higher ruleset in that user's application stack, a circumstanced variant, a date-effective variant, an access group pinned to an older version, a leftover branch ruleset and node cache staleness. The fix depends on whether the override is intentional."

Q6. How do rulesets and versions let you ship safely?

"A version is a layer: a patch version contains only the rules that changed, resolution takes the highest allowed version, and rollback means pointing the application back at the previous one. Released versions are locked, so a hotfix is a new patch version, never an edit. Rulesets sit in layers (enterprise, framework, implementation) so overrides live at the top without touching the framework."

Q7. Pessimistic versus optimistic locking?

"Pessimistic locking holds a case lock while a user has it open, which gives a clean audit story for manual approvals. Optimistic locking takes no lock and checks the save timestamp at commit, failing if the case changed, which suits APIs and processors. I avoid long-held locks from background work and many children updating one parent. A Pega case lock is a logical lock in the lock table; a database row lock is held by a transaction, with different lifetimes and timeouts."

Q8. What are guardrails, and how do you keep a score high?

"They are best-practice warnings on rule forms, rolled up into a compliance score. The score is a lagging indicator, so the leading control is a gate: a minimum score and no new severe warnings on changed rules, plus a review checklist. I fix by pattern, justify only genuine exceptions with an owner and a reason, and never justify warnings to raise the number."

Q9. What is the difference between the clipboard and what is saved?

"The clipboard is the requestor's in-memory page tree and is not durable. A save and commit serialises the page into a BLOB and copies exposed properties into columns. A change that is on the clipboard but not committed is invisible to other requestors and to SQL, and is lost if the session ends."

Q10. How do you package and deploy?

"A product rule defines the rulesets and data instances to include. I export that as an archive, import it into the next environment, run tests and guardrail gates, and import to production with locked ruleset versions and a rollback plan. A pipeline tool such as Deployment Manager automates those stages."

1.Z Where we are now

What the application can do

When Dana's request arrives, the platform can find the right rule for her state and product, run it against a case of the right class on a clipboard belonging to the right operator, stop Marcus and Priya overwriting each other, record who did what, and ship a fix to any of those rules as a locked version through a tested pipeline.

The mechanisms behind it

Rules are named, versioned records keyed by type, class and name. Classes decide both where a case is stored and where its rules are inherited from. Resolution gathers, filters and ranks candidates by class, ruleset, circumstance, circumstance date, date range and version, caches the ranked list, and qualifies it at runtime. Rulesets layer the application and carry versions; branches isolate parallel work; the clipboard, requestors and threads give each request its working memory; locks and history make concurrent work safe and auditable; guardrails and PegaUnit keep it maintainable.

What it still cannot do

Nothing yet moves the request through review and approval. AM-10417 exists and behaves correctly, but no one has been given the work: there is no journey from intake to Marcus to Priya to the core, no deadline, no escalation. That is what Chapter 02 takes up.
