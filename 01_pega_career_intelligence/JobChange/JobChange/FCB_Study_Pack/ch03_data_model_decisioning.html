3.1 What the case holds: properties

Marcus opens AM-10417 and the review screen has to show the customer's name, the address on file, the requested address and the accounts involved. Before deciding how to fetch any of that, Sam has to decide what the case itself stores, because everything a rule reads or writes is a property: a named, typed field on a page of a given class. .AccountNumber on FCB-Dep-Data-Account is a property. A property rule defines the name, the mode (a single value, a list, a group, an embedded page), the type (text, integer, date and so on), validation hints, the table or choices that feed it and its default display.

Properties exist because process rules need a typed, shared vocabulary. Without it every flow would pass untyped maps, the UI could not generate controls, reports could not know which columns to select, and decisions could not compare numbers correctly (the text "100" against the integer 100). Pega's modes cover almost every design need: a single value (.AvailableBalance); a value list (.RestrictionCodes(2)); a value group (.Flags("OFAC")); a page, which embeds one page of a class (.PrimaryOwner.Name); a page list (.Signers(1).Name); and a page group, which is keyed (.Holds("HOLD-1").Amount). Less common modes, such as Java object properties, exist and are rarely wanted.

The type of a single value matters more in banking than anywhere. Account numbers are text, not integers, because of leading zeros, check digits and length changes. Money is decimal, never double, because floating-point arithmetic rounds in ways that a ledger cannot tolerate. A TrueFalse property that has never been set is blank, not false, so every when rule must handle null. A DateTime is stored in GMT while a Date has no time zone, which is why a business date such as a maturity date should be a Date. An encrypted text type protects a tax ID at rest but cannot be used in filters or sorts, which has reporting consequences that 3.3 returns to.

Where a property is defined matters as much as what it is. Sam places each one at the highest class where all descendants need it. Audit properties such as .CorrelationID sit at FCB-; .CustomerID, .AccountNumber and .MakerOperatorID (needed by Chapter 02's maker-checker control) sit at FCB-Dep-Work-; .OrderType and .ResponseDueDate sit only at FCB-Dep-Work-LegalOrder; .ProductCode, .Status and .MaturityDate sit on the account data class. Too high and every class carries clutter; too low and properties get copied with inconsistent types.

One practical point for the people who build in App Studio: a field there is a real property rule, in the right class and ruleset, created with sensible defaults and without exposing the class concept. Dev Studio shows the same rule with every tab visible, including the table-edit source for allowed values, edit-input and edit-validate references, display, security and the optimisation entry point that 3.3 uses. The difference is control, not substance.

The properties to avoid are the ones the guardrails flag. Page-list properties on the work class that will hold thousands of rows bloat the clipboard and the BLOB. Currency stored as text or double corrupts arithmetic. Dynamic property names created by activities with no property rule cannot be reported on. One property reused for two meanings across case types breaks every report that crosses them, and a Boolean stored as "Y"/"N" text in one class and as TrueFalse in another produces comparisons that fail silently.

3.2 What the case only looks up: data classes and data objects

The tempting move is to copy Dana's customer record into the case "so it is there": name, tax ID, all accounts, balances. The case then carries a full copy that goes stale as soon as the core changes, inflates the BLOB, and invites personal data into reports. The better design stores the key on the case (.CustomerID, .AccountNumber), reads the rest on demand (3.5), and copies only what must be frozen for audit, such as the address as it stood when the order was processed. A case holds identifiers and the delta being requested, never a mirror of the customer.

That design needs somewhere to describe the customer and the account as structures, and that is the job of data classes (Chapter 01 §1.4 introduced them). In App Studio the same idea appears as a data object: a named entity backed by a data class, with fields, view and list data pages, and a declared system of record, which may be Pega's own table, a REST service, SQL or another source. A data object generates the repeatable parts together (class, table mapping, properties, data page, maintenance UI) and keeps naming consistent. It is a productivity and governance layer; Dev Studio still shows the real rules underneath.

For Riverbend, a Customer data object has a view data page sourced from the core through the ESB, an Account data object has a list data page by customer, and a LegalOrderType data object lives in Pega's own table and is maintained by the legal operations team as reference data (3.12). Pega-provided base classes (Work-, Data-, Embed-, Assign-, History-, Link-, Index-, Rule-) are inherited from and never modified, and functional framework classes are extended in Riverbend's own layer, never edited in the framework ruleset.

A handful of system properties appear on almost every page and are worth recognising on sight: pxObjClass (the page's class), pzInsKey (the full instance key used for persistence), pyID (the case display ID), pxCreateDateTime and pxCreateOperator, pxUpdateDateTime and pxUpdateOperator, pyStatusWork, pxCoverInsKey and pxCoveredInsKey (parent and child references) and pzPVStream, the compressed serialised page that the next section is about.

3.3 Exposed columns and the BLOB

Priya wants a report: every open address change whose account number matches a given value. Sam writes a Report Definition filtering on .AccountNumber, and it either refuses, or runs for ninety seconds. The explanation is how Pega saves a case, and it is the single most probed data-model topic in Pega screens.

What the BLOB is, and why Pega uses it

When Pega saves a case or a data instance (Obj-Save followed by a commit), it does not create one database column per property. It serialises the entire page, including embedded pages and page lists, into one compressed binary column called pzPVStream in the instance's table (for cases, the work table of the class group). The same row also carries a small set of ordinary columns: the key, pxObjClass, creation and update stamps, status, and any properties that have been exposed.

The design has real advantages. A property can be added to a class without an immediate schema change. One row read returns the whole object, with no multi-table join to rebuild a page. One table can hold many subclasses with different property sets. Those are the reasons Pega pays the cost described next, and the cost is the heart of the topic: a database cannot filter, sort, index or join on content inside a compressed binary. A filter on a property that exists only in the BLOB cannot be written as a SQL WHERE clause, so depending on the release and report type Pega warns at design time, fails at run time or loads rows and filters in memory, which is slow and wrong for pagination. The safe statement is: a property must be exposed to be reliably filtered, sorted, grouped or joined in SQL; otherwise the report is wrong, slow or not allowed.

Exposing a property

An exposed (or optimised) property is mapped to a real column in the class's table. On save, Pega writes the value to the column and keeps it in the BLOB too. Reads of the whole page use the BLOB; reports, filters, sorts and joins use the column. Only single-value properties can be exposed this way, and the elements of a page list use Declare Index instead (3.4). Classes mapped to purpose-built or external tables can store each property in its own column with no BLOB, which is a design choice made per class, not the default for cases.

The procedure is the same each time, and the bank's separation of duties shapes it. Decide the class and its table mapping and confirm the table has a free column of the right type. Use the property optimisation capability in Dev Studio (reached from the property rule or the class-level tool; the exact menu wording differs by release). Where the application's database user cannot run DDL, which is typical in a bank, the tool produces a script for the DBA to apply under change control. Run the backfill for existing rows, off-peak for large tables. Add a database index on columns used for filtering, because an exposed column with no index is still a full scan. Then read the Report Definition's generated SQL to confirm the column appears in the WHERE and ORDER BY.

What to expose follows from the queries the application will actually run. Expose status, stage, case type and priority; foreign keys such as customer ID, account number and parent case ID; dates used in SLA, due and aging reports; amounts used in thresholds, authority queries or aggregates; assignment fields used for queue and supervisor reports; and properties used by batch selection. Do not expose free text, large fields, properties used on only one screen, rarely queried secondary attributes, encrypted properties (which cannot be filtered anyway) or page-valued properties (which cannot be exposed).

The consequences of getting it wrong have predictable shapes. An unexposed filter on a five-million-row work table is a full scan with BLOB decompression per row. Exposing too much makes every save write every column and slows inserts through index maintenance; a table with 150 exposed columns and 20 indexes is a design smell. A property exposed after go-live without a backfill produces reports that show only new data, and the first person to notice is a supervisor whose dashboard has "lost" last quarter. A large embedded list inflates the BLOB, which moves across the network on every open and save, so case pages should stay lean. Bulk work, such as the batch selection in Chapter 06, should select and update by exposed, indexed columns and avoid opening and re-saving large BLOB pages row by row. And analytics that is heavy belongs in a reporting store, not on the transactional table.

A diagnosis for "the legal-orders dashboard takes ninety seconds" runs as follows. Open the Report Definition and look at its SQL, or at the PDC alert for the slow query. Check whether the WHERE and ORDER BY columns are exposed, and whether they are indexed. Read the execution plan (Chapter 11 does this properly): a sequential scan on the work table means a missing index or an unexposed property. Then fix it: expose ResponseDueDate and OrderType, ask the DBA for a composite index, backfill, add a date range and pagination to the report, retest with production-like volume, and prove the improvement with the PDC trend.

Finally, the BLOB contains all the page's properties, including personal data, and exposed columns copy values into plaintext columns unless an encrypted type is used. The table is sensitive data and must be treated according to the bank's data classification (Chapter 10 covers masking and encryption). The anti-patterns are exposing a property after go-live with no backfill plan, exposing a hundred columns "just in case", joining work tables on unexposed properties, storing document content or JSON payloads in properties, and assuming a declarative expression's result is queryable (it is only if it is exposed).

3.4 Declare Index: reporting on lists inside a case

Exposure handles single values. Priya's next question, "find every case where any signer has this tax ID hash", asks about the elements of a list, and those live inside the BLOB too. A Declare Index rule maintains a separate index table with one row per element of a page list or page group, rebuilt on each save of the parent. Elements of .Signers on a closure case become rows that a report can join to.

The rule names the class being indexed, the index class (a class under Index- with its own table mapping, created by the DBA), the page list to iterate, the property mappings that become index columns, and an optional condition. The costs are real: extra writes on every save of the parent, which matters for hot cases; index data that can drift if the declarative engine did not run (data loaded by direct SQL, for example), with heavy reindexing tools to repair it; and huge index tables for lists with thousands of elements.

That is why a Declare Index is better seen as a patch for a data-model choice than as a first resort. If the elements have their own lifecycle or are queried a lot, they should be their own data instances (a signer table, a hold table) with exposed columns. If each element needs workflow, they should be child cases. If only "does any element match" matters for one attribute, copy a key scalar up to the parent as an exposed property. Declare Index fits when the elements are naturally embedded and cross-case search is needed without redesign, such as signers on an account case. For holds and legal orders, separate instances are the better design, giving clean reporting, locking and audit.

3.5 Data pages: one lookup, shared correctly

The closure case for AC-10882 needs Dana's balance at intake, so Marcus can see what is being closed. It needs the same balance on the review screen, on Priya's approval screen, in the fulfilment step that sends the disbursement instruction, and in the confirmation letter. The straightforward design is to call the core wherever the balance is needed, and it works exactly as written: one case now makes five identical calls to a system that bills per call and takes about 400 milliseconds to answer, so each screen waits 400 ms, the bank pays five times, and the five answers can disagree with each other if the balance moves between them.

What is needed is for the answer to be fetched once, remembered, and reused wherever the same question is asked again. That is what a data page is: a rule (conventionally named with a D_ prefix, such as D_AccountBalance) that says, "when someone asks for this data, here is where to get it, how long to keep it, and who can share it." The data is loaded into a clipboard page on demand and cached according to the rule, and consumers (sections, data transforms, flows, reports) simply reference D_AccountBalance[AccountNumber:"CHK-8842-0117"] without caring how it was fetched. It replaces the older habit of writing an activity that called a connector, copied the result into the case and repeated that in every flow, which left data stale, calls multiplied and nobody sure where a value came from. It is a declarative, cached, parameterised, read-through data access layer, which is why the guardrails prefer it to activities for reading data.

Three basic settings define the first version. The structure is a page (one object, D_Customer[CustomerID:"CUS-4417"].LastName) or a list (rows in pxResults, D_AccountList[CustomerID:"CUS-4417"].pxResults(1).AccountNumber), and lists are what populate dropdowns, tables and repeating layouts. The parameters make one rule hold many pages: each distinct parameter set is a separate cached instance, with a cache key of the page name and the parameter values (and, for node scope, optionally the access group). And the source is the mechanism that populates the page on a load: a connector (REST, SOAP or SQL), a Report Definition, a keyed lookup, a data transform, an activity, or, in some releases, a data set. For the balance, the source is a Connect-REST call to the core through the ESB; Chapter 05 builds that connector.

Who shares the answer

Marcus and Priya are different people looking at the same account, and Marcus has two cases open in two tabs. The moment the page is cached, the question "who does this copy belong to?" appears, and the scope setting is its answer. A thread-scope page is created in a single requestor thread and can be accessed as often as needed by processing in that thread; the definition is that it is requestor-thread scoped. In the traditional portal each open case tab usually runs on its own thread, so a thread-scope page is in practice one tab's copy, which is a consequence of how that portal allocates threads and not part of the definition; it does not hold in Constellation or for background requestors. A requestor-scope page is shared by every thread of one user session, so Marcus's two tabs read the same copy. A node-scope page is shared by every requestor executing on that JVM node, so Marcus and Priya, and everyone else on the node, read the same copy.

Each answer fits some data and endangers other data. Thread scope suits case-specific data and anything editable, and costs memory multiplied by users and threads. Requestor scope suits user-specific data such as the operator's profile and entitlements, and is dangerous for case-specific data, because the page is shared across tabs and one tab's case data can appear in another if the parameters are keyed wrongly. Node scope suits reference data that is identical for everyone (product codes, holiday calendars, state exemption tables) and is dangerous for anything user-specific or sensitive, anything consumers modify, and anything with a large parameter space, because each distinct parameter set is a separate entry in the node's memory.

That produces the first rules. A node-scope page is shared by many concurrent threads, so it must be read-only; a consumer that needs to change the data copies it into its own page, and editable pages are thread or requestor scope. Putting user-specific or access-group-specific data in a node page without access-group sharing control exposes one user's data to another. Each node has its own cache and nodes do not synchronise node-scope pages with each other, so after a reference-data change different nodes serve different values until each reloads: the classic "works on node 1, fails on node 2" incident. Two documented warnings follow. A node-scope page on a class that carries access control policies raises a severe guardrail warning, because a shared page cannot honour per-user restrictions. And in Customer Service chat, associate requestors hold their own copy of requestor-level pages, so an editable requestor-scope page edited in one chat is not seen in another phone or chat interaction.

When the answer goes stale

Now the problem the five-call design hid. A data page is loaded on first reference for a parameter set and reused afterwards, so the copy of Dana's balance that Marcus loaded when he opened AC-10882 at the start of the day is the copy Priya's approval screen reads, hours later, when the case has sat in her queue. If an in-flight card authorisation settles in between, the core's ledger balance changes while the page still holds the old one. The case is now displaying a number that is no longer true, and the disbursement instruction that follows would be built from it.

The refresh strategy answers the question "when is an already-loaded page considered stale?" The options trade freshness against load. Do not reload loads once and keeps the page until it is cleared; it suits static reference data, and risks staleness and inconsistent nodes. Reload if older than N refreshes on a time window, which suits slowly changing data such as a rates table, and leaves a window of staleness equal to N. Reload once per interaction refreshes at most once per user request, which suits data that must be fresh on each screen but is referenced many times on it. Do not reload when takes a when rule that skips the reload while a condition holds, such as never reloading once a decision is locked, at the price of logic that is hard to debug. And explicit invalidation removes or reloads the page in logic, as after posting an update to the core, with the risk that forgetting it shows stale values on the next screen. One documented limit: reload once per interaction is available only for pages with thread or requestor scope, not node scope.

For the balance, a refresh window on the page is not enough, and the reasoning is the judgement to take away. The question the application is asking at approval and at fulfilment is not "what was the balance recently?" but "what is the balance now, because I am about to act on it?" Data that must be exact at the moment of an action should be fetched at the step, by an explicit reload or a direct connector call, not read from a cache that may be minutes old. The cached page is right for display; the step that moves money re-reads the balance, compares it with what was approved, and returns the case to approval if it moved by more than a threshold.

The same reasoning decides how a consumer receives the data. A property can take its data from a data page by copying the content into the consumer's own page, a snapshot independent of any later refresh, or by referencing the data page directly, so the consumer always sees whatever the page currently holds and cannot change it if the page is read-only. Reference is right for display, decision inputs and dropdown options. Copy is right when the value must be frozen for audit (the address at the time a legal order was processed) or when the user will edit it, at the cost of memory and BLOB space if the copy is stored on the case. Courses name these ideas differently and the labels vary by release and by where the choice is made, so explain the behaviour rather than the label.

Check your understanding.

Marcus's review screen for AC-10882 loaded Dana's account when he opened it at 09:10. At 09:40 the $200.00 authorisation settles and the core's ledger balance falls from $4,418.55 to $4,218.55. Priya, at 14:00, sees the old figure on her approval screen. What went wrong, and what should change?

Answer. The page was loaded once and its refresh strategy did not call for a reload, so every later reference read the 09:10 copy. Two changes help: a refresh strategy appropriate to a volatile balance (reload when older than a few minutes, or once per interaction, both available at thread scope), and, more importantly, a fresh read at the fulfilment step before the disbursement instruction is built. The first keeps displays reasonably current; only the second makes the action correct, because any cache window leaves a gap. The answer depends on the data page being thread or requestor scope; at node scope there is no once-per-interaction option and one stale copy would be shared by every user on that node.

When the source fails

If the core times out or returns an error, a data page does not throw to the user by default. It loads with page messages attached (the message collection is often described as pxErrorMessages; confirm the exact property path on the clipboard in the version in use), and consumers must check for errors. The usual patterns: a when rule such as "data page has errors" drives the flow to an error assignment or a degraded message in the UI; the error handling is configured so that a failed load is not cached as though it had succeeded (otherwise a transient error sticks for the whole refresh window, which is verified by forcing a failure, fixing the source and observing whether the next reference retries); and there is a fallback, a stale copy, a default or an "unavailable, retry" message. Chapter 05 covers the resilience patterns that belong around the connector itself.

Parameters, cache keys and cache size

Parameters multiply pages, so they carry three obligations. A node-scope page parameterised by account number across millions of accounts fills the heap, so high-cardinality parameters belong at thread or requestor scope or with a short expiry. Differences in case or spacing ("c123" against "C123") produce separate cache entries, so normalise values before the call. And a parameter such as an operator ID must never come from user input without validation, or a user can read another user's page. Short cache windows also create a stampede at the moment of expiry, when many users hit the source together; popular reference data deserves longer or jittered windows.

Writing data back: savable pages and save plans

So far the account page has been something we read. Marcus now needs to correct Dana's address, and the system of record is the core, not Pega. We could write an activity that calls a connector, and people often do — but Pega has a mechanism built for exactly this, and the reason to understand it properly is that it controls when the write actually commits.

A data page's edit mode decides what may happen to it. A read-only page can be modified only while it loads and during post-activity processing; it appears in the clipboard's data page list. An editable page is loaded read-write so a form can bind to it — but it has no refresh strategy and no save plan, and it cannot be node-scoped; it appears in the clipboard's user page list instead. A savable page is read-write in the same way an editable page is, but it is a distinct mode, not editable-plus-something: it is the only mode that carries a save plan, the mechanism that pushes changes back to the system of record. Pega's own documentation describes a savable page loosely as "an editable Data Page that can save data", which is the shorthand worth unpicking — the three modes are mutually exclusive choices in one field, and the one labelled Editable is specifically the one that cannot save.

The save plan can be a direct database save, an activity (which is where an Obj-Save or a Connect-REST call would sit), a REST connector using POST, PUT or PATCH, or robotic automation. A plan runs when its when condition is true, and here is a detail that surprises people: save plans are not mutually exclusive. If two conditions are true, two plans apply. There is an Otherwise condition for the fallback case.

Only a savable page can be named in the places that trigger a save: flow action post-processing, the Save Data Page shape after an assignment, and the Save-DataPage method in an activity.

The part that decides whether the data is really in the database

When you save a savable page you can set the WriteNow parameter, and it changes the transaction boundary. With WriteNow true the save happens immediately, as its own independent transaction. With it false the save is deferred and joins the larger surrounding transaction that commits later. With the direct Database save option you do not have to set it at all.

This is the clipboard-versus-committed distinction with a switch on it. A deferred save has changed nothing that another requestor or a SQL query can see; the row appears only when the enclosing transaction commits. If Priya approves the address change and the case then fails two steps later, a deferred save rolls back with everything else — usually what you want. An immediate save does not, and now Pega and the core disagree.

Check your understanding.

Marcus edits Dana's address on a savable page, the flow action's post-processing saves it with WriteNow false, and the next step throws. What does the core hold, and what does Marcus see?

Answer. The core holds the old address. The save was deferred into the surrounding transaction, which rolled back, so nothing was written. Marcus sees the error and the case has not advanced — consistent, if confusing, because the screen looked as though the edit had been accepted. This is why a fulfilment step that must reach an external system is better modelled as an explicit integration step with its own status, rather than as a side effect of saving a page: with WriteNow true you would instead have the opposite problem, a committed core change behind a failed case.

So is a data page the wrong tool for writes?

Not as a rule, and it is worth being careful here because the blanket version of this advice is common and wrong. Writing a single object back to its system of record is precisely what savable pages and save plans are for, and they save you hand-written persistence logic. What they are poor at is different and narrower: bulk row-by-row work, where one save per row means one call per row and a set-based operation in the database would do the whole job (Chapter 05 §5.8, Chapter 11); and writes that must carry business validation, approval and an audit trail, where the right model is a case step with an Integrator, an idempotency key and a visible status, because a save plan buried in post-processing is invisible to the business and hard to retry.

So the honest rule is about which write, not about data pages: a maintenance screen editing reference or customer data is a good fit; placing a hold on Dana's account during closure is not, because that needs approval, idempotency and a recoverable status.

Where a data page is the wrong tool

Reading is the data page's job, and a few reads are still better done another way. A list of a hundred thousand rows for the UI should be a paginated Report Definition or a view with server-side paging, not a data page loaded fully onto the clipboard. Data that must be strictly real-time at the moment of use is fetched at the step, as above. Bulk batch processing through parameterised pages creates one call per row, and belongs in data flows, data sets or set-based SQL (Chapter 06). Credentials and per-user tokens do not belong in data pages, and a node page must never be used as a global variable or counter. The matching anti-patterns: node scope for customer-specific data, an activity that does Obj-Browse in a loop instead of one list data page, a connector with no timeout, ignoring errors, huge page lists copied into the case, forgetting that a decision reading a data page on node 1 may differ from node 2 after a change, and naming a rule with a verb (D_GetCustomer) rather than a noun.

3.6 Declarative rules: derived values that stay correct

The closure screen shows a figure Marcus does not enter: the amount available for closure, which is the balance less the total of active holds. Computing it in the flow works until some path adds a hold and forgets to recompute. A declarative rule states a relationship ("available for closure equals balance minus total holds") or a reaction ("when this changes, do that") and lets the engine decide when to evaluate it, so that derived data stays consistent without every flow remembering to recalculate it.

Pega has several kinds, and the differences are in what triggers them. A Declare Expression computes a target property from other properties, either when its inputs change (forward chaining) or when the target is read (backward chaining). A Declare OnChange runs an activity when a watched property changes, and is rare and risky. A Declare Constraint validates a condition across properties and flags a message when violated, such as a maturity date that is not after the open date. A Declare Trigger runs an activity when an instance is created, updated or deleted, which means on every save of that class and so should be used sparingly. Declare Index (3.4) maintains index rows, and the data page rule (3.5) is itself declarative.

Forward and backward chaining are worth distinguishing because the choice has a cost. With forward chaining the engine tracks the expression's input properties and recomputes the target the moment any changes, which may in turn trigger other expressions that use it; the stored value stays current, so this suits properties that are exposed and reported on or must always be right in the saved record. The cost is paid on every input change and can cascade. With backward chaining the target is computed when referenced and has no current value (or each time, depending on the option); the cost is paid on read, which suits display-only derived values.

Declare Expression: .TotalHoldAmount (class FCB-Dep-Work-AccountClosure, forward chaining) Expression: Sum of .Holds(*).Amount where .Holds(*).Active = true Inputs tracked: .Holds(*).Amount, .Holds(*).Active A flow sets .Holds(2).Amount = 5000 -> engine detects input change -> recompute .TotalHoldAmount -> any expression using it (.AvailableForClosure = .Balance - .TotalHoldAmount) is recomputed in turn Dependency network: Holds(*).Amount -> TotalHoldAmount -> AvailableForClosure -> (decision table input)

The engine builds that dependency network and tracks property changes so that only affected expressions recompute. If a property is changed in a way the engine does not notice (a direct Java write, or a bulk-set method that bypasses tracking), the derived value can be stale, which is one documented reason to avoid Java steps that write properties.

The hazards come from the same machinery. A circular dependency, A depends on B and B on A, may be caught at design time or loop at run time, so draw the dependency network before adding the third expression. A Declare Trigger on case save whose activity updates and saves the same case fires itself again, so guard it with a when condition and a flag. A Declare OnChange that writes to the property it watches feeds itself. Forward chaining on a large page list recomputes aggregates over every row for each row changed, which is quadratic work during bulk population; populate in bulk and compute once with a data transform. Queue processor items that load pages with thousands of changes can trigger thousands of recomputations, so test at volume. Declare OnChange and Declare Constraint are usually better replaced by post-processing in a flow action and a validate rule (3.11), and the worst uses are an event bus built from Declare Triggers, a connector called from an OnChange, and logic hidden in declaratives that nobody can find.

3.7 Data transforms: setting and mapping data

When Marcus opens the closure case, the case needs to start with Dana's account number, the balance and her signers copied from the account page onto the case. That is mapping, and Pega's preferred rule for it is the data transform: a declarative, ordered list of actions that sets, copies and maps properties on a target page. It initialises pages, maps integration payloads to the canonical model and prefills forms, and it replaced activities and the older Model rules because it is readable, testable with PegaUnit, supports inheritance and raises few guardrail warnings.

Each row of a data transform has an action, a target, a relation and a source, and a transform has parameters (Param.Name), a source page for actions such as Update Page, and a list of ordered rows. The actions are few. Set assigns a value or expression to a property. Update Page opens a page context and runs child actions inside it. Append to adds an empty page to a page list; Append and map to adds one built from a source page. Apply Data Transform calls another transform, which is how reuse works. For Each Page In loops over a list. Call invokes an activity and should be rare. When and Otherwise make actions conditional. Remove deletes a value, page or element, and Exit stops the transform or a loop. A few releases add or rename minor actions, so describe the function you expect and check the action list if an unfamiliar one is named.

DATA TRANSFORM FCB-Dep-Work-AccountClosure : InitFromCoreAccount(Param.AccountPage) 1 Set .AccountNumber = Param.AccountPage.AccountNumber 2 Set .ClosureBalance = Param.AccountPage.AvailableBalance 3 Update Page .PrimaryOwner 3.1 Set .Name = Param.AccountPage.Owner.Name 3.2 Set .CustomerID = Param.AccountPage.Owner.CustomerID 4 For Each Page In Param.AccountPage.Signers 4.1 Append and map to .Signers (copy Name, Role, TaxIDHash) 5 When Param.AccountPage.HasLegalHold = true 5.1 Set .HoldFlag = true 5.2 Apply Data Transform SetLegalReview on . 6 Otherwise 6.1 Set .HoldFlag = false

Because a data transform is a rule, rule resolution applies to it (Chapter 01 §1.6): the same name in a more specific class overrides the parent. To extend instead of replace, the override's first action applies the superclass version (the form has an option to call the same-named transform in the parent class) and then adds its own. pyDefault is the conventional name of the transform that Pega runs when a new page of a class is created through the standard create paths, so default values placed there are set on every creation path, but it is not applied to pages created by Page-New unless the method is configured to. A case also commonly runs a case-type-specific initialisation transform, set on the case type's start settings, distinct from pyDefault.

The comparison with an activity is the reason data transforms are preferred. A data transform sets and maps data and is highly readable, a guardrails favourite, unit testable and usable declaratively as a data page source or a UI refresh. An activity does procedural logic and system methods, is harder to read, draws warnings that each need justification, and is the only one of the two that can save, call connectors or queue work (a data transform calls an activity for that). The anti-patterns are a 300-row transform of copy-paste blocks (split it into reusable transforms), hard-coded business constants (use decision data), setting properties on the wrong page because the primary page was misunderstood, using transforms for side effects through Call, and mapping both directions in one transform.

3.8 Activities: the procedural escape hatch

Some things neither a declarative rule nor a data transform can do: queue background work, save an instance explicitly, call a connector from background logic, route an assignment by custom logic. For these Pega keeps the activity (Rule-Obj-Activity): an ordered list of steps, each calling a method or another activity, with conditions and loops. It is the oldest and most powerful rule type, and that is why the guardrails discourage it wherever a declarative alternative exists: activities are harder to read, test, reuse and upgrade, they can hide database access, bypass declaratives and invite Java steps.

The legitimate uses are narrow and worth listing, because the list is how to decide: queueing work (Queue-For-Processing, with the processor's activity doing the work, Chapter 06); explicit persistence in special cases (Obj-Save, Obj-Delete, Commit, Rollback); calling a connector from background logic; custom router activities; service entry points where a service rule maps to an activity; and utilities invoked from flows when no declarative construct exists.

An activity has parameters (Param.X), a declaration of the named pages it uses and their classes, and steps. Each step names a method, a step page (blank means the activity's primary page, and getting this wrong puts properties on the wrong page; check with Tracer's clipboard view), a description (mandatory good practice, and checked by a guardrail), a transition (a condition and an action: continue, jump, exit, exit with error) and optionally a loop or a precondition. The methods that matter are these.

3.9 Decision rules: is this change sensitive?

Chapter 02 sent AM-10417 down a more careful path because the address changed within 30 days of a card reissue request. Somewhere a rule decides that. If it lives in nested if/else inside an activity, it is understood only by whoever wrote it, and changing it needs a developer. Decision rules externalise logic like this ("which risk tier", "which approver level", "is this account dormant") from process and code into rules that analysts can read, tests can exercise, circumstancing can vary and releases can change without touching flows.

The rule types differ in shape, and picking the right one is most of the skill. A when rule is a boolean condition (or several joined by AND/OR) used for visibility, flow branches, skip conditions, data page refresh conditions and access conditions; name it as a question (IsJointAccount, HasActiveLegalHold) and reuse it rather than writing inline expressions. A decision table is rows of conditions mapped to a result, best for combinatorial business rules and thresholds, and unwieldy beyond three or four conditions. A decision tree is an if/else-if structure with nested conditions and calls to other rules, best for sequential or hierarchical logic where branches test different conditions. A map value is a one- or two-dimensional lookup with ranges, best for fee schedules and tier banding. Decision data holds keyed instances (limits, reason-code mappings) that analysts maintain through a landing page. Choose a table when every row tests the same conditions and business people read it as a matrix; choose a tree when the branches test different conditions or the logic is a sequence.

For Dana's request the decision is a table, MaintenanceRisk, whose inputs are the change type, channel, customer risk rating and recent changes, and whose results are a risk tier and a route path.

The table evaluates top to bottom and, by default, the first matching row wins (an option can evaluate all rows), so row order is part of the logic. Blank or "any" cells match everything for that column. An otherwise row should always exist so the result is never silently empty and a blank does not flow into routing. The result property's allowed values should be a table-edit list so an analyst cannot type a typo. The table is called from a Decision shape in a flow, a property-map method, an expression function or a transform. The pitfalls are gaps and overlaps (for each pair of rows ask whether both can match), a missing otherwise, inconsistent boundaries (use >= 10000 and < 10000 and document inclusive and exclusive bounds), null inputs that match a blank cell unexpectedly, and comparing text with numbers.

Who maintains these rules is a governance decision, not a technical one. Decision tables can be authored in App Studio for simple cases, with branch-based review and PegaUnit tests; business-owned rule changes can go through a revision-management mechanism for proposing, approving and scheduling changes (tooling names and packaging differ by release); reference data can sit in a data type with a maintenance case, giving maker-checker over changes; and developer-managed rules follow the normal release process. In a bank the point is that threshold and mapping changes follow a controlled promotion path rather than ad hoc edits in production.

One boundary belongs here. Decision rules can also call predictive models, adaptive models and scorecards authored in Prediction Studio and combined in strategies; Chapter 08 treats those. The distinction to keep in this chapter is that a decision table is deterministic and explainable: the same input always gives the same output with a visible reason, whereas a model returns a probability. Banks often require both, with a model score used as an input to a deterministic policy rule.

3.10 Circumstancing: North Carolina, and a state-exemption example

Chapter 01 left a thread open: the decision that marks an address change as sensitive has a North Carolina variant for Dana, and that variant is created by circumstancing. Circumstancing creates a variant of a rule that applies only when a condition is true: a property value, a combination of values, or a date range. The base rule and its variants share the same name, class, ruleset and version family. Rule resolution ranks variants by circumstance ahead of version and picks the highest-ranked one whose condition holds at run time, so a newer base rule does not supersede an older circumstanced variant (Chapter 01 §1.6, the legal-order variant example). The caller never changes: it still calls the same rule name and the right variant runs, which is the whole reason to do it this way rather than writing a branch in every rule.

There are three kinds. A single-property variant uses the "specialise by circumstance" action on the rule and one property and value, such as .State = "NC". A multiple-property variant uses a Circumstance Template (which names the properties that participate) and a Circumstance Definition (which lists the value combinations and maps each to a variant). A date-based variant has effective start and end dates, or compares a date property to an "as of" date. In every case the base rule must exist, because it is what runs when no circumstance matches, and the circumstance property must already be set on the page at the point of call.

A worked example: garnishment exemption by state

The legal-order case from Chapter 02 needs to compute how much of an account to restrain, and the answer depends on the state, the order type and sometimes an effective date, because some funds are exempt from seizure under federal and state law. Riverbend's legal operations team must see the calculated amount to restrain without a developer writing if/else for fifty states.

Legal content disclaimer. Every number in this example is an invented placeholder that demonstrates mechanics assumed Riverbend policy. Real exemption rules are determined by Legal and Compliance, and Chapter 12 states the shape of the legal rules with their sources.
DATA Page: FCB-Dep-Work-LegalOrder .State, .OrderType, .EffectiveDate, .AvailableBalance, .ProtectedBenefitAmount, .DebtorCount RULES (class FCB-Dep-Work-LegalOrder, ruleset FCBLegalRules -- owned by Legal Ops, versioned) Decision Table CalcRestrainAmount <- BASE rule (federal default: restrain balance minus protected benefit amount) Decision Table CalcRestrainAmount [State=CA] <- single-property circumstance Decision Table CalcRestrainAmount [State=TX] ... other states only where they differ from the base Circumstance Template StateAndOrderType : properties (.State, .OrderType) Circumstance Definition StateAndOrderType : (CA, TaxLevy) -> CalcRestrainAmount_CA_Levy, ... The base rule is the federal default: for a garnishment or a tax levy the restrained amount is the available balance minus the protected benefit amount, never below zero; for a court freeze it is the full available balance and the case needs legal review; any other order type restrains nothing and needs legal review. A state variant exists only where the logic genuinely differs: one state subtracts an additional exempt amount, another restrains nothing for consumer debts and flags a review, another requires a mandatory exemption notice that triggers a correspondence variant, another restrains only the debtor's share of a joint account. Because the logic depends on both state and order type, the Circumstance Template lists those two properties and the definition maps each differing combination to a variant, so only exceptions to the base exist and the number of rules stays manageable.

For a date-based change, such as a state altering its exempt amount from 1 January 2026, a time-qualified variant is created effective that date and the old variant stays valid until the day before. The circumstance date input should be an explicit property such as .OrderEffectiveDate (the service date or processing date is a legal decision), not "today", so that reprocessing a December order in January produces the December answer.

When the amount for a California order looks wrong, the diagnosis is mechanical. Trace decision rules and rule resolution in Tracer and read the instance key of the winning CalcRestrainAmount with its state and date tag. Check .State on the page at call time (blank, or "California" against "CA", since the circumstance value is an exact match). Check that the circumstance property is set before the call, in the right order within the data transform. Check the date variant, including time zone and boundary day. Check the batch requestor's ruleset list for the latest version of the legal ruleset. Check for a cached resolution after a recent check-in. Then pin the defect with a PegaUnit case that sets a California order with a known balance and asserts the expected amount.

The pitfalls are consistent. A state with no variant and no base fails, so always keep a safe base. A circumstance property not yet set when the rule resolves falls back to the base silently, so set state first. Exact-match strings differ in case, so normalise with a value list and a data page of states. Variants multiply (fifty states times six order types times dates is hundreds of rules), so prefer data-driven parameters, a Decision Data table keyed by state, order type and effective date, when the logic is the same and only the numbers differ, and circumstance only when the logic itself differs. Ranking is class, then ruleset, then circumstance, then circumstance date, then date range, then version (Chapter 01 §1.6), and because ruleset ranks ahead of circumstance, a variant in a lower ruleset is outranked by a base rule on the same class in a higher ruleset, so test through the real application stack. And record which rule or version produced a decision on the case, for audit.

3.11 Validation: refusing bad data

Marcus types the new address and Dana's routing details, and one of them is malformed. A bad routing number, a maturity date before the open date or a negative amount in a bank produces returns, regulatory errors and failed core updates, so the application must refuse bad data before it is saved or before a flow action completes. Pega separates property-level format checks from form-level business checks.

At property level, an Edit Input rule normalises what the user typed before storage (trim, upper-case a state code, strip dashes from an account number), and an Edit Validate rule checks the value's format or range and adds an error message on failure. At form level, a Validate rule (Rule-Obj-Validate) is a list of property validations and conditions run together, referenced from flow actions or called with the Validate method, which can loop over page lists, call Edit Validate rules and call other Validate rules. A required setting marks a field mandatory, with a client-side check and server enforcement; a Declare Constraint (3.6) checks across properties; and custom logic can add messages with message actions or Page-Set-Messages.

The distinction that matters most is client side against server side. Client-side validation runs in the browser as the user types or tabs out (required, format, simple range) and gives fast feedback, and it can be bypassed by an API call, disabled JavaScript or tampering. Server-side validation runs on submit and is the authoritative enforcement. The rule is that client-side validation is a convenience, never a control: every rule a regulator cares about must also exist server side, so that a DX API or Service-REST caller cannot bypass it (Chapter 04 shows why that matters for API-driven channels).

FLOW ACTION SUBMIT "Approve closure" 1 Client-side checks (required fields) -> block if fail 2 Request to server 3 Edit Input normalisation on touched properties 4 Flow action Validate rule runs: required fields, Edit Validate on .RoutingNumber, loop .Signers(*) checks, condition: maker != checker -> message "Maker cannot approve own case" 5 Errors? YES -> messages attached to properties/page, harness redisplays with errors, assignment not advanced NO -> post-processing data transform -> flow advances -> save/commit

That sequence is also where the maker-checker control from Chapter 02 sits server side: a validate rule that refuses the approval when the maker equals the current operator. A Validate rule has an applies-to class, ordered validation steps, message text (use field values for localisation), the property each message attaches to so it displays in the right place, and a choice between stopping on the first error and collecting all of them. The things to avoid are relying on the UI "required" setting alone, validating in post-processing after the flow has advanced, messages with no property association, hard-coded English text, and duplicating validation logic across ten flow actions instead of one reusable Validate rule.

3.14 Interview Q&A

Q1. What is the BLOB, and why does it matter?

"Pega serialises the whole page into one compressed column, pzPVStream, and also writes exposed properties into their own columns. The BLOB gives flexible schema and one-read opening of a case, but a database cannot filter, sort, index or join inside it. So anything used in a report filter, join, sort, queue or batch selection must be exposed and indexed, with a backfill for existing rows. Page-list elements use Declare Index, or better, separate instances. The BLOB also holds personal data, so masking exposed columns alone does not protect it."

Q2. Explain data page scope.

"Scope decides who shares one cached copy. Thread scope is requestor-thread scoped: one thread of one requestor, which in the traditional portal is usually one case tab. Requestor scope is shared by all threads of one session, and node scope by every requestor on the node. I use thread for case-specific and editable data, requestor for user-specific data, and node only for read-only reference data identical for everyone. A node page on a class with access control policies draws a severe guardrail warning."

Q3. How do you keep a data page's data fresh?

"By choosing a refresh strategy per data: do not reload for static reference data, reload if older than a window for slowly changing data, reload once per interaction for screens that need fresh data referenced many times, which exists only at thread and requestor scope, a do-not-reload-when condition for locked decisions, and explicit invalidation after I update the source. For data that must be exact when I act on it, such as a balance before a disbursement, I fetch at the step instead of trusting any cache window."

Q4. Reference or copy when consuming a data page?

"Reference is a read-through to the shared page: always current, no copy cost, and read-only pages cannot be edited. Copy is a snapshot that later refreshes do not change. I reference for display and decision inputs and copy only when the value must be frozen for audit or the user will edit it."

Q5. What is a savable data page, and what does WriteNow do?

"A savable page is an editable page that also has a save plan, which pushes changes back to the system of record by a database save, an activity, a REST call or robotic automation. Plans are not mutually exclusive, and there is an otherwise condition. WriteNow decides the transaction boundary: true saves immediately as an independent transaction, false defers the save into the surrounding transaction, which commits, or rolls back, later. A deferred save is invisible to other requestors and to SQL until commit."

Q6. Are data pages the wrong tool for writes?

"Not as a rule. A single-object write back to a system of record is what savable pages are for. They are the wrong tool for bulk row-by-row writes, where one save per row means one call per row and set-based work is better, and for writes that need approval, idempotency and an auditable status, where the right model is a case step with an integrator, an idempotency key and a visible status. A maintenance screen editing reference data fits a savable page; placing a hold on an account during closure does not."

Q7. Forward versus backward chaining in a Declare Expression?

"Forward chaining recomputes the target whenever an input changes, so the stored value stays current, which suits exposed and reported properties, at the cost of work on every input change. Backward chaining computes on read, which suits display-only values. Forward chaining over a large page list is quadratic during bulk population, so I populate in bulk and compute once."

Q8. Data transform or activity?

"A data transform for setting and mapping data: it is readable, unit testable, inheritable and guardrail friendly. An activity only where no declarative rule can do the job: queueing work, explicit saves, calling connectors from background logic, custom routers. I avoid Java steps, keep activities thin, and never commit inside a loop."

Q9. Circumstancing or data-driven parameters?

"If the formula is the same and only the numbers differ by state, I put the numbers in Decision Data keyed by state, order type and effective date, so Legal maintains them under change control. I circumstance only where the logic or the correspondence genuinely differs. Variants rank ahead of version, so a base-rule fix must be applied to every variant, and the circumstance property must be set before the rule resolves."

Q10. Why is client-side validation not enough?

"It is bypassable by an API call or tampering. Anything a regulator cares about, including maker-not-equal-checker, must be enforced server side in a validate rule or a security rule, so the DX API and Service-REST paths are covered. Client-side checks are only fast feedback."

3.Z Where we are now

What the application can do

The case now has real data. It stores keys and the requested change, reads Dana's customer and account through data pages that fetch once and share by scope, refreshes the balance where it must be exact, can write a single object back through a savable page with a known commit boundary, derives amounts declaratively, decides sensitivity from a decision table, varies by state without copying rules, and refuses bad data on the server.

The mechanisms behind it

Properties and data classes define what is held; saving serialises the page into a BLOB with exposed columns for anything SQL must see, and Declare Index for lists. Data pages carry scope, refresh, parameters, error handling and edit mode, with a save plan and WriteNow deciding when a write commits. Declarative rules, data transforms and activities form a ladder from most to least preferred, decision rules externalise logic, circumstancing varies it, and reference data lives in keyed, effective-dated, owned tables.

What it still cannot do

The data is right, but no one can see or edit it: there is no screen. Marcus cannot open AM-10417, change a field, receive a validation message or submit it. Building that screen, in the traditional UI and in Constellation, and exposing the same change through the DX API, is Chapter 04.
