4.1 The screen Marcus opens: traditional UI 8.8 / traditional UI

Marcus clicks AM-10417 in his DepOps-Maintenance queue and sees a case header with the ID, status and SLA, a summary of Dana's current address and accounts, a form with the requested address, and Approve-style actions. In the traditional, section-based UI, that screen is the output of a stack of rules, and the server turns them into HTML. The server resolves UI rules (harness, sections, layouts, controls, skin), generates HTML, CSS and JavaScript, and the browser displays it. A developer designs each screen by composing layouts and fields.

The reason Pega builds screens this way is the model underneath. Before model-driven UI, every screen was hand-coded and every field's label, format, validation and visibility was repeated in HTML, JavaScript and server code. Pega attaches the UI to the property and rule model from Chapter 03: a property already knows its type, edit rules and table of choices, so a section can generate the right control and server-side behaviour from the same rules the process uses.

Reading the stack from the outside in: a portal is the top-level workspace a user logs into, with navigation, landing pages and work areas, named in the access group's portal list. A harness is the page template for a work context, such as the case and assignment wrapper with its header, tabs and action area. A section is the main reusable building block, a form region composed of layouts, controls and other sections, and a flow action (Chapter 02 §2.4) names the section that renders its form. A layout arranges content inside a section; a control decides how a property is edited or displayed; and a skin supplies the visual theming. Paragraph, correspondence and HTML rules hold static text and legacy fragments.

TRADITIONAL RENDERING PATH Browser requests case AM-10417 assignment | v server: portal rule -> work area -> HARNESS (pyWorkPage context: header, tabs, action area) | -> flow action form refers to SECTION AddressChangeReview | section = layouts (dynamic layout "Current address", dynamic layout "Requested address") | cells -> controls (text input, dropdown, date) bound to properties (.NewAddress.Line1, .NewAddress.State) | -> SKIN supplies CSS classes -> HTML/CSS/JS generated and cached by rule assembly v HTML sent to the browser; Marcus edits fields; refresh-on-change calls the server for a partial section reload Submit -> server validation (Validate rule) -> post-processing -> flow advances -> section refreshed or next assignment shown

Layouts are where most of a section's shape comes from. The dynamic layout is the responsive default, a container of rows and groups in inline, grid or stacked formats whose breakpoints come from the skin; it can nest, but deep nesting hurts performance and readability. A repeating dynamic layout renders a page list or group as repeated rows or cards, with pagination options for large lists. A table layout (repeating grid) shows a page list with sortable columns and per-row actions. Tree and tree-grid layouts show hierarchies, tab groups and accordions organise content (and should lazy-load heavy tabs), and the older fixed column layout should be avoided in new work. Embedded sections are the composition mechanism.

Each cell of a layout has settings that determine what it shows and how it behaves: the cell type (field, label, text, icon, button, link, embedded section, image); the property, using relative notation inside repeating layouts; the control, defaulted from the property and overridable; whether it is editable, read-only or automatic; its visibility, required and disabled conditions, each tied to a when rule or expression; its event-driven actions (refresh a section, set a value, run a data transform, open a local action, show a confirmation, post a value); its label and format; and an optional style class from the skin, with inline styles discouraged. Controls are mostly generated from the property type and table-edit settings: inputs, displays, actions, and special controls such as attachments, signature, maps, charts and case history. Custom controls built from HTML rules and JavaScript are costly and draw guardrail warnings.

A skin defines the visual identity once, as named style classes for colours, typography, spacing and components, and skins can be layered (a base skin, then Riverbend's brand skin). In a bank this is where brand and accessibility contrast decisions are made once instead of per section, and where responsive breakpoints are configured. The portal types an operator meets are the case-worker portal for operations users (worklist, search, create menu), a manager portal for supervisors (team workload, reassignment, reports), the interaction portal for contact-centre agents (4.8), the developer portal (Dev Studio itself) and custom portals designed per audience. Portal and harness rule names vary by release and framework, so describe a portal's role and check which Pega-supplied portal an access group references.

For Riverbend's closure review the same stack looks like this: a harness with the case header (ID, status, SLA chip), a read-only "Account Summary" section populated from D_AccountSummary, a repeating dynamic layout for signers with a per-row verification checkbox, a conditional "Legal hold details" section shown only when HasActiveLegalHold is true, and the checker's approve and reject actions. The disbursement-method dropdown is generated from a property whose table-edit source is a data page.

4.2 Editing, refreshing, validating: traditional behaviour 8.8 / traditional UI

Marcus changes the state dropdown on the requested address, types a ZIP code that does not match, and presses submit. Three behaviours fire in sequence, and each is a rule from earlier chapters made visible.

First, what is on screen follows conditions. A cell, layout or section can be shown, hidden, required or disabled by a when rule or inline expression; reusing a named when rule such as IsJointAccount means a business rule change updates every place at once and the condition can be unit-tested. One caution cannot be repeated too often: hiding a field is not security. A hidden field's data can still be sent by a crafted request, so access is enforced with privileges, Access When rules and server-side validation, and sensitive data is not loaded into the page unless the operator is entitled to it.

Second, a change in one field can change another part of the form. An event on a cell, such as the change of a dropdown, runs a set of actions: post the value to the server's clipboard, then refresh a section. The server recomputes the section and sends back HTML for that region only, preserving the user's context and other unsaved fields. The cost is one round trip per change, so the design rule is to batch dependent updates into one refresh and to refresh the smallest section that contains the affected fields. Refreshing the current section suits dependent fields within it; refreshing a smaller named section suits an isolated area; refreshing the whole harness is rare and expensive; and simple client-side visibility expressions avoid a server call at the price of logic duplicated on the client.

REFRESH ON CHANGE Marcus selects .NewAddress.State in section RequestedAddress | event: change -> action 1: Post value (send field to the server clipboard) | -> action 2: Refresh section CityStateLookup (when rule IsUSAddress true -> section visible) v Server: updates clipboard, evaluates visibility when rules, regenerates ONLY CityStateLookup HTML | v browser swaps the region. Other unsaved fields remain. Cost: one server round trip per change.

Third, submission. Required and simple format checks run in the browser, but they are only convenience. The authoritative checks run on the server at submit: edit-input normalisation on the touched properties, then the flow action's Validate rule, whose messages attach to the property so the section displays them next to the field, and the assignment does not advance (Chapter 03 §3.11). The same server validations apply to any API-driven channel, which is why UI-only checks are never relied on. In this example Marcus sees a message beside the ZIP field, corrects it, and submits again; post-processing then sets the status and the flow advances.

Reuse is what keeps the UI maintainable. A screen is composed from small embedded sections (AddressBlock, SignerRow, HoldSummary) parameterised with section parameters rather than copied. Shared sections sit at the highest class where all consumers share the property structure, such as a common address class, and are specialised lower down by rule resolution (Chapter 01). A single section can render read-only or editable depending on a parameter or surrounding mode. Labels come from field values and not literal text, so the same section serves multiple languages (4.10), and design templates give harnesses a consistent layout.

The temptation to avoid is the hand-coded section. Pega can auto-generate controls and sections from the property model; a non-auto-generated section or an HTML rule with custom JavaScript replaces that with raw markup, and the consequences accumulate: validation and formatting are no longer applied consistently, the markup breaks when Pega changes its client framework (which is exactly why Constellation prohibits it), values written unescaped create cross-site scripting risk and custom posts can bypass anti-forgery protections, hand-built controls often miss keyboard and screen-reader support, the guardrail score falls, only the original author can maintain it and it cannot be changed in App Studio, and custom scripts block rendering and defeat section caching. The usual offences are inline CSS and style attributes instead of skin classes, five or more levels of nested dynamic layouts, a section that loads a 5,000-row page list without paging, sections bound to one flow so nothing is reusable, JavaScript that reads and writes DOM fields directly, hiding sensitive fields with CSS only, and refreshing the whole harness on every keystroke.

4.3 The same screen in Constellation Infinity / Constellation

Everything in 4.1 and 4.2 is one way to build the review screen. Constellation is a different way, and it is a separate implementation path rather than a restyling of the first: the artefacts are different rules, authored in different places, rendered by a different client. Sections, harnesses and custom controls built for the traditional path do not become views, and views are not sections.

In Constellation the platform does not generate HTML. It describes each screen as view metadata, a structured, declarative description of "this screen has a form with these fields, this table, these actions", and a separate JavaScript front end built on Pega's Constellation design system renders that metadata in the browser. A builder authors views by choosing from prescribed templates (one-column form, two-column form, details, list, wizard-style steps) and filling regions with fields, nested views or components. Fields carry presentation settings (editable, read-only, display as a given component), and the control comes from the design system's components (text, dropdown, date, currency, status badge). Authoring happens in App Studio, in the case type's step or stage editor, with a live preview, and the underlying rules are visible in Dev Studio. Visibility, required and disabled conditions still exist, expressed in a Constellation-compatible form, and actions (submit, cancel, refresh-on-change, local actions) are defined in the view or flow action context. The view rule type, the template names and the App Studio screen labels evolve each release; the durable concepts are metadata-driven views, prescribed templates and regions, design-system components, no custom HTML or JavaScript in the standard path, and DX Components as the sanctioned extension.

For Marcus's interaction, then, the same behaviour is expressed differently. The address form is a view with a two-column template, the requested-address fields in one region and the current address read-only in the other. The state dropdown's dependent behaviour is a refresh-on-change in the view. The validation message comes from the same server-side Validate rule, because validation is a case-engine rule and not a UI rule. What changes is who draws the screen: the design system decides spacing, alignment, responsive collapse, accessibility behaviour and interaction patterns, and the builder decides only what appears in which region. That is what "opinionated" or "prescribed" means. One cannot absolutely position elements, inject arbitrary CSS or build one-off controls in the standard path, and the opinion is the feature, because it is what keeps the UI upgrade-safe and consistent.

Pega moved to this model for reasons that all trace to the cost of the first one. Traditional customisation (custom HTML, JavaScript, CSS, deep skins) turned every upgrade into a regression project; Constellation keeps the client and the metadata contract owned by Pega. A prescribed design system produces consistent, accessible, responsive screens without each team inventing layout. View authoring is fast. Because the UI is metadata over an API, the same case engine can serve Pega's front end or a custom client (4.5). The browser renders while the server holds data and process, with an explicit, versionable contract between them, and client-side rendering with cacheable static assets reduces server CPU spent generating HTML.

4.4 DX Components and the cost of changing path Infinity / Constellation

Suppose Riverbend needs a signature pad that the design system does not have. In the traditional UI the answer would be a custom control: an HTML rule plus JavaScript. Constellation does not allow that in its standard path, and offers instead a controlled extension point. A Constellation DX Component is a custom UI component, written in React and JavaScript against Pega's component contract, that is built, packaged and deployed so a view can render a field or region with the team's own UI. Pega's documentation names the types that its component builder supports: layout templates, widgets (added to the case utilities panel or to landing pages), fields (which replace out-of-the-box field components) and, in recent versions, presentation components.

The lifecycle shows what is being taken on. A developer builds the component in a local project using Pega's tooling. The component declares which Pega field or region type it can render and what configuration it accepts. It is packaged and published into the application as an artefact. An author selects it for a field in the view. At run time the client loads the bundle and gives it the view data and callbacks, and the component calls back to update values or trigger actions while Pega handles validation and persistence. From that moment the team owns code: security review, accessibility testing, upgrade compatibility, versioning and CI tests.

The decision whether to write one follows a short sequence of questions. Can a standard component meet the need after a small UX concession? Then do that. Is it needed by many screens? That strengthens the case. Is it a regulatory or brand requirement? Document and approve it first. Does the team have React skills, a test pipeline and an owner? That is required before starting. The anti-pattern is building one for convenience.

The same thinking applies to moving an existing application from one path to the other. It cannot be done by changing a setting: an existing section-based application is not switched to Constellation, because Constellation applications are built or reconfigured on its view model, and existing sections, harnesses and custom controls do not carry over. Case-type forms are rebuilt as views, custom controls are replaced by standard components or DX Components, portals and landing pages are rebuilt, and skin customisations are re-expressed through the design system's theming. Coexistence paths exist (embedding, or using the traditional UI for particular parts, with readiness-assessment tooling that varies by release), but any migration is a project: inventory the case types, sections, controls, portals, skins and scripts; classify each as standard (re-author as views), custom (a DX Component or a redesign) or unsupported (rethink it); pilot one low-risk case type end to end; regression-test and check accessibility; then cut over per case type by user group, with rules for in-flight cases that were created with traditional assignments. Rules, data and integrations are unaffected; only the UI layer is rebuilt. Not every legacy feature has a Constellation equivalent in every release, so the supported-features list for the target version is checked before committing. A new application starts without any of this debt, which is the strongest argument for choosing Constellation at the start (4.11).

The mistakes that recur are promising a client that a traditional application will move to Constellation "in a sprint", porting old custom JavaScript line for line, and ignoring the in-flight cases.

4.5 The DX API: a case engine a front end can consume

Dana does not log into Marcus's portal. She submits her address change on Riverbend's website, and the web team wants its own design system while Pega remains the workflow engine. Without a standard API, that team would need a hand-built Service-REST endpoint for every action (create a case, get the assignment, submit a form, fetch the worklist), duplicating Pega's own knowledge of flow actions, validation, routing and locking. The Digital Experience (DX) API is the REST API family built for exactly this: it exposes case-management semantics, with the platform enforcing security, validation, locking and process rules on each call. That is what separates it from a generic data API, or from a Service-REST designed for system-to-system use.

There are two generations, and they pair with the two UI paths. The traditional DX API (v1) goes with the section-based UI; screens are described by sections and harnesses tied to server rules, so a custom client either embeds server-generated HTML or works out for itself which fields to show and how. The Constellation DX API (v2) goes with view-based UI; it returns structured view metadata alongside data, so the client renders from what it is given. Pega's documentation describes the second as separating data from layout, reducing chattiness, introducing hypermedia-style responses that reference available actions, adding endpoints (for example to follow a case or change stages), and being the most suitable choice for new applications. Some Constellation endpoints can be used with a traditional application, but only applications built on the view-based approach can use every one. Version numbers and base paths are release-dependent: say "the original DX API for traditional and the newer, view-based one for Constellation", and quote URLs only after checking them.

A usable way to see the difference is to ask what a response answers. A normal data API answers "what are the values?" A DX API v2 response to "get this assignment" answers three things at once: the data (account number, owner, balance); the UI metadata (which view, which template and regions, which fields in what order, which are editable, read-only, required or hidden, localised labels, the component type for each field); and the actions and navigation (what the user may do now, such as approve or reject, and what comes next). Because the server decides which fields are visible and required given the current rule state, the client does not duplicate business logic such as "show wire details only if the method is Wire": it renders what it receives, and after each change it asks again and gets new metadata.

This is a teaching sketch of the concept, not the literal DX API schema; the exact schema comes from the documentation of the version in use.

The hypermedia point needs one sentence of its own. Rather than the client hard-coding the sequence of calls, the response for a case lists its available actions and current assignments, the response for an assignment lists its flow actions, and a submit response carries the next assignment (if the same user gets it) or confirms the case has moved on. The client follows what is offered, so when Sam adds a stage or reorders processes in Pega, the client keeps working with no code change. The chattiness difference follows from the same design: assembling a screen from a hand-built service takes separate calls for case data, field definitions and visibility, allowed values for dropdowns, and which actions are allowed, then a submit and a repeat; with the v2 API one response can carry data, the view and the actions, dropdown options are resolved by the server or fetched by a specific data-view call, and the submit response returns information about the next step.

Security is unchanged by the channel. DX API calls run as a Pega operator, so the full model applies: access group, roles, privileges, Access When and work locks, and the API does not bypass rule-based security. Authentication is typically token-based (OAuth 2.0 or OIDC bearer tokens issued by the bank's identity provider and validated through an authentication service), while Pega's own Constellation client uses session cookies; Chapter 05 explains the token flows and Chapter 10 operator provisioning. Concurrency uses version tokens in the ETag style so two clients cannot silently overwrite one another, which is the optimistic-locking model from Chapter 01 §1.11. Server-side validation always applies; a client's own checks are a convenience. One documented constraint for the Constellation DX API is that the application name appears in the URL after the application path segment, and the platform identifies the first access group on the operator that matches the application, so an operator with several access groups on the same application is not supported.

4.6 Dana's address change through the web channel

On Monday 2 March 2026 Dana submits her new address on Riverbend's website. The sequence below is what happens between her browser and the engine, described by function; resource paths, parameter names and headers are release-dependent and are confirmed against the version's API documentation.

DANA'S ADDRESS CHANGE via the web portal (DX API v2 style) Portal (Riverbend design system) Pega DX API Pega engine | login via the bank IdP, get token ------------------------------------------> authentication service | list case types (customer-facing set) -----> entitled case types: "Change address" | create case "AccountMaintenance", {type:"Address"} -----> create case, run pyDefault, Stage 1 Intake, assignment "Enter new address" | <---- case ID AM-10417, assignment info, etag | get assignment -----------------------------> view metadata: address form fields, required flags, state dropdown options | Dana types her ZIP; portal calls refresh ---> server recalculates City/State via data page lookup, returns updated values | submit action "Submit" + values + etag -----> Validate rule (address format), post-processing, flow advances | <---- next step: "We are verifying your request" (no customer assignment), case moved to Stage 2 Verify | poll or push notification: status "Resolved-Completed" (3 March) -> portal shows confirmation Behind the scenes: Verify and Approve run in the ops portal (Marcus, then Priya); core update via an Integrator; correspondence sent.

Read in order, the journey is the sequence a front end has to follow. The client lists the case types the authenticated user may create, and the server applies security and returns only those entitled. Creating a case runs the same creation path as any other channel: pyDefault and the creation transform, the first stage and flow, and the first assignment, returning the case ID, status, assignment information and a version token. Fetching the assignment resolves the flow action's view, evaluates visibility and required conditions and loads data page values, and returns data, view metadata and available actions. A refresh after a field change re-evaluates conditions and transforms on the changed values. Submitting sends the values, the chosen action and the version token; the server applies the values, runs validation and post-processing, advances the flow and may move the case to the next stage, answering with the next assignment or with validation errors keyed to fields. Afterwards the client can fetch the case (summary, stage, status, history, attachments), attach documents, perform local actions and read the worklist.

The channel adds concerns the screen did not have. If the case changed after the client fetched it, the submit fails on the version token, and the client must refetch and either retry or ask the user: never retry blindly with the old token. A customer who double-clicks "Submit" could create two cases, so the portal disables the button, and either stores a client-generated request key on the case and checks it in the creation transform, or applies an idempotency pattern in its backend. Validation errors come back per field and the client maps them onto the form. A step that waits for the core (an Integrator) should be asynchronous so the API call returns quickly and the client shows "processing"; Chapter 05 returns to why. A customer's token maps to a limited operator or external-user model so they see only their own cases (Chapter 10). The mistakes to avoid are calling the DX API directly from a browser with a powerful operator's credentials, a portal that hard-codes stage and step sequences, ignoring version-token conflicts, exposing internal case statuses to customers, and skipping server-side validation because the portal validates.

Check your understanding.

Dana's browser submits her address change and the response is lost on a flaky connection; her browser retries and the portal sends the create request a second time. What stops two AM- cases, and what does it depend on?

Answer. Nothing in the DX API itself stops it: each create is a legitimate new case. The protection has to be added, either with a client-generated request key stored on the case and checked in the creation data transform (so the second request finds the first and returns it) or with an idempotency pattern in the portal's backend that recognises the repeat before it reaches Pega. It depends on the key being generated once per user intention and reused on every retry; a key regenerated on each attempt defeats the check. Chapter 05 develops the same idea for calls to the core.

4.7 SDKs and custom portals Infinity / Constellation

Riverbend's web team is writing the customer portal in its own framework. Pega provides software development kits for building a custom front end that talks to the Constellation DX API and renders Pega views with the design system or the team's own components; the common families are React, Angular and Web Components. The SDK handles authentication helpers, calls to the API, parsing of view metadata and mapping metadata to UI components, so the team does not reimplement that plumbing.

A bank chooses an SDK when it has a mandated enterprise design system for customer-facing channels, when digital teams rather than Pega developers own the portal and want to release independently, when marketing or UX requirements exceed the prescribed look, or when Pega is the case engine behind several front ends. It chooses not to when the screens are internal operations with heavy stage-driven data entry (the standard front end is faster and cheaper), when there is no in-house front-end capacity (the SDK adds a codebase), or when time is short.

TARGET PATTERN: customer portal on the bank design system, Pega as case engine Customer browser / mobile web | Bank portal (React/Angular/Web Components with SDK + bank design system) | tokens via the bank IdP v Backend-for-frontend / API gateway (rate limit, WAF, token translation, idempotency, logging with correlation ID) | v Pega Constellation DX API -> Pega case engine (Maintenance, Closure, Disputes...) -> ESB -> core banking Static content for any Pega-served Constellation views: static content service (CDN)

The division of responsibility is the point to remember: Pega developers own the case types, data model, validations and APIs, and the front-end team owns the portal.

4.8 Agent desktop concepts: interactions and service cases

Dana could as easily phone. A contact-centre agent works inside an interaction, a conversation with a customer (a call, a chat, a branch walk-in) that is a container for the agent's work and context. The interaction portal is the agent workspace: caller identification, a customer context panel, interaction-driven navigation and service-case creation inside the interaction. Customer identification and verification (search, security questions, marking the interaction as verified) is mandatory before disclosing account data. The context panel is a set of data pages that assemble the customer's accounts, recent cases, holds and preferences into one view (D_Customer, D_AccountList, D_OpenCases). A service case is a case created from the interaction, such as a stop payment, an address change or a dispute, and it is the same case type operations use, started by an agent. Wrap-up records a disposition, notes and an outcome for audit and quality reporting, and screen pop and telephony integration (which identifies the caller and opens the context) sit outside Pega and are integrated. Next-best-action suggestions, where used, belong to decisioning (Chapter 08).

AGENT INTERACTION FLOW Call arrives (CTI) -> screen pop with a caller-number match candidate Agent verifies identity (knowledge-based questions / one-time code via integration) -> interaction marked verified Context panel loads thread-scope data pages: D_Customer, D_AccountList, D_Holds, D_OpenCases (personal data; per interaction) Agent selects "Stop payment" -> service case created inside the interaction (case type shared with ops) Case completes real-time steps (core call via an Integrator) or becomes a back-office assignment Wrap-up: disposition, notes -> history; interaction closed

Four design points matter in banking. Disclose data only after verification, tying the visibility of account sections to an "interaction verified" condition enforced by access control, not by the UI alone. Mask personal data by default (last four digits) with a privilege-gated unmask and an audit entry. Keep the agent's synchronous steps short, with tight timeouts on core calls and a fall-back to a back-office case if the core is slow (Chapter 05). And avoid loading everything: lazy-load tabs for accounts, holds and history so the panel appears quickly.

4.9 Supervisor dashboards: what Priya sees

Priya needs a live answer to "are we going to meet today's deadlines, and where is the backlog?" Dashboards combine Report Definitions (Chapter 02 §2.10) with charts, tables and filters on a landing page, so she acts on queues and not on spreadsheets. The useful widgets map to actions: work by queue and age bucket (rebalance staff), SLA at risk and breached (reassign or escalate), throughput today against target (an overtime decision), legal orders due soon (prioritise), ACH returns by reason code (spot a bad originator or a systemic issue), maker-equals-checker exceptions (a control report that must be zero), and integration health such as failed connector calls and queue processor delayed items (trigger an incident response). The operational health widgets are tooling the team builds for itself; Pega does not ship them as a ready-made dashboard.

Dashboards fail by being slow, and the rules that prevent it are the data-model rules again. Every filter, group and sort column is exposed and indexed (Chapter 03 §3.3). Every query is bounded by a date range, lists are paginated and counts are limited. Heavy aggregates are cached through a short-lived data page rather than queried on every refresh by every supervisor. Auto-refresh is limited, because a landing page refreshing every ten seconds for fifty supervisors is a load test nobody intended. Drill-down shows a summary first and detail on click, with a hard row cap and a privilege check.

SUPERVISOR DASHBOARD DATA PATH Widget -> Report Definition (summarise, filters: queue, date range, status) -> SQL on exposed, indexed columns (pc_work_dep + assignment tables) -> short-lived cached data page (e.g. 2 min, node scope for team-level data without personal data) -> chart/table render Drill-down click -> list report limited to 100 rows, pagination, privilege check

The things to avoid are dashboards built on unexposed properties, unbounded counts on millions of rows, each supervisor building private reports against the work table, and personal data in widgets visible to every role.

4.10 Accessibility, localisation and responsive design

A bank must meet accessibility obligations for customer-facing and, increasingly, employee-facing tools; which legal standard applies is a Compliance matter, and WCAG-aligned expectations are the usual reference. Pega's standard controls and Constellation's design system carry keyboard navigation, focus management, labels and ARIA roles; custom controls do not unless they are built. In practice that means every field has a visible, programmatically associated label (not a placeholder alone), the whole journey works from the keyboard with a visible focus, error messages are tied to fields and status changes are announced to screen readers, SLA status is never conveyed by colour alone, session timeouts warn and can be extended, and key journeys get automated checks plus a manual screen-reader pass.

Localisation depends on never putting literal text in a section or view. Labels, messages, button text and dropdown options come from field values or localisation packs, language rulesets (a Spanish one, for example) layer over the base so the language follows the operator's locale or the customer's preference, and dates, numbers and currency are formatted by locale while the stored data stays neutral (ISO dates, decimals with an explicit currency). Regulatory text is translated and approved by Compliance and versioned, not machine-translated casually. Layouts must tolerate text expansion, right-to-left support is a distinct requirement to confirm, and time zones follow the rule from Chapter 02: store GMT, render in the user's zone, keep business dates as dates.

Responsive behaviour differs by path. Constellation's design system is responsive by default and should be tested at tablet and phone widths. Traditional dynamic layouts and skin breakpoints must be configured, and a layout that looks right on a desktop may overflow on a phone. Mobile web for customers is typically a custom portal on the SDK or DX API; field or branch tablets with offline needs are a separate decision, since standard web is online only; and heavy tables on small screens use card views or summarised columns, not horizontal scrolling.

4.12 UI performance and security

The two paths spend effort in different places. In the traditional UI the server generates heavier HTML and JavaScript per page type on first load and regenerates HTML regions on each interaction; its hotspots are deep layout nesting, large repeating grids, many refresh events and uncached data pages, and it is diagnosed with Tracer, PAL, the browser's network tab and a database trace. In Constellation a static bundle is cached or served from a CDN so the shell loads quickly after the first visit, and each interaction returns JSON for the client to render; its hotspots are slow data pages behind views, large lists without paging and chatty custom components, and it is diagnosed with the browser network tab (API timings and response size) plus PAL and PDC for the server side. Four habits apply to both: count server round trips per user action and aim for one; never load large lists into a view, page them on the server; keep the data pages behind a screen fast, because a slow connector inside one makes the screen slow; and defer heavy sections such as tabs until opened.

4.13 Interview Q&A

Q1. Describe the traditional Pega UI stack.

"A portal contains work areas; a harness is the page template for the work context; sections are the reusable form regions built from layouts such as dynamic and repeating layouts; cells bind properties to controls; the skin supplies CSS and responsive behaviour. A flow action refers to a section for its form. The server generates HTML from those rules, and refresh-on-change reloads just a section. The discipline is small parameterised sections, named when rules for visibility, and no custom HTML or JavaScript."

Q2. How do you show or hide fields, and is that security?

"Visibility, required and disabled can be driven by a named when rule or expression. It is presentation only: a hidden field can still be posted, so access is enforced with privileges, Access When and server-side validation, and sensitive data is not loaded into the page unless the operator is entitled."

Q3. What are the risks of custom controls and non-auto-generated sections?

"They bypass the property model so validation and formatting are inconsistent, break on upgrade, raise cross-site scripting and request-forgery concerns, usually miss accessibility, cost guardrail points, and only their author can maintain them. Each is a future upgrade project and an exception to approve."

Q4. Explain Constellation, and say how it relates to the traditional UI.

"Constellation replaces server-generated HTML with view metadata rendered by a client built on Pega's design system. Views are authored from prescribed templates and regions in App Studio; the front end is delivered as static content and talks to the Constellation DX API for data, metadata and actions. It is a separate implementation path from the traditional UI, with different artefacts, not a skin on it. The trade is design freedom for upgrade safety, consistency, built-in accessibility and speed. Custom needs go through DX Components, not HTML and JavaScript."

Q5. What does 'opinionated' mean here, and what do you lose?

"The design system decides spacing, alignment, responsive behaviour and interaction patterns; I decide what appears in which region. I lose arbitrary CSS, one-off controls and direct reuse of old sections, and I get upgrade-safe screens, consistency and accessibility. For a bank's internal operations that is the right trade."

Q6. Can we migrate a traditional application to Constellation by switching a setting?

"No. It is a UI re-platforming: case-type forms are rebuilt as views, custom controls are replaced or become DX Components, portals and skins are redone. Rules, data and integrations are unaffected. I would inventory and classify what exists, pilot one case type, check the supported-features list for the release, regression-test, and cut over per case type. A new build avoids the problem."

Q7. What is the DX API, and what does 'UI metadata in the response' mean?

"It is a REST API for building front ends on the case engine, with case semantics: create a case, get the assignment, perform a flow action, with security, validation and locking enforced by the platform. The Constellation version returns data, view metadata and the available actions together, so the client renders what it is given and does not duplicate rule logic, and it needs fewer calls. Version tokens give optimistic concurrency, and the server-side validation still applies."

Q8. A customer double-clicks Submit in a custom portal. How do you avoid two cases?

"The DX API treats each create as a new case, so I add protection: disable the button, and store a client-generated request key, created once per user intention and reused on retries, on the case and check it in the creation transform, or apply idempotency in the portal's backend. A key regenerated on every attempt defeats it."

Q9. DX API or a custom Service-REST?

"The DX API for human-facing front ends, because it brings flow actions, locks, routing and UI metadata. A custom Service-REST for system-to-system integration with a stable canonical contract, such as the core, partners and a replay endpoint, which is something you build. I would not use the DX API as an integration contract with the core or the ESB."

Q10. Which UI path for a new deposits application?

"Constellation with the standard front end for operations: a new build has no migration debt, stage-driven screens suit the templates, accessibility is built in and upgrade cost is lowest. A thin custom portal on the DX API or SDK only for customer-facing journeys, with Pega as the case engine, and I would confirm the target release and its supported-features list first."

4.Z Where we are now

What the application can do

Marcus can open AM-10417, edit the requested address, receive a server-side validation message beside the field and submit, in either UI path; Priya can see her queues and deadlines on a dashboard; and Dana's web portal can create and complete the same address change through the DX API with a version token and protection against a double submit.

The mechanisms behind it

The traditional path builds a screen from portal, harness, section, layout, control and skin rules that the server renders to HTML, with refresh-on-change for partial updates. Constellation builds it from view metadata, templates and regions rendered by a client on the design system, delivered as static content. The DX API exposes case semantics to any front end, returning data, metadata and actions. Validation, security and locking live in the case engine, so they hold on every path.

What it still cannot do

The screen is there and Marcus can submit, but the core still knows nothing: fulfilment has no way to read Dana's account from it, or to ask it to change her address or place a hold. Calling the core, and what happens when it is slow, when it refuses and when it loses its answer, is Chapter 05.
