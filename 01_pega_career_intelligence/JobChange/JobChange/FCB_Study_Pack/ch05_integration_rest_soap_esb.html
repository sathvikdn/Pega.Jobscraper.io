5.1 Pega calls out, and Pega is called

When Priya approves AM-10417, fulfilment has to tell the core to change Dana's address. When Marcus opens AC-10882, the screen has to read her balance. Before that is possible, the application needs a way to talk to systems it does not own, and that traffic goes in two directions. A connector is an outbound rule: Pega is the client and calls someone else, such as the core, a sanctions screening API or a database. A service is an inbound rule: Pega is the server and someone else calls it, such as the ESB posting an event, a digital channel creating a case or a replay endpoint. Everything in the integration category is one of these two or a rule that supports them (authentication, mapping, listeners, data sets).

Integration rules exist because the alternative, hand-coded calls, left the contract spread through code: build the HTTP request, set headers, serialise the payload, parse the reply, handle errors, differently for each developer. Making the contract (URL, method, headers, mapping, authentication, error handling, simulation) a declarative, reviewable and testable rule lets the platform handle the plumbing consistently.

5.2 Being called: service packages and the service rule

Dana's web portal does not log in as Marcus. It calls Pega, and an inbound call arrives with no Pega session, so the platform must still decide three things: who the caller claims to be and whether that is true, which ruleset version applies, and what rights the call has. A Service Package is the container and security envelope that answers all three for a group of related service rules. It decides who may call (the authentication type), who the call runs as (the access group, which sets the ruleset list and roles) and some runtime options such as requestor pooling. Every inbound service rule belongs to a package, and the package name becomes part of a REST service's URL.

The main package settings are the access group the service requestor runs as; whether authentication is required (switching it off makes the service anonymous, which is almost never acceptable for banking); the authentication type (basic, a custom authentication service, an OAuth 2.0 bearer token through an authentication service, or other options depending on release); context and pooling, including whether the clipboard is cleared between requests; and whether, when the caller authenticates as an operator, that operator's own access group is used instead.

The service rule itself names a service class and method (the rule name used in the URL), a resource path and the HTTP methods it supports, each with its own processing. Its request side defines how headers, query and path parameters and the body map onto the clipboard (including JSON mapping through a data transform or mapping rule); its primary page and processing name where the request lands and which activity or transform handles it; and its response side maps the outcome to an HTTP status and body, including custom error responses and what is logged when processing fails.

SERVICE-REST RUNTIME (inbound event from the ESB) ESB POST https://pega.riverbend.example/.../EventIntake (JSON, bearer token, correlation ID header) 1 Servlet receives; finds service package by URL; applies authentication (validate token / mTLS client cert) 2 Service requestor created/pooled with package access group (ruleset list, roles) 3 Rule resolution: service rule by method (POST) 4 Request mapping: headers -> params, JSON body -> integration-class page (pyWorkPage or a named page) 5 Processing activity: validate, check duplicate (idempotency key), create case or queue item 6 Response mapping: 201/200/202 + body {caseId, status} or 4xx with error body 7 Log request/response metadata (not full body), correlation ID in logs

Six inbound design rules follow. Always authenticate, preferring token-based with short expiry plus transport security, and mTLS between internal systems where mandated. Give each integration its own access group with least privilege: a service that creates cases needs create rights on those case types and nothing else. Validate the payload on the server and return a precise 4xx for client faults and 5xx only for real server faults, because callers (and the ESB) decide retries from the status code. Return 202 Accepted with a tracking ID for work that is queued, not a 200 that claims completion. Make every state-changing operation idempotent using a caller-supplied key (5.9 explains why). And version the contract in the URL or a header and never change the meaning of a field in place.

5.3 What the core's answer becomes: the canonical model

The core's reply for Dana's account looks like {"acctNbr":"...","stCd":"A","availBal":"4218.55",...}. The first thing a developer is tempted to do is to bind a case property directly to stCd. The consequence arrives later: every rule, screen, decision table and report that tests stCd = "A" now depends on the core's code values, so a renamed field ripples into everything, and replacing or adding a core rewrites the application. Banks routinely have more than one system for the same concept, and the contract with each changes regularly.

The remedy is a canonical data model: an application-owned representation of business entities (customer, account, hold, legal order, transaction) that sits between external payloads and the case and data classes. External systems map into it and out of it. Inside Pega everything works with the canonical shape, while the vendor or ESB shape lives only in integration classes and mapping rules.

Code translation belongs in keyed reference data (Chapter 03 §3.12), not hard-coded in transforms, so that when the core adds a status code the change is data, versioned and testable. The one rule that matters most is that an unrecognised code never defaults silently to a valid value: an unknown status maps to Unknown, is logged, and routes to review. The cost side is real: extra classes and transforms to maintain, design effort up front, and the risk of a canonical model with 400 fields nobody uses, so it is kept minimal and driven by actual use. The test for whether it is working is the design-review question: if the core vendor renamed a field tomorrow, how many rules change? The right answer is one data transform and its PegaUnit test. For Dana's account, D_Account[AccountNumber] calls the connector, maps the response into FCB-Dep-Int-CoreAccount, and a post-load transform produces the canonical FCB-Dep-Data-Account page with .Status = "Active" and .AvailableBalance as a decimal; cases and decision tables see only the canonical page.

An ESB sitting in the middle (5.7) usually has a canonical message model of its own, so there can be two canonical layers to map deliberately. The anti-patterns are using the vendor's class as the case's embedded page, business rules that test vendor codes, mapping inside a section or activity, and the same mapping repeated in many places.

5.4 Reading Dana's account: the Connect-REST build

Reading the balance is the first real call, and it is built in an order that is worth following exactly, because each step supplies what the next one needs. The data model comes first: integration classes for the request and response (FCB-Dep-Int-HoldRequest, FCB-Dep-Int-HoldResponse for the later write) and the canonical classes they map to, with correctly typed properties, because the connector's mapping targets must exist and guessing property names is the classic source of rework. Then the contract is obtained from the ESB team: an OpenAPI specification or sample request and response, status codes, error body, authentication method, timeouts and rate limits, because without it mappings and error handling are guesses.

Third, the authentication profile (5.11) is created so that the connector can reference it and credentials are never typed into a rule. Fourth, the connector itself is generated with the accelerator-style wizard (Create REST Integration, from a sample or a specification) or built by hand when the specification is simple or nonstandard; the wizard saves time but generates structure that must be reviewed, renamed to standards and trimmed. Fifth, the endpoint: a base URL held in a Dynamic System Setting or configuration instance so it differs by environment, a resource path with path and query parameters mapped from the page or parameters. Sixth, the method and headers: Content-Type and Accept, a correlation ID header, and for writes an idempotency key header, because headers drive traceability and safe retries.

Seventh and eighth are the mappings. The request transform maps the canonical page to the request integration class and produces the JSON body; the response transform and status handling map success to the response class and then to canonical, map the expected business outcomes (a 409, a 422) to explicit results, and map anything unexpected to a generic error, because the response contract includes its failure shapes. Ninth, timeouts and error handling: explicit connect and read timeouts, and a definition of what a connection error, a timeout, a 4xx and a 5xx each do, because the defaults are not safe for production; 5.9 and 5.10 settle what they should do. Tenth, simulation and tests: connector simulation returning a response from a data transform and PegaUnit cases for the mapping transforms, then a test with Tracer against the real endpoint in a lower environment.

Wizard names, tab names and option labels vary by release; the order and the content of each step are stable. Four habits come with the build. Connection pooling is managed by the platform, so never place a connector call per row in a loop: use a batch endpoint, a queue processor with controlled concurrency or a data flow. Do not log full request and response bodies in production because they hold personal data: log status, latency, correlation ID and a body hash or size. Validate TLS and never disable certificate verification to get something working. And keep responses lean by asking the ESB for only the fields needed.

The connector rule has a familiar shape. Its service tab holds the authentication profile, the endpoint (full URL or a base plus resource path, with a configuration reference for the host) and the methods and parameter definitions. Its request tab says how the body is built; its response tab how it is parsed and which status codes count as success. The advanced settings carry the timeouts (labelled connection and response, set explicitly), proxy and keystore options for mutual TLS (5.14), and simulation and optional pre- and post-processing transforms.

5.5 Mapping: where most integration defects live

The call returns, and what goes wrong next is almost always in the translation: a type that lost precision, a null that arrived as an empty string, an enumeration the core added last week, an array that sometimes arrives as a single object. Mapping is therefore treated as code with tests. The default pattern is a request or response data transform that maps between the canonical page and the integration page, with the connector's own message mapping doing only the JSON-to-integration-class step; it is testable with PegaUnit. Property-level JSON mapping inside the connector suits simple flat payloads. JSON-aware data transform actions suit complex or dynamic structures. Parse rules suit files and nonstandard payloads (Chapter 07). Metadata-driven mapping, where the mapping is itself data interpreted at run time, suits many similar integrations and is the subject of 5.8. An anti-corruption mapping rejects or quarantines payloads that violate the contract rather than passing bad data inward.

5.6 When the core speaks SOAP

Not every system in a bank offers JSON. Banks still run many SOAP services in core banking, payment hubs and vendor products, because SOAP gives strict typing, WS-Security options and mature tooling. It is an XML messaging protocol with a formal, machine-readable contract, a WSDL, and the call for placing the same hold looks like this.

A wizard (Create SOAP Integration) reads the WSDL and generates the connector, integration classes and mapping rules for the chosen operations; generated class names are reviewed and unused operations trimmed. The endpoint comes from the WSDL but is overridden per environment through configuration, so a production URL never ships into a lower environment. Request and response mapping goes from clipboard to XML through the generated mapping, with namespaces and element ordering handled for you and hand-edited only with care. SOAP headers, including WS-Security username tokens and a custom correlation header, are mapped in the request configuration. Authentication is through an authentication profile and often mutual TLS (5.14). A SOAP Fault arrives as HTTP 500 with a fault body, and the mapping must separate business faults (insufficient funds, invalid account) from infrastructure faults (server busy), because treating every fault as retryable means a business fault retried five times is five rejected requests. Large binary content such as a PDF of a legal order is either base64-encoded inline, which inflates size by roughly a third and uses memory, or sent as a separate MIME part with MTOM; confirm MTOM support for the release and connector before promising it.

5.7 The ESB between Pega and the core pattern

Pega does not usually call the core directly. In most banks an Enterprise Service Bus sits between applications so that none connects to another point to point; Pega talks to the ESB, which routes, translates and calls the backends. The reason is arithmetic: with N systems integrating directly there can be up to N x (N-1) connections, each with its own protocol, format, credentials and failure behaviour, whereas a hub reduces that to N connections and centralises transformation, routing, security and monitoring, so a backend can be replaced without changing every consumer.

POINT-TO-POINT (n x (n-1)) HUB-AND-SPOKE VIA ESB (n connections) Pega --- Core Pega -------\ Pega --- Sanctions Digital ----+--> ESB (routing, transformation, Pega --- CRM Branch -----/ security, throttling, monitoring) Digital --- Core | | | | Digital --- CRM ... Core Sanctions CRM Payment hub

What the ESB brings is what Pega then relies on: routing (one logical service, the ESB picks the right core by product), transformation between formats, an enterprise canonical message model (to be mapped deliberately against Pega's own, 5.3), protocol mediation (REST in, SOAP or MQ out), throttling that sets the ceiling on queue processor concurrency, orchestration of several backend calls into one (fewer, coarser calls from Pega, but hidden latency), security enforcement so Pega authenticates to the ESB and not to each backend, reliable messaging through queues, and monitoring and audit with a correlation ID that must pass end to end.

The boundary between Pega and the ESB can take four shapes, and which one is used decides how a failure shows up. Synchronous request-reply (REST or SOAP) means Pega waits: right for reads needed now, such as a balance for a screen, and the caller sees a failure immediately but must handle a timeout and risks tying up threads. Asynchronous with callback means Pega posts a request, receives a 202 and a tracking ID, and the ESB later calls a Pega Service-REST with the result (or Pega polls): right for slow or batch-like operations and long core posting windows, with the case waiting under an SLA and a plan for a callback that never arrives. A fire-and-forget event to a queue or topic suits notifications and downstream updates where no result is needed. A batch file through SFTP suits very high volume and end-of-day settlement, reconciled by counts and trailers (Chapter 07).

ASYNC WITH CALLBACK (account closure posting) Pega case step (Integrator) --POST /closures {caseId, idempotencyKey}--> ESB --> core posting | 202 Accepted {trackingId} | v | (core completes in seconds or minutes) Case status "Pending-Core"; Wait shape + SLA ("no callback within 15 min -> status check") ^ | +-- Service-REST /closureResult (idempotent, authenticated) <--------+ callback {caseId, result, coreRef} Callback handler: look up case by caseId, ignore if already final (duplicate callback), set result, advance flow Safety net: a Job Scheduler or queue processor sweeps cases stuck in Pending-Core and calls the ESB status endpoint

5.8 The bulk path: Connect-SQL and metadata-driven MERGE

Everything so far is one call for one case. Some traffic is different in kind: fifty-odd Kafka topics (Chapter 06), each with its own JSON shape, each landing in one or more relational tables, updating rows that exist and inserting rows that do not. Hand-writing fifty mappings, fifty transforms and fifty SQL statements is slow, error-prone, and makes onboarding a new market a development project. The design response is to make the integration itself data.

A Connect-SQL rule runs SQL against a database configured in Pega (a database instance with a JDBC data source), mapping parameters in and result columns out. It exists so Pega can read and write non-Pega tables (staging, reconciliation, reference replicas) with SQL, instead of Obj-* methods that assume Pega's own table and BLOB structure. It carries the database, the statement or procedure call, parameter mappings, result mapping, a statement timeout and error handling, and a transaction behaviour that must be verified for the release because its commit semantics differ from Obj-Save.

The pattern has a handful of parts. A staging table receives the arrivals: the same columns as the target plus audit columns (batch ID, received time, status), populated in bulk without business logic. Metadata tables describe each integration: source message type, target table, key columns for matching, a list of column mappings (source JSON path, target column, data type, default, whether to update on match) and flags such as soft delete. A runtime resolver reads the metadata for the message type and builds the mapping at run time (the Dataset mapping is resolved, not compiled). A dynamic SQL generator builds the staging insert and the MERGE text from the metadata, with bind parameters. One generic Connect-SQL rule executes it for every target. The MERGE is the single set-based statement that updates a target row when a staging row matches on the key and inserts it when it does not. And a result and audit step records row counts (inserted, updated, rejected), batch status and error rows.

METADATA-DRIVEN UPSERT PIPELINE Kafka topic -> Dataset/Data Flow -> JSON message (type = "account.balance.updated", market = "SG") | v 1 Resolve metadata for (message type, market): | meta_integration: target_table=acct_balance, key_cols=[account_no, market], merge_mode=UPSERT | meta_column_map: $.acct.no -> account_no (VARCHAR) $.bal.avail -> available_bal (DECIMAL) $.ts -> source_ts (TIMESTAMP) v 2 Extract values by JSON path (dynamic JSON-to-SQL mapping) -> row object v 3 Bulk insert rows into stg_acct_balance (batch_id, row_status='NEW') (batch/array insert, one round trip per chunk) v 4 Generated MERGE (one statement per chunk), shown here in SQL Server style: MERGE acct_balance AS t USING (SELECT * FROM stg_acct_balance WHERE batch_id = :batch AND row_status = 'NEW') AS s ON t.account_no = s.account_no AND t.market = s.market WHEN MATCHED AND s.source_ts > t.source_ts THEN UPDATE SET t.available_bal = s.available_bal, t.source_ts = s.source_ts, t.updated_at = SYSDATETIME() WHEN NOT MATCHED THEN INSERT (account_no, market, available_bal, source_ts) VALUES (s.account_no, s.market, s.available_bal, s.source_ts); v 5 Mark staging rows PROCESSED / REJECTED; record counts; PostgreSQL equivalent: INSERT ... ON CONFLICT (account_no, market) DO UPDATE ... WHERE excluded.source_ts > target.source_ts v 6 Dashboard and alerts read counts and reject rate

Why each piece is there is the design argument. Staging first, because loading into a landing table in bulk avoids row-by-row Pega round trips and defers application-level rule evaluation until the data is already inside the database. That is the real benefit, and it is worth being exact about what it is not. A bulk load is not failure-free. It can still fail on NOT NULL and CHECK constraints, on unique and primary-key violations, on foreign keys, on type and length conversion, on encoding, and on malformed input. It can fail partially: depending on the load method and transaction scope the result may be all-or-nothing, or a committed prefix with the remainder rejected, and the design must know which. Business rules are not escaped either; they are moved, either into the MERGE's conditions or into a validation pass over the staging table, and whatever they reject still needs a reject table, a count and an owner. So the loader's error-handling mode is stated explicitly, and no one says rows "cannot fail".

Metadata instead of code, because a new market or topic is then a metadata insert and a test, and mapping changes are audited data changes. MERGE instead of select-then-insert-or-update, because it is one atomic statement with no race between the check and the write, far fewer round trips, and correct under redelivery (reprocessing the same message gives the same row). A source-timestamp guard (s.source_ts > t.source_ts) so that a late event cannot overwrite newer data, with a limit that Chapter 06 §6.3 spells out: the guard is legal for full-state snapshots only, not for partial updates or deltas. One generic Connect-SQL rule instead of fifty, which is one reviewed, guardrail-friendly rule. And rejects routed to a table, so that one bad row does not fail the batch and errors can be reviewed and replayed.

Dialect and safety notes. The MERGE above is SQL Server syntax. PostgreSQL's idiom is INSERT ... ON CONFLICT; MERGE exists only in PostgreSQL 15 and later. Never blend them in one example; Chapter 11 covers both with runnable schemas. Both need the right unique key to arbitrate concurrency, and duplicate source keys inside one statement are a separate failure: SQL Server MERGE raises an error if a target row matches more than one source row, and PostgreSQL ON CONFLICT DO UPDATE cannot affect the same row twice in one command, so staging is de-duplicated by key and latest timestamp first. Values are always bound parameters; table and column names cannot be bound, so they come from an allow-list of validated metadata and never from string concatenation. Money is NUMERIC or DECIMAL, never float, and timestamps are timestamptz (PostgreSQL) or datetimeoffset (SQL Server) so the instant is unambiguous across zones.

5.9 When the core misbehaves: slow, rejecting and silent pattern

On Monday 9 March, fulfilment of AC-10882 has to place a hold on CHK-8842-0117 through the ESB before the disbursement can follow. In testing the call works every time, and a design that only handles that is not finished. A remote call has three outcomes, not two: it succeeded, it failed, or you do not know, because the request was sent and no answer came back. The third is the dangerous one for a financial write, and nearly everything in this section is about it. The way to arrive at the full design is to break the call in three ways, in order: the core goes slow, the core says no, and the core says yes and the answer is lost.

Failure one: the core goes slow

The closure screen reads Dana's balance and the core, having a bad afternoon, takes forty seconds to answer. Nothing has failed, and that is the problem: Pega's request thread sits waiting, the user waits, and every other screen that needs the core queues behind it. The first defence is that a call must not wait forever, and a connector has two different timeouts for two different questions. The connect timeout bounds how long to wait to establish the connection and detects a host that is down or a firewall that is dropping packets; a healthy internal host connects in milliseconds, so two or three seconds is generous, and waiting longer only holds a thread. The read (response) timeout bounds how long to wait for the answer once the request is sent and detects a slow or hung backend; it is set from the measured p99 latency plus margin, not a round number, typically five to eight seconds for an interactive screen and fifteen to thirty for background work. A third, overall deadline for the whole business operation prevents retries from running past what the caller can wait.

The read timeout has to be chosen relative to the layer behind it. If the ESB gives up on the core after three seconds, Pega's read timeout must exceed that, say four, so that the ESB's error arrives before Pega gives up; if Pega abandons first while the ESB carries on, the outcome is unknown for a reason that was avoidable. The arithmetic for an interactive balance read makes the consequence plain.

Target: closure screen loads customer + balance in <= 3 s at p95; user abandons after ~10 s Call chain: Pega --> ESB --> core core p99 latency = 1.2 s ESB overhead p99 = 0.3 s ESB backend timeout = 3.0 s (the ESB gives up on the core after 3 s) Pega read timeout = 4.0 s (must exceed the ESB's 3.0 s, else Pega abandons first) Pega connect timeout = 2.0 s Worst case for one attempt = 2.0 + 4.0 = 6.0 s One retry would exceed the 10 s budget with backoff => for READS on interactive screens: NO automatic retry; show "balance unavailable, retry" with a manual retry button, and serve the last cached value if the business allows.

Pega's connectors expose connection and response timeout settings and the platform default is rarely appropriate, so explicit values are set per connector. Pega's connectors do not provide automatic exponential backoff or a circuit breaker, as far as the documentation shows, so those are built from queue processors, delayed queueing and a health flag; confirm against the release documentation before saying otherwise.

A read that times out is transient and safely retryable, because reading again changes nothing. That is where retry belongs, but not blind retry: retrying immediately, from many clients, against a backend that is struggling makes it worse. The standard form is exponential backoff with jitter.

delay(n) = random(0, min(cap, base x 2^n)) "full jitter" Starting parameters for a background connector call: base = 1 s, cap = 60 s, max attempts = 5 (initial + 4 retries), overall deadline = 5 min attempt 1 at t=0 retry 1 : wait random(0, 2 s) retry 2 : random(0, 4 s) retry 3 : random(0, 8 s) retry 4 : random(0, 16 s) After max attempts: stop retrying, park the item for human or scheduled retry (not infinite). Why jitter: 200 queue-processor items failing at the same instant would otherwise all retry at exactly t+2s, t+4s ... (thundering herd).

What is retried is as important as how. The transient bucket for retry is: connection failures where the request was never sent (connect timeouts, connection refused, DNS failure); a read timeout on a read; and HTTP 429, 502, 503 and 504 for reads, honouring any Retry-After. It is never 400, 401 (refresh the token once and retry once, then stop), 403, 404, 409 (a conflict, not a transient), 422 or a business fault. And one category is deliberately outside the bucket: a timeout, or a 502 or 504 from a gateway that timed out behind it, on a write that may already have succeeded is an unknown outcome, and retrying it is a decision made under the rules of failure three, not a default. A 429 or 503 on a write usually means the request was refused before processing, which is safe to retry under the contract; whether a particular gateway status means "refused" or "I do not know" is exactly what the contract with the middleware team settles (5.7).

Backoff has to be implemented without holding a thread. A sleep inside an activity or flow holds a thread and a lock. Instead, a transient failure queues the work again with a delay: a queue processor supports delayed queueing (Chapter 06), the next delay is computed with the formula from an attempt count carried in the queue item, and the queue processor's own retry configuration gives fixed or limited retry where exponential backoff is not needed. A flow can use a Wait shape for case-level retries ("retry in five minutes"). After the maximum attempts the item moves to a broken or dead-letter state for human review and replay (Chapter 06).

Retries also multiply across layers. The caller retries three times, Pega retries three times, the ESB retries three times, and one business event is up to twenty-seven calls at the core: a modest incident becomes a self-inflicted denial of service. The rule is that exactly one layer owns retrying for any failure class and every other layer fails fast and propagates.

The ownership is written down per integration: the retrying layer, the count, the backoff and what happens when it is exhausted. "Everything retries three times" is not a design.

The second problem a slow core causes is the one that makes it an outage for the whole application. Suppose a queue processor named CoreCalls has ten threads and each healthy call takes half a second: that is twenty calls a second. If the core stops answering and the read timeout is ten seconds, each thread now blocks ten seconds per call, throughput falls to one call a second, a ninety-five per cent loss, and the threads are not even doing useful work. The arithmetic of a one-hour outage at a steady twelve items a second is a backlog of about 39,600 items at recovery and a drain of around eighty minutes at the surplus rate.

Queue processor "CoreCalls": 10 threads. Healthy: avg call 0.5 s => 10 / 0.5 = 20 calls/s = 1,200 calls/min Core goes down; read timeout 10 s: each thread blocks 10 s per call => 10 / 10 = 1 call/s = 60 calls/min (95 percent throughput loss) assume steady arrival of 12 items/s (720/min): during a 60 min outage ~43,200 items arrive and ~3,600 are attempted backlog at recovery ~ 39,600 items; surplus capacity after recovery = 20 - 12 = 8/s drain time = 39,600 / 8 = 4,950 s ~ 82 min (and the threads were also wasted on 10 s timeouts the whole time)

Two mechanisms address that, and neither is a Pega built-in. A circuit breaker stops calling a downstream system that is known to be failing, so callers fail fast instead of waiting on timeouts and the struggling system gets room to recover. It has three states: closed (calls pass and failures are counted in a rolling window; it opens when the failure rate crosses a threshold, for example half of at least twenty calls in sixty seconds, or five in a row), open (calls fail immediately with a "downstream unavailable" outcome and no remote call is made, until a cool-down such as thirty seconds), and half-open (one to three probe calls are allowed; success closes it, failure reopens it with a longer cool-down). Pega has no built-in circuit breaker for connectors; it is something the team builds. State is kept in shared storage (a database row or a Dynamic System Setting-style flag per downstream such as CORE_BREAKER = OPEN until 10:42:30) because it must be shared across nodes, and a node-scope data page alone would let the nodes disagree. A wrapper checks the flag before any call and returns the unavailable outcome immediately if it is open, so cases queue for later and screens show a banner; a small health-probe job calls a cheap health endpoint during the cool-down and flips the flag back; the same flag drives a UI banner and an operations alert. If the ESB or an API gateway already provides a breaker, prefer it and use Pega's flag only to react to its signal.

A bulkhead isolates resources per downstream or per workload, named for the compartments that stop one flooded section sinking a ship, so that one failing dependency cannot exhaust shared capacity. In Pega that means separate queue processors per downstream (core calls, sanctions screening, the notification gateway), each with its own thread count and, in a larger deployment, its own node type; separate service packages and access groups with rate limits at the gateway for noisy callers; background work on dedicated nodes that never share web nodes' thread pools; separate connection pool sizing for heavy integration tables where the deployment allows; and separate queues per priority class, so payment exceptions with legal deadlines do not queue behind low-priority notifications.

WITHOUT BULKHEAD: one QP "AllCalls" (20 threads) -> sanctions API slow (30 s) -> all 20 threads stuck -> core calls starve, SLAs breach WITH BULKHEAD: QP "CoreCalls" (10 threads), QP "Screening" (6 threads), QP "Notify" (4 threads) sanctions slow => only "Screening" saturates; core posting continues; alert on Screening queue depth only

What the application does while a dependency is unavailable is decided in advance, per integration, because the right answer differs by data and by operation. A balance shown for display may show the last known value with an "as of" timestamp, flagged stale, with actions that depend on an exact balance disabled; that is not acceptable for a closure disbursement amount. A customer profile fetch may serve a recent cached profile, or allow case creation with minimal data to be enriched later, but no decision should rest on a stale risk rating without a flag. Sanctions screening unavailable means do not auto-approve: the case moves to a screening-pending status, fulfilment is blocked, the call retries, and a supervisor is told if it persists. A core hold or closure post that is unavailable is accepted, queued with its idempotency key and shown as "Pending core", never reported to the customer as done until confirmed, with the SLA treatment agreed with Compliance in advance. A correspondence gateway that is unavailable queues and retries, with an alternate channel for critical notices. A reference-data service that is down uses the last cached copy. The principle to state aloud is: availability features (showing a cached balance) may fail open; control features (sanctions, authorisation, maker-checker) fail closed.

Failure two: the core says no

The core answers quickly and refuses: the account is already closed, or the amount exceeds the available balance. Nothing is wrong with the connection, and retrying would simply be refused again, five times, wasting capacity and delaying the person who has to fix the cause. A refusal is a business outcome: it routes to an assignment with a clear reason ("fix and resubmit"), and it is never retried. Status codes that mean "your request is wrong" (400, 401 after a single refresh, 403, 404, 405, 415, 422) are client faults and defects to fix and replay; they alert, and they are not retried. A malformed or contract-violating response (a 2xx with an invalid body, a missing mandatory field, an unknown enumeration) is quarantined and alerted, not passed inward. 5.10 turns this into a classification the mapping layer applies once.

One status needs particular care, because it is tempting to treat it as good news. Suppose Pega sends the hold with an idempotency key and receives 409 Conflict. The shortcut reasoning is "the key was already used, so the original worked". That is unsafe: a 409 means the server refused because of a conflict, and it does not say what the conflicting thing was or how it ended.

What a 409 might actually meanCorrect conclusion

Failure three: the core says yes, and the answer is lost

Now the hard one. Pega posts the hold; the core places it successfully; the response is lost to a timeout, a connection reset or a pod restart. Pega holds no information. This is not a failure and it is not a success: it is an unknown, and it is the most important state in financial integration because both obvious reactions are expensive.

Both naive responses are wrong. Retrying blindly can double-post the hold, restraining Dana's funds twice. Marking the call failed can lose a hold the core has already placed, so the disbursement proceeds against funds that were meant to be restrained. "Timeout means it failed" is the assumption that produces duplicate payments in production.

The need is for the second attempt to recognise the first operation instead of placing another hold. That property is called idempotency, and it works through an idempotency key: a unique identifier supplied by the caller for one logical operation, which lets the receiver recognise a repeat and return the original result instead of performing the operation again. Where the receiver honours it by contract, an unknown outcome becomes a safe retry; where it does not, a status lookup or reconciliation is needed.

TIMEOUT-UNKNOWN WITHOUT vs WITH IDEMPOTENCY WITHOUT: Pega POST hold(4218.55) -> core posts hold -> response lost / read timeout at Pega Pega retries -> core posts SECOND hold(4218.55) => customer funds restrained twice WITH: Pega POST hold(4218.55) key=AC-10882-HOLD-1 -> core posts hold, stores key -> response lost Pega retries same key -> core recognises key -> returns original result (holdRef) => one hold IF the downstream has NO idempotency support: before retry, perform a status check (GET holds for the account, look for key/reference); if found treat as success, else re-post. This "check-then-act" is weaker (race) but better than blind retry.

Three design points make a key work. It is deterministic for the business operation, such as case ID plus step plus sequence (AC-10882-HOLD-1), or a UUID generated once and stored on the case before the first attempt; never a new key per retry, which defeats the entire mechanism. It travels in a header (Idempotency-Key) or request field, and into the core's own duplicate-detection field if it has one. And the receiver stores the key with a fingerprint of the request and the response: the first time it processes and stores; a repeat with the same key and payload returns the stored response; the same key with a different payload is rejected as a conflict. The receiver remembers keys for longer than the maximum retry horizon plus replay windows, days and not minutes. When Pega is the receiver (a Service-REST), it checks a key table or a unique business key before creating, returns the existing case ID on a duplicate, and uses a unique constraint as the final guard. When Pega is the sender, the key is stored on the case or queue item before the call, reused on every retry, and reused by support for replays. Any idempotency store that Pega itself keeps is something the team builds.

When the contract does not guarantee idempotency, there are three routes to resolve an unknown outcome, in descending order of preference. A status lookup queries the core by the client-generated ID to find out what happened, which is best when the core exposes it, and is why every write carries a client-generated ID. A contractually safe retry resends with the same key relying on a documented guarantee that the core will not double-apply; it is only valid when the contract states that, and is not an assumption. Reconciliation parks the item in an unknown-outcome state and settles it against the core's end-of-day file, which is the backstop and needs a real queue and a real human process, not a log line.

The unknown outcome is modelled as its own case status, Unknown, not Failed, so it is visible, countable and alertable. An unknown-outcome queue with zero items is a healthy signal; the same items hidden inside a generic error bucket are a future audit finding. The status, the lookup and the reconciliation job are built by the team: Pega does not ship an unknown-outcome state.

Check your understanding.

Pega posts the hold for AC-10882 with key AC-10882-HOLD-1. The call times out. The ESB team's contract says nothing about idempotency, and the core exposes a "holds by account" query. What should the case do?

Answer. Set the status to Unknown, not Failed and not "retry". Then resolve it by status lookup: query the core's holds for CHK-8842-0117 and look for the reference or key. If a hold with that reference exists, record it as placed (success); if none exists, it is now safe to post again with the same key, with a small race that reconciliation covers. Blind retry is wrong because the contract does not promise the core will recognise the key; marking it failed is wrong because the hold may exist. If the lookup itself is unavailable, the item stays Unknown and reconciliation against the end-of-day file settles it. The answer depends on the lookup being authoritative; if the core's query lags its writes, the check-then-act can still miss a hold placed seconds ago, which is why reconciliation remains the backstop.

Accepting the request without waiting for the core

The three failures point to one structural conclusion: a hold on the closure path should not be a synchronous call inside the user's click. The case should record intent, and a separate process should deliver it with retries and a key. That raises a problem of its own. If the application saves the case and then calls the core, a failure between the two leaves the case saying "done" while the core was never updated; if it calls the core first and then saves, a failed save leaves the core updated and the case unaware. This is the dual-write problem. The standard answer is the outbox pattern: in one database transaction, update the case status to "Pending-Core" and insert the intent into an explicit outbox table, commit, and let a queue processor deliver the outbox item with retries and the key; on confirmation the status advances to "Core-Confirmed", and on exhaustion an operations assignment appears. Pega has no built-in outbox; the table and the delivery processor are something the team builds. Whether Queue-For-Processing itself commits in the same transaction as the case update is release-dependent and not assumed here: an experiment on the deployed system settles it (Chapter 06 §6.3 describes one). Throughout, no database transaction is held open across a remote call, because that holds locks and exhausts connection pools.

5.11 Proving who is calling: authentication profiles and services

Every call so far has quietly assumed the core accepts Pega's request. Why would it? The core must be sure the caller is the application it claims to be, and Pega must be sure of the same about whoever calls it. Pega separates the two directions with two records whose names are similar enough to be confused, and the confusion is a common slip. An Authentication Profile is outbound: it answers "how does Pega prove its identity when calling a remote system?", and connectors (Connect-REST, Connect-SOAP, Connect-HTTP and others) reference it. An Authentication Service is inbound: it answers "how does Pega verify who is calling or logging in?", and operator login (SAML, OIDC, LDAP, custom) and service-package authentication (token validation) use it. Profiles are for connectors going out; services are for people and callers coming in.

The outbound profile types range from legacy to preferred. Basic sends a username and password in the Authorization header, base64-encoded and not encrypted, so it is only safe over TLS and should be avoided for new bank integrations when something better exists. NTLM or Kerberos-style authentication serves internal Windows services only. OAuth 2.0 (client credentials, authorization code, and others depending on release) has Pega obtain an access token from a token endpoint and attach it as a bearer token, with the profile storing the endpoint, client ID, secret and scopes and handling caching and refresh; it is the preferred choice for service-to-service access. An API key sent as a header or query parameter suits simple partner APIs and is a bearer secret that must be rotated and protected. A client certificate (mutual TLS, 5.14) is presented during the TLS handshake and is often combined with a token. Header-based custom schemes are a last resort. Which profile types and options exist varies by release, so confirm the OAuth grant types the target release supports before promising one.

Inbound, the service types are SAML 2.0 for browser single sign-on with an enterprise identity provider (5.13); OpenID Connect for browser login and token-based access on top of OAuth 2.0; OAuth 2.0 token validation for services, in which a service package validates bearer tokens from the bank's authorisation server, by introspection or by validating a signed JWT against the issuer's published keys; LDAP or Active Directory against a directory (older but still seen); and custom login logic, which is best avoided.

Secrets handling follows four rules. Credentials live in the authentication profile (encrypted by the platform) or an external secrets store it references, never in a data transform, activity, plain-text Dynamic System Setting or source control. Credentials differ per environment, and promotion packages must not carry production secrets down or lower-environment secrets up. Each integration gets a dedicated technical identity with least privilege, so a leaked credential has a narrow blast radius. And credentials are rotated on a schedule and on suspicion of compromise (5.14). The anti-patterns are hard-coded Basic credentials in a connector header, one service account used by development, QA and production, a client secret pasted into a ticket or chat, disabling certificate validation for convenience, and a service package with authentication switched off "temporarily".

5.12 OAuth 2.0 and JWT

The question that OAuth answers is how the core, or the ESB in front of it, can trust Pega without ever storing Pega's long-lived password. Before OAuth, a client stored the password and sent it on every call: a leaked password gave full access indefinitely, could not be limited to one function, and could not be revoked without changing it everywhere. OAuth 2.0 is a framework for delegated authorisation: a client obtains a short-lived access token from an authorisation server and presents it to a resource server (an API). The resource server trusts the token because the authorisation server issued it, so access can be scoped, short-lived and revocable, and one place can enforce policy and audit.

The roles map directly onto Riverbend. The resource owner is the bank (for machine access) or a customer (for user-delegated flows). The client is Pega calling the ESB, or the digital portal calling Pega's DX API. The authorisation server is the bank's identity platform. The resource server is the ESB or API gateway, or Pega itself as a Service-REST host. The grant types say how the token is obtained.

When a human is involved, the flow is authorization code with PKCE. The client generates a random code_verifier and its hashed code_challenge, redirects the browser to the authorisation endpoint with a state, the user authenticates (password and multi-factor) and consents, the browser delivers a one-time code to the client, and the client exchanges code and verifier at the token endpoint over the back channel, receiving access, ID and refresh tokens; it then validates the ID token's signature, issuer, audience, nonce and expiry before creating a session.

A JSON Web Token is three base64url-encoded parts joined by dots: header, payload, signature. An access token is often a JWT so the resource server can validate it locally without calling the authorisation server on every request. The header names the signing algorithm and the key ID (kid) used to select the public key. The payload carries claims: issuer (iss), subject (sub), audience (aud), expiry, issued-at and not-before times, scope, a unique token ID (jti) and the client ID. The signature is an RSA signature over the first two parts made with the issuer's private key and checked with its public key.

A JSON Web Key Set (JWKS) is a JSON document the authorisation server publishes at a well-known URL listing its current public keys, each with a kid. Resource servers fetch and cache it and select the key by kid, which enables key rotation without redeploying consumers: the issuer adds a key, starts signing with it and later retires the old one, and consumers refresh the set when they see an unknown kid. Scopes describe permitted operations (accounts.read, accounts.holds.write) and should be narrow, so a reporting integration cannot place holds; the profile requests the minimum.

Token lifetime and caching are where operational problems start. Service access tokens are short, typically five to fifteen minutes, set by the authorisation server. The Authentication Profile handles acquisition and caching, so a token is not fetched per call (which doubles latency and can trip the authorisation server's rate limit). Each node may hold its own cached token, which is fine for client credentials but worth watching when many nodes and processors start together after a restart. Revocation relies on short lifetimes, introspection or a deny list. Refresh tokens are stored encrypted, bound to the client, rotated on use and never logged. Clocks are synchronised with NTP and validation tolerates thirty to sixty seconds of skew.

When the ESB or a portal calls a Pega Service-REST, Pega is the resource server: the service package uses an OAuth-style authentication service that validates the bearer token (signature, issuer, audience, expiry), maps the token's client or subject to an operator or service access group, and runs the service as that identity; scope claims can be mapped to roles or checked in the service logic. Configuration screens differ by release. The anti-patterns are long-lived access tokens, requesting every scope, one client ID shared by all integrations, logging tokens, accepting tokens without audience checks, fetching a token per request, retrying a 401 forever and ignoring clock skew.

5.13 SAML 2.0 and single sign-on

Marcus and Priya should not have a separate password for Pega. SAML 2.0 lets a user sign in once with an Identity Provider (IdP), and access many applications, called Service Providers (SP), without a password for each. The IdP sends the SP a digitally signed XML assertion that says who the user is and optionally attributes such as groups and email; the SP trusts it because it trusts the IdP's signing certificate. The reasons a bank wants this are central control: one identity to disable so access ends everywhere, multi-factor enforced once at the IdP, and a single audit trail.

The vocabulary is small. The IdP authenticates the user; Pega is the SP. Metadata is XML describing an entity (entity ID, endpoints, signing and encryption certificates), exchanged at setup. The ACS URL is the SP endpoint that receives the assertion. The assertion is the signed statement, whose NameID identifies the subject and whose attribute statement carries groups and other data. RelayState carries the original destination URL through the login round trip, and a binding says how messages travel (assertions normally arrive by HTTP POST through the browser).

The flow that matters is SP-initiated. The user goes to Pega, which has no session; the authentication service of type SAML 2.0 builds an AuthnRequest (an ID, the SP entity ID, the ACS URL) with the original URL as RelayState and redirects the browser to the IdP. The IdP authenticates the user, with multi-factor, or reuses its own session, and builds a signed response and assertion with attributes, audience and expiry, which the browser POSTs to Pega's ACS URL. Pega validates the signature against the IdP certificate from metadata, the issuer, the audience (which must equal its SP entity ID), the destination and recipient (which must equal the ACS URL), InResponseTo (which must equal the request ID), the validity window with clock skew, and that it has not been replayed. It then maps attributes: the identifier attribute to an operator ID and groups to an access group, creating the operator on the fly if provisioning is enabled and rejecting the login otherwise. It creates the session, applies the access group and redirects to the original URL.

IdP-initiated sign-on, where the user clicks a tile in the IdP dashboard and the IdP posts an unsolicited assertion, has no request to correlate, so there is no InResponseTo: it is weaker, deep links are lost, and many banks disable it or add extra validation. Signing is mandatory in practice, for integrity and authenticity. Encryption is optional but common in banks, protecting the assertion's contents with the SP's public certificate, with the private key held in Pega's keystore. Neither replaces TLS on every hop.

A Pega SAML authentication service is configured by importing the IdP's metadata, setting the SP entity ID and ACS URL (Pega can generate SP metadata for the identity team), placing signing and decryption keys in the keystore and the IdP certificate in the truststore, mapping assertion attributes to operator properties and choosing the operator identifier, optionally enabling just-in-time provisioning, deriving the access group from the groups attribute through a mapping table or transform so role changes in the IdP apply at the next login, and setting session timeout, logout behaviour and clock-skew tolerance.

Just-in-time provisioning creates, and optionally updates, the operator record at login from the assertion's attributes instead of pre-creating every operator. It removes a manual onboarding step and keeps role assignment driven by central groups. Its controls are what make it safe: provision only when the groups attribute maps to a known access group; default to no access if no group matches; update the access group on every login so removals take effect; never let a user-supplied attribute choose an arbitrary access group; and log provisioning events. Deprovisioning happens in the IdP and blocks new logins, but an existing Pega session lasts until its timeout, so timeouts are kept short and a periodic operator-status sync can help.

5.14 mTLS, keystores, SFTP keys, secrets and rotation

Authentication with a token proves identity at the application layer. Beneath it, TLS encrypts traffic and lets the client verify the server through its certificate, and mutual TLS adds the reverse: the server also demands a client certificate and verifies it, so only callers holding a trusted certificate can even open a connection. Banks use it for internal service-to-service and partner links, often together with an OAuth token as two independent controls.

mTLS HANDSHAKE (simplified) Pega (client) ESB (server) | 1 ClientHello ------------------------------------------>| | <-- 2 ServerHello + server certificate + CertificateRequest| | 3 verify server cert chain against Pega TRUSTSTORE (CA) and host name | 4 send client certificate (from Pega KEYSTORE) + proof of private key (CertificateVerify) -->| | 5 ESB verifies client cert chain against ITS truststore; maps subject to identity | <-- 6 Finished; encrypted channel established ---------------| | 7 HTTP request (plus bearer token if required) over the channel

Two stores recur. A keystore holds your own private keys and certificates, the identity you present: the mTLS client certificate, the SAML signing and decryption key, a JWT signing key. A truststore holds the certificates, usually of certificate authorities, that you trust when verifying others. A certificate chain (leaf, intermediate, root) must be imported in full, since missing intermediates are a frequent cause of handshake failures; the common name or subject alternative name must match the endpoint's DNS name, not an IP; and certificates expire, often within a year, so an inventory with alerts at sixty and thirty days is kept, because certificate expiry is one of the most common avoidable production outages. Where keystores live differs by deployment (client-managed or Pega Cloud), so follow the platform team's standard.

File exchange (Chapter 07) uses SSH keys rather than passwords for SFTP. Pega as the client holds the private key; the server holds the matching public key in the account's authorised keys; and Pega also verifies the server's host key against a known-hosts entry to prevent interception, which is never disabled. Practice: modern key types and sizes (RSA 3072 or 4096, or Ed25519 where supported); the private key in the platform's secure keystore under a passphrase, never in a rule, repository or readable share; one identity per partner and environment, to limit the blast radius and allow independent rotation; the host key pinned and updated through a controlled process; and least-privilege directory permissions.

Rotation has to be designed so that nothing drops. A client secret (ninety days or per policy) rotates with an overlap, the authorisation server accepting old and new for a window, the profile updated in each environment during it, and the old one revoked after verification. A client certificate rotates by adding the new one to the server's truststore beside the old, switching Pega's keystore entry, verifying and removing the old. An IdP signing certificate is published in metadata ahead of the switch so the SP accepts both during overlap. An SFTP key is added beside the old, switched and removed. The issuer's JWKS keys need no consumer change if validation is by kid and the JWKS refreshes on an unknown kid. A client-secret rotation as a runbook: calendar reminder and change ticket two weeks ahead, confirming dual-secret support; the new secret generated and tested in lower environments a week ahead; on the day the new secret added to the production profile with the old left valid and the 401 rate watched; a day later all nodes and processors confirmed on the new secret (the token cache refreshes on expiry); two days later the old secret revoked and 401 alerts watched for a day, with evidence documented; and a rollback of re-enabling the old secret while it is still valid.

5.16 Interview Q&A

Q1. Walk me through building a Connect-REST integration.

"I start with the data model and the contract: integration classes for request and response, the canonical classes they map to, and the OpenAPI or sample payloads, status codes, authentication and timeouts from the ESB team. Then the authentication profile, then the connector, through the accelerator or manually. The endpoint host comes from environment configuration, with the resource path, the method, and headers including a correlation ID and, for writes, an idempotency key. Request and response mapping are data transforms between the canonical page and the integration class, with expected business statuses mapped explicitly. I set connect and read timeouts and classify errors. Finally I add simulation and PegaUnit cases for each mapping transform and test against the real endpoint in a lower environment with Tracer."

Q2. What do you ask the ESB team before building?

"Who owns retries, because retrying in both layers multiplies calls; idempotency key support and retention; which operations are synchronous and which asynchronous with callback; throttling limits and how a 429 is signalled; the ESB's backend timeout, which must be shorter than my read timeout; the error contract; correlation ID propagation; ordering guarantees; maintenance windows; versioning; and whether support can see message status by correlation ID. I write it as a one-page integration contract per operation."

Q3. The core is down for four hours. What happens?

"Reads fall back to cached values with an as-of timestamp where the business allows. Writes are accepted and queued with an idempotency key through a bulkheaded queue processor. A circuit breaker, which I would build because Pega does not provide one for connectors, stops threads wasting time on timeouts, and a probe closes it. Cases show pending core. Sanctions screening fails closed. On recovery we drain at a throttled rate within the ESB's limit, duplicates are prevented only where the core honours the keys by contract, exhausted items land in a human queue, and we reconcile Pega against the core by counts and keys."

Q4. A write to the core times out. What do you do?

"It is an unknown outcome, not a failure and not a transient to retry. I set the case to Unknown. I resolve it by status lookup using the client-generated ID, or by a retry with the same idempotency key if the contract guarantees the core will not double-apply, or by reconciliation against the end-of-day file as the backstop. Retrying blindly can double-post and marking it failed can lose a payment. A timeout on a read, by contrast, is safely retryable."

Q5. You send an idempotency key and get a 409. Is that success?

"Not by itself. A 409 says there was a conflict, not what it was. It might be the original succeeding, the original failing or still in flight, a different payload under the same key, or an unrelated business-state conflict. I check what the contract defines for 409 on that endpoint, confirm the payload matches, and look up the original outcome. A different payload is a defect and alerts. If the contract does not define 409 for replayed keys, it is an error, not a receipt."

Q6. Where do you put the retry, and what do you retry?

"Exactly one layer owns retrying for each failure class, written down per integration with the count, backoff and exhaustion behaviour, because three layers each retrying three times is up to twenty-seven calls. I retry transient failures where the request was never sent or was refused, and reads, with exponential backoff and jitter, bounded by attempts and an overall deadline, honouring Retry-After, implemented by re-queueing with a delay and not sleeping. I never retry 400, 403, 404, 409, 422 or business faults, I refresh a token once on 401, and a timeout on a write is an unknown outcome, not a retry."

Q7. What is a circuit breaker and what does Pega give you?

"It stops calling a failing dependency: closed, open after a failure-rate threshold, half-open to probe. Pega gives me timeouts, error handling, queue processor retries and delayed queueing, but no built-in breaker for connectors. I would implement the pattern with a shared health flag checked before calls and a probe job, or rely on the ESB or gateway's breaker and react to its signal. The reason is thread economics: ten threads with ten-second timeouts lose about ninety-five per cent of their throughput during an outage."

Q8. How do you avoid the dual-write problem?

"I do not save the case and call the remote system as two independent steps. In one transaction I update the case status to pending and write an explicit outbox row, commit, and a queue processor delivers it with an idempotency key and retries. On confirmation the status advances. Pega has no built-in outbox, and I would not assume Queue-For-Processing is transactional with the case save on a given release; I would test it. I never hold a database transaction open across a remote call."

Q9. Staging then MERGE: can the bulk load not fail?

"It can. Staging avoids row-by-row Pega round trips and defers application-level rule evaluation, but a bulk load can still fail on NOT NULL, CHECK, unique, foreign key, type and length conversion, encoding and malformed input, and it can fail partially, so I state the loader's error-handling mode. Business rules are moved, into MERGE conditions or a validation pass over staging, and what they reject needs a reject table, a count and an owner. I de-duplicate staging by key first, because duplicate source keys break a MERGE, and I use bind parameters for values and an allow-list for identifiers."

Q10. OAuth client credentials, and how Pega validates inbound tokens?

"For machine integration Pega obtains a short-lived token from the token endpoint with its client ID and secret, certificate or signed assertion, with a narrow scope, caches it until shortly before expiry and attaches it as a bearer token; on 401 it refreshes once and retries once, then alerts. Inbound, the service package validates the signature against the issuer's keys, plus issuer, audience, expiry and scope, maps the client to a least-privilege access group, and runs the call under it. I ask who owns key rotation and whether the resource server pulls the JWKS, because that decides whether rotation is invisible or an outage."

Q11. How does SAML login work and what breaks it?

"Pega, as the service provider, builds an AuthnRequest and redirects the browser to the IdP, which authenticates the user and posts a signed assertion to Pega's ACS URL. Pega validates the signature, issuer, audience, destination, InResponseTo and timestamps, maps attributes to an operator and groups to an access group, creates the session and redirects to the original URL. What breaks it is certificate rotation, audience or destination mismatch behind a proxy, clock skew and missing group attributes, and I find the cause by decoding the assertion and comparing it with what Pega expects. IdP configuration belongs to the identity team."

5.Z Where we are now

What the application can do

Pega can read Dana's account from the core through an ESB with the right credentials, map it to a canonical page, change her address and place a hold for AC-10882 without double-posting, survive a slow or refusing core, and treat an unknown outcome as its own visible state. It can also take inbound calls securely, load many message types through one metadata-driven MERGE, and log every call under one correlation ID.

The mechanisms behind it

Connectors and services, a canonical model with mapping, an ordered build, explicit timeouts, backoff with jitter, one owner for retries, a breaker and bulkheads that Pega does not supply, idempotency keys with status lookup and reconciliation, an outbox for the dual write, a classification of errors that agrees with those rules, and token, SAML and certificate authentication with planned rotation.

What it still cannot do

Everything so far is the application asking the core for something. Balances are still up to a day old between batch runs, because nothing pushes changes to Pega when the core's data moves. Receiving a stream of those changes, one event at a time and in order, is Chapter 06.
