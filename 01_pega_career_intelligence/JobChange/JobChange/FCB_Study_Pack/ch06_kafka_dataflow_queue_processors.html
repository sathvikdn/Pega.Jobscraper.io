6.1 One event on a log: Kafka fundamentals through EVT-55121

At 09:40 on Monday 9 March 2026 the $200.00 merchant authorisation on CHK-8842-0117 settles, and the core's ledger balance falls from $4,418.55 to $4,218.55. Riverbend wants Pega to know within seconds, so the core publishes an event. This one is EVT-55121, sequence 882 for that account, carrying the account's new balances, onto the topic rb.deposits.account.balance.v1. Understanding where that event goes next needs a handful of precise terms.

Apache Kafka is a distributed, durable, append-only log. Producers write records to named logs called topics; consumers read at their own pace and remember where they were. Unlike a traditional queue, a record is not removed when it is read; it stays for a configured retention period, so many independent consumers can read the same data and a consumer can go back and read again. That is why banks put account events on it: traditional integration was either point-to-point calls (tightly coupled, failing together) or nightly batch files (stale by up to a day, all-or-nothing), whereas Kafka decouples producers from consumers in time and availability. The producer writes once and carries on, consumers process when they can, a consumer outage means lag and not data loss, and a new consumer added later can replay history.

It is worth placing Kafka against its neighbours, because interviewers do. After consumption a Kafka record stays until retention expires, whereas a JMS-style queue removes it on acknowledge and a database queue table updates or deletes the row. Several independent consumers are native in Kafka and awkward in the others. Replay is an offset reset in Kafka, generally impossible with a queue and possible with a table only if rows were kept. Ordering is per partition in Kafka. Throughput is very high because of sequential I/O and batching. What Kafka lacks is rich routing, per-message priority and delay, which queues and tables provide. The matching failure modes are treating Kafka as a database for queries, one giant topic for unrelated events, assuming global ordering across a topic, consuming without monitoring lag, storing megabyte payloads in events instead of references, and trusting default retention without checking that it covers the worst outage plus a replay window.

6.2 Why the key is the account number: partitioning and ordering

The producer chose partition 3 for EVT-55121 because of the key. Kafka guarantees order only within a single partition. Records with the same key go to the same partition (with the default partitioner, so long as the partition count does not change), so all events for one key are ordered relative to each other. There is no ordering guarantee across partitions, and so none across the topic as a whole: a consumer reading partitions 0, 1 and 2 may see an event from partition 2 that was produced earlier or later than one from partition 0, in any order.

That shapes the key choice for deposits. Events for one account must be applied in order (open, deposit, hold placed, hold released, close), so the account number is the key, putting every event for that account in one partition and one consumer thread. Events for different accounts have no ordering relationship and run in parallel on different partitions, which is where scale comes from. A transfer between two accounts has no ordering across them, so the event carries both sides or processing is made commutative and idempotent, never assuming the debit is seen before the credit. A key that is too coarse, such as a market code, creates hot partitions in which one market's volume lands on one consumer and parallelism collapses. A random or absent key spreads the load evenly but gives up per-account ordering, so two events for one account can be reordered.

Account number is the right key because it is the natural unit of consistency (balances, holds and status belong to one account and must apply in order), it has high cardinality so volume spreads evenly, and it lets a consumer keep per-account state without cross-partition coordination. A very hot account, such as a corporate sweep account with millions of events, is still a hot key; the response is to monitor partition skew and, if needed, move that event type to its own topic.

The partition count is a decision to make early. Consumers beyond the partition count sit idle, so the count caps parallelism: plan for peak throughput divided by per-consumer throughput, plus headroom. Adding partitions later changes hash(key) mod N, so new events for a key can land in a different partition from old ones, breaking per-key ordering across the change; choose a count with growth headroom and coordinate any increase with a drain. Too many partitions bring more open files, replication traffic, longer rebalances and leader elections. And skew is watched through per-partition lag and rate, because one hot partition dominates total time.

ORDERING SCENARIO: account events E1 deposit +500 E2 hold 300 E3 hold released E4 withdrawal -200 GOOD (key = account number): all four land in one partition in produce order -> one consumer processes E1,E2,E3,E4 in order. BAD (no key / random): E1->P2, E2->P0, E3->P2, E4->P1 -> parallel consumers may apply E3 before E2: "release a hold that does not exist yet" -> error or silently lost release. One caveat has to be carried through the rest of the chapter. Kafka orders per partition, but once Pega pulls records into a data flow and queues them to a queue processor, independent threads can reorder work after Kafka (6.3 returns to this), and the partition-to-thread behaviour inside Pega is release-dependent, so strict ordering is never promised on the strength of the key alone.

6.3 Delivered twice, late, or while the consumer crashes pattern

A consumer reads EVT-55121, updates the account's balance row in Pega's database, and the process dies before it tells Kafka it finished. On restart Kafka, which has no record that the event was handled, delivers it again. Nothing has malfunctioned; this is the delivery guarantee working as designed. The three possible guarantees explain why, and why banks choose the one that produces this behaviour.

At-most-once loses money events: a lost "hold released" or "payment returned" is a customer-impact and reconciliation incident, and a bank cannot accept silent loss. True exactly-once is not generally available once a side effect leaves Kafka (a database write, a REST call to the core), and a claim of exactly-once for external effects hides an idempotency mechanism somewhere. At-least-once is simple, cheap and robust, with duplicates a known and bounded problem, and making consumers idempotent is a discipline needed anyway for retries and replays, which then become safe. So the design is at-least-once delivery with idempotent processing.

The word "idempotent" has been used loosely in event-driven designs, and three different things hide inside it. A design that solves one and assumes the other two came free is the usual source of defects.

The sentence that captures it: de-duplication stops the same event being processed twice, idempotent state changes make it harmless if it is, and a safe business operation means the outcome is correct even so. All three are designed for, because event-ID de-duplication alone fails the moment a retry arrives after the de-duplication record has aged out.

The crash, and where the duplicate must be caught

Back to the crash. For the redelivered EVT-55121 to be harmless, recording "I have seen this event" and applying its effect must happen in the same transaction. Split them and the bug appears in one direction or the other.

OrderCrash in the gapResult
Record the event ID, commit; then apply the effectAfter the first commitLost update. The retry sees the ID, concludes "already processed" and skips. The effect never happens, silently
Apply the effect, commit; then record the event IDAfter the first commitDuplicate. The retry does not see the ID and applies the effect again
Both in one transactionAnywhereCorrect. Either both happened or neither did; the retry is clean

When the effect is a local database write, this is easy: one transaction inserts the event ID and the business row together, and the unique constraint on event ID is the de-duplication. When the effect is a remote call it is impossible, and the design falls back to an idempotency key the remote side honours plus reconciliation (Chapter 05 §5.9). Knowing which of the two situations one is in is the whole design. Kafka's own transactions do not change this: they give atomicity within Kafka, across writes to topics and partitions and the consumer offset commit, but a row in the database or a REST call to the core is outside that transaction, and there is no two-phase commit between Kafka and the core.

The same constraint answers a second scenario: the same event arriving twice at the same instant on two nodes. Both check "have I seen this event ID?", both see no, both proceed. A read-then-write check cannot fix this however carefully it is written; the window between the read and the write is the bug. The fix is a unique constraint on the event ID so that the database arbitrates: one transaction commits and the other receives a constraint violation, which it treats as a duplicate. In Pega, the case lock does the same job when the work is keyed to a case.

The event arrives late: what shape it has decides what is legal

Now suppose EVT-55120 (sequence 881), the snapshot from before the settlement, reaches the consumer after EVT-55121 (882). Applied naively, it would overwrite the new balance with the old one. The obvious guard is "apply only if the sequence is newer than what I have", and whether that guard is correct depends entirely on what kind of event is on the topic.

Event shapePayloadSafe to drop a stale one?Correct guard
Full-state snapshotThe entire current state of the entityYes. A newer snapshot fully supersedes an older oneLatest-wins on source sequence. Dropping the older event loses nothing
Partial updateOnly the fields that changedNo, not per entity. Only per fieldPer-field version or sequence, or merge semantics. A row-level latest-wins silently discards a different field's valid update
Transactional / delta eventA change to apply, not a state to assume (a $50 debit)Never. Every event is independently meaningfulDe-duplicate by event ID and apply all survivors. Latest-wins here destroys money

For the balance topic, whose events are full snapshots, discarding the late 881 is exactly right. The same guard applied to a topic of payment deltas is the most dangerous single line in event-driven banking: two debits of $50 and $30 on one account in the same second are both valid, and a latest-wins guard keeps one and silently drops the other, so the ledger is wrong by $50 with no error anywhere. Before writing a latest-wins guard, say aloud which of the three shapes the topic carries; if a topic mixes shapes, that is the defect.

The partial-update case is the quiet one. Sequence 5 changes an address and sequence 6 changes a phone number; they arrive as 6 then 5. A row-level guard rejects 5 because 5 is less than 6, and the address change is lost, though the two events never conflicted and nothing reports it. The options are per-field sequence tracking, publishing full-state snapshots instead of partial updates (usually the right answer), or merging non-overlapping fields and applying latest-wins per field.

The ordering metadata itself needs care. A timestamp is a poor ordering key because the producer's clock is authoritative for nothing: two producers, or one after a time correction, can emit a "newer" event with an older timestamp, and millisecond resolution collides under load so that > drops a valid event and >= reapplies one. The remedy is a source sequence number, issued by the system of record and monotonic per key, with the timestamp kept as diagnostic. A gap (sequence 7 arrives when 5 was the last applied) must be decided explicitly, by parking with a timeout or applying and flagging, never silently accepted. A late arrival is discarded for snapshots; for deltas it must still be applied, which means the state model tolerates out-of-order arithmetic or the event goes to a repair queue.

And there is a place where ordering is lost that the key does not protect. Kafka's guarantee stops at the data flow: the partition is read in order, but once the data flow queues work to a queue processor, independent threads execute the items and can commit them in either order.

Kafka partition (ordered) -> Data Flow reads in order -> OK so far | v Queue-For-Processing / queue items | +------------------+------------------+ v v v QP thread 1 QP thread 2 QP thread 3 <-- INDEPENDENT execution | | | +------------------+------------------+ v ORDER IS NOW LOST

So "I keyed by account number, therefore ordering is safe" is incomplete: the key puts the events in one partition in order and does nothing about what happens after dispatch. If strict per-account order must survive, one of three things is needed: processing inline in the data flow without re-queueing; a per-key lock so only one thread handles an account at a time (Pega's case lock gives this when the key is the case); or, usually, a consumer designed not to need order, using the sequence guard for snapshots.

Check your understanding.

A payment topic carries $50 and $30 debit events for one account, keyed by account number, and a developer adds the sequence guard "apply only if newer" that works well on the balance topic. What goes wrong, and what is the right design?

Answer. Each debit is a delta, independently meaningful, so dropping a "stale" one loses money: if the $30 arrives before the $50 the guard discards the $50 with no error. The right design de-duplicates by event ID in the same transaction as the effect and applies every survivor, with the state model tolerating arithmetic applied out of order (or a repair queue for what cannot be). This assumes the debits can be applied in any order; if a business rule depends on order (an overdraft check), the topic needs per-account serialisation, which Chapter 11's locking material provides.

The core succeeds and the response is lost, again

When the consumer's effect is a call to the core rather than a database write, the crash scenario changes character. Pega posts a debit; the core applies it; the gateway times out. This is Chapter 05's unknown outcome, and the same resolution applies: move to Unknown and resolve by status lookup on the correlation ID, a contractually safe retry, or reconciliation against the core's end-of-day file. "Retry with the idempotency key" is the wrong answer unless the contract also guarantees de-duplication for that endpoint.

The replay that arrives after newer events

Support replays yesterday's events at 14:00 to recover a gap, and account CHK-8842-0117 has already received today's. What happens depends on shape again. For snapshots the sequence guard discards the stale replay, which is safe. For deltas the replayed debit is a real debit, event-ID de-duplication is the only thing between the replay and double-posting, and if the de-duplication window has aged out the effect is applied again. Therefore the de-duplication retention must be at least as long as the replay window, and replay is scoped by key and time range, not "replay the topic". The replay mechanism, a scoped endpoint with its audit, is something a team builds (6.11).

Is Queue-For-Processing a transactional outbox?

A transactional outbox requires that the queued item commit in the same database transaction as the business write. Whether Pega's Queue-For-Processing does that, rather than committing independently, is release- and configuration-dependent and is not asserted here. It matters enormously: if the queue write commits separately, there is a dual write, and either the business row or the queue item can survive alone. The question is settled on the deployed version with a ten-minute experiment in a lower environment: run an activity that performs a business write, then Queue-For-Processing, then deliberately throws before any explicit commit, and inspect whether the queue item exists; repeat with the rollback after the commit point. The reason for hedging here, unlike a regulatory figure that has a citation, is that the answer genuinely cannot be known without the deployed system, which is why the experiment is supplied. If the item survives, the outbox has to be an explicit table written in the same transaction as the business change, with a separate dispatcher; Pega does not provide that as a built-in.

On the producer side, acks chooses how many replicas must acknowledge a write (all of them, with a minimum in-sync count of at least two on a replication factor of three, is the banking choice); the idempotent producer setting makes the broker de-duplicate producer retries so a retry does not create a duplicate record; retries and the delivery timeout are generous but bounded; and transactions suit Kafka-to-Kafka processing and are not a substitute for idempotent external effects. On the consumer side, auto-commit commits offsets on a timer regardless of processing success and risks at-most-once behaviour, so commit after successful processing; the maximum poll interval is the time between polls before the broker considers the consumer dead and rebalances, so a batch that takes longer than it gets the consumer evicted, causing rebalance storms and duplicates; the auto offset reset decides what happens with no committed offset, and latest skips history while earliest replays everything, so it is chosen deliberately for a new group; and the isolation level should be read-committed when producers use transactions.

These are Kafka's settings, and in Pega one of the most useful operational facts about them is that the usual playbook does not apply. The standard Kafka answer to "we need to reprocess" is to reset the consumer group's offset and let the consumer read again. Pega's documentation states why that does not work: the consumer group in the Kafka Data Set is used only for monitoring purposes, to track the offset and the lag for each partition; assigning partitions to consumers is still done by a data flow, and the data flow also tracks the current offsets and controls which messages are processed next. In its words, it is not possible to make the data flow reprocess or skip messages by manually changing offsets on the consumer group, because consumers are not being subscribed to consumer groups. When a Kafka dataset is the source of a data flow, the group name that appears in Kafka is the configured prefix followed by the data flow run ID, which is why lag is read against that name and why it changes with each run.

The consequence is the reason a replay mechanism has to be built rather than operated. If resetting offsets cannot reprocess history, then recovering from a gap, a bad mapping fixed after the fact, or a dead-lettered batch needs something the team creates: a dead-letter store that preserved the payloads, and a scoped, audited replay path that re-injects them (6.11). Two related facts from the same documentation help with planning. A Kafka dataset can be migrated to a new Kafka cluster while preserving consumer offsets, so a cluster move does not by itself force a reprocessing. And version alignment is a release matter: Pega Platform '26 moves to the Apache Kafka client 4.x line, which is not fully compatible with older brokers, so client and broker versions are aligned before an upgrade. Which other Kafka settings are surfaced in Pega, and their labels, depend on the release, so the design discipline is to configure the group naming, the starting position and the resilience settings, and to make the downstream processing idempotent so redelivery is safe.

Each of these claims is testable, and the tests are the same list: publish the same event ID twice and kill the node between the effect and the offset commit, then assert row counts and balances are unchanged; fire the same event from two threads at once and assert exactly one effect; deliver a snapshot pair and a two-field partial-update pair in reverse and two deltas with equal timestamps and assert the newest state, both fields, and both deltas respectively; add an optional field to a topic and then remove a required one, and assert the compatible change flows while the breaking one is rejected to the dead-letter path with its payload preserved; run a poison item, then an outage, then a replay scoped by key and time range; and load-test at production-like volume and target-table size against criteria agreed first.

6.4 A backlog behind the event: consumer groups, lag, retention and compaction

The settlement event is one of thousands. At 09:41 the database behind Pega slows, the consumer falls behind the producers, and a growing line of unprocessed events builds up behind EVT-55121. This is where Kafka's group mechanics matter. Within a consumer group each partition goes to exactly one consumer: three consumers on six partitions get two each; eight consumers on six partitions leave two idle, because parallelism is capped by the partition count. A consumer that stops sending heartbeats is removed after the session timeout, the group rebalances, its partitions are reassigned and its uncommitted work is redelivered. A consumer that takes too long between polls is treated as failed, with the same effect, and its in-flight batch is processed again by another consumer, a duplicate. A new consumer joining triggers a rebalance. Two applications with different group IDs each receive everything; two instances accidentally sharing a group ID that should be separate each see only part of the data, a classic misconfiguration when development and production share a cluster.

REBALANCE STORM (what it looks like and why) consumers: pega-node-1, pega-node-2, pega-node-3 max.poll.interval = 5 min batch processing slows (downstream DB slow) -> node-2 does not poll within 5 min broker removes node-2 -> REBALANCE: partitions of node-2 -> node-1/node-3 (all pause briefly) node-2 comes back, re-joins -> REBALANCE again while rebalancing, nobody processes; in-flight batches are redone -> duplicates; lag climbs; processing slows further -> repeat FIX: shrink batch size or per-batch work, raise max.poll.interval deliberately, fix the slow dependency (the real cause), use cooperative rebalancing where available, avoid GC pauses/heap pressure on nodes

The primary health metric for all of this is consumer lag: for a partition, the log end offset minus the group's committed offset, the number of records written but not yet processed, summed across partitions. Lag in records is useful; lag converted to time, how old is the oldest unprocessed record, is what the business feels. Its shape diagnoses the cause: flat near zero is healthy; a sawtooth that rises and drains is bursts processed within tolerance, to be checked against the SLA; steadily rising on all partitions means consumers are slower than producers (a slow dependency, too few threads or nodes, database contention, a stopped data flow); rising on one partition only means skew or a stuck record (a hot key, a poison message retried forever, one slow node); flat but non-zero and not moving means the consumer stopped committing (the data flow crashed, the group ID changed, authentication failed); and a sudden fall to zero with nothing processed means offsets were reset to latest or retention deleted unconsumed data.

That last case is why retention must be sized against outages. Retention has to cover the longest tolerable consumer outage plus the time to detect and fix it plus the replay window. With seven days of retention, a consumer that is down from Friday 18:00 and noticed on Monday 09:00 (63 hours) loses nothing, and the lag drains once it is fixed. With 24 hours, Friday-night data starts expiring on Saturday evening and by Monday part of the weekend is gone. Time-based and size-based limits both apply, whichever is hit first, so a high-volume topic with a size cap can expire data sooner than the time setting.

Compaction is the other cleanup policy. A compacted topic keeps at least the latest record per key, older versions are eventually removed, and a record with a key and a null value (a tombstone) deletes that key. It suits a current-state changelog such as account master data or reference data, used to rebuild a cache or table by reading from the beginning, and it must not be used where each event matters on its own, such as an audit trail, since a consumer starting late will not see the removed intermediates. The failures to avoid are auto-commit with slow processing, unmonitored lag, default retention unchecked against weekend and holiday outages, consumers sharing a group ID across environments, resetting offsets in production without an idempotency plan, and ignoring one stuck partition because average lag looks fine.

6.5 How Pega reads the topic: datasets, data flows and node types

So far the consumer has been generic. In Pega it is built from a small number of rules, and the shape of that machinery is what the rest of the chapter works on. Pega's streaming layer has changed across releases, so the building blocks below are stable in concept and their exact names and labels are confirmed against the version in use.

A Kafka configuration instance (a Data-Admin record) defines the connection to a Kafka cluster: bootstrap servers, security protocol, credentials and truststore references, and optional extra client properties; it is one per cluster or environment. A Kafka Dataset represents a topic as a Pega source or sink: the topic, the key and value serialisation (JSON, Avro or another format), the partition key fields used when writing, the consumer group prefix (used for monitoring, as 6.3 explained), and the class that records map into. It is a source of a data flow when it reads and a destination when it writes. Pega's documentation notes that Kafka datasets require an external Kafka service that is independent of the Kafka service Pega itself uses for its own streaming; reading a bank's topic is done with a Kafka Dataset, not with Pega's internal stream.

That internal stream service is a different thing: a Pega-managed stream (itself built on Kafka) used inside the platform for queueing, real-time processing and, in many releases, Queue Processors. Other datasets exist (database table, file and repository datasets for batch ingestion, decisioning stores that a deposits ingestion pipeline mostly does not use). A Data Flow rule is a visual pipeline with one source, shapes and one or more destinations, and a data flow run executes it on a service node pool. The shapes are: source; convert (change the page's class, mapping properties); filter (drop records that fail a condition); compose (enrich by joining with another source on a key); data transform; merge (combine two flows); strategy and event strategy (decisioning, out of scope here); and destination (a dataset, case creation, an activity, another flow, or an abstract destination for reuse), including an exception-handling path that receives records that fail processing so that one bad record does not stop the run. Nodes are classified to run this work: real-time nodes and batch nodes for data flow runs, stream nodes for the internal stream service, and background processing nodes for queue processors, job schedulers and agents.

6.6 Data flow runs and resilience: poison versus outage

The data flow now has to decide what to do when the event cannot be handled. A batch data flow run has a finite source (a table, report or file), starts, processes everything and completes, runs on batch service nodes, and fails by being restarted with progress tracked per partition of the run. A real-time run has an unbounded source such as a Kafka topic, keeps running until stopped, runs on real-time nodes, and fails according to its resilience settings; because nobody is "waiting for it to finish", it must be alerted on.

Resilience settings decide behaviour on failure, and their labels vary by release, but their concepts are fixed. On node failure, a run can resume on another node from the last checkpoint, which makes a node restart invisible for real-time ingestion at the price of possible reprocessing since the checkpoint (which is why idempotency matters), or it can fail. A record-level error threshold decides whether the run stops after N failed records or continues and sends failures to an error destination: an ingestion pipeline never stops because of one bad record, and stops only on a high error rate, which signals a systemic contract break. Checkpoint frequency trades reprocessing against overhead. The starting position (earliest, latest, committed) is decided deliberately for a new group, since replaying months of data into production is a classic mistake. Auto-restart should be capped and alerted, since infinite silent restarts hide a poison message. Parallelism is bounded by the topic's partitions.

ERROR POLICY FOR A REAL-TIME INGESTION RUN record fails mapping/validation -> error destination (dead letter) with reason + payload + offset; run continues record fails because DB is down -> transient: bounded retry/backoff; if persists, STOP consuming (commit nothing) rather than dead-letter every record error rate > threshold (e.g. 5% over 5 min) -> systemic: stop run, page on-call (contract break or downstream outage), do not flood the DLT node dies -> run resumes elsewhere from last checkpoint; duplicates possible; consumers idempotent Distinguish: POISON (this record is bad) vs OUTAGE (everything fails). Dead-letter poison; pause on outage.

The distinction in the last line is the one to hold on to. A poison record is bad in itself, and parking it lets the pipeline continue. An outage makes everything fail, and dead-lettering every record would flood the dead-letter store with thousands of good events that then need replay; the right behaviour is to pause consumption. The anti-patterns are a run that stops on the first bad record, a run that dead-letters every record during a database outage, starting a new group at "earliest" in production by accident, and no alert on a stopped real-time run.

6.7 Handing the event to a queue processor

The data flow reads quickly and should do little work; the application of the event belongs somewhere that has retries, concurrency control and a place to park failures. That somewhere is a Queue Processor: Pega's mechanism for asynchronous background processing of individual work items. Logic puts an item on a queue (Queue-For-Processing); a queue processor picks items up, one at a time per thread, and runs an activity for each, with automatic retry on failure and a place to park items that keep failing. It replaced agents that polled work lists on a timer with limited retry, scaling and visibility: items are persisted, processing is distributed across nodes with controlled concurrency, failures are retried with delay, exhausted items are retained as broken items for inspection and requeue, and the whole is monitored in Admin Studio.

Pega distinguishes two kinds, and the difference is isolation. A standard queue processor (Pega's documentation names pzStandardProcessor) is a system-provided, general-purpose one that is used when an item is queued without naming a processor: its settings are shared, it cannot be tuned for a workload, it shares capacity with every other user of it including Pega's own background work, and it suits light, occasional processing that does not need high throughput. A dedicated queue processor is a rule created for a specific job, with its own activity, thread count, retry settings, delay behaviour and node-type association, so a slow job cannot starve others and it scales independently. Anything with volume, an SLA or special retry needs, such as the ingestion apply here, core calls, notification dispatch or bulk reconciliation, uses a dedicated one.

A dedicated processor's rule carries a handful of settings that are the tuning levers. The activity that runs per item receives the item's saved parameters, and it must be thin, idempotent and handle its own exceptions. Threads per node set the concurrent items processed on each node, so total concurrency is threads times eligible nodes (subject to platform limits) and is the main throughput lever. The maximum attempts decide how many times an item is tried before it is considered failed, and should match the error classes: transient errors deserve several attempts and permanent errors should not burn them. The initial delay and retry interval control the wait before a retry and, depending on the release, may grow; for exact exponential backoff with jitter, compute the delay and re-queue yourself (Chapter 05 §5.9). Items can be processed immediately or at a future time, and delayed queueing is how timed retries and scheduled follow-ups are done; throttle options pause intentionally to respect an ESB limit. The associated node type is normally background processing, never web nodes. The access group sets the ruleset list and roles, with least privilege. And a processor can be enabled or disabled, which has to be re-verified after maintenance.

QUEUE ITEM LIFECYCLE Producer logic (flow, data flow destination, service, scheduler) Queue-For-Processing (processor = BalanceEventApply, parameters = {eventId, accountNo, payload ref, attempt:0}, optional delay) | item persisted (platform queue store; in many releases built on the stream service) v READY --> picked by a free thread on a node of the right type --> IN PROCESS (activity runs, parameters restored) |-- success --> item removed (COMPLETED) |-- failure, attempts < max --> DELAYED retry (re-queued with delay) --> READY again |-- failure, attempts = max --> BROKEN (retained with error details; visible in Admin Studio) BROKEN: support can inspect the error, fix the cause, REQUEUE (single or bulk) or delete Metrics to watch: ready (waiting) count, oldest item age, delayed count, broken count, throughput per minute, thread utilisation

Two flags qualify that picture. Whether Queue-For-Processing enlists in the surrounding database transaction, and how items are stored (stream service or database table), varies with the release, and it affects the outbox pattern, as 6.3 showed. And which processors a node runs depends on node-type classification: a dedicated processor with no eligible node simply never runs, a quiet and common failure.

Six design rules keep queue processor activities healthy. They are idempotent, because an item can run more than once. They take small parameters, keys and small values, not whole case pages, loading data inside the activity. Each item is one unit of work with its own commit, never ten thousand records in one item, because a failure repeats all of it. They distinguish failure types: throw only for transient errors that deserve retry, and for permanent errors record the outcome and complete the item or route it to a human queue, otherwise it burns retries and ends up broken. They avoid long locks, holding no case locks across slow calls. And they avoid per-item expensive setup, reusing node-scope read-only data pages for reference data. One caution on ordering: items are processed concurrently and retried later, so a queue processor does not preserve order.

6.8 Two hundred thousand records in five minutes: a designed experiment

Suppose the application must apply a file of 200,000 balance records, or work off a backlog that size, inside a five-minute window. Whether that is achievable is a question of arithmetic first, and the arithmetic is worth doing before touching any configuration. It is a reconstruction of how to reason, and a designed experiment that a reader could run in a lower environment; it is not a measurement of anything that happened.

The required rate is 200,000 records over 300 seconds, about 667 records per second. For item-at-a-time processing, throughput is threads divided by seconds per item, and by Little's law the concurrency required is the target rate multiplied by the time each item spends in the system. At roughly 170 milliseconds per item, 667 per second needs over a hundred threads, which is impractical. At roughly ten milliseconds per item it needs about seven threads: if six or seven threads each handled a record in about ten milliseconds, the throughput would land near the target. That is how a target is sanity-checked, not a description of what any system did. The conclusion is that the job is not "add threads": it is to cut the per-item cost by more than an order of magnitude and only then size the threads.

200,000 records / 300 seconds = ~667 records per second required Throughput = threads / seconds per item (item-at-a-time processing) Threads = target rate x seconds per item (Little's law: concurrency = rate x time in system) at ~170 ms per item: 667 x 0.170 = ~113 threads -> impractical at ~10 ms per item: 667 x 0.010 = ~7 threads -> realistic This is an order-of-magnitude reconstruction, not a measurement.

A plausible starting point, before tuning, spends its time in five places per item: opening the target record (one database round trip, BLOB decompression and a lock attempt, in the order of ten milliseconds); a per-item connector call for enrichment (network latency and downstream capacity per item, which dominates, in the order of a hundred milliseconds); mapping and decision logic in a heavy activity (page copies, declaratives firing, ten or so milliseconds); a save and commit per item (index and BLOB write and a commit flush, tens of milliseconds); and queue overhead per item (a few milliseconds). Summed, that is in the neighbourhood of a few hundred milliseconds per item, a handful of items per second per thread, and with a few threads on the order of an hour for 200,000 records. The precise figures are not the point; the shape is, with one connector call dominating.

How to run it as an experiment: establish a repeatable benchmark (a fixed 10,000-record sample in a lower environment with production-like volume in the target table); profile with PAL and Tracer on the sample, never at volume in production, counting database interactions and connector calls per record, where an interaction count per item shows the N+1 pattern at once; check the database (slow-statement log, an execution plan for the MERGE and lookups, lock waits; Chapter 11); change one lever at a time and re-measure, recording each result, which is how a reliable before and after is obtained; load-test at full volume off-peak with production-like node classification, watching the database, heap and GC, queue depth and thread utilisation; and add dashboards and alerts so regression is visible.

TUNING LOOP baseline -> measure per-record cost breakdown (PAL: DB calls, connector calls, CPU) -> remove biggest cost -> re-measure -> next lever -> ... until the required rate is met with headroom (target 2x peak) THEN: scale threads/nodes only to the point the DB tolerates; stop; document the knee of the curve

The ways to get it wrong are adding threads to hide a connector call of a hundred milliseconds per item, committing every record, leaving Tracer on during a load test, tuning with ten records, measuring only the average (the slowest chunk and the 99th-percentile item determine the finish time), and declaring victory without checking the database.

6.9 Job Schedulers and legacy agents: related but distinct

Chunks do not create themselves. Something must wake at the batch time, find the work and queue it, and that role belongs to a different rule. A Job Scheduler runs an activity on a schedule: every N minutes, daily at a time, weekly, monthly or at several defined times. Agents were the original scheduled background mechanism; Pega moved to Job Schedulers for time-based work and Queue Processors for item-based work because agents were hard to scale, hard to monitor and tied to per-node schedule configuration. 6.10 The event contract: schema and its evolution

One more thing can break EVT-55121 without any infrastructure failing: the producer team renames a field. Kafka does not enforce what is inside a record, so without a written contract a producer can add, rename or re-type a field and every consumer breaks, often silently (a field now null, a number now a string). An event contract is the agreed, documented shape and meaning of the events on a topic: the topic name, key, headers, payload fields and types, allowed values, semantics (what the event means and when it is emitted), delivery expectations, ownership and versioning rules. It is the integration equivalent of an API specification.

TOPIC NAME : rb.deposits.account.balance.v1 (domain.entity.type.version; one event family per topic) KEY : accountNumber (string, normalised, no leading/trailing space) -> per-account ordering HEADERS : correlationId, eventId (UUID), eventType, schemaVersion, producer, traceparent (if used) VALUE (JSON) : { "eventId": "EVT-55121", unique, used for de-duplication "eventType": "BALANCE_SNAPSHOT", enumerated and documented "schemaVersion": "1.2", "occurredAt": "2026-03-09T09:40:12.123Z", business time at source (ISO 8601, UTC) "publishedAt": "2026-03-09T09:40:12.456Z", "sequence": 882, per-account monotonically increasing (issued by the source of record) "correlationId": "...", "market": "US", "account": { "accountNumber": "CHK-8842-0117", "productCode": "CHK01" }, "payload": { "ledgerBalance": "4218.55", "availableBalance": "4218.55", "currency": "USD" } } RULES: money as string or integer minor units (never binary float); timestamps in UTC; enumerations documented; unknown extra fields ignored by consumers; no personal data beyond what the consumer needs (reference IDs rather than names or tax IDs); payload small (kilobytes).

A contract only works if change is governed. A backward-compatible change lets new consumers read old data (adding an optional field with a default); a forward-compatible change lets old consumers read new data (adding optional fields, which they ignore); full compatibility is both, and means adding optional fields and almost nothing else. Renaming or re-typing a field, adding a required field with no default or changing the meaning of an existing field are breaking changes, and a breaking change publishes a new topic version (.v2) and runs both during migration, with .v1 deprecated by date, never an edit in place. Consumers are tolerant readers: they ignore unknown fields and handle missing optional ones, and they route unknown event types to quarantine with an alert and do not drop them. Where the bank runs a schema registry (commonly Avro, Protobuf or JSON Schema), compatibility is enforced at publish time; whether a given bank has one is a question to ask, not to assume. Any contract change goes through review with all consumers, a compatibility check and a rollout order, consumers first for backward-compatible additions.

Three boundaries carry contracts: upstream (source system or ESB to topic: schema, key, ordering and delivery guarantees, volume and burst expectations, retention, correction and replay policy, how deletes are represented), Pega's consumption (consumer group naming, offset policy, idempotency approach, error and dead-letter policy, the SLA from publish to applied) and downstream (events Pega publishes, such as case resolved, with the Pega team as producer). In the consumer, conditions are handled by detection and response: a duplicate (event ID seen, or sequence not greater than the last applied) is ignored with a counter and not treated as an error; an out-of-order event is handled by the guard that is legal for its shape (6.3); a gap is parked briefly for strict domains and raised if it persists, while state-carrying events are simply applied; a late arrival, hours after occurrence, is applied by business-time rules, and a late "hold placed" for an account since closed is a business decision routed to review; and a poison message that fails deserialisation or validation every time is dead-lettered after limited attempts with full context.

6.11 Dead letters and replay: what Pega does not provide

Some records cannot be processed: malformed JSON, a missing mandatory field, an unknown enumeration, a rule failure or a downstream error that persists. If the consumer retries one forever it blocks the partition, since a poison message holds up every later event behind it, and if it drops the record, data is lost silently. The need is a place for failures that preserves them, explains them and lets them be reprocessed after the fix. Pega has no built-in dead-letter store, no replay API and no requeue dashboard, and, as 6.3 showed, the standard Kafka recovery of resetting a consumer group's offset does not work with a Kafka dataset, so these are something you build, from a Kafka topic or a table, a Service-REST and data pages.

The dead-letter store is a dedicated topic per source topic (for example rb.deposits.account.balance.v1.dlt) or a database table. A topic keeps original ordering and is replayable by tooling; a table is easy to query and report on; many designs do both, with the topic for replay and a table projection for the dashboard. It stores the original payload exactly as received (so it can be replayed unchanged), the source topic, partition, offset, key, headers, received time, error class, error message, a trace ID, retry count, correlation ID, consumer group and application version. The error classes are deserialisation, validation or contract, mapping, business, a downstream transient that exhausted its retries, and unknown event type. Retention is long enough for investigation and replay (weeks), and longer than the source topic's if the dead-letter store is the only copy. Because payloads may contain personal data, access is restricted, the dashboard masks, and replays are audited.

Check your understanding.

The database behind the ingestion is down for twenty minutes. The data flow dead-letters every event it cannot apply, so 18,000 good balance events are in the dead-letter store when the database returns. What should have happened, and what does cleaning up involve?

Answer. An outage is not poison: when everything fails the right behaviour is to stop consuming and commit nothing, so the events wait on the topic (retention covers them) and are processed in order when the database returns. Dead-lettering them instead means 18,000 good events must be replayed, in a scoped, throttled, audited replay. The replay is safe only if apply is idempotent, and ordering is protected by the snapshot sequence guard, which holds here because the topic carries snapshots. The distinction rests on being able to tell the two apart quickly, by an error-rate threshold; where the failures look like individual bad records but are in fact the database, the threshold is what stops the flood.

6.13 Monitoring and paging

A pipeline that fails visibly is easier to run than one that degrades silently, so the signals matter. Consumer lag, in records and as the age of the oldest unprocessed record, says whether processing keeps up. Data flow run status and throughput say whether the run is alive. Queue depth, oldest-item age, delayed count and broken count say where the backlog and failures are at each processor. Throughput per minute against the baseline for the same hour reveals silent slowdowns. Dead-letter count and age by error class show bad data, a contract break or neglected items. Node health and node types present show whether a needed background or stream node is missing. Database lock waits, slow statements and connection pool use are usually the real bottleneck. JVM heap and garbage-collection pauses explain timeouts and rebalances. The job scheduler's last successful run shows whether scheduled jobs actually ran, and reconciliation counts (selected, applied, broken) show whether anything was lost.

6.16 Interview Q&A

Q1. Explain Kafka to someone who only knows queues and databases.

"Kafka is a distributed append-only log. Producers write events to topics; each topic is split into partitions, which are ordered sequences identified by offsets. Consumers read at their own pace and remember their offset, and records stay for a retention period, so several applications can read the same stream independently and one can replay by resetting its offset. Partitions give parallelism and, with a key, per-key ordering; replication with an in-sync replica set gives durability. Unlike a queue, reading does not delete."

Q2. What does Kafka guarantee about ordering, and what does it mean for account events?

"Order is guaranteed only within a partition. Keying by account number puts all events for an account in one partition, in order, while different accounts run in parallel. The key does not protect ordering once Pega dispatches to a queue processor, where independent threads can reorder, so I use a sequence guard for snapshots, event-ID de-duplication for deltas, or serialise per account."

Q3. What delivery semantics do you choose for a bank, and why?

"At-least-once with idempotent processing. At-most-once loses money events, and true exactly-once ends at Kafka's boundary: a database write or a core call is outside a Kafka transaction. So I accept duplicates and make the effect idempotent, which also makes replay safe. I separate three things that get called idempotency: duplicate-event detection, idempotent state change, and a safe business operation."

Q4. A consumer crashes after updating the database but before the offset commit. What happens?

"The event is redelivered, which is at-least-once working. It is harmless only if the event ID and the business effect are written in the same transaction, so the retry hits the unique constraint and commits the offset without reapplying. If the event ID is recorded separately, the order of the two commits decides whether I get a lost update or a duplicate."

Q5. Is a 'only apply if the timestamp is newer' guard safe?

"Only for full-state snapshots, where a newer event supersedes an older one. For partial updates it discards a different field's valid update, and for deltas it destroys money: two debits in the same second are both valid and the guard keeps one. I say which shape the topic carries before writing the guard, and I prefer a source-issued sequence number to a timestamp."

Q6. Does queueing in Pega give you a transactional outbox?

"I would not assume so. It depends on whether Queue-For-Processing commits in the same transaction as the business write on that release, so I would test it in a lower environment by throwing before the commit and checking whether the item exists. If it does not, the outbox is an explicit table written in the same transaction with a separate dispatcher, which is a custom build."

Q7. Lag is rising. How do you diagnose it?

"I look at the lag shape: all partitions rising means consumers are slower than producers, one partition means skew or a poison message, flat and not moving means the consumer stopped. Then the data flow run, queue depth and broken items at the apply processor, database lock waits, node types and heap, and whether upstream volume spiked or the contract changed. I contain, then communicate on a cadence."

Q8. Standard or dedicated queue processor, and how do you tune one?

"Dedicated for anything with volume, an SLA or special retry, because it isolates capacity and has its own threads, retries and node association; the standard one is shared and untunable. Throughput is threads times eligible nodes, but the first lever is cutting per-item cost: no per-item connector calls, chunked items, set-based database work, exposed and indexed columns, thin activities and background nodes. Then I size threads to the database's tolerance."

Q9. How would you reason about processing 200,000 records in five minutes?

"That is about 667 records a second. By Little's law, at ten milliseconds a record I need roughly seven threads, and at a few hundred milliseconds I would need a hundred or more, so the work is to cut per-record cost, mostly by removing per-item connector and database round trips with chunked staging and one MERGE per chunk. It is a sizing argument and a designed experiment, not a measurement; I would benchmark a sample, change one lever at a time, and watch the database, which is the next limit."

Q10. Can you replay Kafka events into Pega by resetting the consumer group offset? And design a dead-letter and replay mechanism.

"Not with a Kafka dataset: the consumer group there is for monitoring only, the data flow assigns partitions and tracks offsets, and changing offsets on the group will not make it reprocess or skip, so replay has to be built."

"Poison records go to a dead-letter store with the original payload, topic, partition, offset, error class and correlation ID, while the pipeline continues; an outage pauses consumption instead of dead-lettering good events. A dashboard shows counts by class, market and age. Replay is an authorised, audited, throttled endpoint, with a dry run, scoped by key and time range, re-injecting into the same idempotent path, with de-duplication retained at least as long as the replay window. Pega provides none of this; it is built."

Q11. Job Scheduler, queue processor or data flow?

"A scheduler for time-based triggers, which creates chunks and queues items; a queue processor for processing items with retry and concurrency control; a data flow for continuously consuming a stream or bulk-transforming a dataset. A scheduler should orchestrate, not process, and it is single-node for jobs that create business records."

6.Z Where we are now

What the application can do

Balances now reach Pega within seconds, not a day later. EVT-55121 travels from the topic to a data flow, a queue processor and the database, is safe against being delivered twice, late or while a consumer crashes, and leaves a trail in a dashboard that tells support when a pipeline is stalled and lets them replay what failed.

The mechanisms behind it

A keyed topic gives per-account order within a partition; at-least-once delivery with idempotent processing, in which the duplicate check and the effect share a transaction, gives the effect once; the event's shape decides which ordering guard is legal; a data flow reads, a dedicated queue processor applies, and a job scheduler orchestrates; poison is parked while an outage pauses; and lag, queue age and dead-letter age are the signals that page a human.

What it still cannot do

Events cover the partner that publishes them. Another partner can only send a file, and a third communicates by email. A file such as RB_BAL_20260309_0730.csv must be recognised as complete, parsed, validated row by row, applied and reconciled, and an inbound email must become a case without being created twice. That is Chapter 07.
