7.1 A partner that can only send files

Riverbend's card and ledger processor sends a balance reconciliation extract each morning. It does not publish events and it does not expose an API; it writes a CSV to an SFTP location and that is its entire interface. This is not an anomaly. File-based integration, in which one system writes a file (CSV, fixed-width, XML, JSON, or a standard such as NACHA) to a shared location and another picks it up and processes it, is the oldest integration style and it has not gone away, for reasons that are structural in banking.

What a file-based interface introduces is the batch window: the period in which everything that depends on the file (returns posted, holds applied, notices queued) must finish, such as after core end-of-day close and before operations open. The window squeezes from both ends: files arrive later than planned, volumes grow, and the business opens at a fixed time. For the processor's extract, the file is due at 07:30 and operations open at 09:00, so the window is ninety minutes.

Window budget: arrival time of file + transfer + validate + parse + load + process + reconcile <= business-open deadline Example (illustrative): file due 07:30, operations open 09:00 => 90 min window. validate+parse 4 min + load to staging 3 min + apply 5 min + reconcile 2 min = 14 min => 76 min slack. If the file arrives at 08:30, slack = 90 - 60 - 14 = 16 min: still OK. At 08:50, processing cannot finish: the need is a late-arrival escalation, not just a faster job.

A small file in a wide window hides the failure modes that matter at scale, which are the ones this chapter is organised around: the file is read while it is still being written (7.8); the same file is delivered twice (7.10); one bad row fails the whole file (7.10); the file never arrives and nobody notices until the morning (7.11); the record count in the trailer does not match the rows received (7.10); and encoding, line endings or a changed layout break the parser (7.9, 7.14).

7.3 The service package for files

The Service Package that Chapter 05 described for REST gives file services their identity too, and for a listener it matters more, because there is no login prompt: the package's access group decides the ruleset list and roles for everything the listener does. A listener-driven service that runs under an access group pointing at an older application version is the classic "behaves differently in batch" defect, and one that runs under an administrator-like group "because it was easier" is a standing security finding.

The design guidance is to create one package per integration family (ACH, legal orders, positive pay) and not one for everything, so that one change cannot affect all; to give each a dedicated technical access group with only the case create and update and data rights the file needs and the correct application and ruleset versions; to keep the package from being callable anonymously from elsewhere, since the listener supplies the context for its own invocations but a file service must not be left callable over HTTP without authentication; to know that, if requestors are pooled, the clipboard is not clean between files, and to clear working pages; and to keep per-environment values out of the package.

7.4 The Service File rule: unit of work and unit of commit

Once the listener has the file, a Service File rule defines how Pega processes it: how to read it, what to map it to and which activity to run. It is named by package, class and method (ACHReturns_ProcessFile, say), refers to a parse rule, maps the parsed fields onto the properties of a primary page (an integration class, not the case class, with canonical mapping done afterwards in a transform, Chapter 05 §5.3), names the processing activity (thin: validate, stage, queue, with heavy logic in queue processors), and says what to do on completion and on faults. The design question that must be answered, and that is stable across releases though the tab names are not, is what the unit of work and the unit of commit are, because it decides how a failure in the middle of a file behaves.

There are three answers. Record-by-record service invocation runs the service method once per record: it is simple, has natural per-record isolation and low memory, but it means one transaction and one queue or database interaction per record, which is slow at a hundred thousand rows unless the activity is very light. Whole-file service plus chunked bulk staging is fast and set-based, with one reconciliation point, but error isolation and restart must be built. File to staging only, then queue processor chunks decouples arrival from processing, is restartable and parallel, at the cost of extra tables and monitoring, and is the preferred pattern for high volume and batch windows (the same shape as Chapter 06 §6.8). Two distinctions apply on faults: a whole file that is invalid is rejected as a file, while an invalid record is rejected as a row, and a record-level problem never fails the file. The transaction behaviour is release-dependent and verified, so that a failure mid-file neither rolls back a hundred and fifty thousand good rows nor commits half a file inconsistently.

7.5 The File Listener

The listener is the first thing that touches the processor's file. A File Listener is a background component (a Data-Admin record plus a running thread on selected nodes) that watches a location for files matching a name pattern and, when one appears, invokes a Service File rule on it. It is Pega's polling listener for files, and what it watches is a source location, which 7.6 examines.

In a cluster with several background nodes, one file must not be processed twice. The listener's usual failures are a mask that also matches the file while it is uploading, polling every second against a storage service, a lower-environment listener pointed at the production directory, no archive step so processed files are re-picked after a restart, and no alert when the listener thread is stopped.

7.6 Native listening and custom SFTP polling: two different mechanisms

The processor's file sits on an SFTP server, and it is tempting to say "the File Listener reads the SFTP server". That sentence blurs two different mechanisms, and keeping them apart is what prevents a design from promising something the platform does not do. The first is native File Listener processing: Pega's listener monitors a location Pega can see and calls a Service File rule on what it finds. Pega's documentation describes the listener monitoring a folder in a file system or a configured repository and calling a file service to process the files; the repository types it lists for this use are Pega Cloud File Storage (the default in Pega Cloud), Amazon S3, Microsoft Azure and JFrog Artifactory, and the local file system, which is supported on-premises and recommended only on shared network storage, and is not supported in Pega Cloud because node-local storage there is ephemeral. The documentation also states that file listeners do not support custom repository implementations.

The second is custom SFTP polling: something that connects to a remote SFTP server, lists matching files and downloads them. That is not what the native listener's source location is described as doing. When the partner's server is the place the file lives, the pull is a separate piece of the design: an activity (scheduled by a job scheduler) that uses SFTP-capable connector or repository methods to fetch the files into a location the native listener can see, or a managed file transfer product in front that receives, scans, decrypts and lands clean files in an internal location, or, in Pega Cloud, the platform's SFTP service whose home folder is mapped to Pega Cloud File Storage, so that a partner writes to SFTP and the native listener watches the mapped repository folder. Which of these a deployment uses depends on the release and on the bank's architecture, and it is confirmed with the platform team, not assumed.

For Riverbend's extract, the design that keeps the two apart is: the processor writes the file and its trigger to the SFTP inbound area; a landing step (MFT, or a custom polling job if there is no MFT) moves complete, verified files to an internal repository folder; and the native File Listener watches that folder. Everything in 7.5 and 7.8 then concerns the native listener, and everything about connecting to the partner (keys, host keys, retries) concerns the landing step. A design that names only one of the two will have a gap in the other.

7.7 SFTP specifics

SFTP (SSH File Transfer Protocol) transfers files over an encrypted SSH connection. It is unrelated to FTPS (FTP over TLS) despite the similar names. It uses one port, normally 22, and supports key-based authentication, which is why banks prefer it to plain FTP. Where Chapter 05 §5.14 covered the keys and rotation, this section is what the landing step and the interface agreement have to settle.

Key issuance, certificate authority work and managed-file-transfer administration normally sit with security and platform teams; the file integration's part is the processing side and knowing what to ask them for and how to test rotation.

7.8 Knowing the file is complete: the trigger-file handshake

The processor's upload is not instantaneous. The balance extract is small, but a larger file, such as the 300 MB ACH return file in 7.12, takes minutes to transfer, and during that time the file already exists in the inbound directory with its final name and a growing size. A listener polling every sixty seconds sees it, picks it up, and parses what is there so far. The result is a file that "processes successfully" with half its records, or a parse error on a truncated last line, or a missing trailer. Sometimes there is no error at all, which is worse: 100,000 of 200,000 entries are posted and nobody knows.

THE RACE t=00:00 the partner starts uploading a large file file visible, size growing (50 MB ... 120 MB ...) t=00:45 Pega listener poll: finds a name matching the mask -> claims the file -> starts parsing t=01:10 the upload completes (300 MB) Pega already read 120 MB, hit EOF mid-record, or parsed 100K of 200K rows RESULT : truncated processing; "success" status; downstream counts wrong; no trailer validation if the parser stops cleanly at a line end

The defences range from weak to strong. A size stability check (poll twice, process only if size and modified time have not changed for N seconds) is weak: a stalled upload looks stable, and it adds latency. A sender-side temporary name then rename (upload as .part and rename when done, with the mask matching only final names) needs the sender's cooperation and depends on rename atomicity. Trailer validation detects truncation but does not prevent it. The strongest is a control (trigger, sentinel) file handshake: the sender writes the data file, then writes a small .done file only after the data file is completely uploaded and closed. The listener's mask matches only the trigger, and the trigger names the data file and can carry its size, record count and checksum, so Pega processes the data file only when the trigger exists and the data file verifies against it. It requires the sender's discipline, and the trigger must be written strictly last. A checksum comparison completes it.

Whether the mask can match the trigger alone and then process a differently named data file depends on how the Service File activity is built: usually the service method is invoked for the trigger and the activity then reads the data file through the repository or file methods; confirm the pattern on the release before presenting it as the only way. The sender-side rename technique needs no trigger and is simpler where the sender can do it. The mistakes are a mask of * or *.csv that matches files still uploading, deleting the trigger before the data file is archived (no evidence), relying on "file size looks stable" alone, processing before verifying the checksum, no alert when a trigger is missing, and a sender that writes the trigger first "to save time".

7.9 Turning bytes into rows: parse rules

The trigger verified, the file is now trustworthy as a whole, and the next question is what each line means. A parse rule converts text or bytes into clipboard properties (or the reverse), so that file layout knowledge is declarative and reusable and not hidden in string-splitting code. The balance extract is a delimited file with a header, detail rows and a trailer.

RB_BAL_20260309_0730.csv (UTF-8, LF; header / detail / trailer; RFC 4180 quoting for any field containing a comma, quote or line break) H,BALANCE_EXTRACT,20260309,0730,BATCH0309 D,0001,CHK-8842-0117,4418.55,4218.55,20260309T073000Z D,0002,SAV-8842-0233,12040.00,12040.00,20260309T073000Z ... (14,207 detail rows in total) T,14207,198204511.06 <- trailer: record count, control total (sum of ledger balances) VALIDATION ORDER 1 header present, correct file type, business date = expected (not a stale or future file) 2 every detail line parses; failures go to the reject table with line number and raw line 3 trailer present; trailer count == parsed detail count (+ rejects accounted for); control total == sum of detail amounts 4 any mismatch => file-level failure or "needs review" status; never silently continue

Pega has parse rules for the layouts a bank meets. Parse Delimited handles records separated by line breaks with delimited fields (comma, pipe, tab): the delimiter, quote character, escape handling, header-row handling and field-to-property mapping with types are defined, with attention to embedded delimiters, quotes and multi-line quoted fields, which RFC 4180 specifies for CSV. Parse Structured handles fixed-position layouts, including multi-record-type files such as NACHA's 94-character records: record types are identified by a position, with field start and length, padding and number formats, each record type mapped to its own page class (some documentation treats fixed-width as part of structured parsing, so confirm the rule type name in the release). Parse XML maps elements and attributes by path, handles namespaces and, for large files, prefers streaming over loading a whole document. JSON is handled by the JSON mapping features, transforms and parse support of the release, mapping arrays to page lists, with line-delimited JSON preferred for very large arrays; the exact rule types vary, so describe the capability.

A parse rule's configuration is mostly decisions about edge cases: record types (header, detail, trailer, addenda) with their layouts and target classes; field definitions (position or index, length, type, format such as YYMMDD for NACHA, trimming, default); mapping to integration-class properties with canonical mapping afterwards; encoding and line endings (CRLF against LF, and a byte-order mark at the start of a file that can corrupt the first field name or record type code); what happens on a malformed record (raise, skip, or capture for the reject path, preferring capture of the raw line and the reason); and strictness for numbers and dates (reject impossible dates and non-numeric amounts at parse time, keep money as decimal, and agree implied decimal places, since NACHA amounts are in cents with no decimal point). The mistakes are substring parsing inside an activity, trusting trailer counts without comparing them, ignoring a BOM or CRLF, parsing money as a float, loading a multi-gigabyte XML into memory, and failing the whole file on one malformed row, which the next section addresses.

7.10 Bad rows and a second copy: staging, isolation, duplicates and reconciliation

The file passes its handshake and parses, and then the realistic things happen. Six of its 14,207 rows are malformed: two have a balance field that is not a number, one has a truncated line, one has an unknown account format, and two have an impossible date. And at 07:52 the processor, which retried its upload, delivers the same file again. The design has to absorb both without failing the whole batch and without applying it twice. The foundation is not to create cases or update balances while parsing, but to separate arrival from business processing in layers.

LAYERS RAW : the original file, archived untouched with its hash (evidence, replay source) STAGING : one row per record, loaded in bulk, with: fileId, lineNumber, rawLine (or key fields), parsedFields, rowStatus (NEW, VALID, REJECTED, PROCESSED, FAILED), errorCode, errorText WORK : the balance table or cases updated from VALID staging rows by queue processor chunks (Chapter 06) Benefits: parse and validate quickly; reconcile counts BEFORE business processing; restart from staging, not from the file; replay one row; dashboards read staging

Large files are read as a stream, not into memory, written to staging in batches of a thousand to five thousand rows per insert, each in its own short transaction, and then turned into chunk work items (about five hundred staging row IDs each) for a dedicated queue processor with parallel threads (Chapter 06 §6.8). The parsed rows are never held as a page list on the clipboard.

The teaching point is per-record error isolation: one malformed or invalid row must not fail the file. It is applied at every layer. At parse, a failing line is captured with its raw text, line number and reason into the reject table, and parsing continues. At validation, rows failing format or business checks are marked REJECTED with an error code and do not stop the batch. At processing, each chunk handles its rows individually, a failing row is marked FAILED with its error while the chunk's other rows commit, or the chunk is retried row by row to find the culprit. At file level, a threshold (for example two per cent rejects) stops the file and flags it for review, because a high reject rate means a layout or encoding problem, not bad rows. A reject report with line number, raw record and reason goes to the data owner, and corrected rows are resubmitted individually, as a replay of one record, not by resending the file.

THE BALANCE FILE, 6 BAD ROWS parse + validate : 14,201 VALID, 6 REJECTED (line numbers, raw lines, reasons) reject rate 0.04 percent < 2 percent threshold -> continue chunk processing : 29 chunks of ~500; 2 rows fail on a downstream constraint -> marked FAILED; the chunk's others commit RECONCILIATION : trailer says 14,207 detail rows. staged 14,207 = valid-and-applied 14,199 + rejected 6 + failed 2 OK OUTPUT : file COMPLETE_WITH_EXCEPTIONS; exceptions report; 8 items to an operations work queue; summary alert NOT: "the file failed at line 9,412 so none of the 14,207 balances were updated and the window closed"

The second copy is stopped by a file registry: a table that records every file received (an ID, the interface name, file name, SHA-256, size, declared record count, business date, received and completed times, status, counts of parsed, valid, rejected, failed and processed rows, archive and error paths, and the identity and node that handled it). A unique constraint on interface plus hash lets the database arbitrate a race between two nodes. The decision when a file arrives is a short table: the same name and the same hash is an exact resend, so it is skipped, acknowledged and logged; the same name with a different hash is a corrected or replacement file, or tampering, and is not processed automatically but alerted for a business decision on whether to void the prior file; a different name with the same hash is the same content under a new name, treated as a duplicate and alerted; and a new file for a business date that already has a completed file for the same interface is a policy decision about second files and sequence numbers.

There is a subtler consequence for this particular file, because it carries snapshots. Suppose the duplicate had a different name, was not caught, and was applied at 09:50. Its row for CHK-8842-0117 shows the 07:30 balances, ledger $4,418.55. The 09:40 settlement event, EVT-55121 from Chapter 06, has already moved the ledger to $4,218.55. A file apply that simply overwrote the row would put the old balance back. The snapshot guard from Chapter 06 §6.3 applies here as well: each row carries its as-of time from the source, and the apply updates the balance only if the incoming as-of is newer than what is stored. The registry stops the same file twice; the guard stops an older file overwriting a newer fact.

Counts are reconciled, not eyeballed. The declared trailer count and control total are checked against what was staged and applied, and any non-zero difference stops processing and alerts; counts are never "adjusted to tie".

Declared (trailer): records = N_t, control total = C_t Staged: parsed = N_p, rejected = N_r, control total of parsed amounts = C_p Check 1: N_p + N_unparseable_lines == total lines read - header - trailer Check 2: N_t == N_p + N_unparseable (everything the sender declared is accounted for) Check 3: C_t == sum(amounts of all parsed detail rows) (hash total or dollar total) Check 4 (after processing): valid = processed + failed + still pending ; processed + failed + rejected == N_t Any non-zero difference: stop, flag, alert. Do not "adjust" counts to make them tie.

Reprocessing is controlled: a whole file only through an operation that checks the registry, marks the previous run superseded and relies on idempotent record application (a unique business key per record: the account plus the as-of time for balances, trace number plus file date for ACH, order number plus version for legal orders); a single record is replayed by selecting a REJECTED or FAILED staging row, correcting or re-evaluating it and re-queueing it, with an apply step that makes a second apply harmless; and staging rows are kept for the retention period as the audit trail of what each record did. The anti-patterns are a case per row inside the listener's thread, all-or-nothing file processing, trusting file names for uniqueness, deleting the file once processed (no replay, no evidence), reconciliation by eye, a registry without a unique constraint, and reprocessing by dropping the file back into the inbound directory.

Check your understanding.

A re-delivered copy of RB_BAL_20260309_0730.csv arrives with the same name and the same hash at 07:52. Separately, a corrected file with the same name but different content arrives at 08:10. What should the registry do with each?

Answer. The 07:52 copy is an exact resend: same name, same hash, so it is skipped, acknowledged to the sender and logged, and the unique constraint on interface and hash makes this safe even if two nodes see it at once. The 08:10 file has the same name but a different hash, so it is either a legitimate correction or a tampered file, and it must not be processed automatically: it is alerted and held for a business decision, including whether the earlier file's effects must be voided. This depends on the partner's contract saying whether corrections reuse the name or carry a sequence number; where the contract says a replacement gets a new sequence, a same-name different-content file is a defect to raise, not a correction.

7.11 Bank-grade controls around file integration

The mechanics above make the file processed correctly. The controls below make it provable and recoverable, which is what a bank is actually asked about. Every expected file has a due time, and absence is an incident, not silence: a job scheduler per expected file, calendar-aware so there is no alert on a bank holiday, checks the registry at the due time plus a grace period, and a missing registry row alerts supervisors and the sender, with a second escalation before the window closes (Chapter 06 §6.9). Late files have a pre-agreed treatment, processed with priority and an extended window or deferred to the next cycle, recorded and approved by operations. Manual reprocessing and force-accepting a rejected record are privileged actions that require a reason and a second approver, the maker-checker control of Chapter 02 §2.6, and are audited.

7.13 Variations: a legal-order file and a positive-pay file

Two further file types follow the same architecture with different business keys and clocks. There is no single published standard for them as there is for NACHA, so the layouts below are teaching designs; real ones come from the sending party.

A legal-order file is a bulk delivery of garnishments or levies from a service provider. Each record is keyed by order number plus version, so an amended order supersedes and never duplicates.

Per record, in a queue processor chunk: the key is checked (the same content is skipped as a duplicate; a higher version takes the amendment path, raising the AMENDED_ORDER ticket on the existing case, Chapter 02 §2.4); the customer is matched against the core (zero matches creates a "no match" case for legal operations, more than one an "ambiguous match" case for manual resolution, exactly one proceeds, and a fuzzy single match is never auto-restrained without an agreed confidence rule); a legal-order case is created (Chapter 02 §2.13) with its SLA from the response-due date on the business-day calendar; and an acknowledgement is queued per state and order type. Reconciliation proves the trailer count equals staged equals cases created plus no-match plus ambiguous plus rejected plus duplicates. The risks, and their controls, are wrong-customer restraint (strict match rules, human confirmation for anything but exact key matches, maker-checker on restraint), a missed deadline (the SLA computed at intake, escalation and a due-soon report), amended or released orders arriving as new rows (the version key, with amendment and release handled as tickets), exposure of sensitive content (a restricted role, masked dashboards, retention under Legal policy) and notice prohibitions (a decision by order type and jurisdiction, owned by Legal).

A positive-pay file serves a check-fraud control. A business customer sends the bank a file of the checks it has issued; when checks are presented, the bank compares each to the issue file; items that do not match become exceptions that the customer decides to pay or return by a cut-off.

ILLUSTRATIVE ISSUE FILE (CSV) ILLUSTRATIVE PRESENTED-ITEMS FILE H,PPAY_ISSUE,20260310,CUST_001 H,PRESENTED,20260310 D,000123456789,100245,2500.00,20260305,VENDOR LLC,I D,000123456789,100245,2500.00,20260310 D,000123456789,100246,980.25,20260305,UTILITY CO,I D,000123456789,100246,9800.25,20260310 <- amount mismatch D,000123456789,100247,0.00,20260306,VOIDED CHECK,V D,000123456789,100250,125.00,20260310 <- not in issue file T,3 T,3 MATCH LOGIC (key = account + check number): present, issued, amount equal -> PAY (no exception) present, issued, amount different -> EXCEPTION: AmountMismatch present, not issued -> EXCEPTION: NotIssued present, issued as VOID -> EXCEPTION: VoidedCheck presented twice -> EXCEPTION: Duplicate (second presentment)

An exception becomes a child case per item; the customer is notified through a secure channel; the decision (pay or return) is due by the customer's cut-off, with a default under the customer agreement if there is no response, implemented as an audited decision rule; the SLA is the cut-off time on the business calendar and the bank's time zone; a bank override carries maker-checker; and the decision is posted to the check system through an idempotent integrator. At volume, issue items are loaded to an indexed table (account plus check number unique) and matching is a set-based SQL join in staging, not item by item in Pega. A customer may send a full replacement or incremental updates, which the contract states and the registry keeps from being mixed, and a late presented-items file is an incident.

For both file types the architecture is the one this chapter built for the balance file: handshake and registry, staging with per-row status, set-based matching in SQL for volume, a decision table for treatment, idempotent case creation and reconciliation. What differs is the business key (order number plus version; account plus check number), the cut-off clock, and the cost of acting on a wrong match, which is why restraint and pay decisions carry dual control.

7.15 When the request is an email: listener or channel

The file path is built. The other request in this chapter arrives differently: a counsel's office writes to Riverbend's legal intake mailbox with an order attached as a PDF. Email integration lets Pega receive messages sent to a mailbox and turn them into work: a case created, a document attached to an existing case, a task for a person. Pega offers two broad approaches, built for different needs.

An Email Listener (with a Service Email rule) is a listener that polls a mailbox and invokes a rule that the developer authors to map the message (sender, subject, body, attachments) into an activity. Pega's documentation describes it this way: an email listener monitors an inbox on a server identified by an email account record, routes arriving messages to an email service rule, and the service activity processes the message, typically creating or updating cases and attaching attachments to them; a message carrying delivery-status information, such as an undeliverable notice, is routed to someone who investigates such things. Service Email rules can handle plain text, HTML or XML messages, a message that uses SOAP is routed to a SOAP service instead, and a change to the Service Email rule requires restarting the listener from Admin Studio before it takes effect. The control is complete: rule logic decides exactly what happens to each message. An Email Channel is a channel configuration in the application's channel settings that receives email as an interaction channel, with configurable case creation, conversation handling and, optionally, language processing. Control is configuration-driven, with extension through defined hooks. Email service rules are in fact generated automatically for some configurations, such as creating an email channel or enabling case creation by email.

7.16 One inbound email, followed: correlation, attachments, loops, bounces and security

The counsel's message arrives with the subject "Order for account holder, response required" and one PDF attached. The listener reads it, and the sequence of questions it must answer is the sequence of this section: is it automatic mail, who is it from, does it belong to a case that already exists, what do the attachments contain, and has this exact message already been processed.

Whether it belongs to an existing case is correlation, and when a customer replies to a bank email the reply should attach to the same case, not open a new one. The techniques are usually combined. A case token in the subject (outbound subjects carry [Ref: AM-10417] and the inbound parser extracts it with a strict pattern and validates that the case exists and matches the sender) is simple, but customers edit subjects and mail clients prefix "RE:" differently. Standard mail headers are stronger: the reply's In-Reply-To and References contain the Message-ID of the original outbound email, which is stored on the case and matched, though some clients and gateways strip or rewrite headers and forwarded emails lose them. A per-case reply address (service+AM-10417@riverbend.example) needs mail platform support. A sender plus open-case heuristic (attach if the sender has exactly one relevant open case) is risky with several open cases and is a candidate only, with review. For an Email Channel the channel manages conversation IDs.

CORRELATION DECISION inbound message In-Reply-To matches a stored outbound Message-ID? YES -> case found (high confidence) else subject token [Ref: XX-nnnn] valid and sender matches the case customer/contact? YES -> case found (medium) else sender has exactly ONE open case of an email-eligible type? -> candidate only: create a "Review email" assignment suggesting the case else -> new inbound email case in the triage queue ALWAYS: attach the original email (.eml) and attachments to the case; add History "Email received"; do not auto-act on instructions

The counsel's message carries no token and no In-Reply-To, so it creates a new intake case in a restricted queue, with the original message attached as an .eml and the PDF stored in a content repository, linked to the case, with its hash and metadata (Chapter 02 §2.10). Attachments are handled with care: real attachments are extracted and inline signature images and tracking pixels ignored (otherwise a case collects dozens of small logos); a type allow-list accepts PDF, common images and office documents and blocks executables and scripts, comparing the actual content type, not just the extension; size limits route oversize files and tell the sender; malware scanning happens at the gateway and again at storage, and an attachment is never rendered in the UI before it is scanned; images and office documents are converted to PDF where a standard view is needed, with password-protected files routed to manual handling; and a structured attachment such as a partner's CSV is parsed into staging as in 7.9 and 7.10, with the same registry and reconciliation controls.

Before any acknowledgement goes back to the sender, there is a trap to avoid. Suppose Pega sends "We received your request" to every inbound email, and a sender's mailbox has an out-of-office auto-reply. The auto-reply arrives in the service mailbox, which sends another acknowledgement, which triggers another auto-reply, and so on. Within an hour thousands of messages are exchanged, mailboxes fill, cases multiply and the sending domain may be flagged as spam. Two automated systems talking to each other can loop indefinitely.

Bounces on outbound mail are the mirror image. An outbound bounce arrives asynchronously as an email to the sending or bounce address; a listener on that mailbox parses the delivery status notification, extracts the original Message-ID or case token, and records the failure. A hard bounce flags the contact point invalid and triggers a fallback (a letter, a task to verify the address), a soft bounce retries later within limits, and bounces are themselves automatic mail that must never trigger an acknowledgement (Chapter 02 §2.9).

The last practical limit is throughput. A listener's ceiling is roughly messages per poll divided by the poll interval when the activity is quick, but per-message cost dominates: at a sixty-second poll and fifty messages per poll the ceiling is about 0.83 messages a second, and if processing a message with an attachment conversion takes two seconds, one thread handles 0.5 a second and a backlog builds during a burst. The fix is the same as the file path's: keep the listener activity thin (store the raw message and queue an item for heavy work such as conversion and parsing), raise messages per poll modestly, run one listener per mailbox, and monitor the age of the oldest unread message. Pega's documentation also lists throttling during email processing as a troubleshooting topic.

Check your understanding.

Riverbend's listener restarts in the middle of a batch of 40 messages and re-reads the last ten as unread. Two of them were counsel's emails that had already created intake cases. What prevents duplicate cases, and what would still go wrong without it?

Answer. The intake record keyed on Message-ID, with a unique constraint, makes the second pass recognise the message and skip it, and the same constraint protects against two listener instances racing. Without it, each re-read creates another case and, worse, another acknowledgement, and the auto-mail and rate-limit rules become the only barrier. The key depends on Message-ID being present and unique, which a well-behaved mail platform guarantees but a forwarding gateway can rewrite; where it cannot be trusted, a hash of the message's headers and body is a fallback key.

7.17 Classifying email with a model: understood, with its governance

A high-volume customer mailbox raises one more question: can the application read what the email is about and route it? Language analysis in an email channel adds several capabilities, each a trained classifier or extractor, and not a generative model. Language detection identifies the language, so a Spanish message goes to a bilingual queue and template. Topic detection classifies the subject from the text (address change, stop payment, statement request, complaint, fraud report, legal notice). Intent detection infers what the sender wants done ("please close my account" against "why was I charged this fee"). Entity extraction pulls structured items such as account numbers, dates and amounts. Sentiment detection estimates tone, to escalate very negative complaints. Each prediction carries a confidence score used for routing.

EMAIL -> ANALYSIS -> ROUTING (conceptual) inbound email (after auto-mail checks, de-dup, attachment scan) -> text analysis (configured analyzer / model): topic scores, entities, sentiment, language -> decision: topic with confidence >= HIGH (for example 0.85) AND low-risk topic -> create a typed case, route to a queue (still verify before acting) confidence between LOW and HIGH (for example 0.5 to 0.85) -> triage queue with the suggested topic shown to the agent confidence < LOW or topic in a sensitive set (legal, fraud, complaint, death) -> human triage, never auto-route; priority flag -> a human agent confirms or corrects the topic -> the correction is recorded as feedback (training data) -> monitoring: precision and recall by topic, share auto-routed, override rate by agents, drift over time

The governance matters more than the mechanism. Confidence thresholds are set from measured precision per topic, not a global default, and low-confidence or sensitive topics always go to a person; legal notices, fraud reports, bereavement and regulatory complaints are never fully automated because a false negative is costly. Training needs a sizable, representative and correctly labelled set of past emails, with a privacy review before customer text is used and redaction of personal data. Evaluation before go-live uses a holdout set, a confusion matrix per topic and cost-weighted errors, with acceptance criteria agreed with the business. Monitoring tracks override rate and drift, since topics change with a new fee, product or news event, and retraining is scheduled. The predicted topic, confidence and model version are stored on the case, because an auditor may ask why an email was routed. If the service is down all mail goes to human triage, with no loss. And a classifier that routes customer communications is a model under the bank's model risk policy, needing validation and approval; Chapter 08 develops that governance. The exact analyzers, rule types and screens for text analysis in an email channel differ by release and licence, so the capabilities and governance are described and rule names are not quoted, and topic classification is kept distinct from the generative features of Chapter 08.

7.18 Interview Q&A

Q1. Walk me through the artifacts for a File Listener integration, in build order.

"Data model first: integration classes for the file records and the staging structure. Then the parse rule, the processing activity, the Service Package with a least-privilege access group, the Service File rule that ties the parse rule and activity together and decides per-file or per-record processing, and finally the File Listener with the source location, name mask, polling interval, node classification and after-processing handling. Supporting pieces are the repository or landing step, keys, the file registry, the reject table and alerts. At runtime the listener picks up the file, the service parses it, the activity registers and validates it, stages the rows and queues chunks for a queue processor."

Q2. Does the File Listener read from an SFTP server?

"The native listener watches a location Pega can see, a file system path or a repository such as Pega Cloud File Storage, S3, Azure or Artifactory, and calls a Service File rule. Pulling from a partner's SFTP server is a different mechanism: a custom polling activity, a managed file transfer tool, or in Pega Cloud the SFTP service mapped to file storage, landing the file where the listener can see it. I keep the two separate in a design and confirm which the platform team uses."

Q3. How do you stop a file being processed before it is fully uploaded?

"A trigger-file handshake: the sender writes the data file, then a small trigger file last, carrying size, record count and checksum. The listener mask matches only the trigger. Pega verifies the data file exists, the size matches and the SHA-256 matches, checks the registry for a duplicate, then claims and processes it. Size stability is weaker, and a missing trigger raises an alert, not a guess."

Q4. One row in a 200,000-row file is malformed. What happens?

"Nothing happens to the other rows. The bad line goes to a reject table with its line number, raw text and reason, and parsing continues. Validation rejects mark rows REJECTED, chunk processing marks a failing row FAILED while the chunk's others commit, a reject-rate threshold stops the file if the rate signals a layout problem, and reconciliation proves trailer count equals applied plus rejected plus failed. Corrected rows are replayed individually."

Q5. The same file is delivered twice. What do you do?

"A file registry with a unique constraint on interface and hash. The same name and hash is an exact resend and is skipped and logged; the same name with different content is a correction or tampering and needs a business decision; a different name with the same hash is treated as a duplicate. For snapshot files I also apply the source as-of guard, so an older file cannot overwrite a newer balance."

Q6. How do you reconcile a file?

"The trailer's declared count and control total against what I staged and applied: declared equals parsed plus unparseable, control total equals the sum of parsed amounts, and after processing processed plus failed plus rejected equals declared. Any difference stops sign-off and alerts. I never adjust counts to make them tie."

Q7. How do you handle a NACHA return file?

"Layered: the handshake and registry, a structured parse of the 94-character records, structural validation with the batch and file control totals, then staging, then an idempotent apply keyed on original trace plus return trace. Business matching to the original entry is separate, a decision table by reason code drives the case, SLA and notice, and amounts are in cents, so I test the conversion. Deadlines come from reference data on the right calendar."

Q8. Email Listener or Email Channel?

"A listener when I want deterministic control over structured or semi-structured inbound mail, such as partner attachments, operations mailboxes or a counsel's office, because I author the Service Email rule. A channel for customer-facing conversational email that needs threading, agent routing and replies, and possibly language analysis. A change to a Service Email rule needs the listener restarted from Admin Studio."

Q9. How do you stop an auto-reply loop?

"Detect automatic mail by headers (Auto-Submitted, X-Auto-Response-Suppress, Precedence, bounce senders) and never acknowledge it; mark my own acknowledgements as auto-replied; never send to my own domain; rate-limit acknowledgements per sender; de-duplicate on Message-ID; pause acknowledgements on a volume spike; and include out-of-office and bounce samples in regression tests."

Q10. Can you automate email routing with a model?

"With governance. Confidence thresholds set per topic from measured precision, sensitive categories always to a person, a labelled and privacy-reviewed training set, evaluation before go-live, drift monitoring, the prediction, confidence and model version stored on the case, a human fallback, and model-risk validation. Email is never authorisation: it starts a case, and sensitive changes are verified through a controlled process."

7.Z Where we are now

What the application can do

The processor's balance file is picked up only when complete, parsed, staged, applied in chunks and reconciled to its trailer, with six malformed rows isolated and a re-delivered copy refused; an ACH return file and the two other file types follow the same path; and a counsel's email becomes a protected intake case, de-duplicated, with its attachment scanned and stored and no automatic acknowledgement to automatic mail.

The mechanisms behind it

A chain of artifacts, each owning one concern; a native listener separate from the landing step that fetches from a partner; a trigger handshake and checksum; parse rules for delimited, fixed and structured layouts; staging with per-record status; a registry with a unique constraint; reconciliation by declared and observed counts; and, for email, a listener and Service Email rule with correlation, loop prevention and a thin listener thread.

What it still cannot do

Every input is now handled, but the judgement work still falls on people. Marcus has to find the right procedure for an unusual request and classify documents by hand, and the application so far only moves, stores and checks data. Where assistance from rules, models, retrieval and agents helps, and what a bank must govern around it, is Chapter 08.
