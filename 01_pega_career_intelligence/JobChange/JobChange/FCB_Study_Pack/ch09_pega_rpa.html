9.1 The screen with no API

Scope of this chapter. RPA is treated here as a conceptual topic: it is explained from the integration and case-management side (where it fits, how a case hands work to a robot and gets a result back, why bots are fragile, what auditors ask) and not from the side of building or operating robots. Product names and screens are described by function; Pega's robotics tooling has changed across releases, and dollar and time figures in worked examples are illustrative arithmetic, not benchmarks.

On Monday 9 March, as AC-10882 moves toward disbursement, one more step is needed. Riverbend's branch teller platform keeps its own restraint list, separate from the core that the ESB fronts, and closing an account in the core without marking it on the teller platform leaves a branch able to hand out cash against an account that is closing. The teller platform is an old thick-client application. It has screens, a terminal-style navigation and a field for a restraint reference. It has no API, no batch interface and no one willing to fund one this year. Today an analyst reads the approved details from the case and keys them into that screen, three to five minutes each, and writes the reference back into the case.

That is the problem this chapter takes: a step in an otherwise automated process that can only be done through a user interface. It looks small, and it forces nearly every concern of the previous chapters to reappear, because a robot driving a screen has the same needs as an integration (idempotency, retries, classification, evidence) with far weaker signals to work with. Marcus's work item is AC-10882-R1, and the rest of the chapter follows it.

9.2 What RPA is and why it exists

Robotic Process Automation (RPA) is software that operates other applications through their user interface, the way a person would: opening a screen, reading values, typing into fields, clicking buttons, copying results. The robot is a program that sees and manipulates the screen elements (or a terminal emulator session) of an application that offers no better way in. It exists because integration normally means calling an API, reading a file or querying a database, and many systems in banking were built before APIs were common or were never given one. Replacing them is a multi-year, high-risk programme, and in the meantime staff re-key data between screens. RPA automates that human work without modifying the target system, because the robot uses the same front door a person does.

The teller platform is one of a recognisable family of places where no-API systems appear in a bank.

What it is good at follows from its nature: high-volume, repetitive, rule-based steps with structured inputs; stable target screens that rarely change; systems with no practical API for the foreseeable future; a short-lived bridge while an API or replacement is built; work that tolerates asynchronous completion and retry; and well-understood processes with clear exception rules. It is a poor fit for judgement on unstructured information, targets in frequent flux (vendor portals redesigned every quarter), systems that already have a usable API, permanent architecture for core processing, real-time customer interactions needing millisecond response, and poorly documented processes in which humans handle many variations.

9.3 Robot, API or workflow: the decision framework applied to the screen

The first question about the teller screen is not how to automate it but whether a robot is the right way to reach it at all, and the framework for that question is the most reusable thing in the chapter. Three technologies do three different jobs. BPM and case management orchestrate the work: stages, assignments, SLAs, approvals, audit, who does what and when. API and data integration exchange data and trigger actions between systems programmatically and reliably (REST, SOAP, SQL, messaging, files). RPA performs an action in a system that offers no programmatic interface by driving its UI. They are not alternatives for the same job: BPM orchestrates, and APIs and RPA are two ways to reach a system, so the decision is API versus RPA for the integration step, inside a case.

Applied to the teller platform: there is no API and no batch interface (Q1 is no); the owner will not provide one this year, though the closure volume needs relief now (Q2 gives a time-boxed bridge); the restraint entry is rule-based, the inputs are structured, the screen has been stable, and exceptions can go to a human queue (Q3 is yes); and so a robot behind the case is justified, with the controls of Q4 and a written end date. The mistakes in tool choice are using RPA because it is the tool the team has when a REST endpoint exists, using it to avoid a conversation with the system owner, automating a broken process (a robot does the wrong thing faster), building bots for processes that change monthly, and having no owner or budget for maintenance.

9.4 Attended and unattended automation

The same screen can be driven in two ways, and the choice is a control decision as much as a technical one. In attended automation (robotic desktop automation) the robot runs on the employee's own desktop and is triggered by the human: it pre-fills fields, copies data between screens, fetches data to display and validates entries, under the employee's own session and identity, with the human handling any exception on the spot. In unattended automation the robot runs on a server or virtual machine with no one present, triggered by a schedule, a queue of work items or a case assignment, using a dedicated robot identity from a vault, and any exception has to be routed to a human work queue. Pega's documentation draws the same line: unattended automations perform work without human intervention, typically back-office tasks submitted to a queue and processed in batch, while attended automations run on a user's desktop, for example retrieving customer information from several applications, presenting it, allowing changes and updating the original applications.

The common bank pattern is hybrid: an unattended robot does the routine majority and routes exceptions to a human queue inside the case, while an attended robot helps the human resolve the exception. For Riverbend's restraint entry the sensible order is attended first (the analyst presses a button, the screen is pre-filled, the analyst confirms), because it preserves a human actor on a money-adjacent transaction and simplifies maker-checker and attribution, and unattended later, with the strongest controls of 9.10. Some banks restrict unattended automation on money-affecting screens to read-only or non-financial updates.

9.5 The robotics toolchain

Pega's robotics products (descended from technology Pega acquired) have had name and packaging changes, and three components are the stable mental model. Robot Studio is the development environment where automations are built: connect to the target applications, identify (interrogate) their screen controls, design the logic visually, test and package. Robot Runtime executes an automation on a machine, attended on a user's desktop or unattended on a robot virtual machine. Robot Manager is the server-side management application: it deploys and versions automations to runtime machines, schedules runs, manages work queues and work items for robots, assigns work, monitors robots, and collects logs and screenshots. Current names, licence metrics and capabilities are confirmed in the documentation before being quoted.

Supporting concepts connect it to the case. An automation project is the versioned deployable unit. Adapters and interrogation (9.7) are how a robot connects to an application and recognises its controls. A work queue holds items for robots to process, each with input data and a status. A work item is one unit of robot work, mapping to one case-level request. A robot pool is a group of runtime machines taking work from a queue, so more machines process more items in parallel. Pega's documentation describes the case-side integration: work is assigned to a robot through Case Management using the Assign to robot queue smart shape (or through data pages), and in Robot Manager robots are configured to subscribe to work groups associated with work queues, in single-purpose or multi-purpose arrangements. A credential store for robots is part of the product family.

9.6 The work item travels: the case-to-bot loop

The design principle that makes the whole arrangement governable is that the case owns state and the bot is a worker. A robot has no memory of the business context, no SLA, and no audit trail beyond logs; the Pega case has all of those. So the case decides what to do and records the outcome, and the bot performs one bounded UI task and reports a structured result. That keeps process logic out of the bot, where it is expensive to change and hard to audit, and in rules, where it is testable and governed.

Why is the approval of AC-10882 performed in the Pega case before the work item exists, and not as a step the robot performs on the teller screen?

Answer. The teller platform treats the robot as an ordinary user, so the robot has no way to know whether a second person approved. If the approval lived in the robot, maker-checker would depend on a screen the robot could bypass or mis-key. Doing the approval in the case makes it a governed, audited rule with a human actor, and the work item then carries a reference to it, so the robot executes only approved items and an auditor can trace from the screen action back to the approval. The limit is that this only holds if the robot's role in the target application cannot itself approve anything, which is why its role is restricted to entry (9.10).

9.7 The screen changes: adapters, interrogation and why UI changes break bots

The first thing that goes wrong in practice has nothing to do with the work item. The teller platform vendor ships a patch over a weekend, and on Monday morning the restraint screen has a new "confirm identity" banner and the account field has moved one row down. Nobody told the robotics team, because from the vendor's side nothing contractual changed: a screen has no versioned contract the way an API does. That is the structural reason RPA carries a higher maintenance cost and a higher risk of silent failure, and understanding how a robot finds things on a screen explains exactly how it breaks.

A robot cannot read a screen visually the way a person does. It connects to an application through an adapter suited to the application technology and then interrogates it: it inspects the application's UI structure and records each control (a text box, a button, a table cell) with match rules, the set of properties used to find that control again at run time. A web adapter works with the page's document structure and matches on element IDs, names, classes, text and position. A Windows desktop adapter works with native controls exposed by the operating system and matches on window class, control name and automation ID. Java and other framework adapters work with component class, name and hierarchy. A terminal or mainframe adapter works with the character grid of a session: row and column positions, screen text patterns and field coordinates. Virtualised applications (remote desktop, Citrix) often expose only pixels and keystrokes, so image recognition and coordinates are the most brittle approach of all. Office, email and file adapters work with cell addresses, headers and files.

Of these, the dangerous ones are the silent failures. A "control not found" error stops the robot and tells someone, which is a good failure. A layout change that makes position-based matching type a restraint reference into the wrong field produces no error, and the first sign is a wrong record. Every defence is therefore aimed at making a robot refuse to proceed on a state it does not recognise. It prefers stable match properties (IDs and names rather than positions, and image recognition only when nothing else exists). It verifies state at every critical step: before typing, the expected screen title and field labels; after submit, a confirmation pattern; failing rather than guessing. It waits for conditions, not fixed delays, with a timeout. It handles known dialogs explicitly (session timeout, "are you sure", banners). It runs a canary against a non-production or low-risk record on a schedule and alerts if match rules fail, and it subscribes to the target's release calendar. It keeps a regression pack of test data and expected results that is run after any target release or robot change, and keeps UI-specific logic in small reusable blocks so one screen change is fixed in one place. On money-affecting screens it never retries blindly and stops the queue on an unexpected state, and the governance includes a named owner, a notice agreement with the target system owner and version control of automations.

The failures here are coordinate or image matching where controls exist, fixed sleeps, no verification of what was typed, processing continuing after an unexpected screen, no notice agreement with the target owner, and bots built against a production-only environment with no test target. In the example, the identity banner makes the robot's screen-title check fail on item AC-10882-R1; it stops, captures a screenshot, and the item becomes a system exception rather than a mis-keyed restraint.

9.8 The robot times out after possibly finishing: unknown outcome, exceptions, evidence and retry

The second failure is different in kind, and it is the most important idea in the chapter. Suppose the screen did not change. The robot logs in, finds the restraint screen, keys the account, reason and reference, and presses submit. The teller platform saves the restraint. Then the confirmation never renders, because the session drops, or the application hangs, or the robot's VM is reset. The robot's timeout fires. From the robot's side nothing was confirmed. From the teller platform's side, a restraint may now exist.

This is the unknown outcome of Chapter 05 §5.9 again, in a new guise. There, a core call timed out after the request was sent and Pega held no information about whether the hold had been placed; here, a UI action timed out after the submit and the robot holds no information about whether the restraint was saved. The two wrong reactions are the same. Retrying blindly can key a second restraint, so the account shows duplicate restraint records. Marking the item failed can lose a restraint that exists, so the branch believes the account is not restrained when it is. And the same three resolution routes apply, translated to a screen: a status lookup (search the account's existing restraints for the order reference, which is the idempotency pre-check of step b in 9.6); a contractually safe retry (not available, because the teller platform makes no promise to de-duplicate, which is why the pre-check is performed by the robot and not assumed of the target); and reconciliation (the end-of-day report of restraints from the teller platform compared with the case records). What is worse than with an API is the quality of signal: a bot has screen text, timeouts and dialogs, not structured status codes, so the verification step (read back the confirmation) and the pre-check carry more weight than they would in an integration.

The exception handling follows the same classification discipline as Chapter 05 §5.10. A business exception means the data or the business situation prevents completion and the automation worked correctly (account already closed, amount over a limit, account not found, duplicate restraint already exists): it is never retried and returns a structured code to the case, which routes it to a human with the reason. A system exception means the automation or environment failed (login failure, control not found, timeout, an application error dialog, a VM crash): it is retried with a limit and delay, only for safe operations, with a screenshot, an alert if systemic, then manual routing. Retries are limited to two or three attempts with a delay, so a struggling legacy system is not hammered and accounts are not locked by repeated bad logins; idempotency is ensured before any retry; an unknown outcome on a money-affecting transaction is never retried without verification; and a circuit-breaker rule stops the queue if N consecutive items fail with the same system exception, because continuing wastes items and can lock credentials.

Evidence is what makes any of this provable. Screenshots are captured at defined points (before submit, after confirmation) and on every failure, stored with the work item and correlation ID and retained per policy. And an independent report from the target system, the restraints created today, compared with the case records, proves the bot did what it claimed.

Item AC-10882-R1 times out after submit. The robot's retry logic, written by a developer who treats "timeout" as "retry", runs the item again and keys the restraint. The pre-check was left out because "the screen rejects duplicates". What happens, and what is the right design?

Answer. If the screen does not in fact reject duplicates, the account now has two restraint records, and the branch will later have to find and clear one of them, or a release will clear the first and leave the account apparently unrestrained. The right design never assumes the target's behaviour: the robot searches the account's existing restraints for the order reference before keying, returns the existing reference if found, and routes to human verification if the search itself fails. It depends on the reference being searchable on that screen, and if it is not, the only safe alternatives are human verification of every unknown outcome and end-of-day reconciliation. The decision to leave out the pre-check is exactly the assumption Chapter 05 warns about with APIs.

9.9 When the input is a document: OCR and intelligent document processing

Many manual processes begin with a document: a scanned legal order, an ID card, a signed form, a statement PDF. A robot cannot read an image, so optical character recognition (OCR) converts the image of text into machine-readable text, and intelligent document processing (IDP) goes further, classifying the document type and extracting named fields (order number, due date, amount, names) using templates or machine learning. The approaches trade predictability for flexibility: template-based extraction (fixed zones or anchor text) is accurate on a fixed form and breaks when the layout varies; machine-learning extraction handles variation such as different courts' formats but needs labelled training data and monitoring and produces probabilistic errors; LLM-assisted extraction (Chapter 08 §8.7) is flexible for unstructured documents with hallucination risk, governance needs and a mandatory verification step; and a hybrid of OCR, rules and ML with validation checks is the practical choice.

ApproachHow it worksStrengthWeakness
Template-based extractionFixed zones or anchor text locate fields on a known form layoutAccurate and predictable for fixed formsBreaks when the layout varies; needs a template per form
Machine-learning extractionA trained model locates and reads fields across layoutsHandles variation (different courts' formats)Needs labelled training data and monitoring; probabilistic errors
LLM-assisted extraction (Chapter 08 §8.7)A language model reads the recognised text and returns structured fieldsFlexible for unstructured documentsHallucination risk; governance; must be verified
HybridOCR plus rules plus ML, with validation checksPracticalMore components to run

Every extracted field carries a confidence score, and the control design uses confidence and validation rules to decide whether a human must look. An order number is checked against a format pattern and a uniqueness check, and is always verified by a person for legal orders until measured accuracy proves otherwise. An amount is numeric, within a plausible range, matches the words-amount if present, and is human-verified whenever it drives a restraint. A due date is a valid date, not in the past beyond tolerance and after the service date, human-verified because it drives the SLA. Names and identifiers are matched against customer data with fuzzy rules, and ambiguous or low-confidence matches go to a human because of the wrong-customer risk. A document with low overall confidence or poor image quality goes entirely to manual keying.

DOCUMENT -> DATA PIPELINE WITH HUMAN GATE scan/email attachment -> image quality check (skew, resolution) -> classify the document type (court order / levy / subpoena / proof of address / other) -> OCR + field extraction with confidence scores -> validation rules (format, ranges, cross-field) -> ALL fields pass validation AND confidence >= threshold AND the document type is allowed for straight-through? -> pre-populate the case, still require human confirmation for legal orders -> otherwise -> human data-entry task showing the image beside extracted fields with low-confidence fields highlighted -> human confirmation recorded (who, when, which fields corrected) -> feedback to improve extraction Metrics: field-level accuracy, straight-through rate, correction rate by field, processing time; sampled QA review

Legal orders are high-consequence: a misread amount or a wrong customer match causes a wrong restraint or a missed deadline. A sensible policy is human verification of key fields for the foreseeable future, with automation reducing typing effort and highlighting uncertainty and not removing the human check. Treating extraction as a model also brings it under model risk governance (Chapter 08 §8.11).

9.10 A privileged non-human user: credentials, least privilege, segregation of duties and audit

Once the robot works, an auditor arrives. Controls in banking assume that every action on a system is attributable to an accountable person, and that critical actions need two different people. A bot logs in and performs actions that look, to the target system, exactly like a user, so the questions are who is accountable for what the robot does, whose identity it uses and whether that identity is shared, whether a robot developer can also approve and run transactions, whether the robot bypasses a control a human would face, how the bank proves what it did and that it did only what was authorised, and who reviews its access and when.

9.11 Operating the robot: infrastructure, sessions, licences, monitoring and the 2 a.m. runbook

A robot in production is infrastructure with a dependency on someone else's screen. Unattended robots run on dedicated virtual machines (often Windows) with the target application clients installed, from a golden image with a patch cadence, locked down and separate from user desktops, with an environment per stage. Robots need a logged-in desktop session, which can disconnect, lock or time out, and target applications may allow only a limited number of concurrent sessions per account, so session keep-alive and recovery are handled, one account is used per concurrent robot where the target forbids concurrent sessions, and each item starts from a clean state. Robot licences and target session licences cap parallel robots, so capacity is planned as items per hour per robot times the number of robots against the SLA: at four minutes an item and five robots that is 75 items an hour, so 600 restraints overnight take eight hours, not one. Targets have maintenance windows and end-of-day batches during which the UI is unavailable or slow, so a calendar of target availability pauses robots outside the window and items queue.

Monitoring covers queue depth and oldest item age, robot heartbeat, success and failure rate, average item time, login failures and failure screenshots, in Robot Manager and the case system, alerting robotics operations and integrating with the bank's monitoring (Chapter 10). Change coordination subscribes to the target's release calendar, runs a canary after a release and keeps the ability to roll back the robot version. Business continuity treats robots as a dependency with a tested manual fallback, trained staff and a documented recovery time. Versions are deployed through the manager and recorded on each work item result, and documentation (process design, exception catalogue, runbook, owners) is maintained as part of the release.

TRIGGER: alert "TellerRestraints queue: 0 completions in 30 min, 47 pending, 12 failed" 1 ASSESS SCOPE (5 min) Is it one robot or all? all failing with the same error? which step/screen? since when? is the target application reachable (a person tries manually)? Is the queue being drained at all? are credentials locked? is Robot Manager healthy? 2 CONTAIN (before debugging) if systemic and money-adjacent: STOP the queue (kill switch) to prevent mis-keying, credential lockouts or duplicate transactions notify the business owner: closure restraints are SLA-bearing; switch to the MANUAL FALLBACK (named staff key the restraints from the case work queue) 3 CAPTURE EVIDENCE: failure screenshots, step logs, last successful run time, robot VM status, recent target release or credential change tickets 4 DIAGNOSE by symptom LOGIN_FAILED on all robots -> password rotated or account locked: security/vault team; do NOT retry blindly (lockout) SCREEN_NOT_FOUND / control not matched since a specific time -> the target UI changed (patch or release): the robotics developer re-interrogates; the target owner confirms the change TIMEOUTS -> the target is slow or in a maintenance window; check target health; pause ONE robot only -> VM issue (session disconnected, disk, patch): restart or remove from the pool Robot Manager unreachable -> platform incident 5 FIX AND VERIFY: fix on a non-production target if possible; run a canary item on a low-risk or test record; confirm the screenshot and reference 6 RESUME AND DRAIN: resume the queue at limited concurrency; reconcile items completed manually against queued (the pre-check prevents duplicates) 7 CLOSE: RCA, preventive action (change notification agreement, canary, better match rules), update the runbook; record the SLA impact

The runbook's order is the discipline: contain first, capture evidence, fall back to manual, fix, verify with a canary, drain safely and reconcile. It is the incident model of Chapter 10 applied to a robot, with the added step of checking by hand whether the target is up before blaming the robot.

9.13 The business case

The business wants the teller restraint automated this quarter, and RPA proposals are often justified by labour saved while ignoring run cost. A lead does the full arithmetic and compares it with the API alternative. The figures below are invented to show the structure.

Illustrative process: restraints keyed manually Volume = 300 per week = 15,600 per year ; manual time = 4 min each ; analyst cost = $45/hour (loaded) Manual cost/year = 15,600 x (4/60) h x $45 = $46,800 Bot time = 2 min each, unattended; exceptions 8% handled manually at 6 min each (review + fix) Bot-handled share = 92% -> manual effort after = 15,600 x [0.92 x 0 + 0.08 x 6 min] = 15,600 x 0.48 min = 7,488 min = 124.8 h = $5,616 Gross saving = 46,800 - 5,616 = $41,184 / year RUN COSTS (illustrative): robot licence + VM $18,000 ; monitoring/support 0.2 FTE $15,000 ; maintenance after UI changes (2 breakages/yr x 40 h x $90) $7,200 Run cost = $40,200 / year Net saving = 41,184 - 40,200 = $984 / year -> essentially break-even, BEFORE build cost (say $60,000) and risk cost. Payback on build alone: never within 5 years at this volume. Compare an API/batch interface: build $80,000 once, run $6,000/year, saving about $46,800 - $6,000 - residual manual = ~ $38,000/year -> payback about 2.1 years, and reliability and audit are better.

The lesson to state is that the full run cost, including maintenance and exceptions, is asked for and compared with the API alternative before anyone agrees that RPA saves money.

9.14 Replacing the robot: API first, a time-boxed bridge and a decommission plan

The business wants relief this quarter and the architect wants the API; a lead reconciles the two instead of choosing a side. The manual pain is real, the cost and risk of a permanent bot are real, and the answer is a bridge with an end date, written before the first line of automation.

Objection from the businessResponse
"The API will take a year; we need this now.""Agreed, the pain is real. We can run an attended automation in six to eight weeks to remove the re-keying, with a written decommission date tied to the API delivery milestone."
"The bot is cheaper.""Cheaper to start. Let's compare five-year cost including maintenance, exceptions, licences and audit. At our volume the API pays back in about two years."
"Why not just keep the bot?""Every vendor release can break it silently, and a bot acting as a user is an audit finding waiting to happen. We keep it only while the interface does not exist."
"The vendor says no API.""Then we ask for a batch file load or a controlled database interface, and record the vendor constraint as a risk on the modernisation roadmap with an owner."
"It's only keying, how risky can it be?""A mis-keyed restraint is a customer harm and a regulatory event. The controls (dual control before the work item, read-back verification, caps, reconciliation) are the price of automating it."

The bridge charter is the document that makes the bridge a bridge. It states purpose and scope (which process and screens, and what is explicitly out of scope), a named business owner and technical owner accountable for maintenance and retirement, the interface alternative being pursued with its owner, milestone and date, a time box with a review date and a hard end date (for example twelve months) and an explicit process to extend it, and the decommission trigger, the condition that ends the bot (the ESB restraint service passing UAT, or the end date arriving). The decommission plan lists the steps: cut over to the API for new items, drain the robot queue, disable the robot schedule, revoke robot credentials and vault entries, remove the VMs and licences, archive automation versions and evidence per retention, update the process documentation and close the access-review entries. It also carries the controls of 9.10, success and stop criteria (straight-through rate, failure rate, incidents, and a stop rule such as two money-affecting incidents in a quarter pausing the bot), cost tracking against the business case, and an entry in the automation registry with its owner and expiry, so that expiring entries trigger a review.

RPA BRIDGE LIFECYCLE Month 0 : approve the charter (owner, end date, API milestone) ; attended pilot on 1 process Month 2 : unattended for approved items with caps; reconciliation daily Month 3-9 : the API/batch interface is built in parallel (funded and scheduled BEFORE the bot goes live) Month 9 : API in UAT ; dual-run: API and bot results compared Month 10 : cut over new items to the API; drain the bot queue Month 11 : disable the robot, revoke credentials, release licences/VMs, archive evidence Month 12 : close the bridge; lessons learned; entry removed from the automation inventory If the API slips: a formal extension decision by the sponsor with updated risk and cost, not silent drift.

The principle is API-first without dogmatism: a bank has systems with no interface, and a person re-keying all day is also a risk, so the bridge is funded together with the API and nothing ends up as a permanent bot that nobody owns. In Riverbend's example, the teller restraint robot is retired when the teller platform's replacement offers a restraint service, and the case simply starts creating an integration call in place of a robot work item, because the case, not the robot, owned the process all along.

9.16 Governance and a Centre of Excellence

Organisations that adopt RPA without governance accumulate unmanaged bots, shadow automations built on user desktops with personal credentials, and audit findings. A small governance function prevents that. A Centre of Excellence provides a single intake for automation ideas with API-first screening at the door, scored by value, risk, stability and API availability; standards and reusable components (naming, logging, exceptions, credentials, evidence, login handling, screenshots, structured results); a mandatory control framework aligned with audit, security and, where AI or OCR is involved, model risk; an inventory (an automation register) recording owner, purpose, target systems, identity, risk tier, volumes, cost, expiry and decommission trigger; shared operations, monitoring, incident process, capacity and licence management; change management with target system owners through a release calendar and notice agreements; skills and training; benefits tracking of measured savings against the business case including run cost; and retirement reviews that retire bots when APIs arrive or processes change.

TierCharacteristicsRequired controls
Tier 1 (high)Money-affecting, customer-affecting or legal actions; writes to core or payment systemsAll controls in 9.10; dual control before execution; volume and amount caps; kill switch; independent review; daily reconciliation; quarterly access review; a board-level inventory entry
Tier 2 (medium)Non-financial updates to internal systems; data movement with personal dataA unique identity and vault; least privilege; evidence; change control; periodic review
Tier 3 (low)Read-only, non-sensitive retrieval; internal convenienceBasic identity and vault; logging; an owner; an expiry date

A CoE reports a short set of metrics: the straight-through rate (items completed without human intervention), the exception rate by class (business against system) and its trend, mean time to repair after a break, UI-change breakages per quarter per bot (a fragility measure that informs retire-or-replace decisions), run cost per item including maintenance and support, the number of bots with an API alternative in progress, and control findings and aged items. The anti-patterns are bots built by individual teams on personal desktops with personal credentials, no register of bots, no owner after the project, savings tracked without costs, and a CoE that cannot say no to RPA when an API exists. The restraint robot of this chapter is a Tier 1 automation.

9.17 Interview Q&A

Q1. When would you use RPA instead of an API?

"Only when the target has no usable interface, the owner cannot provide one within the business need window, and the process is high-volume, rule-based and stable enough to justify the run cost. Even then I treat the bot as a bridge with a decommission date. If a REST endpoint, a SQL view or even a nightly file exists, I use that, because it is reliable, versioned, idempotent and auditable."

Q2. How does a case hand work to a robot and get the result back?

"The case owns state and the bot is a worker. After validation and approval, the case creates a work item with a minimal payload and a deterministic ID in a robot queue, waits with an SLA, and the robot performs one bounded task and returns a structured result: success with a reference, business exception, or system exception. The result comes back by callback or polling, and the case records the evidence, routes exceptions to humans and has a sweeper for items with no result."

Q3. A robot times out after submitting a transaction. What do you do?

"It is an unknown outcome, the same problem as a timed-out API write: retrying can double-post and marking it failed can lose a real transaction. I look up the state first, by searching the target for the unique reference the robot keyed, which is the idempotency pre-check; if that is not possible I route to human verification instead of re-keying, and reconcile against the target's end-of-day report. The robot's error signals are weaker than an API's, so read-back verification and the pre-check matter more."

Q4. Why do bots break, and how do you defend against it?

"A screen has no versioned contract, so any change in IDs, layout, dialogs, terminal coordinates or login can break the match rules, and the worst case is silent mis-keying. I use stable match properties, verify the screen state before typing and the confirmation after, wait on conditions, handle known dialogs, run a canary, subscribe to the target's release calendar, keep a regression pack, and stop the queue on an unexpected state."

Q5. How do you control a robot so an auditor is satisfied?

"It is a privileged non-human user: a unique named identity from a vault, least-privilege role without approval rights, no developer access to production credentials, the approval done in the case before the work item exists, volume and amount caps with a kill switch, and complete evidence tied to the case. The audit answer is the case history linking the approval, the work item and the screenshot."

Q6. Attended or unattended?

"Attended keeps a human actor on the transaction, so attribution and maker-checker are simpler, and it suits agent-desktop work. Unattended suits back-office batch but needs the strongest controls on money-affecting screens. For a risky screen I start attended, then move to unattended with caps, pre-checks and read-back."

Q7. Is RPA cheaper than an API?

"Cheaper to start, often not over five years. I include licences, VMs, session licences, monitoring, exception handling, maintenance after UI changes and audit costs, and compare with the API's build and run cost. In an illustrative example at 300 items a week the bot is break-even before build cost, while the API pays back in about two years."

Q8. How do you handle document inputs to a robot?

"OCR or document extraction with a confidence score on every field, validation rules, and a mandatory human verification of key fields, such as order number, amount and due date, for legal orders until measured accuracy proves otherwise. Low-confidence documents go to manual keying, the human confirmation is recorded, and the extraction is governed as a model."

Q9. How do you retire a bot?

"Plan it before building: a charter with a named owner, end date, the API milestone and a stop rule. At cutover, send new items to the API, drain the queue, disable the schedule, revoke credentials and vault entries, release VMs and licences, archive evidence per retention and close the access-review entries. Because the case owned the process, the change is the case calling an integration instead of creating a work item."

Q10. What would you do at 2 a.m. when a robot queue stalls?

"Assess scope (one robot or all, which error, since when), contain first by stopping the queue if it is systemic and money-adjacent, switch to the manual fallback, capture evidence, diagnose by symptom (login, screen not found, timeout, one VM), fix and verify with a canary, resume at limited concurrency, reconcile manual against queued with the idempotency pre-check, then run an RCA with a prevention action."

9.Z Where we are now

What the application can do

The one step with no API is no longer a gap. A queued work item for AC-10882 goes to a robot, which verifies the screen, checks for an existing restraint, keys it, reads back the confirmation and returns a structured result the case records with evidence; a changed screen stops the robot instead of mis-keying; an ambiguous timeout is treated as unknown and verified; and there is a written plan for retiring the robot when an interface exists.

The mechanisms behind it

A framework for choosing between an interface and a robot; attended and unattended modes; Robot Studio, Runtime and Manager with work queues and pools; a case that owns state with a bot as worker; adapters and match rules; classification of business and system exceptions, with an unknown outcome handled by pre-check, verification and reconciliation; a controlled identity with least privilege and dual control in the case; and a bridge charter with a decommission plan.

What it still cannot do

The application now takes in files, events, emails and screens, and it is time to ask who is allowed to do what with all of it, how it is deployed and how it is watched. Access control, identity, deployment pipelines, monitoring and incident handling are Chapter 10.
