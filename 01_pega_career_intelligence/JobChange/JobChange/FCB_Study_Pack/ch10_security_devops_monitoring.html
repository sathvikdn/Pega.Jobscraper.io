10.2 The access model: where Marcus is refused and Priya is not

Marcus clicks Approve on AM-10417 and nothing happens, and then he sends the same action through the DX API with a crafted request, because the front end is only a client. Both are refused. The reason is that Pega's access control answers a single question at the point of every operation, whatever the channel: which user, in which application context, may do what to which kind of object, under which conditions? It is built from a chain of records. A person (an Operator ID) belongs to an Access Group, which names an application and a set of Access Roles. Each role has Access of Role to Object (ARO) rules that grant permissions on classes of objects, optional Privileges for specific actions, and Access When conditions that make permissions depend on data. Access Deny rules block access explicitly and override grants. Authorisation in hand-coded systems is scattered through controllers; in Pega it is declarative and attached to the model, so the engine enforces it in the UI, reports, services, the DX API and background processing alike. That is the strength, and the risk is an under-designed role set that grants far more than intended with nobody able to explain who can do what.

Priya's approval of the same case reaches step 2: she holds a Checker role with the ApproveChange privilege, the Access Deny condition is false because she did not prepare it, and the ARO grants the action. Her second attempt, editing Dana's captured address while she is meant only to approve, fails at step 3: the Checker role has no modify grant outside the approval assignment, and the Access When on that grant is false. Her third, bulk-reassigning the approval queue, succeeds, because the Supervisor role inherits Checker and adds the reassign privileges. Each outcome is a rule, not a screen.

The same attempt through the interface illustrates why UI hiding is not security. If the Approve button were only hidden from makers by a visibility condition, Marcus would not see it, and a crafted request, another channel or a service call could still reach the rule that does the work. Privileges are therefore required on the rule that does the work (flow action, activity, data page, report, service) and the UI merely reflects them. A privilege on a flow action means a user without it does not see or cannot run it; a privilege on an activity or data page restricts who can run or read it, including from services; a report definition's privilege controls who can run it; and a Service-REST or DX API caller is bounded by the service access group and privileges. The server-side Validate rule on the Approve action is a second layer that rejects maker equals approver even if the grant were wrong (Chapter 04 §4.2).

The permission grid, and what the 0–5 numbers mean

Priya's role works in production and Marcus's colleague's new "diagnostics" role does not, and the reason is the part of the ARO most candidates get wrong. Each ARO corresponds to one access role and one class and defines the access controls the role has over instances of that class. The controls are named on the rule form: Open instances, Modify instances (save new or modified instances), Delete instances, Run reports and Execute activities (whose Applies-to class is this class). Practitioners shorthand this as read, write, delete and execute, which is fine in conversation, but using the form's own wording signals that the rule has actually been opened. For each control one enters either a production level (0 to 5) or an Access When rule name. Pega's documentation states that the production level is compared with the production level of the current system, that the permission is granted only if the access control's level is greater than or equal to the system's, that 0 gives no access and 5 allows access on all systems, and that it is possible to enter an Access When rule name instead, which is evaluated to decide access.

Permission is granted only if the access control's production level >= the production level of the current system 0 (or blank) = no access 5 = access on all systems System production levels: 1 Experimental / Sandbox 2 Development 3 Test / QA 4 Pre-production / Staging 5 Production

The level is not a "how much access" dial; it is a "on which systems" dial. A setting of 5 grants the permission everywhere including production, while a setting of 3 grants it on development and test systems but silently withdraws it in staging and production. That is the mechanism behind the classic complaint that it worked in QA and the button is missing in production, and the diagnosis is to read the ARO that governs the action and compare its production levels with the system's. Used deliberately, it is a genuine control: diagnostic and administrative capabilities get a level below 5 so they cannot be exercised in production even if the role is accidentally granted there, while business permissions get 5 and are constrained by Access When conditions. An over-broad role assignment in production then fails safe. Access Manager and the ARO rule form expose slightly different production-level options, and Pega-supplied roles arrive pre-populated, so the actual ARO is read and not recited.

The anti-patterns are using Pega-supplied broad roles as-is in production, an "all privileges" role for everyone, a role per person, permissions granted at the top class when only one case type needs them, relying on UI visibility, a production access group that includes developer or admin roles, and no periodic access review.

Check your understanding.

A new "reassign" privilege works in the QA system and for Priya's supervisor tests, but in production the Reassign action is missing for the real supervisors, and the access group and role assignments look identical in both systems. What do you check first, and what is the likely cause?

Answer. Read the ARO that grants the reassign privilege and look at its production levels: a level of 3 or 4 on the relevant controls would grant it in QA and withdraw it in staging and production without any error. The fix is to set the business permission to 5 and constrain it with Access When. This explains the symptom only if the action is governed by an ARO production level; if the levels are 5, the next suspects are an Access Deny with a condition true only in production data, a ruleset version in the production access group that predates the privilege, or a missing data instance in the deployment package.

10.3 Designing the deposit-ops role set

Marcus's refusal and Priya's success are two rows of a role set that someone designed. A bank will ask for that design on a whiteboard, and the method is to start from duties, not people, express each duty as privileges and AROs, then check segregation of duties. 10.4 Segregation of duties, made explicit

The refusal of Marcus's approval is one instance of a general principle. Segregation of duties (SoD) means no single person can complete a sensitive process end to end, because that would allow error or fraud to pass unnoticed. Maker-checker is its most visible form, and SoD also applies across roles (a developer should not deploy their own code to production) and across lifecycles (the person who creates a user should not approve their access).

10.5 Conditional access, field-level security, masking and encryption

Role-based access answers "what can a Checker do", and it struggles with conditions on data: only cases for my branch, only accounts in my state, only if the customer is not an employee. Pega offers conditional mechanisms. Access When on AROs evaluates a condition on the instance and the current operator, such as modify only if the status is open and the case belongs to the operator's work group. Attribute-based access control applies policy conditions on attributes of the user and the data, to classes and, in some releases, individual properties, managed separately from roles (deny read of high-profile accounts to anyone outside the VIP team). Client-based access control restricts by client or tenant attribute in multi-entity setups. Work-group and organisation hierarchy conditions limit a supervisor to their team, and data page and report privileges control who can read sensitive data pages and run sensitive reports. Availability, authoring screens and enforcement scope (for example property-level restriction) of ABAC and client-based control depend on the release, so the concept is described, the capability confirmed on the target version, and always paired with Access When and privileges.

10.6 Authentication wiring, API security, timeouts and the OWASP view

Chapter 05 covered how OAuth, SAML, JWT validation, mTLS and rotation work. What follows is the Pega-side wiring and governance around them, which an auditor asks about as a checklist. Employees authenticate by SAML or OIDC against the corporate identity provider and technical callers by token or certificate, with no local passwords for humans in production except a controlled break-glass account. Operators are provisioned just in time with the access group derived from IdP group claims through a controlled mapping table, unmapped users are denied and mapping changes are change-controlled. Idle timeouts for operations users are short (15 to 20 minutes, set by policy), with an absolute session lifetime, re-authentication for sensitive actions, and full logout on shared workstations. Multi-factor authentication is enforced at the IdP and Pega relies on the assertion's authentication context, with step-up for high-risk actions where the IdP supports it. One or two locally authenticated emergency accounts hold credentials in a vault, and their use triggers an alert and review and is followed by rotation. Every Service-REST requires authentication with token validation or mTLS and a least-privilege service access group, and lockout and brute-force handling sit at the IdP, with Pega login failures going to the security alert log and onward to the SIEM.

10.8 What each diagnostic tool reveals, and what it cannot

Before the deployment and the incident, the tools need to be distinguished by the question each uniquely answers, because the common failure in an incident is reaching for the tool one knows and getting an answer to a different question. Dual control and segregation of duties apply to the pipeline itself: the pipeline service accounts can deploy but not edit rules; developers can edit in development but cannot trigger production deployment; production deployment needs an approval by someone other than the developer and the person who triggered it; emergency changes follow an expedited approval path with retrospective review, never a bypass; and pipeline configuration changes are controlled and audited. The environments have distinct purposes: development (synthetic data, full developer rights there only), integration or build (merged build against stubs), QA (regression, stable test data), UAT (business acceptance, a frozen release candidate), staging (production-like rehearsal for performance, deployment and rollback) and production (locked, controlled access). The release-26.3 pipeline passes every gate: the widget works in QA with a few hundred cases, and the performance check, run against QA's small data volume, finds no problem. That omission is where the incident begins.

The failures to avoid are importing archives by hand into production, different packages built for different environments, production deployment by the developer who wrote the change, gates an admin can skip without a trace, skipping the staging rehearsal for schema changes, and environment data inside the package.

10.12 Rollback, hotfix and release evidence

When release 26.3 misbehaves, the first instinct is "redeploy the previous version". For rule-only changes that largely works, since rules are versioned and the application can be pointed back to the previous ruleset versions. For anything that changed state it does not, because rolling back code does not roll back what the new code has already done.

Rollback becomes real through a set of strategies. Expand and contract for schema and data: release 1 adds the new column, with code writing both and reading the old; release 2 switches reads to the new and backfills; release 3 stops writing the old and later drops it, so at every step the previous release still works. Backward-compatible releases (N and N-1 compatible). Feature toggles, in which new behaviour is guarded by a switch held as configuration, so turning it off is faster and safer than redeploying. Roll forward when the fault is small and the state has changed, with a decision owner defined in advance. Rolling or canary deployment, switching a subset of access groups first. Backup and point-in-time recovery is a disaster option and not a rollback tool, since restoring loses all work since the restore point. Rehearsal in staging executes and times both deployment and rollback. And rollback decision criteria are written before the release: error rate above X, a severe defect in a core journey, a reconciliation break, with a decision owner and a time limit.

Release evidence for audit is the set of records the pipeline should already hold: the change request with justification and risk assessment; the scope (rules, data instances and DDL changed); code review and merge approvals; the guardrail score and warnings report; test results (PegaUnit, scenario, API, performance, access); UAT sign-off; production approval by someone independent of the developer and deployer; the package identity (version and hash); the deployment log with who triggered it; post-deployment verification (smoke tests, health checks, alert trends); the rollback plan and any decision record; and the locked ruleset versions.

10.13 A production incident, in order: symptom to prevention

Symptom, then evidence

The first fifteen minutes follow a checklist: acknowledge the report and open the incident record with the start time and detection source; assess impact and set severity; identify what changed (a release, a configuration, a data load); look at the aggregate view before any single user; contain if there is a safe, fast containment; communicate to the stakeholders on the cadence; and keep a timeline. The aggregate view is PDC and the alert log, and they answer a question about the whole cluster over time. The HTTP-interaction-time alerts for the supervisor dashboard rule start at 02:12, twelve minutes after the 02:00 deployment, and the slow-query alerts start at the same time; before 02:00 there are none. That evidence establishes when and what changed, and it narrows the suspects to release 26.3. What PDC cannot say is why Priya's one screen is slow, which is the next tool's question.

Hypothesis, then the tool that tests it

The hypothesis, given the new widget, is that it loads its data in a way that does not scale to production volume: either an unbounded query on an unexposed column, or one query per row. The tool that discriminates between them is PAL, run on a reproduction of Priya's screen, because the two hypotheses predict different interaction counts. It reports 212 database interactions and about 11.8 seconds of the 14 spent in the database; a screen that loads one list should make a handful. A count in the hundreds is the signature of one query per row, the N+1 pattern from Chapter 06 §6.8. PAL says that the screen makes 212 queries; it cannot say which rule is responsible. Tracer, run on the same reproduction in staging (not left running in production), shows the data page for a single case being resolved once for each of the 200-odd rows of the widget. The database trace shows the single statement repeated, and EXPLAIN on it, with the DBA, shows a sequential scan on a work table because the filter column is not exposed and indexed (Chapter 03 §3.3, Chapter 11). Each tool answered the question the previous one raised, in order of scope: cluster and time, then one requestor's counters, then the rule sequence, then the statement, then the plan.

Containment, verification, prevention

Containment comes before the proper fix, and it is the feature toggle designed in the release: the dashboard widget is switched off by a configuration value, with no redeployment, and Priya's screen returns to about two seconds. This is containment and not a fix, and it is stated as such in the incident record. Verification then uses two independent checks: PAL on the same scenario shows the interaction count back to a handful, and the PDC before and after trend shows the alerts falling to the pre-release baseline, which is the evidence that closes the incident. The permanent fix (load the widget's rows with one set-based query on an exposed, indexed column, with pagination) goes through the pipeline as a normal change, with the toggle turned back on only after it is verified in staging at production-like volume. Prevention is what the root-cause analysis in 10.14 turns into pipeline gates and standards. The ownership throughout is the method, not the heroics: evidence before containment, containment before fixing, and a verification step that someone other than the author can read.

10.14 Root cause analysis, prevention and handover

An incident is closed when it will not recur, and that is a different question from whether it is fixed. A root-cause analysis separates the trigger (the release introduced the query) from the cause (a defect in how the widget loads data) from the contributing conditions (the QA data volume was small enough that nothing looked wrong; the pipeline had no gate on interaction counts; the toggle existed, which is why impact was brief). The five whys applied to the incident run: the screen was slow because it issued 212 queries; because the widget resolved a data page per row; because the developer built it as the case-level pattern was built; because no standard or review item flagged N+1 for list widgets; because no performance gate exercises list widgets at production-like volume; and so the preventive actions are a standard and review item, a pipeline gate comparing PAL interaction counts and alert counts with a baseline on a production-like data set, an exposed and indexed filter column, and a regression test for the dashboard.

The review itself is blameless and evidence-based: a timeline with timestamps and sources, the impact (who, how long, what was affected), what worked (the toggle, the trend evidence), what did not, the root cause and contributing factors, and owned, dated actions that are tracked to completion and reported to the service owner. Handover between shifts in 24/7 support follows the same discipline: the open incidents with their severity and next action, what has been tried and what is ruled out, the evidence captured, the containment in place and who owns the next step, so the next engineer does not repeat work or undo containment. The method, severity first, evidence before containment, containment before fix, verification by trend and by reproduction, and prevention as a pipeline gate, is the reusable part.

10.16 Interview Q&A

Q1. Walk me through Pega's access model.

"An operator belongs to an access group, which names the application and the access roles. Roles carry Access of Role to Object rules that grant Open, Modify, Delete, Run reports and Execute activities per class, with privileges and Access When conditions, and Access Deny rules override grants. The default is deny, permissions are the union of role grants minus denies, and everything is enforced server-side in every channel."

Q2. Why is hiding a button not security?

"A hidden control only affects the screen. A crafted request or another channel such as the DX API can reach the rule that does the work, so the privilege or Access When is required on that rule, with server-side validation as a second layer. I test the denial through the API too."

Q3. It worked in QA but the button is missing in production. What do you check?

"The ARO's production levels. The level is a 'which systems' control: an access control passes only when its level is at least the system's production level, so a 3 grants in QA and withdraws in staging and production without an error. Then access group ruleset versions, an Access Deny condition, and whether the data instance made it into the package."

Q4. How do you enforce maker-checker?

"In four independent layers: routing excludes the maker from the approvers' queue; an Access Deny blocks the approve privilege when the maker is the current operator; a server-side validation on the action rejects maker equals approver; and a daily detection report that should be zero. I test the edge cases: reassignment to the maker, bulk approval, delegation and the DX API."

Q5. What do Tracer, PAL, PDC and the logs each tell you, and not tell you?

"PDC and the alert logs show the cluster over time: what is new or growing and whether a fix worked, but not why one user's screen is slow. PAL gives one requestor's counts and timings, so it exposes N+1, but not which rule is responsible. Tracer shows the rule sequence and resolution for one session, but nothing across nodes or over time, and is used briefly and carefully in production. The database trace and EXPLAIN give the statement and plan. I move from the widest scope to the narrowest."

Q6. Describe your incident method.

"Set severity by impact, then symptom, evidence from the aggregate view, a hypothesis, the diagnostic tool that discriminates between hypotheses, containment before the fix, verification by trend and by reproduction, and prevention as a pipeline gate or standard. Evidence before containment, and a blameless review with owned actions."

Q7. Why is 'redeploy the previous version' not a rollback plan?

"Because code rollback does not undo state: schema, data migrations, in-flight cases, queue items, outbound messages and reference data. I design releases backward compatible with expand and contract, use feature toggles to switch behaviour off without a deployment, rehearse deployment and rollback in staging, and write rollback criteria and the decision owner before the window. Point-in-time restore is a disaster option."

Q8. What gates would you put in a Pega pipeline?

"Peer-reviewed merge, a guardrail score threshold with no new severe warnings, PegaUnit at full pass, coverage on regulatory rules, scenario and API tests including negative access tests, secret and environment-data scans, a performance check against production-like volume comparing interaction counts with a baseline, an environment parity check, and dual control on production approval. The same artifact is promoted through environments."

Q9. How do you handle sensitive data across environments?

"Synthetic data where possible, otherwise irreversible masking with referential integrity preserved, including the BLOB, because masking only exposed columns leaves personal data in the serialised page. Outbound channels are disabled or redirected in test, and egress paths such as exports, logs and AI prompts are controlled."

Q10. How do you trace one transaction across Pega, the ESB and the core?

"A correlation ID generated at the start, stored on the case, sent on every call and written to logs. In the log platform one search across the three indexes sorted by time reconstructs the timeline, which in a timeout case shows whether the first attempt completed late, so I can see that an unknown-outcome status and an idempotency key behaved correctly."

Q11. Containment or fix first?

"Containment first, when harm is ongoing: it limits harm and restores service in minutes (pause a processor, toggle a feature off, manual fallback, throttle, restart after capturing evidence). The fix removes the root cause through the change process, the hotfix path if urgent. The risks are hiding the problem or losing evidence on the containment side, and a rushed change causing a second incident on the fix side."

Q12. How do you do a root-cause analysis?

"Blameless: a timeline from logs and the scribe's notes, the impact, then five whys down to the conditions that allowed it, usually a process or detection gap as well as a technical cause. Actions are corrective, preventive, detective and mitigating, each with an owner and date. I verify detective controls by breaking the thing deliberately in staging and confirm the fix with a PDC before and after trend. When SLA escalations silently stopped overnight, the deepest cause was that nobody was alerted on a stalled processor or a missing node type, so the actions added those alerts and a synthetic SLA test, not just a restart."

Q13. What is your hotfix process?

"Triage and look for a workaround first; emergency approval by named approvers who are not the developer; branch from the exact production ruleset version; a minimal fix with a test that reproduces the defect; a patch ruleset version through the product rule and the pipeline with expedited but real gates; verification in a production-like environment; deployment in a window with smoke tests and a PDC watch; backport to the main line; and a retrospective. It is the normal pipeline accelerated, never bypassed."

Q14. What release evidence would an auditor want?

"The change request and risk assessment, the scope of rules, data and DDL, review and merge approvals, the guardrail score, test results across PegaUnit, scenario, API and access tests, UAT sign-off, an independent production approval, the package version and hash, the deployment log, post-deployment verification, locked ruleset versions and the rollback plan. The pipeline produces most of it automatically, which is a reason to use it."

10.Z Where we are now

What the application can do

Marcus is refused when he tries to approve his own change, by the rule and not the screen; Priya can approve, reassign and supervise but not edit capture data; a release reaches production through gates with dual control; and a production slowdown is diagnosed from the widest evidence to the narrowest, contained by a toggle and verified by trend.

The mechanisms behind it

Declarative access control with default deny, Access Deny and ARO production levels; four-layer maker-checker; masking, encryption and audit layers; tools matched to the question each answers; a pipeline of build-once, promote-many with gates; rollback by compatibility and toggles; and an incident method that ends in prevention.

What it still cannot do

Most of the evidence in this chapter ended in a database: an unexposed column, a sequential scan, a lock. The application's data lives in tables, and understanding what a query does, how concurrent sessions affect Dana's row and why a plan changes is the subject of Chapter 11.
