11.2 The dataset

The tables are few: customers, their accounts, a ledger of transactions, holds, a balance summary, and a small case history that mirrors AM-10417. The balances for Dana's checking account follow the ledger: $4,418.55 ledger at 07:30 on 9 March, with a $200.00 card authorisation outstanding, so $4,218.55 available. Amounts are NUMERIC(14,2), never floating point.

-- POSTGRESQL: SCHEMA CREATE TABLE customers ( customer_id INTEGER PRIMARY KEY, customer_ref TEXT UNIQUE, -- NULL where the reference is not in this teaching set full_name TEXT NOT NULL ); CREATE TABLE accounts ( account_id INTEGER PRIMARY KEY, account_number VARCHAR(17) NOT NULL UNIQUE, customer_id INTEGER NOT NULL REFERENCES customers(customer_id), product_code TEXT NOT NULL, status TEXT NOT NULL CHECK (status IN ('ACTIVE','DORMANT','FROZEN','CLOSED')), opened_on DATE NOT NULL, closed_on DATE -- NULL while the account is open ); CREATE TABLE transactions ( txn_id INTEGER PRIMARY KEY, account_id INTEGER NOT NULL REFERENCES accounts(account_id), posted_on DATE NOT NULL, amount NUMERIC(14,2) NOT NULL, -- signed: credits positive, debits negative txn_type TEXT NOT NULL ); CREATE TABLE holds ( hold_id INTEGER PRIMARY KEY, account_id INTEGER NOT NULL REFERENCES accounts(account_id), hold_type TEXT NOT NULL, -- CARD_AUTH, LEGAL, DEPOSIT amount NUMERIC(14,2) NOT NULL CHECK (amount >= 0), status TEXT NOT NULL CHECK (status IN ('ACTIVE','RELEASED')), legal_order_no TEXT -- only for LEGAL holds ); CREATE TABLE balances ( -- a maintained summary (denormalised), used for the concurrency examples account_id INTEGER PRIMARY KEY REFERENCES accounts(account_id), ledger_balance NUMERIC(14,2) NOT NULL, row_version INTEGER NOT NULL DEFAULT 1 ); CREATE TABLE case_history ( -- the history of case AM-10417, as it would be recorded hist_id INTEGER PRIMARY KEY, case_id TEXT NOT NULL, actor TEXT NOT NULL, action TEXT NOT NULL, at_ts TIMESTAMP NOT NULL -- shown without a zone to keep the example short );

Two properties of the data are chosen on purpose and worth noticing before any query is written. Customers 2 and 3 have a NULL customer_ref, which sets up a NULL trap in 11.3. And the balances table is a denormalised summary of the ledger: a maintained copy that must always equal the sum of transactions, which is why a reconciliation query appears in 11.13. Denormalising is a deliberate copy for read speed, with one owner of the write path, because every copy can drift.

11.3 Types, NULL and keys, through three small questions

A relational database stores data in tables of typed columns and rows, linked by keys, and SQL is declarative: the query says what result is wanted and the optimiser decides how to get it. That separation of the logical view from physical storage, together with integrity rules, concurrent-access control and a standard language, is why banks rely on it: balances, holds and legal orders must be consistent, auditable and recoverable.

Question 1: how does money behave? The first rule of the schema is the type. NUMERIC(p,s) is exact decimal arithmetic; REAL and DOUBLE PRECISION are binary floating point, which cannot represent 0.10 exactly, so 0.1 + 0.2 is not 0.3. Money is therefore always NUMERIC.

-- POSTGRESQL SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision AS float_equal, 0.1::numeric + 0.2::numeric = 0.3::numeric AS numeric_equal; float_equal | numeric_equal -------------+--------------- f | t WHY: binary floating point stores 0.1 and 0.2 as nearby binary fractions, so their sum is not exactly the nearest double to 0.3; NUMERIC keeps decimal digits.

The other types that matter in deposits are BIGINT and INTEGER for surrogate keys and counters (account numbers are not stored as integers: leading zeros, check digits and length changes), VARCHAR/TEXT for numbers and codes (trailing spaces and case differences break equality joins, so values are normalised on write), DATE for business dates such as a maturity or response due date (no time zone, which is right for a business date and wrong for an instant), TIMESTAMPTZ for instants (the zone-less TIMESTAMP is ambiguous), BOOLEAN (three values including NULL), BYTEA for binary data such as Pega's BLOB column, which SQL cannot filter, and JSONB for semi-structured payloads, which are indexable with GIN and are no substitute for modelling.

Question 2: which customers are not Dana? This looks trivial, and it returns the wrong answer.

-- POSTGRESQL SELECT customer_id, full_name FROM customers WHERE customer_ref <> 'CUS-4417'; customer_id | full_name -------------+----------- (0 rows) SELECT customer_id, full_name FROM customers WHERE customer_ref IS DISTINCT FROM 'CUS-4417' ORDER BY customer_id; customer_id | full_name -------------+-------------------- 2 | Victor Osei 3 | Harlow Freight Co. WHY: NULL means "unknown", not zero or empty. NULL <> 'CUS-4417' is not true or false but UNKNOWN, and WHERE keeps only rows whose condition is true, so both customers whose reference is NULL are silently dropped. IS DISTINCT FROM is the null-safe inequality.

SQL has three truth values, and the rules to remember are these. NULL = NULL is unknown, so IS NULL or IS NOT DISTINCT FROM is used. NULL AND false is false and NULL OR true is true, since some combinations resolve despite the unknown, but NOT (NULL) is unknown. x NOT IN (1, 2, NULL) is never true, the classic trap that makes NOT IN return no rows when the list contains a NULL; prefer NOT EXISTS. COUNT(*) counts rows while COUNT(col) skips NULLs. SUM and AVG ignore NULLs, and the sum of all-NULL is NULL, so COALESCE(SUM(x),0) where a zero is wanted. Two dialect differences follow: a UNIQUE constraint allows multiple NULLs in PostgreSQL and only one in SQL Server, and ascending ORDER BY sorts NULLs last in PostgreSQL and first in SQL Server.

Question 3: what stops bad data entering? Constraints are the cheapest and most reliable control. A primary key identifies a row uniquely; a unique constraint prevents duplicates (account_number), a foreign key prevents orphans, a CHECK constraint enforces a row-level rule (amount >= 0), and NOT NULL and DEFAULT enforce mandatory and default values. Using a surrogate primary key plus a unique natural key is safer than the natural key alone, because an account number can change format and a surrogate does not. Banks rarely cascade deletes of financial records and use RESTRICT with soft deletes (a status). A unique constraint on (interface_name, sha256) in a file registry (Chapter 07 §7.10) prevents a duplicate file even when two nodes race, which an application check alone cannot.

-- POSTGRESQL: a constraint refusing what an application check might miss INSERT INTO holds VALUES (4, 1, 'CARD_AUTH', -50.00, 'ACTIVE', NULL); ERROR: new row for relation "holds" violates check constraint "holds_amount_check" INSERT INTO accounts VALUES (5,'CHK-8842-0117',1,'CHK01','ACTIVE','2026-03-09',NULL); ERROR: duplicate key value violates unique constraint "accounts_account_number_key"

Normalisation is the discipline behind a schema like this. First normal form wants each column atomic, with no repeating groups (signers = 'A, B' in one column becomes a table). Second normal form wants every non-key column to depend on the whole key, which matters for composite keys. Third normal form wants non-key columns to depend only on the key and not on other non-key columns (a product name depends on the product code, so it belongs in a products table). Sensible denormalisation is a deliberate, measured copy for performance or history: a stored running balance, a maintained summary like balances, a snapshot of the customer's address on a legal order at the time of processing (it must not change when the customer later moves), and exposed columns in Pega work tables (Chapter 03 §3.3).

Design decisions on this schema, and what breaks without them

Each choice in the dataset is a decision with a failure behind it, and it is worth making the failure visible once.

Why money is NUMERIC. Summing ten amounts of 0.10 should give exactly 1.00. With binary floating point it does not.

-- POSTGRESQL SELECT sum(0.1::double precision) AS as_float, sum(0.1::numeric) AS as_numeric FROM generate_series(1,10); as_float | as_numeric -----------------------+------------ 0.9999999999999999 | 1.0 WHY: each 0.1 is stored as the nearest binary fraction, and the tiny errors accumulate; NUMERIC keeps decimal digits and adds them exactly. On a ledger of millions of rows, float drift is a reconciliation break with no cause anyone can find. NUMERIC(14,2) also enforces two decimal places and a ceiling, so a corrupt amount is refused at insert.

Why instants are TIMESTAMPTZ. A zone-less TIMESTAMP records a wall-clock reading with no instant behind it, so the same text can mean two moments across a daylight-saving change or across the India and US teams. TIMESTAMPTZ stores a single instant (internally UTC) and renders it in the session's zone, so everyone agrees on when and differs only in how it is displayed. Priya's Monday afternoon rejection can be stored once and shown to each reader in their own zone.

-- POSTGRESQL: one stored instant, displayed in the zone of the reader SELECT TIMESTAMPTZ '2026-03-02 20:20:00+00' AT TIME ZONE 'America/New_York' AS eastern_wall_clock; eastern_wall_clock --------------------- 2026-03-02 15:20:00 WHY: Eastern Standard Time is five hours behind UTC on 2 March (daylight saving began on 8 March), so 20:20 UTC is 15:20 in New York, Monday afternoon. A business DATE (a due date, a maturity date) is a different thing and correctly has no zone.

Why holds are their own table. A hold is not a transaction: it does not change the ledger balance, it has a lifecycle (ACTIVE, then RELEASED), several can exist at once, and its history matters (the released $500.00 deposit hold on Dana's savings is still a fact). Putting a single held_amount column on the account row would lose the history, make two concurrent holds update the same row, and make "what was held last Tuesday" unanswerable. As a separate table it is queried with SUM(...) WHERE status = 'ACTIVE', as in 11.5, and each hold keeps its own legal order reference.

What breaks if the balance is denormalised, and what protects it. The balances table is a copy of what the ledger says. If one code path inserts a transaction and forgets to update it, the copy drifts silently.

-- POSTGRESQL (inside a transaction that is rolled back, to leave the dataset unchanged) BEGIN; INSERT INTO transactions VALUES (11, 1, '2026-03-09', -25.00, 'FEE'); -- a fee posted, but balances not updated SELECT a.account_number, b.ledger_balance AS summary, SUM(t.amount) AS from_ledger, b.ledger_balance - SUM(t.amount) AS difference FROM balances b JOIN accounts a ON a.account_id = b.account_id JOIN transactions t ON t.account_id = b.account_id GROUP BY a.account_number, b.ledger_balance HAVING b.ledger_balance <> SUM(t.amount); account_number | summary | from_ledger | difference ----------------+---------+-------------+------------ CHK-8842-0117 | 4418.55 | 4393.55 | 25.00 ROLLBACK; WHY: the copy says 4418.55 and the ledger now says 4393.55. A denormalised column is acceptable only with one owner of the write path (one stored procedure or one service that updates both in one transaction) and a reconciliation that proves it (11.13). Without those, every extra copy is a future break.

Keys follow the same logic: each table has a surrogate-style integer key, and the natural identifiers (account_number, customer_ref) are unique constraints, so an account number can change format without breaking a foreign key. Foreign keys should also be indexed on the child side (transactions.account_id, holds.account_id), because without that index a join, or a delete on the parent, scans the whole child table.

Normalisation, as design choices on this schema

Normal forms are the discipline that made this schema look the way it does, and each is a rule with a visible violation. First normal form wants each column to hold one atomic value with no repeating groups. A column signers = 'D. Whitfield, V. Osei' on accounts violates it: finding every account Victor can use needs a string search, and removing one signer rewrites the text. The fix is a separate table with one row per account and holder, which is why Dana's two accounts hang off customer_id and a joint holder would be another row, not another comma. Second normal form wants every non-key column to depend on the whole key, which matters for composite keys: in an account_holders(account_id, customer_id, holder_role, customer_name) table, customer_name depends only on customer_id, so it is repeated on every account the customer holds and updated in many places; it belongs in customers. Third normal form wants non-key columns to depend only on the key and not on each other: if accounts carried both product_code and product_name, the name depends on the code, so a rename must touch every account, and a products table holds it once.

Denormalising is then a measured exception, made for a stated read benefit with one owner of the write path: a stored running balance on a ledger row for fast statements and audit, a maintained summary like balances (with the reconciliation that proves it), a snapshot of the customer's address on a legal order at processing time (so the order records where the customer lived then), and exposed columns on Pega work tables (Chapter 03 §3.3). The rule that unites them is that every copy can drift, so a copy needs an owner and a check.

11.4 Which accounts does Dana hold? Joins, from simple to outer

Business question. Marcus has Dana's customer reference CUS-4417 on AM-10417 and needs her accounts with their ledger balances. The input rows are Dana's customer row, her two account rows and their six transactions. A join combines rows from two tables where a condition matches; the order of tables does not matter to correctness, only to how it is read.

-- POSTGRESQL SELECT a.account_number, a.product_code FROM customers c JOIN accounts a ON a.customer_id = c.customer_id WHERE c.customer_ref = 'CUS-4417' ORDER BY a.account_number; account_number | product_code ----------------+-------------- CHK-8842-0117 | CHK01 SAV-8842-0233 | SAV01 WHY CORRECT: the join condition a.customer_id = c.customer_id pairs each account with its owner; the WHERE keeps only Dana's customer row, so only her two accounts pair. An inner join drops rows with no match on either side.

The join types are best understood by which unmatched rows they keep. An inner join keeps only matching pairs. A left outer join keeps every row of the left table and fills the right side with NULLs where there is no match. A right outer join is the mirror and is rarely used (swap the tables and use a left join). A full outer join keeps unmatched rows from both. A cross join pairs every row with every row and is almost always a mistake outside generating a calendar. A semi-join (EXISTS) asks only whether a match exists and does not multiply rows, and an anti-join (NOT EXISTS, or a left join filtered to NULL) finds rows with no match.

Harder question. Which customers have no active hold on any account? The input rows are three customers, four accounts and three holds, one of which is released.

-- POSTGRESQL: anti-join with NOT EXISTS (null-safe, and cannot multiply rows) SELECT c.full_name FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM accounts a JOIN holds h ON h.account_id = a.account_id WHERE a.customer_id = c.customer_id AND h.status = 'ACTIVE') ORDER BY c.customer_id; full_name -------------------- Harlow Freight Co. WHY CORRECT: Dana has an ACTIVE hold (the 200.00 card authorisation) and Victor an ACTIVE legal hold. Her released DEPOSIT hold on the savings account does not count because the status filter is inside the subquery. Only Harlow has no active hold on any account. -- the same result with a left join (read it as "customers whose join to active holds found nothing") SELECT c.full_name FROM customers c LEFT JOIN accounts a ON a.customer_id = c.customer_id LEFT JOIN holds h ON h.account_id = a.account_id AND h.status = 'ACTIVE' GROUP BY c.customer_id, c.full_name HAVING COUNT(h.hold_id) = 0; -- NOTE the status filter is in the ON clause, not WHERE: in WHERE it would turn the left join back into an inner join and drop the customer.
Check your understanding.

In the left-join version above, a developer moves h.status = 'ACTIVE' from the ON clause to a WHERE clause. What does the query return for the three customers, and why?

Answer. It returns no rows at all. For Harlow, the left join produces a row with NULL in every h column; the WHERE h.status = 'ACTIVE' is then unknown for that row and the row is dropped, along with every other row that has no matching active hold, so the outer join has behaved as an inner join and the HAVING COUNT(...) = 0 has nothing left to test. Conditions on the optional side of an outer join belong in the ON clause. This is true for outer joins in both dialects; it is a property of how NULLs and WHERE interact, not of PostgreSQL.

11.5 What can each account actually spend? Aggregates, fan-out, CTEs, HAVING and CASE

Business question. For every account, what are the ledger balance, the amount currently held and the available balance? This is the number a teller or the closure screen needs. The input rows are the ten transactions and the three holds, one of them released. Aggregation collapses rows into groups: SUM(amount) per account gives the ledger, and the available balance is the ledger minus active holds. The obvious attempt joins both tables at once, and it is wrong in a way that is worth seeing.

-- POSTGRESQL: THE WRONG WAY (fan-out) SELECT a.account_number, SUM(t.amount) AS ledger, SUM(h.amount) AS held FROM accounts a JOIN transactions t ON t.account_id = a.account_id LEFT JOIN holds h ON h.account_id = a.account_id AND h.status = 'ACTIVE' WHERE a.account_number = 'CHK-8842-0117' GROUP BY a.account_number; account_number | ledger | held ----------------+---------+-------- CHK-8842-0117 | 4418.55 | 800.00 <-- the hold is 200.00 WHY WRONG: the account has 4 transactions and 1 hold. Joining both multiplies them: 4 x 1 = 4 rows, each carrying the 200.00 hold, so SUM(h.amount) = 800.00. The ledger happened to survive because there is only one hold row; with two active holds, SUM(t.amount) would be doubled as well. Never aggregate two independent one-to-many branches in one join.

The fix is to aggregate each branch to one row per account before joining, with a common table expression (CTE), a named subquery that reads top to bottom like steps.

-- POSTGRESQL: THE RIGHT WAY WITH ledger AS ( SELECT account_id, SUM(amount) AS ledger_balance FROM transactions GROUP BY account_id ), held AS ( SELECT account_id, SUM(amount) AS held_amount FROM holds WHERE status = 'ACTIVE' GROUP BY account_id ) SELECT a.account_number, l.ledger_balance, COALESCE(h.held_amount, 0) AS held_amount, l.ledger_balance - COALESCE(h.held_amount, 0) AS available FROM accounts a JOIN ledger l ON l.account_id = a.account_id LEFT JOIN held h ON h.account_id = a.account_id ORDER BY a.account_id; account_number | ledger_balance | held_amount | available ----------------+----------------+-------------+----------- CHK-8842-0117 | 4418.55 | 200.00 | 4218.55 SAV-8842-0233 | 12040.00 | 0.00 | 12040.00 CHK-8842-0719 | 2310.40 | 1500.00 | 810.40 CHK-8842-1055 | 58900.00 | 0.00 | 58900.00 WHY CORRECT: each CTE yields exactly one row per account, so the joins cannot multiply rows. The LEFT JOIN keeps accounts with no active hold (their held_amount is NULL, which COALESCE turns into 0). The released 500.00 hold on the savings account is excluded by WHERE status = 'ACTIVE'. Dana's checking figure, 4,218.55, is the available balance in the ledger. Check by hand: 2500.00 - 120.45 + 2100.00 - 61.00 = 4418.55; minus the 200.00 authorisation = 4218.55.

Aggregate functions summarise a group (COUNT, SUM, AVG, MIN, MAX), GROUP BY defines the groups, and HAVING filters groups after aggregation as WHERE filters rows before it. A question that needs HAVING: which customers have more than $10,000 on deposit in total?

-- POSTGRESQL SELECT c.full_name, SUM(t.amount) AS total_on_deposit FROM customers c JOIN accounts a ON a.customer_id = c.customer_id JOIN transactions t ON t.account_id = a.account_id GROUP BY c.customer_id, c.full_name HAVING SUM(t.amount) > 10000 ORDER BY total_on_deposit DESC; full_name | total_on_deposit ----------------------+------------------ Harlow Freight Co. | 58900.00 Dana Whitfield | 16458.55 WHY CORRECT: Dana's two accounts sum to 4418.55 + 12040.00 = 16458.55; Victor's 2310.40 fails the HAVING test. There is a single branch (transactions) in this join, so no fan-out.

Two further tools finish the section. CASE classifies rows (CASE WHEN available < 1000 THEN 'LOW' WHEN available < 10000 THEN 'STANDARD' ELSE 'HIGH' END labels Victor's 810.40 as LOW and Dana's checking as STANDARD) and conditional aggregates count or sum inside one pass (count(*) FILTER (WHERE status = 'ACTIVE') in PostgreSQL; SUM(CASE WHEN status = 'ACTIVE' THEN 1 ELSE 0 END) in SQL Server). Set operations combine whole result sets: UNION removes duplicates and UNION ALL keeps them and is faster (the right default), INTERSECT keeps rows in both, and EXCEPT (MINUS in Oracle, EXCEPT in SQL Server) keeps rows in the first but not the second, which is a compact way to express "in the file but not in the ledger" during reconciliation. A correlated subquery (one that refers to the outer row) is run conceptually once per outer row and is usually clearer or faster rewritten as a join or EXISTS.

11.6 What happened in order? Window functions

Business question. Priya wants Dana's checking statement with the balance after each transaction. Aggregation cannot answer it, because GROUP BY collapses the rows, and the question needs every row kept and a running figure beside each. A window function computes over a set of related rows, the window, without collapsing them. The input rows are the four transactions on account 1.

-- POSTGRESQL SELECT posted_on, txn_type, amount, SUM(amount) OVER (ORDER BY posted_on, txn_id) AS balance_after FROM transactions WHERE account_id = 1 ORDER BY posted_on, txn_id; posted_on | txn_type | amount | balance_after ------------+----------+----------+--------------- 2026-03-02 | ACH_CR | 2500.00 | 2500.00 2026-03-03 | CHECK | -120.45 | 2379.55 2026-03-04 | ACH_CR | 2100.00 | 4479.55 2026-03-05 | CARD | -61.00 | 4418.55 WHY CORRECT: OVER (ORDER BY ...) turns SUM into a running sum over every row up to and including the current one in that order (the default frame is "unbounded preceding to current row", and including txn_id as a tie-breaker makes the order deterministic). The last value, 4418.55, equals the ledger balance computed by GROUP BY in 11.5, which is the cross-check.

A window has three parts: PARTITION BY (the groups the function restarts in, such as per account), ORDER BY (the order within each partition) and an optional frame (which rows relative to the current row are included). The same pattern answers harder questions. What was the latest transaction on every account? numbers the rows within each account and keeps number one.

A correlated subquery refers to the outer row and is conceptually run once per outer row. 11.7 A snapshot arrives twice, and late: upsert and MERGE

Business question. Chapter 07 loaded the 07:30 balance file, and Chapter 06's EVT-55121 carried the 09:40 settlement. Both write to the same summary row for CHK-8842-0117. How should the summary be written so that it holds the newest balance whether events arrive in order, twice, or late? The statement for "insert if absent, update if present" is an upsert, and the guard that makes it safe for snapshots is the as-of comparison from Chapter 06 §6.3.

-- POSTGRESQL CREATE TABLE balance_snapshot ( account_number VARCHAR(17) PRIMARY KEY, ledger_balance NUMERIC(14,2) NOT NULL, available NUMERIC(14,2) NOT NULL, as_of TIMESTAMPTZ NOT NULL ); -- the upsert (PostgreSQL idiom): needs a unique key to arbitrate; the WHERE makes it a latest-wins guard, legal for full-state snapshots only INSERT INTO balance_snapshot (account_number, ledger_balance, available, as_of) VALUES ('CHK-8842-0117', 4418.55, 4218.55, '2026-03-09 07:30:00+00') ON CONFLICT (account_number) DO UPDATE SET ledger_balance = EXCLUDED.ledger_balance, available = EXCLUDED.available, as_of = EXCLUDED.as_of WHERE EXCLUDED.as_of > balance_snapshot.as_of; -- 1. the 07:30 file row arrives first: INSERT 0 1 row: 4418.55 / 4218.55 / 07:30 -- 2. EVT-55121 (09:40) arrives: same statement with 4218.55, 4218.55, '2026-03-09 09:40:00+00' INSERT 0 1 row: 4218.55 / 4218.55 / 09:40 -- 3. the 07:30 row is delivered AGAIN, late: same statement as step 1 INSERT 0 0 row unchanged: 4218.55 / 4218.55 / 09:40 account_number | ledger_balance | available | as_of ----------------+----------------+-----------+------------------------ CHK-8842-0117 | 4218.55 | 4218.55 | 2026-03-09 09:40:00+00 WHY CORRECT: ON CONFLICT names the key that decides "already present". On a conflict, DO UPDATE runs only if its WHERE is true; in step 3 EXCLUDED.as_of (07:30) is not greater than the stored 09:40, so nothing changes and the command reports 0 rows affected. The write is idempotent (repeating step 2 changes nothing) and order-independent for snapshots. THE LIMIT: this guard is wrong for deltas. A table of debits cannot be written with "latest wins", because every debit is independently meaningful (Chapter 06 §6.3).

The same intent is written differently by dialect, and the two must never be blended. PostgreSQL 15 and later also supports the standard MERGE; SQL Server has had it far longer.

-- POSTGRESQL 15+ (MERGE) MERGE INTO balance_snapshot t USING (VALUES ('CHK-8842-0117', 4218.55, 4218.55, TIMESTAMPTZ '2026-03-09 09:40:00+00')) AS s(account_number, ledger_balance, available, as_of) ON t.account_number = s.account_number WHEN MATCHED AND s.as_of > t.as_of THEN UPDATE SET ledger_balance = s.ledger_balance, available = s.available, as_of = s.as_of WHEN NOT MATCHED THEN INSERT (account_number, ledger_balance, available, as_of) VALUES (s.account_number, s.ledger_balance, s.available, s.as_of); -- SQL SERVER (T-SQL) MERGE balance_snapshot AS t USING (VALUES ('CHK-8842-0117', 4218.55, 4218.55, CAST('2026-03-09T09:40:00Z' AS datetimeoffset))) AS s(account_number, ledger_balance, available, as_of) ON t.account_number = s.account_number WHEN MATCHED AND s.as_of > t.as_of THEN UPDATE SET t.ledger_balance = s.ledger_balance, t.available = s.available, t.as_of = s.as_of WHEN NOT MATCHED THEN INSERT (account_number, ledger_balance, available, as_of) VALUES (s.account_number, s.ledger_balance, s.available, s.as_of); -- the semicolon is mandatory

Two failure modes apply to both. A statement whose source contains duplicate keys fails differently: SQL Server MERGE raises an error if a target row matches more than one source row, and PostgreSQL ON CONFLICT DO UPDATE cannot affect the same row twice in one command, so the staged set is de-duplicated by key (keeping the newest as-of) first. And both need a unique key to arbitrate concurrency: without it, two sessions can both decide "absent" and both insert. Table and column names cannot be bound parameters, so dynamic SQL for a metadata-driven loader (Chapter 05 §5.8) takes identifiers from an allow-list, quoted with format('%I', name) in PostgreSQL and QUOTENAME() in SQL Server, and values only as bind parameters.

For the file's 14,207 rows the same mechanics apply at volume: rows are bulk-loaded to staging (COPY in PostgreSQL, BULK INSERT or bcp in SQL Server), de-duplicated, then upserted in one set-based statement per chunk. The bulk load is not failure-free: NOT NULL, CHECK, unique and foreign-key violations, type conversion and encoding can all reject rows or the batch, depending on the load method and transaction scope.

11.7b Set-based against row-by-row: the staging pattern, with numbers

Multi-version concurrency control means an update never overwrites a row in place: it writes a new version (a tuple) and marks the old one ended, each tuple recording the transaction that created it (xmin) and the one that superseded it (xmax). 11.9 Locks, deadlocks, and the Pega commit: a case lock is not a row lock

Row locking is how the blocked statement in 11.8 waited. SELECT ... FOR UPDATE locks the selected rows against update, delete and other FOR UPDATE; FOR NO KEY UPDATE is weaker (it allows concurrent foreign-key checks, and is what a plain UPDATE takes); FOR SHARE and FOR KEY SHARE block modification while allowing other readers; NOWAIT fails immediately if a row is locked instead of waiting; and SKIP LOCKED skips rows locked by others, which is how many workers claim distinct batches without blocking. Table-level locks matter for DDL: ACCESS EXCLUSIVE, taken by many DDL commands, blocks all access, and a DDL statement queues behind long transactions and then blocks everyone queued behind it, which is why DDL on a busy table is dangerous.

-- POSTGRESQL: QUEUE-CLAIM PATTERN WITH SKIP LOCKED (many workers take distinct batches without blocking or double-processing) WITH batch AS ( SELECT stg_id FROM stg_balance_rows WHERE file_id = 42 AND row_status = 'VALID' AND (claimed_at IS NULL OR claimed_at < now() - interval '10 minutes') -- a dead worker's claim becomes recoverable ORDER BY stg_id LIMIT 500 FOR UPDATE SKIP LOCKED ) UPDATE stg_balance_rows s SET claimed_at = now() FROM batch WHERE s.stg_id = batch.stg_id RETURNING s.stg_id, s.account_number, s.ledger_balance; -- SQL SERVER: SELECT TOP (500) ... Two kinds of lock, two lifetimes. While Marcus has AM-10417 open in his screen, Pega holds a case lock for him: a logical lock in a lock table, with its own timeout, that stops Priya modifying the case (she can open it read-only) for as long as he holds the screen, which can be minutes. A database row lock is held only for the duration of a database transaction, in milliseconds. They have different lifetimes, timeouts and failure modes, and confusing them leads to wrong diagnoses: a case lock explains "the case is locked by mreed", and a row lock explains a blocked statement in pg_stat_activity. The two also interact with saving. A Pega Obj-Save does not necessarily write immediately: the save is held pending until a commit (an explicit commit, or the platform's commit at the end of the interaction or unit of work), and a "write now" option writes within the open transaction. Until commit, the change is a deferred save: invisible to other sessions and to SQL run by anyone else, and rollback-able.

A long-running transaction does damage beyond waiting. How to read it. A plan is a tree read from the innermost node outward, each node showing an estimated cost and rows and, with ANALYZE, actual time and rows (per loop: multiply by loops when it is above one); a node's time includes its children. In the before plan, the Parallel Seq Scan reads every page, Rows Removed by Filter: 1,666,666 per worker is the tell (it read five million rows to keep four), and read=26710 buffers show disk I/O. After the index, the engine seeks to account 1 and reads a contiguous range of recent rows, touching five buffers. The access path changed from reading all the data to seeking the few rows wanted.

What an index is, and what it costs

An index is a separate, sorted structure mapping column values to row locations, so the database can find rows without reading the whole table, as a book's index avoids reading every page. It speeds reads and taxes writes: every insert, delete and update of an indexed column must also maintain each index, and indexes occupy storage and memory. Indexes are therefore added for a measured query, not speculatively, and unused ones are removed (pg_stat_user_indexes.idx_scan = 0 over a representative period). A table with fifteen indexes ingests slowly.

Designing a composite index

The leftmost-prefix rule: an index on (account_id, posted_on) serves filters on account_id alone or on both, and does not efficiently serve a filter on posted_on alone, because the entries are sorted by account first. Equality columns come first, the range column last: WHERE account_id = 1 AND posted_on >= ... matches (account_id, posted_on), and the reverse order would scan a wide date range across every account. Selectivity decides whether an index helps at all: it must narrow the search to a small fraction of the table, so a column with four values (status) is a poor index by itself, and works as a partial index or as a trailing column. An index that returns rows already sorted avoids a sort: (account_id, posted_on DESC) answers "latest transactions for this account" directly. Foreign key columns on the child side are indexed, since without them joins and parent deletes scan the child. And indexes are designed from the actual predicates, joins and sorts (Chapter 03 §3.3 for Pega Report Definitions).

11.11 What keeps the table healthy: vacuum, bloat, partitioning and pooling

Because MVCC writes new row versions (11.8), updated and deleted rows leave dead tuples that nothing can see and that must be reclaimed. VACUUM marks their space reusable and updates the visibility map and free-space map; autovacuum runs automatically when dead tuples exceed a threshold (a base number plus a fraction of the table, by default about 20 per cent); and ANALYZE refreshes the statistics the optimiser plans with. Bloat is the accumulation of dead space when vacuum cannot keep up or is blocked, and the precise cause of the most serious kind is the one from 11.9: a long-running transaction holding an old snapshot keeps the xmin horizon back, so dead tuples newer than it cannot be removed, tables and indexes grow and queries slow. An idle connection with no open transaction does not do that; idle in transaction does.

Connection pooling. Each PostgreSQL connection is a server process with memory, and thousands of connections degrade performance, so a pool reuses a limited number. The application pool (the JDBC pool in each Pega node's data source) means total demand is nodes times pool size, which must stay below max_connections with headroom for administration and jobs, interactive and background nodes both counting. An external pooler such as PgBouncer multiplexes many client connections onto few server connections, but transaction-pooling mode breaks session state (session-level settings, SET commands, advisory locks and some prepared-statement use), so compatibility with Pega's use of the connection is verified first. A sizing rule of thumb is active connections near the core count times two to four for CPU-bound work, since more connections do not increase throughput past saturation, and queueing in the pool is better than thrashing in the database. The symptoms of exhaustion are threads waiting for a connection and "unable to get connection" errors across many requests, usually caused by long transactions or a slow query holding connections, not by a pool that is too small (Chapter 10 §10.9). The failures to avoid are VACUUM FULL on a live table, disabling autovacuum "to improve performance", deleting a year of history in one statement instead of dropping partitions, raising max_connections instead of fixing long transactions, and a per-node pool sized without counting nodes.

Direct DDL and DML on Pega tables is dangerous for reasons specific to how Pega works. Pega caches table metadata in node memory and maps properties to columns by name, so a hand-dropped or renamed exposed column breaks saves and reports and nodes can disagree until caches refresh; generated DDL keeps names and types matching. An UPDATE of an exposed column in SQL to fix a status is the classic mistake, with a qualifier that must be stated precisely: for a BLOB-backed class, Pega treats the BLOB as authoritative when the case opens, so the UI shows the old value, the next save overwrites the SQL change from the BLOB, and no history, declarative rules, SLA recalculation, audit trail or index maintenance occurs. Not every class is BLOB-backed (external or mapped classes and Pega-managed system tables), so this has exceptions, and the rule is to verify the storage of the class in question before any direct change. DELETE from work, assignment or history tables orphans assignments, history and index rows and destroys audit evidence. Long DDL on a live case table takes ACCESS EXCLUSIVE locks, queues behind long transactions and stalls every session behind it, so it is done in a window with lock_timeout set, with online-safe forms (adding a nullable column without a default is quick; a volatile default or a type change rewrites the table) and CREATE INDEX CONCURRENTLY. And reports run directly on production case tables at peak compete with the application: use a replica or off-peak windows, read-only and with a limit.

THE SAFE ROUTE FOR PEGA DATA CORRECTIONS needs data fixed (for example 400 cases with a wrong exposed value)? 1 First choice: use Pega itself: a Queue Processor activity or a Data Flow that opens, corrects and saves each case (BLOB + columns + history + declaratives stay consistent), through the controlled replay/requeue tooling with audit (Chapter 06 §6.11) 2 Only for non-Pega tables (staging, reconciliation): SQL under change control, dual control, a backup or rollback script prepared, run with row-count checks inside a transaction 3 Never: UPDATE/DELETE on pc_work-style tables to "fix" cases; if there is no alternative, the DBA and Pega support agree a documented procedure that also updates the BLOB through Pega (or marks the cases for re-save), and the data change is recorded as evidence.

11.13 Operational SQL for support

Three questions a support engineer or an auditor actually asks of this dataset show the pattern. First: did anyone approve their own work? The control of Chapter 10 §10.4 is "target zero", and the detection query is the daily proof. The input rows are the five history rows of AM-10417.

-- POSTGRESQL: segregation-of-duties detection (maker and checker the same person on one case) SELECT case_id, actor FROM case_history WHERE action IN ('SUBMIT','APPROVE') GROUP BY case_id, actor HAVING COUNT(DISTINCT action) = 2; case_id | actor ---------+------- (0 rows) WHY CORRECT: mreed only submitted and praman only approved, so no actor has both actions on the same case; zero rows is the healthy result. If an actor had both, they would appear. A zero is only meaningful if the query is known to be able to return a row: test it once against a seeded violation.

Second: how long did each step take? Elapsed time between consecutive events is a LAG over the case's history.

-- POSTGRESQL SELECT action, actor, at_ts, at_ts - LAG(at_ts) OVER (PARTITION BY case_id ORDER BY at_ts) AS since_previous FROM case_history WHERE case_id = 'AM-10417' ORDER BY at_ts; action | actor | at_ts | since_previous ----------+--------+---------------------+---------------- CREATE | portal | 2026-03-02 08:40:00 | SUBMIT | mreed | 2026-03-02 10:15:00 | 01:35:00 REJECT | praman | 2026-03-02 15:20:00 | 05:05:00 SUBMIT | mreed | 2026-03-03 09:10:00 | 17:50:00 APPROVE | praman | 2026-03-03 11:30:00 | 02:20:00 WHY CORRECT: LAG looks one row back within the partition (this case) in time order, so each row subtracts the previous event's time; the first has no previous row, so NULL. The 17:50:00 between Priya's rejection on Monday afternoon and Marcus's resubmission on Tuesday morning is mostly overnight, which is why SLA clocks use business time (Chapter 02).

Third: does the summary table still agree with the ledger? Reconciliation compares a maintained copy with the source of truth, and it should return nothing.

-- POSTGRESQL SELECT a.account_number, b.ledger_balance AS summary, SUM(t.amount) AS from_ledger, b.ledger_balance - SUM(t.amount) AS difference FROM balances b JOIN accounts a ON a.account_id = b.account_id JOIN transactions t ON t.account_id = b.account_id GROUP BY a.account_number, b.ledger_balance HAVING b.ledger_balance <> SUM(t.amount); account_number | summary | from_ledger | difference ----------------+---------+-------------+------------ (0 rows) WHY CORRECT: every account's summary matches its transactions (4418.55, 12040.00, 2310.40, 58900.00). After the lost update in 11.8, the summary would be 4428.55 against a ledger of 4418.55 plus the unrecorded fee and adjustment, and this query would return that account: the reconciliation catches the silent error that no exception reported.

The reconciliation pattern: core end-of-day against the Pega side

The third query above compared a copy with its source inside one database. The reconciliation that Chapter 12 and Chapter 13 depend on compares two systems: the core's end-of-day balances, which arrive as a file and are staged (Chapter 07), against the Pega-side balances. The result is not a yes or a no but a list of breaks, each with a type, because each type has a different owner and a different cure. Business question. For business date 6 March, where does the core disagree with the summary table? The input rows are the four Pega-side balances and a staged core file with five rows, including one the Pega side has never heard of.

-- POSTGRESQL CREATE TABLE core_eod (account_number VARCHAR(17) PRIMARY KEY, ledger_balance NUMERIC(14,2) NOT NULL, business_date DATE NOT NULL); INSERT INTO core_eod VALUES ('CHK-8842-0117', 4418.55,'2026-03-06'), ('SAV-8842-0233',12040.00,'2026-03-06'), ('CHK-8842-0719', 2810.40,'2026-03-06'), ('CHK-8842-1055',58900.00,'2026-03-06'), ('CHK-8842-0888', 150.00,'2026-03-06'); SELECT * FROM ( SELECT COALESCE(c.account_number, p.account_number) AS account_number, c.ledger_balance AS core_balance, p.ledger_balance AS pega_balance, c.ledger_balance - p.ledger_balance AS difference, CASE WHEN p.account_number IS NULL THEN 'MISSING_IN_PEGA' WHEN c.account_number IS NULL THEN 'MISSING_IN_CORE' ELSE 'AMOUNT_DIFFERS' END AS break_type FROM core_eod c FULL JOIN (SELECT a.account_number, b.ledger_balance FROM balances b JOIN accounts a ON a.account_id = b.account_id) p ON p.account_number = c.account_number ) x WHERE core_balance IS DISTINCT FROM pega_balance ORDER BY account_number; account_number | core_balance | pega_balance | difference | break_type ----------------+--------------+--------------+------------+----------------- CHK-8842-0719 | 2810.40 | 2310.40 | 500.00 | AMOUNT_DIFFERS CHK-8842-0888 | 150.00 | | | MISSING_IN_PEGA WHY CORRECT: a FULL OUTER JOIN keeps rows present on only one side, so the two failure shapes that an inner join would hide (an account the core has and Pega does not, and the reverse) become rows with a NULL on one side. IS DISTINCT FROM is the null-safe inequality, so a missing balance counts as a difference; a plain <> would drop those rows (11.3). The three matching accounts produce no output. Victor's 500.00 difference is a candidate timing break: compare it with the holds and transactions around the business date before raising a case.

The query is one set-based statement over the staged file, so it runs in the same way for 14,207 rows or fourteen million, and it follows the staging pattern of 11.7b: load, validate, then compare in the database. A break then flows through its own lifecycle. Breaks are classified (amount differs, missing on either side, duplicate, timing), a tolerance and a timing window are applied (a difference explained by an item in flight on the business date is not yet a break), each remaining break becomes a case with an owner and an age, aged breaks escalate, and write-offs need approval and dual control (Chapter 10 §10.4). The controls around reconciliation are that the reconciliation is itself reconciled (the count of core rows loaded equals the count in the file trailer), that it runs on a fixed schedule with an alert if it does not, that its output is retained as audit evidence, and that the people who post transactions are not the people who clear breaks.

More operational queries, in the same shape

Stuck work. A queue-claim pattern (11.9) records claimed_at; a worker that dies leaves a claim that never completes. The query that finds them is a plain filter on state and age.

-- POSTGRESQL (against the staging table of 11.7b; illustrative rows) SELECT stg_id, account_number, claimed_at, now() - claimed_at AS claimed_for FROM stg_balance_rows WHERE row_status = 'VALID' AND claimed_at < now() - interval '10 minutes' ORDER BY claimed_at LIMIT 50; stg_id | account_number | claimed_at | claimed_for --------+----------------+---------------------+------------- 9812 | CHK-8842-0719 | 2026-03-09 07:41:12 | 00:23:40 (1 row) WHY CORRECT: a claim older than the ten-minute expiry on a row that is still VALID (not APPLIED) means the worker never finished; the claim-expiry rule of 11.9 makes the row eligible for re-claim, and this query lists what is waiting, with an index on (row_status, claimed_at) to keep it cheap.

Cases about to breach. SLA-at-risk work is a selection on an exposed, indexed due column, never on the BLOB.

-- POSTGRESQL (a work table with exposed columns, as in 11.12; illustrative) SELECT pyid, pystatuswork, due_at, due_at - now() AS time_left FROM dep_work_case WHERE pystatuswork NOT LIKE 'Resolved%' AND due_at < now() + interval '4 hours' ORDER BY due_at LIMIT 100; -- never SELECT * here (it would drag the BLOB across the network for every row); the bounded LIMIT and the indexed due_at keep it safe to run against production at peak

Duplicates. A duplicate is a group on the business key with more than one row, and the cure is a constraint so the database refuses it from then on.

-- POSTGRESQL: any file hash recorded twice for one interface (should be impossible with the unique constraint of Chapter 07 §7.10, so zero rows is the expected, checked result) SELECT interface_name, sha256, count(*) FROM file_registry GROUP BY interface_name, sha256 HAVING count(*) > 1;

Deadline arithmetic in SQL: Dana's dispute DS-10915

Chapter 12 makes every regulatory deadline a computed record on a named calendar. The calendar is data, and SQL can compute it. Business question. Dana gave notice on Monday 8 December 2025; on the institution's Reg E calendar (weekdays only, with its own holidays), what is ten business days later, and what is 45 calendar days later? The input is the notice date and a small holiday table.

-- POSTGRESQL CREATE TABLE institution_holidays (holiday DATE PRIMARY KEY); -- the institution's own Reg E calendar (Chapter 12 §12.10) INSERT INTO institution_holidays VALUES ('2025-12-25'), ('2026-01-01'); -- the 10th business day after the notice: generate candidate days, keep weekdays that are not holidays, take the tenth SELECT d::date AS tenth_business_day FROM generate_series(DATE '2025-12-09', DATE '2026-02-28', INTERVAL '1 day') AS g(d) WHERE extract(isodow FROM d) < 6 -- 1 = Monday ... 5 = Friday AND d::date NOT IN (SELECT holiday FROM institution_holidays) ORDER BY d OFFSET 9 LIMIT 1; -- OFFSET 9 skips the first nine, leaving the tenth tenth_business_day -------------------- 2025-12-22 -- the 45-day investigation deadline is CALENDAR days, so it is plain date arithmetic, with no calendar table SELECT DATE '2025-12-08' + 45 AS investigation_due; investigation_due ------------------- 2026-01-22 WHY CORRECT: counting forward from 9 December, the weekdays are 9, 10, 11, 12 (four), 15 to 19 (nine) and 22 (ten), with no holiday in between, so the tenth is Monday 22 December 2025. Adding 45 to the date counts calendar days, which is what Reg E specifies for the investigation; adding 45 business days would use the same generate_series query with OFFSET 44 and would give a much later, wrong date. The two clocks must be typed (business or calendar) and stored with their calendar and inputs, never recomputed silently. SQL SERVER: DATEADD(day, 45, '2025-12-08') for the calendar clock, and a calendar table (or a recursive CTE) joined with a weekday and holiday filter for the business clock.

In practice the generated series is replaced by a permanent calendar table with one row per date and flags for weekday and holiday per calendar (one for Reg E, one for the Reg CC statutory list, one for the ACH operator), so a deadline is a lookup, not a computation, and the calendar can be audited and versioned. That is the SQL shape of "calendar as an input to the deadline".

Dynamic SQL for a metadata-driven loader

The metadata-driven loader of Chapter 05 §5.8 builds statements from a table describing each target. Values are always bind parameters; names cannot be bound, so they are quoted safely and taken only from an allow-list of validated metadata.

-- POSTGRESQL (PL/pgSQL): identifiers quoted with %I, values passed with USING DO $$ DECLARE tbl text := 'balance_snapshot'; -- from validated metadata, never from a file or a user acct text := 'CHK-8842-0117'; n int; BEGIN EXECUTE format('SELECT count(*) FROM %I WHERE account_number = $1', tbl) INTO n USING acct; RAISE NOTICE 'rows: %', n; END $$; -- SQL SERVER: QUOTENAME() for the identifier and sp_executesql with parameters for the value DECLARE @tbl sysname = N'balance_snapshot', @sql nvarchar(max); SET @sql = N'SELECT count(*) FROM ' + QUOTENAME(@tbl) + N' WHERE account_number = @acct'; EXEC sp_executesql @sql, N'@acct varchar(17)', @acct = 'CHK-8842-0117';

Concatenating a value into the text, instead of binding it, is SQL injection, and an identifier that has not been validated against the catalogue is the same hole in a different place (Chapter 10 §10.6).

Conditional aggregates, and a constraint that forbids overlap

-- POSTGRESQL: one pass, several counts (SQL Server: SUM(CASE WHEN ... THEN 1 ELSE 0 END)) SELECT count(*) AS holds_total, count(*) FILTER (WHERE status = 'ACTIVE') AS holds_active, sum(amount) FILTER (WHERE status = 'ACTIVE') AS active_amount FROM holds; holds_total | holds_active | active_amount -------------+--------------+--------------- 3 | 2 | 1700.00 WHY: of the three holds, the released DEPOSIT hold is excluded from both active measures; the active ones are Dana's 200.00 card authorisation and Victor's 1,500.00 legal hold, 1,700.00 in total. -- POSTGRESQL: an exclusion constraint makes "two active restraints overlapping in time on one account" impossible (needs the btree_gist extension) -- ALTER TABLE holds ADD COLUMN active_during tstzrange; -- ALTER TABLE holds ADD CONSTRAINT no_overlap EXCLUDE USING gist (account_id WITH =, active_during WITH &&) WHERE (hold_type = 'LEGAL');

The exclusion constraint is the strongest form of the rule that a constraint beats an application check: the database refuses the second overlapping restraint even if two sessions race, which is the problem the write-skew example of 11.8 could only avoid with serialisable retries.

Other operational queries have the same form and are stated in words: stuck queue items are rows claimed more than a threshold ago and not completed; SLA-at-risk cases are open cases whose due time is within a window, selected on an exposed, indexed column; duplicates are groups with COUNT(*) > 1 on the business key (a file hash, an event ID, an order number plus version), and the fix is a unique constraint so that the database refuses them in future. Every such query is read-only, bounded by a limit or date range, and run against a replica where there is one.

11.14 Backup, point-in-time recovery and replicas

The last question about data is how it comes back, and the answer has more than one layer. A backup is a copy from which the database can be rebuilt, and in PostgreSQL a base backup plus the archive of write-ahead log lets recovery stop at any chosen moment: point-in-time recovery. That is the answer to "restore to just before the bad data change", and it is a disaster tool, not a rollback tool, because everything committed after the chosen moment is lost unless it is replayed from another source. A replica (streaming replication) maintains a second copy that can serve read-only reporting and take over after a failure; replication lag means a replica is briefly behind, and long queries on a replica can conflict with the cleanup that replication must apply. Replication is not a backup, since a mistaken DELETE replicates. Recovery objectives are stated as a recovery point (how much data may be lost) and a recovery time (how long it may take); both are tested by actually restoring, because an untested backup is an assumption. Backup retention is aligned with deletion obligations, and backups are encrypted (Chapter 10 §10.7).

11.15 Interview Q&A

Q1. Why does WHERE status <> 'CLOSED' miss some rows?

"NULL comparisons are unknown, not true or false, and WHERE keeps only true. Rows with a NULL status are dropped. I use IS DISTINCT FROM, or handle NULL explicitly, and prefer NOT EXISTS to NOT IN because a NULL in the list makes NOT IN return nothing."

Q2. A report sums holds and transactions together and the held amount is too big. Why?

"Fan-out: joining two independent one-to-many branches multiplies rows, so each hold is counted once per transaction. I aggregate each branch to one row per account in CTEs first and then join, so the joins cannot multiply."

Q3. How do you get a running balance, and the latest transaction per account?

"Window functions: SUM(amount) OVER (ORDER BY date, id) for the running balance, and ROW_NUMBER() OVER (PARTITION BY account ORDER BY date DESC) filtered to 1 in an outer query for the latest row. A tie-breaker keeps the order deterministic, and the last running value should equal the grouped total."

Q4. How do you write a safe upsert for snapshots?

"INSERT ... ON CONFLICT on the unique key with DO UPDATE ... WHERE excluded.as_of is newer than the stored one, so it is idempotent and order-independent. That guard is only legal for full-state snapshots, never for deltas. PostgreSQL 15 adds MERGE and SQL Server has its own MERGE, and I label the dialect and never mix them; duplicate source keys must be de-duplicated first."

Q5. Two sessions both read a balance, change it and write it back. What goes wrong and how do you fix it?

"A lost update: the second write overwrites the first with a value computed from a stale read. I make the arithmetic atomic in one statement (balance = balance - n), use SELECT FOR UPDATE for multi-step logic, or a version column with retry. For multi-row invariants, write skew needs a parent-row lock, SERIALIZABLE with retry, or a unique constraint."

Q6. How is a Pega case lock different from a database row lock?

"A case lock is a logical lock held for a requestor while the case is open, with its own timeout, and the database shows nothing. A row lock is held for the length of a database transaction. A deferred save is pending and invisible to SQL until commit. The danger is a connector call between the write and the commit, which holds row locks across the network wait."

Q7. What causes a deadlock and how do you prevent it?

"A cycle of waits, for example two transfers locking the same two accounts in opposite order. I lock in a consistent global order, keep transactions short, take locks up front, set lock and statement timeouts, and retry on 40P01 and 40001 with bounded attempts."

Q8. How do you read EXPLAIN ANALYZE, and what is the warning about it?

"I read from the innermost node outward, compare estimated and actual rows, and look for sequential scans with large 'rows removed by filter', then the access path and buffers. A composite index with the equality column first and the range column second turns a scan into a seek. EXPLAIN ANALYZE executes the statement, so UPDATE, DELETE and INSERT really change rows: I wrap them in a transaction I roll back, or use plain EXPLAIN."

Q9. What stops vacuum from reclaiming dead tuples?

"A long-running transaction holding an old snapshot holds back the xmin horizon, so dead tuples newer than it cannot be removed and tables bloat. The dangerous state is idle in transaction; a plain idle connection with no open transaction does not do it. I look at the oldest transaction age and set idle-in-transaction timeouts."

Q10. Can you fix a Pega case's status with a SQL UPDATE?

"Not safely. For a BLOB-backed class the BLOB is authoritative when the case opens, so the UI shows the old value and the next save overwrites the change, with no history, SLA recalculation or index maintenance. Not every class is BLOB-backed, so I verify the storage first, and the correction is made through Pega with a queue processor or data flow that opens, corrects and saves, under change control."

Q11. Why is a loop that updates 14,207 rows one at a time the wrong design, and what replaces it?

"Because the cost is the round trips and the per-row transactions, not the work: about 28,000 round trips, and a failure mid-loop leaves a half-applied file. I stage the rows with a bulk load, validate and reject in the database with set-based updates, de-duplicate, apply with one guarded upsert per chunk, and reconcile that staged equals applied plus rejected plus failed. Bad rows become counted rejects and the batch continues."

Q12. You added an index and the planner still scans. Why?

"Usually the index does not match the predicate: the equality column must lead and the range column follow, a function or cast on the column disables it, or the filter is not selective enough and a sequential scan really is cheaper. Stale statistics can also mislead the planner, so I compare estimated and actual rows in EXPLAIN (ANALYZE, BUFFERS). A covering index can then remove the table visit entirely, at the price of a wider index and write cost."

Q13. How would you reconcile the core's end-of-day balances against the Pega-side balances?

"Stage the core file, then one full outer join on account number and keep the rows where the balances are distinct from each other, null-safe. That yields typed breaks: amount differs, missing in Pega, missing in core. I apply a timing window and tolerance, turn the remainder into cases with an owner and age, escalate aged ones, and reconcile the reconciliation itself against the file trailer count. The people who post are not the people who clear breaks."

Q14. How do you compute a Reg E deadline in SQL, and what mistake do you avoid?

"Ten business days is a lookup on the institution's calendar (weekdays minus its own holidays), so the tenth business day after 8 December 2025 is Monday 22 December 2025, whereas 45 days is plain calendar arithmetic and gives 22 January 2026. The mistake is adding 45 business days, which is later than the law allows. Each deadline is stored with its type, calendar and inputs and is never recomputed silently."

11.Z Where we are now

What the application can do

The data behind the application can be questioned precisely: Dana's accounts, her available balance, a running statement, the elapsed time of each step of AM-10417, a segregation-of-duties check and a reconciliation that should return nothing. Concurrent writes to her row are safe, a late snapshot cannot overwrite a newer one, and a slow query has a method for diagnosis and a fix.

The mechanisms behind it

Typed, constrained tables; joins and aggregates that avoid fan-out; window functions; idempotent upserts with an as-of guard; MVCC with atomic updates, row locks and consistent lock order; Pega's case lock and deferred save as separate things from database locks; plans read from the innermost node, with an index that changes the access path; vacuum and its horizon; and the discipline of correcting Pega data through Pega.

What it still cannot do

All the SQL assumes the figures mean what the business says they mean. A "hold", an "available balance", a "business day" and a response deadline are defined by regulation and by policy, not by the database. What the rules are, in what order a deposit account lives and which clocks apply to which action, is Chapter 12.
