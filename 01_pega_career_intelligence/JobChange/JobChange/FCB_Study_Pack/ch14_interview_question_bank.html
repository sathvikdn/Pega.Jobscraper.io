Before you start: how to use this chapter, and the traps

Chapter 13 ended with an application whose every boundary can be justified and whose one request, Dana's closure AC-10882, can be followed from the screen to the audit trail. Understanding that is not the same as being able to say it. An interviewer gives about a minute and a half, interrupts, and asks what happens when something fails. This chapter is where understanding becomes answers: each important question has a direct answer to say first, the mechanism behind it, one example that is clearly either confirmed or hypothetical, the two follow-ups an interviewer asks next, and the misconception to avoid. Where an answer needs depth, it gives the compressed version and points to the chapter that teaches it, because this chapter is not a second textbook.

14.2 Group 2: Pega platform and rule resolution

Q9. How does Pega differ from hand-written Java or Spring?

Direct answer (20–30s): Pega stores process, decisions and mappings as versioned rules the engine resolves at run time, so variation is specialisation, not if/else.

"In Pega, behaviour is rule records in a database: flows, data transforms, decision tables, sections, connectors. At run time the engine uses rule resolution to pick the right rule for the class, the ruleset stack, the date and circumstances, generates and caches Java for it, and runs it. In Spring I'd write the variation as strategy beans or conditionals; in Pega I get specialisation through class inheritance, ruleset layering and circumstancing. Process engine, SLAs, assignments, audit and reporting are native, and state is the clipboard, persisted as a BLOB plus exposed columns. The trade-off is that without governance a rule platform sprawls, which is why I cared about guardrails and layering."

Example hypothetical: Dana's address change AM-10417 needs a different review requirement for a California variant of a product. In Spring that is a strategy bean; in Pega it is a circumstanced variant of one rule, chosen at run time. See Chapter 01 §1.6.

Likely follow-ups: 1) How is the clipboard persisted? 2) What stops a rule platform sprawling?

Common misconception: that Pega is a code generator you configure once. Rules are resolved at run time against class, ruleset list, date and circumstance.
Q10. Explain rule resolution.

Direct answer (20–30s): Gather, filter, rank by class, ruleset, circumstance, circumstance date, date range, then version (version last), cache the ranked list, and qualify at runtime.

If they want more: "The engine gathers every candidate with that name from the Applies-To class up the inheritance structure, filters out anything whose ruleset is not on my list, whose version is above what the list allows, or that is Not Available. It ranks what is left by class, then ruleset, then circumstance, then circumstance date, then date range, then version — version last, which is why a newer base rule does not override an older circumstanced one. Withdrawn rules take out the lower versions in their own ruleset, the highest unqualified candidate becomes the default, and the ranked list is cached. At runtime the engine takes the highest-ranked candidate whose circumstances actually match this case, falling back to the default. If that candidate is Blocked, the run fails rather than falling through. In a real tie I confirm with Tracer and the rule's instance key rather than memory." See Chapter 01 §1.6.

Example: a base rule patched at 01-03-02 while a California variant sits at 01-02-04: California keeps the old logic. hypothetical

Likely follow-ups: 1) Does a higher ruleset beat a more specific class? 2) What does Blocked do versus Withdrawn?

Common mistake: saying "the resolved rule is cached" or that a newer version beats a circumstanced rule.

Q12. Pattern versus directed inheritance?

Direct answer (20–30s): Pattern inheritance comes from the class name; directed inheritance is an explicit parent; I keep directed minimal.

"Pattern inheritance strips trailing segments of the name, so FCB-Dep-Work-AccountClosure inherits from FCB-Dep-Work-, FCB-Dep-, FCB-. Directed inheritance names a parent on the class rule so a class can inherit from outside its name path. Resolution checks the class, then its inheritance chain, ending in Pega base classes. I use directed inheritance sparingly because long chains make resolution hard to explain at three in the morning. Rule specialisation should mostly come from the class path, circumstancing and ruleset layering."

Example hypothetical: FCB-Dep-Work-AccountClosure, the class of AC-10882, inherits by pattern from FCB-Dep-Work-, then FCB-Dep-, then FCB-. See Chapter 01 §1.4.

Likely follow-ups: 1) When would you use directed inheritance? 2) Which wins when both apply?

Common misconception: that inheritance is only the class name. A class rule can name an explicit parent, and resolution follows the chain.
Q13. How do rulesets, versions and branches work, and how do you release a hotfix?

Direct answer (20–30s): Rules live in ruleset versions; branches isolate work; release locks a version; a hotfix is a new patch version.

"A ruleset version is major-minor-patch. The application's ruleset list defines which versions are in play, and resolution prefers the highest allowed version. Developers work in short-lived branch rulesets on top of the base, run PegaUnit and guardrail checks, merge with the merge wizard, and the pipeline locks the target version at release. For a hotfix I branch from the exact production version, make the minimal change with a test, create the next patch version, package it with the product rule, and promote through the pipeline with expedited but real gates, then backport to the main line. Rollback for rule-only changes is repointing the application at the earlier version, but state changes need more, which I design for."

Example hypothetical: a defect in the closure eligibility decision is fixed as patch version 01-01-03 branched from production, tested with a case that reproduces it, promoted through the pipeline and backported. See Chapter 10 §10.12.

Likely follow-ups: 1) Why is redeploying the previous version not a rollback plan? 2) What does locking a ruleset version do?

Common misconception: that rollback is always redeploying the old package. Schema, data, in-flight cases and queue items persist.

Q16. Explain the clipboard, requestor types and the request lifecycle in a minute.

Direct answer (20–30s): The clipboard is the requestor's in-memory page tree; requestor type tells you where to look when something is slow.

"The clipboard is the in-memory tree of pages for a requestor: the case page, embedded pages, page lists and groups, data pages, parameters. A request arrives, authenticates, builds the ruleset list from the access group, resolves and assembles rules, runs the flow action or activity, fires declaratives, and on commit serialises the page into the BLOB plus exposed columns and writes history. Requestor types matter in support: browser requestors serve users, batch requestors run queue processors, schedulers and agents, application requestors serve services and listeners. Browser slowness sends me to data pages and refresh scope; batch slowness sends me to per-item database calls, locks or large pages; service slowness to downstream timeouts."

Example: hypothetical Priya's approval screen for AM-10417 takes fourteen seconds: a browser requestor, so the first look is the data pages it loads and their refresh scope. 14.3 Group 3: Case management, BPM and SLA

Q17. Explain case type, stage, process and step.

Direct answer (20–30s): A case type is the template; stages are lifecycle phases; processes are flows in a stage; steps are the tasks in a process.

"The case type defines the data and lifecycle for a business request. Stages are phases: primary stages in order, alternate stages for off-path events like cancellation or hold review, and a resolution stage. Each stage holds processes, which are flows, and each process is made of steps such as assignments, automation, approvals or child cases. At run time a case instance has an ID, a status, and assignments on a worklist or work queue. I keep five to seven stages in business language so supervisors can read the lifecycle, and hide technical detail in subprocesses."

The distinctions: a case is one instance of the case type (AC-10882); an assignment is one piece of work waiting for a person (Priya's approval) and a case may have several over its life. A stage is a phase of the lifecycle, a process is a flow inside a stage, and a step is one task in that flow.

Example: hypothetical AC-10882 is the case; its Approve stage holds an approval process whose step creates the assignment Priya works. See Chapter 02.

Likely follow-ups: 1) When does a case leave the primary stages for an alternate one? 2) Where does the SLA attach: case, stage or assignment?

Common mistake: using "case" and "assignment" interchangeably, or describing a stage as a flow. A stage contains flows.
Q18. Child case versus subprocess versus Split-Join?

Direct answer (20–30s): Child case when the sub-work has its own owner, SLA or audit; subprocess or Split-Join for short same-team work on shared data.

"A child case has its own lifecycle, owner, SLA, security and audit, and can outlive the parent; a subprocess or Split-Join runs inside the parent on the same clipboard and creates a lock contention point. For a legal order that restrains several accounts I'd create one hold-placement child case per account, so each core call succeeds or fails on its own with its own audit, and the parent waits on case dependency rather than being updated by many children. I avoid Split-For-Each over large lists on one case."

Example: hypothetical the order LO-20331 restrains one account: its hold-placement child case calls the core with its own key, so a failure on one account does not roll back another. See Chapter 02 and Chapter 13 §13.8.

Likely follow-ups: 1) How does the parent wait for children? 2) Why does a Split-Join on one case create lock contention?

Common mistake: modelling independent work as a subprocess on one case, so every branch fights for the same case lock.
Q19. What are tickets and when do you use them?

Direct answer (20–30s): A ticket is a named jump point raised from anywhere, for exceptions that can strike at any step.

"A ticket is a marker in a flow that can be raised by an activity, an SLA escalation, a declarative rule or an external event, and the flow resumes from that point regardless of where the case currently is. 14.13b Architecture and design scenarios, from Chapter 13

These are the design questions that follow from the architecture of Chapter 13: where to begin, how to structure layers, how to pick an integration pattern, what happens when a hop fails, how to size, and how to roll out. Each uses the five-part shape, and every example is hypothetical and built on the closure AC-10882 or the other ledger cases, because none of this is a claim about a real project. None of it claims a greenfield bank platform was architected end to end; it is the approach and the first questions.

D1. We are starting a greenfield Pega Deposits platform. Where do you begin?

Direct answer (20–30s): "With questions, then structure. I ask which case types and markets are in release one, what the core and ESB expose, who owns the regulatory rules, what the identity and security model is, the volumes and recovery objectives, and what the legacy process is. How it works: The questions reduce risk because greenfield banking platforms fail on integration contracts, ownership of regulatory content, control design and migration, not on screens. Each answer changes a design decision: which interfaces exist decides sync against async and whether a robot is needed; who owns the exemption and notice rules decides that they become effective-dated reference data; the recovery objectives decide the topology (Chapter 13 §13.1, §13.4, §13.10).

Example hypothetical: asked "which interfaces does the core expose for holds and closure?", the answer that holds are an API but closure is a batch file turns AC-10882 from a synchronous closure into a hold-then-file design with a status lookup, which is a different case type from the one drawn for an API.

Likely follow-ups: 1) Which three questions matter most, and why? 2) What if the sponsor wants a diagram on day one?

Common misconception: that confidence means arriving with a finished design. A diagram before the answers is a guess; the questions are the senior move.
D2. How would you structure rulesets so everything does not end up in one layer?

Direct answer (20–30s): "By change cadence and ownership: an enterprise layer of canonical classes and frameworks, a deposits framework layer of case types and flows, a thin implementation layer for true state or product differences done through circumstancing, and separate rulesets for integration, business-owned decision data and tests. Dependencies run one way, enforced by prerequisites and a pipeline check."

How it works: Rule resolution searches the application stack top-down, so a lower layer cannot see a higher one's rules, which is exactly the constraint wanted. Business thresholds live in decision data with their own approval path so they change without a code release (Chapter 13 §13.5, Chapter 01).

Example hypothetical: the closure authority bands sit in the data ruleset, so changing the band for Priya's approval is a maker-checker data change, not a release of the closure flow.

Likely follow-ups: 1) What is the warning sign that layering is failing? 2) How do you stop the implementation layer filling with copies?

Common misconception: that one application and one ruleset is simpler. It is simpler until the third case type needs copy-paste.
D3. For each interface, how do you choose sync, async, event or batch?

Direct answer (20–30s): "One logic. A safe read with a person waiting is synchronous and cached; a write that must not be lost or duplicated is queued with an idempotency key; a long or multi-system operation is asynchronous with a callback and a sweeper; continuous change is an event if there is a backbone; volume and vendor standards are batch with trigger files; compliance controls fail closed."

How it works: The deciding questions are who is waiting and what a repeat would do. A repeated read costs nothing, so it can retry; a repeated write may duplicate an effect, so it needs a key and an outcome state for the case where the response is lost (Chapter 05 §5.9, Chapter 13 §13.4).

Example hypothetical: in AC-10882 the balance read is synchronous, EVT-55121 is an event, the hold AC-10882-HOLD-1 is queued with an outbox, the disbursement is asynchronous with a callback, and the nightly comparison is batch.

Likely follow-ups: 1) What if there is no interface at all? 2) Who owns retries?

Common misconception: that asynchronous is always better. It adds states and reconciliation; it is chosen when the work is long or the outcome cannot be known now.
D4. The hold call times out. What is the case's status and what happens next?

Direct answer (20–30s): "The case stays in Pending-Core and the request is an unknown outcome. I do not re-post with a new key: I look up the status by the same key, and an event or a status answer resolves it."

How it works: A timeout on a write means the effect may or may not have happened. The key identifies the intent, so the same key is safe to ask about and, if the core never received it, to re-post; a new key is a second request. The outbox row and the case status commit together so the intent is never lost (Chapter 05 §5.9, Chapter 13 §13.7).

Example hypothetical: the call for AC-10882-HOLD-1 times out at 10:21:08; the core creates the hold at 10:21:41 and publishes EVT-55122; the status lookup and the event both return the hold reference, and the case moves on with exactly one hold.

Likely follow-ups: 1) What if the ESB does not honour the key? 2) How long must keys be retained?

Common misconception: that a timeout means the request failed and is safe to retry. For a write, it means nobody knows.
D5. The ESB is down for four hours. What happens?

Direct answer (20–30s): "Reads fall back to cached values with an as-of stamp; writes queue with idempotency keys behind a breaker; sanctions screening fails closed; legal restraints use the manual fallback with dual control if a deadline is at risk; on recovery the queues drain throttled and counts are reconciled."

How it works: Each of those was decided in advance. The breaker is something that is built, not a Pega feature, and it stops threads waiting on a dead dependency; bulkheaded queue processors mean the outage affects only the work that needs the ESB. Exhausted items land in a human queue (Chapter 13 §13.10).

Example hypothetical: closures started during the outage sit in Pending-Core with a banner; Priya's team sees them with the as-of time, and none is posted twice when the ESB returns, because the keys hold.

Likely follow-ups: 1) How is the SLA treated during the outage? 2) How do you know nothing was posted twice?

Common misconception: that a retry storm on recovery is harmless. Draining unthrottled can overwhelm a core that has just come back.
D6. A 150,000-row return file must be processed in the batch window. How do you design it?

Direct answer (20–30s): "Trigger-file handshake and a registry on name and hash, staging with per-row status, chunked idempotent apply keyed on the business key, reconciliation of counts, and an expected-file alert."

How it works: The registry stops a duplicate or partial file from starting; staging separates rejects from applies so one bad row does not fail the file; the chunked apply is idempotent so a restart is safe; and declared equals staged equals applied plus exceptions plus rejects proves nothing was lost. The sizing is an order-of-magnitude budget (about 42 rows per second, roughly 10 ms per record, a designed experiment to run and not a measurement), which is one thread's work, with four for headroom (Chapter 07, Chapter 13 §13.10).

Example hypothetical: Harlow Freight's return file for PE-30142 arrives with a trailer count that does not match the staged rows; the batch is held and the discrepancy becomes a counted break, not a silent loss.

Likely follow-ups: 1) What if the same file arrives twice under a new name? 2) Why stage as text?

Common misconception: that the load is failure-free. Bulk loads can reject rows or the batch on constraints, type conversion, encoding and partial failure.
