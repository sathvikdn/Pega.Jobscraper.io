3.1 The UI lineage and the 8.8 renaming

3.2 The architectural break

Plain-English definition

In the traditional UI the server decides how a screen looks. It resolves harness, section and layout rules, assembles HTML, CSS and JavaScript, and sends them to the browser. In Constellation the server describes the screen as view metadata, structured data saying what content, fields and actions belong in this step, and a client-side engine in the browser, using the Constellation design system, renders that metadata. Pega describes the architecture as client-side orchestration.

Why it exists

The server-rendered model coupled UI to server state: every refresh was a round trip that regenerated HTML for a region, and every customisation (custom controls, JavaScript, deep skins) became a regression burden on upgrade. A metadata contract between server and client breaks that coupling. The client owns presentation; the server owns data, process and rules; the contract between them is explicit.

AspectTraditional UIConstellation
Who rendersServer generates HTMLBrowser renders from metadata with the design system
Unit of UI authoringHarness, section, layout, controlView, from prescribed templates and regions
Where UI is authoredDev Studio and App StudioPrimarily App Studio, with live preview
Server state per userStateful requestor, clipboard held across interactionsStateless requestor; clipboard released after each DX API call
CustomisationCustom HTML, JavaScript, skinsPrescribed templates; DX Components for genuine gaps
DebuggingTracer, clipboard viewer, UI inspectorBrowser developer tools on the DX API calls, plus server-side Tracer for the server portion

MVC, microservices and stateless requestors

Three architectural ideas explain Constellation's behaviour. First, a Model-View-Controller separation: the data and process are the model on the server, the view metadata is the description of presentation, and the client engine is the controller and renderer. Second, a microservices approach: the static front-end content is served by its own service (3.3), separate from the Pega application server. Third, stateless operation: the server does not keep continuing client state between calls.

Pega's Constellation FAQ describes the stateless idea as on-demand access rather than continuous connection: each request is processed independently, and everything needed is included in each request. In practice the DX API uses a stateless requestor, and the clipboard is released after each DX API call. A Case is opened, worked on and saved within the call, and the persisted case data, not a lingering session, carries the state.

STATEFUL VERSUS STATELESS TRADITIONAL (stateful): browser --> requestor holds clipboard and thread over many interactions --> user keeps a server-side session CONSTELLATION (stateless): browser --> DX API call --> stateless requestor opens case, applies the action, saves --> clipboard released ^ | +--- next call carries the identity (token) and what the server needs; state lives in the case, not the session

3.3 The Constellation UI Service

Plain-English definition

Pega's documentation describes the Constellation UI Service as a static content microservice that delivers front-end components and other static content to the browser. Constellation applications rely on it. To obtain configuration, context and data, the client interacts with the server exclusively through DX APIs. The documentation notes that keeping the Constellation container separate from other services avoids dependencies, gives developers the tools to create new UI components without interfering with other work, and improves overall application performance. When creating a new application you can choose between a view-based Constellation UI and a section-based traditional UI, which can be extended with hybrid components.

Provisioning

On Pega Cloud the Constellation UI Service is provisioned automatically. In a client-managed deployment someone must stand it up, and the mechanism varies by release; confirm it in the version's documentation.

WHERE THE SERVICE SITS Browser | 1 load app shell and design-system bundles ------------> Constellation UI Service (static content) | 2 API calls (JSON) with a token -----------------------> Pega application server: Constellation DX API | <---- data + UI metadata + available actions | 3 render with design system; custom DX Components loaded from the service v Pega engine: cases, flows, rules, data pages, decisioning, database (unchanged by the UI choice)
Lead-level framing. "The UI Service is a static-content microservice. The browser gets the design system and components from it and talks to the application server only through the DX API for data and metadata. On Pega Cloud it is auto-provisioned; on a client-managed estate someone has to stand it up, so I would put that on the platform checklist early."

3.4 Constellation DX API versus Traditional DX API

Plain-English definition

The Digital Experience (DX) API is Pega's REST API family for building front ends on top of the case engine. It exposes case-management semantics (create a case, get the assignment, perform an action, get the worklist) rather than raw data, and the platform enforces security, validation, locking and process rules on each call. There are two generations, and Pega's documentation has a page comparing them. The comparison below follows it.

The comparison

What a Constellation DX API response contains

Pega's response documentation describes elements that depend on the endpoint. Common examples: a data element holding the case and assignment details (for example case information and referenced users); a uiResources element holding the UI metadata needed to render a page or form; information about the next assignment; and links in HATEOAS format describing the actions the user may take. The content element carries only the fields configured in the view returned by the endpoint, so each view can have different content. The documentation also notes that a view-type parameter can select what is returned.

ANATOMY OF A CONSTELLATION RESPONSE (conceptual; not the literal schema) { data: case and assignment details (the values) uiResources: the metadata to render this step (which view, which fields, which are editable or required) nextAssignment: what comes after, if the step completes links: HATEOAS references to the actions available now (for example submit, refresh, change stage) } The client renders uiResources against data, and offers only the actions in links. Changing a view or flow on the server changes what the client renders with no client code change.
Do not quote the schema. The block above is a teaching sketch of the elements named in Pega's documentation. Do not present it as the literal payload, and do not quote an endpoint path. Say the response carries data, view metadata and available actions together, and that you would confirm the exact schema in the release's API documentation.
Lead-level framing. "The Traditional DX API mirrors screen state and suits existing section-based applications; the Constellation DX API is view-based, separates data from layout, uses HATEOAS so responses carry available actions, and needs fewer calls. I would choose by the application's UI architecture, not by preference, and I would never use either as a system-to-system contract. I have built Service-REST contracts for that, but I have not built against the DX API."

3.5 Web Embed, coexistence and hybrid adoption

Mashups are replaced by Web Embed

The traditional way to place Pega inside another web page was the mashup: a snippet that pulled a Pega-rendered gadget into the host page. For Constellation, the equivalent is Web Embed: a way of embedding a Constellation-rendered Pega experience in an external web page without building a full custom front end. The practical statement is that mashups are replaced by Web Embed for Constellation applications. The LTM workshop syllabus includes "Web Embed and its use cases" (3.13), so expect a question on it.

OptionWhat you getWho owns the front endWhen it fits
Standard Constellation portalThe Pega-rendered portalPega design systemInternal operations; fastest and most upgrade-safe
Web EmbedA Pega experience (for example a case or a view) placed inside another site's pageThe host page owns the surroundings; Pega owns the embedded experienceAdding a Pega-driven step to an existing portal without rebuilding it
Constellation DX API with a custom front endFull control of the UI using the APIThe digital teamA bespoke or heavily branded channel
React SDKA React application connecting the Constellation engine to a non-Pega design system (3.9)The digital team, using the SDK's componentsThe client's design system is mandated and cannot be Pega's

Coexistence and hybrid adoption

Real estates are rarely all-or-nothing. Pega's documentation supports several coexistence forms. A traditional, section-based application can use the Constellation UI Service to host Constellation landing pages, tables and Constellation Cases inside the section-based application, a hybrid arrangement the documentation presents as a way to adopt Constellation progressively. In Pega Customer Service the Constellation Interaction Portal can run service requests that were built with the UI Kit (Chapter 02, 2.4), so the agent desktop can move first while individual service request types migrate over time.

Why an app's UI architecture cannot be casually flipped

An existing section-based application cannot be switched to Constellation by changing a setting. Existing sections, harnesses and custom controls do not carry over; forms are rebuilt as views, custom controls are replaced or become DX Components, and portals and landing pages are rebuilt. This is covered in FCB Chapter 04 (4.4). The implication for you: a client with a long-lived traditional application will almost certainly be in a hybrid or phased state, and "what stage of Constellation adoption is the client at" is the right question (Chapter 01, 1.11).

Anti-patterns: promising a client that a traditional app moves to Constellation "in a sprint"; embedding with Web Embed what should be a first-class view; forking the whole UI into a custom front end when the standard portal would do; assuming a hybrid configuration works because a documentation page says it is possible, without checking the release's supported combinations.
Lead-level framing. "Mashups are replaced by Web Embed. For adoption I think in stages: standard Constellation portal for internal users; Web Embed to put a Pega step in someone else's page; the API or SDK only when the client's design system demands it. Coexistence lets a traditional app host Constellation pieces, and lets the Constellation Interaction Portal run UI Kit service requests, which is how large estates actually migrate."

Common confusions

Three statements candidates wrongly merge. "I would build a DX Component" does not mean you are building a React front end; the component lives inside Pega's UI. "I would use the React SDK" does not mean you are writing DX Components for App Studio authors, although in the SDK context DX components are the mechanism for connecting the alternative design system. "Constellation is React" is true of Level 1 only; most developers using Constellation never write a line of React.
Lead-level framing. "There are three places React appears: the design system, which Pega writes and I consume; DX Components, custom React that I would publish into Pega so low-code authors can use it; and the React SDK, which bridges the Constellation engine to a different design system for a separate front-end application. Most Constellation delivery needs none of the last two, so I would ask which level the engagement actually involves."

3.7 Level 1: the design system is React

Plain-English definition

The Constellation design system is the library of prescribed UI components and templates that renders every Constellation view. It is built in React, but you do not write it. Your interface to it is authoring: you choose a template, fill regions with fields, and the design system decides spacing, alignment, responsive collapse, accessibility behaviour and interaction patterns.

What "opinionated" costs and gives

The design system decides layout, so you lose arbitrary CSS, one-off controls and direct reuse of old sections. In exchange you get upgrade-safe screens, consistent behaviour, built-in accessibility and responsive behaviour, and fast authoring. The FCB pack covers this trade in more depth (FCB Chapter 04, 4.3).

Lead-level framing. "At the authoring level I need views, templates, regions and conditions, not React. I treat any requirement that drives me out of the prescribed components as an exception to be justified, because that is where React, a build pipeline and an upgrade cost enter."

3.8 Level 2: Constellation DX Components

Plain-English definition

A Constellation DX Component is a custom React component, built with Pega's Constellation DX Component Builder (DXCB), published to the Pega server, and then used by low-code authors in App Studio exactly like an out-of-the-box component. It is Pega's sanctioned extension point for needs the design system does not meet. A DX Component can be used in native Pega UI, in Web Embed, or in a React SDK application. Building one needs React, npm and Git.

Why it exists

In the traditional UI the extension mechanism was custom controls and HTML rules with JavaScript, which were powerful and fragile. Constellation closes that route in the standard path and offers DX Components instead: a bounded, versioned, publishable unit that Pega's tooling understands.

Types of component

Pega's DXCB documentation lists four types of component sample, each with sub-types: layout templates, widgets, fields and presentation components. The older shorthand "templates, widgets and controls" maps onto this: what some material calls a control is a field component in the current documentation. Use the current names.

TypeWhat it doesTypical use
FieldRenders and edits a single property value in a custom wayA specialised picker, a branded rating control
WidgetAdds a self-contained feature to a page or panel; documentation mentions configuring a widget for the Utilities panelA chart, a summary tile, a custom utility
Layout templateDefines how content is arranged in form, details and page contextsA bespoke arrangement not offered by the standard templates
Presentation componentRenders content in a non-input, display wayA formatted display element
Not every App Studio component can be built. The documentation states that DXCB supports selected App Studio components, not all, and advises choosing the type and sub-type closest to the behaviour you want.

The workflow, as documented

DX COMPONENT LIFECYCLE (functional; verify commands in the Component Builder documentation) 1 Create the component from a DXCB sample of the right type (field, widget, layout template, presentation) 2 Edit it: React code that receives data and configuration from the engine and renders UI 3 Mock and test it in Storybook with sample data, with no Pega server needed 4 Build it: assets are bundled and packaged with Webpack into a gzipped package 5 Authenticate to the Pega Infinity server, then publish 6 The Builder uses a Pega service to create or update a Rule-UI-Component instance; a declare trigger on it performs the onward publish to the Constellation UI Service 7 Configure it for App Studio so authors can see it in the component palette 8 Authors use it like any other component; test it with Pega NOTE: authentication can expire during publishing and must be refreshed

A worked example, conceptual

A requirement says the case needs a numeric "confidence" display as a coloured bar instead of a plain number. The standard design system does not offer it. After checking that no standard component fits (3.12), a team creates a field component from a sample, edits the React code so it reads the value and draws a bar, mocks three values in Storybook (low, medium, high) and checks colour contrast, builds and publishes it, configures it for App Studio, and an author then selects it for the field in the view like any other component. The decisions that matter are not the React lines: they are why this could not be met by a standard component, who owns it, and how it is tested for accessibility.

Honest framing. You have not built a DX Component. The truthful line today: "I understand the lifecycle: build from a DXCB sample, test in Storybook, publish through a Rule-UI-Component to the Constellation Service, and then author-use it. I have not built one yet and have a plan (3.14). I would own the case types and data, and I would pair with front-end capacity for the React." After the ramp plan, the honest claim is that you built a sample component.
Lead-level framing. "A DX Component is the sanctioned escape hatch: bounded, versioned and usable by low-code authors, but code I now own. Before building I would ask whether a standard component after a small UX concession meets the need, whether it is reusable, who owns it and how it is tested for accessibility and upgrade. The build is the easy part."

3.10 The minimum React you need

Why a Pega server-side developer finds it unfamiliar

Your daily model is rules on a server: a rule is resolved, an activity or data transform runs, the clipboard holds the state, and the UI is a consequence. React is the opposite. State lives in the browser, the UI is a function of that state, and a screen is a tree of small components that re-render when their inputs change. You do not "run" a screen; you declare what it looks like for a given state and the library reconciles the page. The mental shift is from procedural server logic to declarative client rendering.

A generic illustration

The block below is plain React, not the Pega component contract. It exists only to show the shapes you will meet. Do not present it as Pega code.

// GENERIC REACT, NOT THE PEGA COMPONENT API import { useState, useEffect } from 'react'; function ConfidenceBar({ value, label }) { // props: value and label come from the parent const [percent, setPercent] = useState(0); // state: owned by this component useEffect(() => { // effect: runs after render when 'value' changes setPercent(Math.max(0, Math.min(100, value))); }, [value]); return ( // JSX: describes the UI for the current state <div aria-label={label}> <div className="bar" data-percent={percent} /> </div> ); } export default ConfidenceBar;

Reading it: the function is the component; it receives props; it keeps a piece of state; an effect synchronises that state when the prop changes; it returns JSX. In a Pega DX Component the engine supplies the inputs and callbacks to a component of this general shape, but the exact interface is defined by the Builder samples and documentation, which you must read rather than assume.

The toolchain, briefly

Node runs JavaScript outside the browser and npm installs the packages named in the package file; the lock file pins exact versions so builds are reproducible. A bundler (Webpack in the DX Component flow) combines modules into the files a browser loads, Storybook previews a component in isolation with mock data, and Git holds the source. Treat every one of those as something a component owner maintains.

What you do not need

You do not need to be a front-end specialist to work well on Constellation. You need to read a component, run the build, understand props and state, and know when to bring in front-end capacity. A realistic, honest position for a Pega lead is: "I own the case model, data, validations and APIs, and I can read and review a DX Component; a front-end engineer writes the non-trivial React."

Lead-level framing. "React is declarative client-side rendering: components, props, state, effects and JSX. As a server-side developer I think in rules and a clipboard, so the shift is that the UI is a function of client state. I can read a component and run the build; for non-trivial React I would pair with a front-end engineer, and I would be explicit with a client about that boundary."

3.11 Debugging Constellation

Why your tools change

In the traditional UI, Tracer, the clipboard viewer and the UI inspector all live on the server and show you what the server rendered. In Constellation the server returns data and metadata and the browser renders, so a large part of what you used to inspect on the server now happens in the browser. Tracer does not see client-side rendering. That is not a defect; it is the architecture.

Where the server portion is still traceable

Everything the server does in response to a DX API call remains observable with the tools you already know: Tracer, PAL, logs and PDC. A flow action, validation, data page load or decision rule runs on the server and shows up there. What you lose is visibility of rendering, and you replace it with the browser's developer tools. The LTM workshop listed "debugging concepts and best practices in Constellation" as its seventh topic, which suggests this is a practical, examinable area.

Where your experience applies. You use Tracer, PAL, PDC and logs in production already. The new skill is reading network traffic as the first step. The reasoning (find where the wrong value first appears, then fix at that layer) is the same discipline you apply to an integration.
Lead-level framing. "My first step would be the browser network tab, to see what the DX API returned for the step, because that tells me whether the problem is on the server or in the client. Tracer cannot see client rendering, but the server portion of every call is still traceable with Tracer, PAL and logs, which I already use. I have not debugged a Constellation app myself; I would practise this on the MediaCo sample."

3.12 Governance: every custom component is a future upgrade cost

The argument

The FCB pack makes the argument about custom controls in the traditional UI: each is code you must test and migrate on every platform upgrade. The same argument applies, with the same force, to DX Components and to SDK applications. Constellation's value proposition is upgrade-safe UI. Every custom component you add is a hole in that protection: it is code Pega's regression tests do not cover.

A decision gate

QuestionIf yes
Can a standard component meet the need after a small UX concession?Do that; do not build

Anti-patterns: building a component to avoid a conversation about UX; porting old traditional custom JavaScript into a component line for line; publishing without Storybook states and accessibility checks; leaving a component without an owner; choosing the SDK because the team prefers React rather than because the design system is mandated.
Lead-level framing. "Every custom component is a future upgrade project, so I would keep a register of them: purpose, owner, test coverage, accessibility result and a retirement trigger. The default answer to 'can we build a custom component' is 'what does the standard component lack, and can we live with it'."

3.15 Interview Q&A (Sathvik's voice)

Every answer is conceptual understanding plus a plan. None claims Constellation, DX API, DX Component, SDK or React experience.

Q1. Explain Constellation.

"Constellation replaces server-generated HTML with view metadata that a client-side engine renders using the Constellation design system. I author views from prescribed templates and regions in App Studio. The front end is served as static content by the Constellation UI Service and talks to the server through the Constellation DX API, which is stateless. The trade is design freedom for upgrade safety, consistency and speed. I understand it conceptually; I have not delivered it in production."

Q2. What changed at Pega 8.8?

"Pega consolidated the new UI technology under the name Constellation. Cosmos React became the Constellation design system, DX API v2 became the Constellation DX API, and the SDKs became the Constellation SDKs. The traditional UI stayed, with the DX API v1 now called the Traditional DX API. Constellation has been the recommended UI for new applications since Pega '23."

Q3. What does stateless mean for Constellation, and what are the consequences?

"Each DX API call is processed independently by a stateless requestor, and the clipboard is released after the call, so state lives in the case. The consequences are that the load balancer does not need session affinity except for the Studios, extra browser tabs do not multiply server threads, and background processing such as queue processors is unchanged. I would verify the data-page and locking behaviour per release."

Q4. What is the Constellation UI Service?

"A static-content microservice that delivers the front-end components to the browser, separate from the application server. It is auto-provisioned on Pega Cloud; on a client-managed estate someone has to set it up. A published custom DX Component ends up there too."

Q5. Constellation DX API versus Traditional DX API: what is the difference?

"The Traditional DX API mirrors screen state and suits existing section-based applications and mashup-style use. The Constellation DX API is view-based, separates data from layout, uses HATEOAS so responses reference available actions, and reduces chattiness. Only Constellation applications can use every endpoint, though some work with a traditional application. I would confirm paths and schemas in the release documentation, and I would not use either as a system-to-system contract."

Q6. What is in a Constellation DX API response?

"The data for the case and assignment, UI metadata describing the view to render, information about the next assignment, and HATEOAS links to the actions available. So the client does not duplicate rules like which fields are required; the server evaluates them. I know this from the documentation, not from building against it."

Q7. What is Web Embed and how does it differ from a mashup?

"Web Embed places a Constellation-rendered Pega experience inside an external web page; it is the Constellation-era replacement for mashups. It fits when a client wants a Pega-driven step inside its own page without a full custom front end. For a different design system entirely I would consider the React SDK instead."

Q8. Can we migrate our traditional application to Constellation?

"Not by changing a setting. It is a UI re-platforming: forms become views, custom controls are replaced or become DX Components, portals are rebuilt. Rules, data and integrations are unaffected. Coexistence helps: Constellation pieces can be hosted in a traditional app, and in Pega Customer Service the Constellation Interaction Portal can run UI Kit service requests. I would inventory, classify, pilot one case type and phase the cutover."

Q9. Where does React appear in Constellation?

"At three levels. The design system is built with React, which Pega writes and I consume. DX Components are custom React components built with the DX Component Builder and published so low-code authors can use them in App Studio. The React SDK is a bridge from the Constellation engine to a non-Pega design system for a separate front-end application. Most Constellation work needs none of the last two."

Q10. What is a DX Component and when would you build one?

"A custom React component built with the DX Component Builder, published to the server through a Rule-UI-Component and the Constellation UI Service, and used in App Studio like any other. Types include fields, widgets, layout templates and presentation components. I would build one only when a standard component cannot meet a documented requirement and there is an owner, tests, an accessibility check and a retirement trigger. I have not built one yet; I have a plan to build a sample."

Q11. What is the React SDK and when would you use it?

"A React bridge from the ConstellationJS engine to a non-Pega design system, Material UI in the reference implementation, shipped as packages @pega/react-sdk-components and @pega/react-sdk-overrides, with MediaCo as the sample. Embedded use, placing Pega work inside an existing React application, is the most common; portal use renders the whole experience. I would only use it when the client's design system is mandatory, and I would pin the SDK to the Infinity release. I have not built an SDK application."

Q12. How much React do you know?

"Honestly, none hands-on. I understand components, props, state and effects, JSX and the npm and bundling toolchain conceptually, and I can read a component. My plan is to learn by building a sample DX component against the SDK. On a real engagement I would own the case model, data, validations and APIs and pair with a front-end engineer for non-trivial React."

Q13. How would you debug a Constellation screen that shows the wrong thing?

"Start in the browser network tab: find the DX API call for the step and check the data, the view metadata and the available actions. If those are wrong, the problem is on the server and I use Tracer, logs and the rules, because when rules and validation run on the server. If the response is right and the screen is wrong, it is client side: an expression or a component. Tracer cannot see client rendering. I have not debugged a Constellation app yet and would practise on the MediaCo sample."

Q14. What are the governance risks of custom components?

"Each custom component is a future upgrade project: regression on each release, security and accessibility review, ownership, toolchain drift and, for SDK applications, version coupling to Infinity. I would keep a register with purpose, owner, tests and a retirement trigger, and I would approve a component only after confirming no standard component fits. It is the same argument as for custom controls in the traditional UI."

Q15. The role asks for Constellation DX API on Infinity 24x. You have neither. Why consider you?

"I am an exact match on the Kafka, queue processor and CSSA-at-this-experience parts, and the back end of Constellation delivery is still case design, data and asynchronous processing. The two gaps I will close are the Constellation DX API and the 24 release. I know the platform, not the release, and verify release behaviour in the documentation. My plan: Academy topics, a Constellation case type in a sandbox, the React SDK and MediaCo sample, and a sample DX component. After that I can say I have built a sample, not that I have delivered Constellation."

Q16. How would you decide between the standard portal, Web Embed, the DX API and the SDK?

"By who owns the experience. Internal operations with Pega's design acceptable: the standard Constellation portal, the cheapest and most upgrade-safe. A step inside someone else's page: Web Embed. A bespoke channel: a custom client on the Constellation DX API. A mandated client design system in React: the SDK. I would default to the first and treat each step down as an exception with an owner, tests and an upgrade cost."
